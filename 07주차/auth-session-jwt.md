# 인증과 상태 유지

## 인증/인가

### 인증과 인가의 차이

- **인증(Authentication)**: 사용자가 **누구인지** 확인하는 과정. 예) 아이디/비밀번호 로그인, 소셜 로그인
- **인가(Authorization)**: 인증된 사용자가 **무엇을 할 수 있는지** 권한을 확인하는 과정. 예) 관리자만 회원 목록 조회 가능

인가는 인증 이후에 이루어진다. 누구인지 알아야 그 사람의 권한을 판단할 수 있기 때문이다.

> 비유: 회사 출입증을 찍고 건물에 들어가는 것이 인증, 출입증 등급에 따라 들어갈 수 있는 층이 정해지는 것이 인가다.

### 401과 403

| 상태 코드 | 이름 | 의미 |
| --- | --- | --- |
| 401 | Unauthorized | **인증 실패**. 로그인하지 않았거나 토큰이 없거나 만료됨 |
| 403 | Forbidden | **인가 실패**. 누구인지는 알지만 권한이 없음 |

- 401의 이름이 Unauthorized지만 실제 의미는 "Unauthenticated"에 가깝다. 이름 때문에 자주 헷갈린다.
- 401 응답에는 어떤 방식으로 인증해야 하는지 `WWW-Authenticate` 헤더를 담는 것이 표준이다.
- 프론트에서는 보통 401이면 토큰 재발급이나 로그인 페이지 이동을, 403이면 "권한이 없습니다" 안내를 한다.

## Cookie/Session

HTTP는 [Stateless](../05주차/http-basics.md#stateless)하므로 서버는 이전 요청을 기억하지 않는다. 로그인 상태를 유지하려면 매 요청마다 "나 누구야"를 증명할 수단이 필요하다.

### 쿠키 기반 세션 인증 흐름

1. 사용자가 아이디/비밀번호로 로그인한다.
2. 서버는 인증에 성공하면 세션을 만들고, 세션 저장소에 `세션 ID → 사용자 정보`를 저장한다.
3. 서버는 `Set-Cookie: JSESSIONID=abc123` 헤더로 세션 ID만 클라이언트에 보낸다.
4. 브라우저는 이후 같은 도메인 요청마다 `Cookie: JSESSIONID=abc123`를 자동으로 붙인다.
5. 서버는 세션 ID로 저장소를 조회해 사용자를 식별한다.

```http
HTTP/1.1 200 OK
Set-Cookie: JSESSIONID=abc123; Path=/; HttpOnly; Secure; SameSite=Lax
```

- **쿠키**: 브라우저에 저장되는 작은 데이터. 요청 시 자동 전송된다.
- **세션**: 서버에 저장되는 사용자 상태. 클라이언트는 세션 ID만 가진다.

장점

- 민감한 정보는 서버에만 있고 클라이언트는 의미 없는 ID만 가진다.
- 서버에서 세션을 삭제하면 **즉시 로그아웃/강제 만료**가 가능하다.

단점

- 매 요청마다 세션 저장소를 조회해야 한다.
- 서버가 상태를 가지므로 서버를 여러 대로 늘릴 때 문제가 생긴다. (아래 참고)
- 쿠키가 자동 전송되므로 CSRF 대비가 필요하다.

### 쿠키 보안 옵션 (HttpOnly / Secure / SameSite)

| 옵션 | 역할 | 막는 공격 |
| --- | --- | --- |
| `HttpOnly` | JS(`document.cookie`)에서 쿠키 접근 불가 | XSS로 인한 쿠키 탈취 |
| `Secure` | HTTPS 연결에서만 쿠키 전송 | 네트워크 도청 |
| `SameSite` | 교차 사이트 요청에 쿠키를 보낼지 결정 | CSRF |

`SameSite` 값

- `Strict`: 같은 사이트 요청에만 쿠키 전송. 다른 사이트의 링크를 눌러 들어와도 쿠키가 안 실려서 로그인이 풀린 것처럼 보일 수 있다.
- `Lax`: 같은 사이트 요청 + 다른 사이트에서 링크로 이동하는 최상위 `GET` 요청에는 전송. 대부분의 브라우저 기본값이다.
- `None`: 모든 요청에 전송. 반드시 `Secure`와 함께 써야 한다.

그 외 `Domain`, `Path`로 쿠키가 전송될 범위를, `Max-Age`/`Expires`로 수명을 정한다. 수명을 지정하지 않으면 브라우저를 닫을 때 사라지는 세션 쿠키가 된다.

> "사이트(site)"와 "출처(origin)"는 다르다. `a.example.com`과 `b.example.com`은 다른 출처지만 같은 사이트(eTLD+1이 `example.com`)다. SameSite는 사이트 기준, SOP/CORS는 출처 기준이다.

### 세션 저장소와 서버 확장

서버가 여러 대일 때, 서버 A에서 로그인하고 다음 요청이 서버 B로 가면 B에는 세션이 없어 로그인이 풀린다. 해결 방법은 다음과 같다.

| 방식 | 설명 | 단점 |
| --- | --- | --- |
| Sticky Session | 로드밸런서가 같은 사용자를 항상 같은 서버로 보냄 | 특정 서버에 부하가 몰리고, 그 서버가 죽으면 세션 유실 |
| Session Clustering | 서버끼리 세션을 복제 | 서버가 늘수록 복제 비용 증가 |
| 외부 세션 저장소 | Redis 등 공용 저장소에 세션 저장 (Spring Session) | 저장소가 단일 장애 지점이 될 수 있음 |

실무에서는 **Redis 같은 외부 세션 저장소**를 많이 쓴다. 이 경우 애플리케이션 서버는 상태를 가지지 않게 되어 자유롭게 확장할 수 있다.

## JWT

JWT(JSON Web Token)는 **사용자 정보를 JSON으로 담고 서명한 토큰**이다. 서버가 상태를 저장하지 않고도 토큰 자체를 검증해 사용자를 식별할 수 있다.

### JWT 구조 (Header / Payload / Signature)

`xxxxx.yyyyy.zzzzz` 형태로, 점(`.`)으로 구분된 세 부분을 각각 Base64URL로 인코딩한 문자열이다.

```json
// Header: 토큰 타입과 서명 알고리즘
{ "alg": "HS256", "typ": "JWT" }

// Payload: 클레임(담고 싶은 정보)
{ "sub": "42", "role": "USER", "iat": 1761350400, "exp": 1761352200 }
```

```text
// Signature
HMACSHA256(base64UrlEncode(header) + "." + base64UrlEncode(payload), secret)
```

- 주요 등록 클레임: `iss`(발급자), `sub`(주체, 보통 사용자 ID), `aud`(대상), `exp`(만료 시간), `iat`(발급 시간), `jti`(토큰 ID)
- **Payload는 암호화가 아니라 인코딩일 뿐**이다. 누구나 디코딩해서 볼 수 있으므로 비밀번호 같은 민감 정보를 넣으면 안 된다.
- Signature는 **위변조 여부**를 확인하기 위한 것이다. Payload를 한 글자라도 바꾸면 서명이 맞지 않는다.
- 서명 알고리즘
  - `HS256`: 대칭키. 발급과 검증에 같은 비밀키를 쓴다. 서버 하나가 발급/검증을 모두 할 때 간단하다.
  - `RS256`/`ES256`: 비대칭키. 개인키로 서명하고 공개키로 검증한다. 인증 서버와 API 서버가 분리되어 있을 때 유리하다.

### JWT 인증 흐름

1. 사용자가 로그인하면 서버가 JWT(Access Token)를 발급한다.
2. 클라이언트는 토큰을 저장하고, 요청마다 헤더에 담아 보낸다.
3. 서버는 DB 조회 없이 **서명과 만료 시간을 검증**하고 Payload에서 사용자 정보를 꺼낸다.

```http
GET /api/me HTTP/1.1
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
```

가장 큰 문제는 **발급한 토큰을 서버가 강제로 무효화하기 어렵다**는 것이다. 토큰이 탈취되면 만료될 때까지 유효하다. 그래서 Access Token은 수명을 짧게(15~30분 등) 잡고, [Refresh Token](./spring-security-token.md#refresh-token)으로 재발급하는 방식을 함께 쓴다.

### Session과 JWT 비교

| | Session | JWT |
| --- | --- | --- |
| 상태 저장 위치 | 서버 (세션 저장소) | 클라이언트 (토큰 자체) |
| 서버 확장 | 공용 세션 저장소 필요 | 서명 키만 공유하면 됨 |
| 요청마다 비용 | 저장소 조회 | 서명 검증 (CPU 연산) |
| 강제 로그아웃 | 세션 삭제로 즉시 가능 | 어려움 (블랙리스트 등 별도 처리 필요) |
| 데이터 크기 | 쿠키에 ID만 → 작음 | 클레임이 많을수록 커짐 |
| 탈취 시 | 서버에서 세션 폐기 | 만료 전까지 유효 |
| 적합한 경우 | 일반 웹 서비스, 즉시 제어가 중요할 때 | MSA, 모바일 앱, 여러 서비스 간 인증 |

> **JWT를 쓰면 서버가 완전히 Stateless해질까?**
>
> Access Token 검증만 보면 Stateless다. 하지만 Refresh Token 저장, 로그아웃 토큰 블랙리스트, 토큰 재사용 감지 등을 구현하려면 결국 서버(Redis, DB)에 상태를 두게 된다. 실무에서는 "완전한 Stateless"보다 **Access Token은 Stateless하게, Refresh Token은 서버에서 관리**하는 절충안을 많이 쓴다.

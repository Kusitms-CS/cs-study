## 1. Local Cache (로컬 캐시)

> 애플리케이션 서버의 **메모리 안**에 데이터를 저장

| 구분 | 내용 |
|---|---|
| 언제 쓰나 | 거의 바뀌지 않는 데이터 (카테고리 목록, 공통 코드, 설정값) / 조회가 아주 많이 몰리는 핫 데이터를 보조로 처리할 때 |
| 장점 | 네트워크를 타지 않아 **가장 빠름** (나노초~마이크로초) / 외부 시스템이 필요 없어 구성이 단순 |
| 단점 | 서버마다 따로 저장해 **서버 간 값이 달라지는 정합성 문제** / 서버 재시작 시 캐시 사라짐 / 애플리케이션 메모리를 같이 써서 **GC 부담** 증가 / 서버 수만큼 **중복 저장** |

---

## 2. Distributed Cache (분산 캐시)

> **여러 서버가 함께 쓰는 별도의 캐시 서버**

| 구분 | 내용 |
|---|---|
| 언제 쓰나 | 서버가 여러 대이고 모두 같은 값을 봐야 할 때 (로그인 세션, 장바구니, 가격, 재고) / 수평 확장 환경 (쿠버네티스 Pod 오토스케일링) |
| 장점 | 모든 서버가 같은 데이터를 봐서 **정합성이 좋음** / 애플리케이션 서버가 재시작돼도 캐시 유지 |
| 단점 | 네트워크 왕복으로 로컬 캐시보다 느림 (보통 1ms 안팎) / 캐시 서버가 죽으면 전체 영향 → **단일 장애점(SPOF)** / 특정 키에 요청이 몰리면 노드 하나에 부하 집중 (**Hot Key**) |

| 보완 기술 | 무엇을 보완하나 |
|---|---|
| Memcached | 단순한 키-값 캐시만 필요할 때 쓰는 가벼운 대안 (멀티스레드) |

**Local vs Distributed 비교**

| | Local Cache | Distributed Cache |
|---|---|---|
| 위치 | 각 서버 메모리 | 별도 캐시 서버 |
| 속도 | 가장 빠름 | 빠름 (네트워크 경유, 약 1ms) |
| 서버 간 정합성 | 불일치 가능 | 일치 |
| 서버 재시작 시 | 사라짐 | 유지 |
| 대표 | Caffeine, Ehcache | Redis, Memcached |

## 3. Redis

| 구분 | 내용 |
|---|---|
| 언제 쓰나 | 캐시, 로그인 세션 저장 / 실시간 순위표(Sorted Set), 카운터, 선착순 처리(INCR, DECR) / 분산 락, 요청 수 제한(Rate Limit), 간단한 메시지 큐(Pub/Sub, Streams) |
| 장점 | 메모리 기반이라 매우 빠름 / 명령을 하나씩 처리해 **원자적으로 실행** (동시성 문제가 적음) / TTL, 복제, 영속화 기능 내장 |
| 단점 | 명령을 하나씩 처리하므로 **무거운 명령(`KEYS *`, 큰 키 조회) 하나가 전체를 막음** / 메모리 기반이라 비싸고 용량 한계 / 복제가 비동기라 **장애 전환 시 데이터 유실 가능** |

| 보완 기술 | 무엇을 보완하나 |
|---|---|
| AWS ElastiCache | 장애 전환, 백업, 모니터링 같은 운영 부담 감소 |

## 4. TTL (Time To Live)

> 데이터가 캐시에 머무는 시간(유통기한). 시간이 지나면 **자동 삭제**

| 구분 | 내용 |
|---|---|
| 언제 쓰나 | 캐시에 넣는 거의 모든 데이터 (기본 안전장치) / 인증번호, 세션, 일시적인 차단처럼 시간이 지나면 의미가 없어지는 데이터 |
| 장점 | 무효화를 놓쳐도 언젠가는 최신 값으로 돌아오는 **마지막 안전장치** / 안 쓰는 데이터를 자동 정리해 메모리 절약 / 구현이 매우 간단 |
| 단점 | TTL이 끝날 때까지 오래된 데이터(**stale**)가 보일 수 있음 / 적절한 값을 정하기 어려움 (길면 정합성↓, 짧으면 적중률↓) |

## 면접 질문
-TTL 만료가 몰리는 문제를 어떻게 막나요? / 캐시 스탬피드가 왜 장애로 이어지나요?

**TTL과 관련된 장애 패턴**

| 현상 | 원인 | 결과 |
|---|---|---|
| **Cache Avalanche** | 같은 TTL로 넣은 키들이 **한꺼번에 만료** | DB에 요청이 몰림 |
| **Cache Stampede** | **인기 키 하나**가 만료되는 순간 | 요청이 한꺼번에 DB로 몰림 |

## 5. Cache Aside (Lazy Loading)

> 애플리케이션이 **캐시를 먼저 확인**하고, 없으면 DB에서 읽어 캐시에 넣는 가장 기본적인 캐시 사용 패턴. 수정 시에는 DB를 바꾼 뒤 캐시를 삭제

| 동작 | 흐름 |
|---|---|
| 읽기 | 캐시 조회 → 있으면(Hit) 반환 / 없으면(Miss) DB 조회 → 캐시에 저장 → 반환 |
| 쓰기 | DB 수정 → 캐시 삭제 |

| 구분 | 내용 |
|---|---|
| 언제 쓰나 | 읽기가 쓰기보다 훨씬 많은 서비스 (상품 상세, 게시글, 프로필) / 대부분의 일반적인 웹 서비스의 기본 전략 |
| 장점 | 실제로 요청된 데이터만 캐시에 올라가 메모리 효율적 / 캐시가 죽어도 DB에서 읽으면 되므로 서비스가 멈추지 않음 (느려질 뿐) / 구현이 직관적 |
| 단점 | 처음 조회는 항상 Miss라 느림 (**Cold Start**) / 수정과 조회가 동시에 일어나면 **옛 값이 다시 캐시에 들어가는 경쟁 조건** / 캐시와 DB를 맞추는 책임을 애플리케이션이 직접 짐 |

## 6. Cache Invalidation (캐시 무효화)

> 원본 데이터가 바뀌었을 때 캐시에 남은 **옛 데이터를 지우거나 갱신**

**방법 3가지**

| 방법 | 설명 | 특징 |
|---|---|---|
| TTL 기반 | 시간이 지나면 자동 만료 | 가장 간단하지만 그동안 옛 값이 보임 |
| 명시적 삭제 | 데이터를 수정할 때 코드에서 직접 `DEL` | 즉시 반영, 삭제를 빼먹을 위험 |
| 이벤트 기반 | 변경 이벤트를 발행해 여러 서버의 캐시를 한꺼번에 무효화 | 서버 간 동기화에 적합 |

| 구분 | 내용 |
|---|---|
| 언제 쓰나 | 가격, 재고, 권한처럼 바뀌면 바로 반영돼야 하는 데이터 / 로컬 캐시를 여러 서버에서 함께 쓸 때 (서버 간 동기화) |
| 장점 | 수정 즉시 반영되어 정합성이 좋음 / TTL을 길게 잡아도 되므로 적중률 유지 |
| 단점 | 무효화 메시지가 **유실되거나 늦게 도착**할 수 있음 (Pub/Sub은 메시지를 보관하지 않음) / 메시지 **순서가 뒤바뀌면** 옛 값이 최종 상태가 될 수 있음 / 어떤 캐시를 지워야 하는지 **추적하기 어려움** (상품 하나가 목록, 검색, 추천 캐시 등 여러 곳에 존재) / 수정이 잦으면 캐시가 계속 지워져 의미가 없어짐 |

| 보완 기술 | 무엇을 보완하나 |
|---|---|
| Redis Streams, Kafka | 메시지를 보관해 유실 없이 무효화 이벤트 전달 |
| CDC (Debezium) | DB 변경 로그(binlog)를 읽어 무효화 이벤트를 자동 생성. 코드에서 삭제를 빼먹을 일이 없음 |
| TTL 병행 | 무효화를 놓쳐도 결국 만료되도록 하는 마지막 안전장치 |

## 7. Distributed Lock (분산 락)

> 여러 서버 중 **락을 먼저 잡은 한 곳만** 작업을 실행하게 하는 방법

| 구분 | 내용 |
|---|---|
| 언제 쓰나 | 재고 차감, 선착순 쿠폰 발급, 좌석 예매 / 여러 Pod에서 같은 스케줄러 작업이 중복 실행되는 것을 막을 때 (예: 쿠폰 만료 배치) |
| 장점 | 서버가 여러 대여도 **한 번에 하나만** 작업 / Redis를 이미 쓰고 있다면 추가 인프라 없이 구현 / 중복 실행을 막아 불필요한 작업 감소 |
| 단점 | GC 멈춤이나 네트워크 지연으로 **작업이 끝나기 전에 락이 만료** / TTL 없이 락을 잡은 서버가 죽으면 **락이 영원히 풀리지 않음**(Deadlock) / Redis 장애 전환 때 **복제가 안 된 락이 사라질 수 있음** / 모든 요청이 락을 기다리면 성능 저하(병목) |

| 보완 기술 | 무엇을 보완하나 |
|---|---|
| Fencing Token | 락마다 증가하는 번호를 붙여, 만료된 락으로 들어온 쓰기를 저장소가 거부 |
| DB 락 (`SELECT ... FOR UPDATE`, 낙관적 락 version 컬럼) | 정합성을 DB가 직접 보장 |
| 원자 연산 (Redis `DECR`, 조건부 `UPDATE ... WHERE qty > 0`) | 재고 차감 같은 단순한 작업은 락 없이도 안전하게 처리 |

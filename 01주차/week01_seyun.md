# 1주차 - 자료구조 / 시간복잡도

## **1. Big-O**

- 알고리즘의 입력 크기(N)가 커짐에 따라 실행 시간이나 메모리 사용량이 어떻게 증가 하는지를 나타내는 척도
- **최악의 경우(Worst-case) 기준**: Big-O 표기법은 주로 알고리즘이 실행되는 데 걸리는 **최대 시간**을 보장하고 표현하기 위해 사용
  ⇒ 안정성 보장 목적으로 worst case를 기준 상한선으로 잡음
- **시간 복잡도**: 입력 크기에 따른 기본 연산의 실행 횟수가 어떻게 증가 하는지를 나타냄
- **공간 복잡도**: 알고리즘이 실행되는 동안 사용하는 메모리 공간의 총량을 나타냄
  ⇒ 시간 복잡도와 공간 복잡도는 서로 트레이드 오프 관계

### ⭐️ 자주 사용되는 복잡도 (빠른순)

| 표기       | 이름     | 예시                             |
| ---------- | -------- | -------------------------------- |
| O(1)       | 상수     | 배열 인덱스 접근, 해시맵 조회    |
| O(log n)   | 로그     | 이진 탐색, 균형 트리 탐색        |
| O(n)       | 선형     | 배열 순회                        |
| O(n log n) | 선형로그 | 병합정렬, 퀵정렬(평균)           |
| O(n^2)     | 이차     | 이중 for문, 버블정렬             |
| O(2^n)     | 지수     | 재귀 피보나치(메모이제이션 없이) |
| O(n!)      | 팩토리얼 | 완전 순열 탐색                   |

## 2. Array (배열)

- **동일한 타입**의 데이터를 **연속된 메모리 공간**에 저장하는 자료구조
- **인덱스**를 통해 **O(1)**로 임의 접근 가능
  ⇒ 시작 주소 + (인덱스 × 요소 크기)로 바로 계산되기 때문
- 크기가 고정된 **정적 배열(C, Java)**, 내부적으로 재할당하며 크기를 늘리는 **동적 배열(JS Array, Java ArrayList, C++ vector)로 나뉨**

### ✏️ 동적 배열의 재할당 원리

- 용량이 꽉 차면 보통 2배로 새 배열을 만들고 기존 요소를 복사
- 매번 1칸씩 늘리면 삽입마다 O(n) 복사가 발생하지만, 2배씩 늘리면 전체 n번 삽입에 대해 총 복사 비용이 O(n)에 수렴 → 삽입 1회당

### 🕐 시간 복잡도

| 연산                | 복잡도           | 이유                                                      |
| ------------------- | ---------------- | --------------------------------------------------------- |
| 접근 (index)        | O(1)             | 주소 계산으로 바로 접근                                   |
| 검색 (값으로 찾기)  | O(n)             | 처음부터 순회해야 함                                      |
| 끝에 삽입/삭제      | O(1) (amortized) | 동적 배열의 경우 재할당이 가끔 발생하지만 평균적으로 O(1) |
| 중간/앞에 삽입/삭제 | O(n)             | 뒤 요소들을 한 칸씩 밀거나 당겨야 함                      |

## 3. Li**nkedList (연결 리스트)**

- 각 노드가 **데이터 + 다음 노드에 대한 포인터(참조)**를 가지며 메모리상에 흩어져 존재하는 자료구조
- **단일 연결 리스트:** 다음 노드만 참조
- **이중 연결 리스트:** 이전/다음 노드 모두 참조 (**양방향 순회 가능**, 메모리는 더 사용)
- **원형 연결 리스트:** 마지막 노드가 다시 첫 노드를 가리킴

### 🕐 시간 복잡도

| 연산                                         | 복잡도 | 이유                                               |
| -------------------------------------------- | ------ | -------------------------------------------------- |
| 접근 (index)                                 | O(n)   | 처음부터 포인터를 따라가야 함 (random access 불가) |
| 검색                                         | O(n)   | 순회 필요                                          |
| 앞/뒤(head/tail 노드 참조 보유 시) 삽입/삭제 | O(1)   | 포인터만 갱신하면 됨                               |
| 중간 삽입/삭제 (위치를 이미 알고 있을 때)    | O(1)   | 해당 노드 앞뒤 포인터만 변경                       |
| 중간 삽입/삭제 (위치를 탐색해야 할 때)       | O(n)   | 탐색 비용 포함                                     |

## **⭐️⭐️ Array vs LinkedList**

#### **1. Array**

- **메모리 구조:** 메모리상에 데이터가 연속적 공간에 할당
- **장점: 인덱스**를 통한 특정 요소 접근과 조회가 매우 빠름**(O(1))**
- **단점: 크기가 고정**되어 있으며(정적 배열), 중간에 데이터를 **삽입하거나 삭제**할 때 나머지 요소들을 **모두 이동**시켜야 하므로 비효율적(**O(N))**

#### 2. LinkedList

- **메모리 구조:** 메모리상에 비연속적으로 흩어진 노드(데이터 + 포인터)들이 서로 연결된 형태
- **종류:**
  - **단일 연결 리스트 (Singly Linked List):** 다음 노드만 참조하는 가장 기본적인 형태
  - **이중 연결 리스트 (Doubly Linked List):** 이전 노드와 다음 노드를 모두 참조. 양방향 순회가 가능해 탐색에 유리하지만, 포인터를 저장할 메모리 공간을 더 많이 사용함
  - **원형 연결 리스트 (Circular Linked List):** 마지막 노드가 널(Null)이 아닌 첫 번째 노드를 다시 가리키는 순환 구조. (운영체제의 라운드 로빈 스케줄링 등에 활용)

#### 💡 삽입/삭제가 잦으면 무조건 LinkedList가 좋을까요?

**⇒ 이론상 특정 위치를 알고 있을 때 LinkedList의 삽입/삭제는 O(1)이지만, 그 위치를 찾기 위한 탐색에 O(N)이 걸림. 또한 Array는 메모리가 연속되어 있어 CPU가 데이터를 캐시로 가져올 때 주변 데이터까지 한 번에 가져오기 때문에 유리(캐시 지역성)하므로 실제 동작 속도는 Array가 빠를 때가 많음**

## 4. Stack (스택)

- **LIFO 구조**로 마지막에 넣은 데이터가 가장 먼저 나옴
- 함수 호출 스택 - 재귀 호출, 실행 컨텍스트 관리
- 괄호 짝 검사, 문자열 역순 처리
- 브라우저 뒤로가기 기능
- 실행 취소 기능
- DFS (깊이 우선 탐색)의 내부 구현

### 📍핵심 연산

- **push:** 맨 위에 삽입 - O(1)
- **pop:** 맨 위에서 제거 - O(1)
- **peek/top:** 맨 위 값 확인 - O(1)

### 📍구현

- **배열 기반:** 끝에서 push/pop → O(1), 구현 간단
- **연결 리스트 기반:** head에서 push/pop → O(1)

#### 💡 재귀함수 & Stack

**⇒ 재귀 호출 시 종료 조건이 없거나 호출이 너무 깊어지면 한정된 메모리의 함수 콜 스택(Call Stack) 영역을 초과하게 되어 Stack Overflow가 발생할 수 있음**

---

## 5. **Queue (큐)**

- **FIFO 구조로**, 먼저 넣은 데이터가 먼저 나옴
- **일반 Queue**
- **원형 Queue:** 배열을 재사용해 공간 낭비 방지
- **우선순위 Queue:** 우선순위가 높은 요소가 먼저 나옴 (보통 Heap으로 구현)
- **Deque:** 양쪽 끝에서 삽입/삭제 모두 O(1)
- BFS(너비 우선 탐색) 사용
- 작업 스케줄링, 프린터 대기열 사용
- 비동기 데이터 버퍼링(Kafka 등 메세지 큐 시스템)

### 📍핵심 연산

- **enqueue:** 뒤에 삽입 — O(1)
- **dequeue:** 앞에서 제거 — O(1) (단, 배열로 구현 시 앞에서 빼면 나머지가 당겨져야 하므로 실제로는 O(n)이 될 수 있음 → circular buffer나 연결 리스트로 구현해야 진짜 O(1))

#### 💡 큐를 배열로 구현했을 때의 문제점은 무엇인가요?

**⇒ 배열 특성상 맨 앞의 데이터를 dequeue하면 뒤에 있는 나머지 모든 데이터를 한 칸 씩 앞으로 당겨야 하므로 시간 복잡도가 O(N)으로 저하됨. 이를 해결하기 위해서 실제로는 원형 큐나 연결리스트를 활용해 O(1)를 보장하도록 구현해야함.**

## 6. Hash Table

- **Key를 해시 함수로 변환해 배열의 인덱스로 매핑**하여 저장하는 자료구조
- JS의 Object, Map과 Java의 HashMap의 기반
- 탐색/삽입/삭제 평균의 경우 O(1), 최악의 경우(Worst-case) O(N)

**⇒ 최악의 경우는 해시 충돌이 심하게 발생하여 모든 데이터가 하나의 버킷에 몰릴 때 발생하며 사실상 연결 리스트를 탐색하는 것과 같아짐**

### 📍동작 원리

- Key를 해시 함수에 넣어 고유한 해시값을 생성
- 해시값을 테이블 크기로 나눈 나머지 등을 이용해 저장할 버킷 인덱스를 결정
- 해당 버킷에 (Key, Value) 쌍 저장

### 📍해시 충돌 해결 방법

- **Chaining (분리 연결법):** 같은 버킷에 여러 데이터가 해싱되면 연결 리스트로 이어붙이는 방식
  - Java 8 이상부터는 하나의 버킷에 요소가 8개 이상 모이면 연결 리스트를 **Red-Black Tree**로 변환하여, 최악의 경우에도 탐색 시간을 O(\log N)으로 방어합니다.
- **Open Addressing (개방 주소법):** 충돌 발생 시 다른 빈 버킷(슬롯)을 찾아 데이터를 저장하는 방식
  - 탐사 방식: 선형 탐사(Linear Probing), 제곱 탐사(Quadratic Probing), 이중 해싱(Double Hashing) 등

### 📍적재율과 리사이징

- **현재 저장된 요소의 수 / 전체 버킷의 수**
- **Rehashing:** 데이터가 차올라 특정 임계값(Load Factor, 보통 0.75)을 넘으면, 성능 저하를 막기 위해 버킷 크기를 약 2배로 늘리고 **모든 요소를 새로운 테이블에 재배치함.** 이 순간에는 O(N)의 비용이 발생하지만, 동적 배열과 마찬가지로 분할 상환 분석에 의해 평균적으로 O(1)을 유지

### 📍좋은 해시 함수의 조건

- **결정적:** 동일한 Key 입력에는 항상 동일한 해시값을 반환
- **고른 분포:** 버킷 전체에 데이터가 균등하게 분산되어 충돌을 최소화
- **빠른 계산:** 해시값을 구하는 연산 자체가 가벼워야함

## 7. Tree (트리)

- 노드들이 부모-자식 관계로 연결된 계층적 자료구조
- **Root:** 최상위 노드
- **Leaf:** 자식이 없는 노드
- **Depth:** 루트에서 특정 노드까지의 거리
- **Height:** 트리의 최대 깊이

### 📍이진 트리 (Binary Tree)

- 각 노드가 최대 2개 자식(left, right)를 가짐

### 📍이직 탐색 트리 **(BST, Binary Search Tree)**

- 왼쪽 서브트리 < 부모 < 오른쪽 서브트리 규칙을 유지
- 탐색/삽입/삭제: 평균 O(log n), **최악 O(n)** (한쪽으로 치우쳐 사실상 연결 리스트가 되는 경우 — skewed tree)

### 📍**균형 트리 (Self-Balancing Tree)**

- 이직 탐색 트리의 최악의 케이스(**O(n))**를 방지하기 위해 삽입/삭제 시 자동으로 균형을 제조정
- AVL Tree (높이 차 균형), Red-Black Tree (색상 규칙으로 균형, Java TreeMap/HashMap 내부에 사용)
- 탐색/삽입/삭제 모두 O(log n) 보장

### 📍트리 순회 (**Traversal)**

- **DFS 계열**
  - **Pre-order (root → left → right):** 트리 구조 복사/직렬화에 사용
  - **In-order (left → root → right):** BST에서 정렬된 순서로 값을 얻을 수 있음
  - **Post-order (left → right → root):** 하위 노드부터 처리해야 할 때
- **BFS 계열**
  - **Level-order:** 큐를 이용해 레벨(깊이) 순서대로 순회

### 📍**B-Tree / B+Tree**

- 자식을 여러 개(다진 트리) 가질 수 있는 균형 트리로, 디스크 I/O를 최소화하도록 설계 → DB 인덱스, 파일 시스템에서 사용

## 8. Heap (힙)

- 완전 이진 트리 기반의 자료 구조, 부모-자식 간 우선순위 규칙을 만족함
- BST와 다르게 좌우 순서 규칙은 없고, “부모-자식” 간의 대소 관계만 만족하면 됨 (정렬된 상태는 아님)
- **Max Heap:** 부모 ≥ 자식 → **루트가 항상 최댓값**
- **Min Heap:** 부모 ≤ 자식 → **루트가 항상 최솟값**
- Heap Sort — O(n log n), 추가 메모리 없이 in-place 정렬 가능 사용
- 다익스트라 최단 경로 알고리즘에서 최소 비용 노드 선택 사용
- "K번째 최댓값/최솟값 찾기" 류의 문제 사용

### 📍구현

- 배열로 구현 (포인터 없이도 인덱스 연산만으로 부모/자식 탐색 가능)
- 완전 이진 트리 → 배열에 빈틈없이 채워 넣을 수 있음, 공간 효율적
- **부모 인덱스:** (i - 1) / 2
- **왼쪽 자식:** 2i + 1, **오른쪽 자식:** 2i + 2

### 🕐 시간 복잡도

| 연산                                 | 복잡도   | 설명                                                                       |
| ------------------------------------ | -------- | -------------------------------------------------------------------------- |
| 최댓값/최솟값 조회 (peek)            | O(1)     | 루트 값                                                                    |
| 삽입 (insert)                        | O(log n) | 맨 끝에 넣고 부모와 비교하며 위로 올림 (sift-up / bubble-up)               |
| 삭제 (extract-max/min)               | O(log n) | 루트 제거 후 마지막 노드를 루트로 올리고 아래로 내림 (sift-down / heapify) |
| 배열 전체를 힙으로 구성 (build heap) | O(n)     | 아래에서부터 heapify하면 O(n log n)이 아니라 O(n)                          |

## **1. JS Array / Object / Map / Set**

- **Map을 쓰는 이유:**
  - Object는 프로토타입 체인 때문에 `toString`, `hasOwnProperty` 같은 상속된 프로퍼티와 충돌 가능성이 있고 key가 문자열로 강제 변환됨
  - Map은 순수한 key-value 저장에 최적화되어 있고 빈번한 추가/삭제 시 성능도 더 나음
- **Set을 쓰는 이유:**
  - 배열에서 중복 제거는 `indexOf`로 매번 O(n) 탐색이 필요(전체 O(n^2))하지만, Set은 해시 기반이라 `has` 체크가 O(1) → 중복 제거가 O(n)

|                     | Array                       | Object                                                                    | Map                                | Set               |
| ------------------- | --------------------------- | ------------------------------------------------------------------------- | ---------------------------------- | ----------------- |
| 용도                | 순서 있는 목록              | key-value (key는 string/symbol)                                           | key-value (key는 모든 타입 가능)   | 중복 없는 값 집합 |
| key 타입 제약       | 인덱스(정수)                | string, symbol만 (숫자 키도 내부적으로 문자열 변환)                       | 제약 없음 (객체, 함수도 key 가능)  | -                 |
| 순서 보장           | 보장                        | ES2015+에서 삽입 순서 보장하지만 스펙상 보증 대상은 아니었음(관례로 보장) | **삽입 순서 보장** (스펙으로 명시) | 삽입 순서 보장    |
| 크기 확인           | `.length`                   | `Object.keys(obj).length`                                                 | `.size` (O(1))                     | `.size` (O(1))    |
| 반복 가능(iterable) | 가능 (`for...of`)           | 불가 (`for...in`, `Object.keys` 등 우회 필요)                             | 가능                               | 가능              |
| 내부 구현           | 동적 배열(엔진에 따라 다름) | 해시 테이블 유사 구조                                                     | 해시 테이블                        | 해시 테이블       |

## 2. 배열 연산의 시간복잡도

- `map().filter().reduce()`처럼 체이닝하면 각 단계가 O(n)이라도 전체는 O(3n) = O(n)이지만, 배열을 여러 번 순회하므로 큰 데이터에서는 하나의 `reduce`나 `for`문으로 합치는 게 성능상 유리할 수 있음

| 메서드                               | 복잡도           | 이유                                              |
| ------------------------------------ | ---------------- | ------------------------------------------------- |
| `arr[i]`, `arr.length`               | O(1)             | 인덱스 접근                                       |
| `push`, `pop`                        | O(1) (amortized) | 끝에서 삽입/삭제                                  |
| `shift`, `unshift`                   | O(n)             | 앞에 삽입/삭제 시 나머지 요소를 전부 한 칸씩 이동 |
| `indexOf`, `includes`, `find`        | O(n)             | 순차 탐색                                         |
| `splice` (중간 삽입/삭제)            | O(n)             | 이후 요소들을 이동                                |
| `map`, `filter`, `forEach`, `reduce` | O(n)             | 전체 순회 (콜백 자체가 무거우면 그만큼 더 커짐)   |
| `sort`                               | O(n log n)       | V8은 팀소트(TimSort) 계열 사용                    |
| `concat`, `slice`                    | O(n)             | 새 배열로 복사                                    |

## 3. 불변성

- 기존 메모리 영역에 있는 데이터(상태)를 **직접 변경(mutate)하지 않고**, 변경이 필요하면 새로운 메모리 영역에 복사본을 만들어 반환하는 방식

### 📍Mutable vs Immutable 예시

```js
// Mutable (원본 변경 -> 지양하는 방식)
const arr = [1, 2, 3];
arr.push(4); // 원본 배열 변경
arr.splice(0, 1); // 원본 배열 변경
obj.key = "new"; // 원본 객체 프로퍼티 변경

// Immutable (새 값 생성)
const arr = [1, 2, 3];
const newArr = [...arr, 4];
const newArr2 = arr.filter((_, i) => i !== 0); // 불변성을 유지하는 내장 메서드
const newObj = { ...obj, key: "new" };
```

### 💡불변성을 지키는 이유

- **참조 비교(===)로 변경 감지 가능:** React가 `props`/`state`가 바뀌었는지 판단할 때 얕은 비교로 리렌더링 여부를 결정 → 객체를 직접 mutate하면 참조가 동일해서 변경을 감지 못함
- **side effect 방지:** 원본 객체를 직접 수정하면 해당 객체를 참조하고 있던 애플리케이션의 다른 부분에서도 예기치 않게 값이 변경되는 버그가 발생할 수 있음
- **undo/redo, 상태 히스토리 관리가 쉬워짐** → 이전 상태 객체가 그대로 보존됨

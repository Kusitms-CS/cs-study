# 1주차 - 자료구조 / 시간복잡도

## Big-O

### 개념

- 입력 크기 `n`에 따른 시간·공간 사용량의 증가율
- 실제 실행 시간보다 입력 증가에 따른 **변화 추세**에 집중
- 상수와 영향력이 낮은 항은 생략

```javascript
function printAll(array) {
  for (const item of array) {
    console.log(item);
  }
}
```

- 배열 길이만큼 반복: `O(n)`
- `2n` → `O(n)`
- `3n² + 5n + 10` → `O(n²)`

### O(log n)

```javascript
for (let i = 1; i < n; i *= 2) {
  console.log(i);
}
```

- 작업할 때마다 처리 범위가 일정한 비율로 감소
- 대표 사례: 정렬된 배열의 이진 탐색
- 데이터 약 100만 개 → 약 20번의 범위 축소

### 주요 시간 복잡도 비교

| 시간 복잡도 | 대표 사례 |
| --- | --- |
| `O(1)` | 배열 인덱스 접근 |
| `O(log n)` | 이진 탐색 |
| `O(n)` | 전체 요소 순회 |
| `O(n log n)` | 병합 정렬 |
| `O(n²)` | 이중 반복문 |
| `O(2ⁿ)` | 모든 부분집합 탐색 |
| `O(n!)` | 모든 순열 탐색 |

입력 크기가 커질 때의 일반적인 성능 순서:

```text
O(1) < O(log n) < O(n) < O(n log n) < O(n²) < O(2ⁿ) < O(n!)
```

### 최선·평균·최악의 경우

- 최선: 첫 번째 원소가 정답 → `O(1)`
- 평균: 중간에서 발견 → `O(n)`
- 최악: 마지막에 있거나 존재하지 않음 → `O(n)`
- 별도 조건이 없다면 일반적으로 최악의 경우를 기준으로 설명

- `O`: 증가율의 상한
- `Ω`: 증가율의 하한
- `Θ`: 상한과 하한이 같은 정확한 증가율

### 공간 복잡도

- 입력 크기에 따른 메모리 사용량의 증가율
- 입력 자체를 제외하고 추가로 사용하는 **보조 공간 복잡도**가 주요 분석 대상

- 변수 몇 개만 추가로 사용: `O(1)`
- 입력 크기만큼 새로운 배열 생성: `O(n)`
- 재귀 호출: 호출 스택에 쌓이는 메모리도 포함

### 핵심 정리

- Big-O: 입력 크기에 따른 시간·공간 사용량의 증가 추세
- `O(n)`: 입력 크기에 비례해 연산량 증가, 예시: 선형 탐색
- `O(log n)`: 처리 범위가 일정 비율로 감소, 예시: 이진 탐색
- 입력 약 100만 개 기준
  - 선형 탐색: 최대 약 100만 번
  - 이진 탐색: 약 20번

### 자주 묻는 질문

#### Big-O는 항상 최악의 경우를 의미할까?

- Big-O: 함수 증가율의 상한
- 최악의 경우를 Big-O로 자주 표현할 뿐, 두 개념은 동일하지 않음

## Array

### 개념

- 같은 종류의 데이터를 순서대로 저장하는 자료구조
- 각 요소에 인덱스 부여
- 일반적인 배열은 연속된 메모리 공간 사용
- 인덱스를 이용한 접근: `O(1)`
- 원하는 값을 찾는 순차 탐색: `O(n)`

```javascript
const numbers = [10, 20, 30, 40];

numbers[2]; // O(1)
numbers.find((number) => number === 30); // O(n)
```

### 주요 연산

| 연산 | 시간 복잡도 | 이유 |
| --- | ---: | --- |
| 인덱스 접근 | `O(1)` | 위치를 바로 계산 |
| `push()`, `pop()` | 분할 상환 `O(1)` | 배열 끝에서 작업 |
| `shift()`, `unshift()` | `O(n)` | 기존 원소 이동 |
| `includes()`, `find()` | `O(n)` | 순차 탐색 |
| `splice()` | `O(n)` | 원소 이동 가능 |
| `map()`, `filter()` | `O(n)` | 전체 원소 순회 |

### 동적 배열

- `length`: 현재 저장된 원소 개수
- `capacity`: 확보된 내부 저장 공간
- 공간이 가득 차면 더 큰 공간을 확보한 뒤 기존 원소 복사
- 확장하는 순간: `O(n)`
- 여러 번의 끝 삽입을 평균: 분할 상환 `O(1)`

### JavaScript Array

- 전통적인 배열과 달리 특수한 객체
- 엔진이 배열 형태에 따라 내부 저장 방식 최적화
- 연속된 메모리 저장을 명세에서 보장하지 않음
- 일반적인 밀집 배열의 인덱스 접근은 `O(1)`로 분석
- `delete array[index]`: 원소 자리를 비우지만 `length`는 유지

### 배열 메서드의 중첩

```javascript
users.filter((user) => selectedIds.includes(user.id));
```

- `filter()`: `O(n)`
- 각 순회에서 `includes()`: `O(m)`
- 전체: `O(nm)`
- `selectedIds`를 `Set`으로 변환하면 평균 `O(n + m)`
- 조회 성능을 얻는 대신 `O(m)`의 추가 공간 사용

### 핵심 정리

- 장점: 빠른 인덱스 접근, 순회에 적합
- 단점: 앞이나 중간의 삽입·삭제 시 원소 이동 필요
- 코드에 보이는 반복문뿐 아니라 호출한 메서드의 내부 반복도 함께 분석

### 자주 묻는 질문

#### `push()`는 항상 O(1)일까?

- 일반적인 끝 삽입: `O(1)`
- 저장 공간 확장과 기존 원소 복사가 발생하는 순간: `O(n)`
- 여러 번의 삽입 비용을 평균하면 분할 상환 `O(1)`

## Linked List

### 개념

- 데이터를 노드 단위로 저장
- 각 노드는 값과 다음 노드를 가리키는 참조 보유
- 노드가 메모리의 연속된 위치에 있을 필요 없음
- 특정 위치 접근 시 `head`부터 순회: `O(n)`

```text
head → [10 | next] → [20 | next] → [30 | null]
```

### 종류

- 단일 연결 리스트: `next`만 저장, 한 방향 이동
- 이중 연결 리스트: `prev`와 `next` 저장, 양방향 이동
- 이중 연결 리스트는 이동과 삭제가 편리하지만 추가 메모리 필요

### 주요 연산

| 연산 | 시간 복잡도 | 조건 |
| --- | ---: | --- |
| 인덱스 접근·값 탐색 | `O(n)` | `head`부터 순회 |
| 맨 앞 삽입·삭제 | `O(1)` | `head` 변경 |
| 맨 뒤 삽입 | `O(1)` | `tail` 관리 시 |
| 맨 뒤 삭제 | `O(n)` | 단일 연결 리스트 기준 |
| 중간 삽입·삭제 | `O(1)` | 필요한 노드를 이미 아는 경우 |
| 위치 탐색 포함 | `O(n)` | 대상 위치까지 순회 |

### Array와 비교

| Array | Linked List |
| --- | --- |
| 인덱스 접근 `O(1)` | 인덱스 접근 `O(n)` |
| 앞·중간 삽입 및 삭제 `O(n)` | 연결할 노드를 알면 `O(1)` |
| 추가 포인터 공간 불필요 | 노드마다 포인터 공간 필요 |
| 캐시 효율이 좋음 | 노드가 흩어져 캐시 효율이 낮을 수 있음 |

### 핵심 정리

- 장점: 연결할 노드를 알 때 빠른 삽입·삭제
- 단점: 느린 임의 접근, 포인터를 위한 추가 공간
- 삽입·삭제가 `O(1)`이라는 설명은 **탐색 비용을 제외한 경우**
- JavaScript에는 기본 연결 리스트 자료형이 없어 필요하면 직접 구현

### 자주 묻는 질문

#### tail이 있는데 단일 연결 리스트의 마지막 노드 삭제가 O(n)인 이유는?

- `tail`로 마지막 노드에는 바로 접근 가능
- 새로운 `tail`이 될 이전 노드는 알 수 없음
- 이전 노드를 찾기 위해 `head`부터 순회: `O(n)`
- 이중 연결 리스트는 `tail.prev`가 있어 `O(1)`

## Stack

### 개념

- 나중에 들어온 데이터가 먼저 나가는 LIFO 구조
- 데이터의 삽입과 삭제가 한쪽 끝에서만 발생
- 가장 위에 있는 데이터만 접근 가능

```text
push(10) → push(20) → push(30) → pop() = 30
```

### 주요 연산

| 연산 | 역할 | 시간 복잡도 |
| --- | --- | ---: |
| `push` | 맨 위에 데이터 추가 | `O(1)` |
| `pop` | 맨 위 데이터 제거 및 반환 | `O(1)` |
| `peek` | 맨 위 데이터 확인 | `O(1)` |
| `isEmpty` | 비어 있는지 확인 | `O(1)` |

### JavaScript 구현

```javascript
const stack = [];

stack.push(10);
stack.push(20);
stack.at(-1); // peek: 20
stack.pop(); // 20
```

- 배열의 끝을 스택의 맨 위로 사용
- `push()`, `pop()`: 분할 상환 `O(1)`
- `unshift()`, `shift()` 사용 시 원소 이동으로 `O(n)`

### 활용 사례

- 함수 호출 스택
- 실행 취소
- 괄호 짝 검사
- 깊이 우선 탐색
- 후위 표기식 계산

### 호출 스택

- 함수 호출 시 실행 정보를 스택에 추가
- 함수 종료 시 가장 최근 실행 정보부터 제거
- 종료 조건 없는 재귀 호출은 스택 오버플로 발생 가능
- JavaScript 오류 예시: `Maximum call stack size exceeded`

### 핵심 정리

- 삽입과 삭제가 `O(1)`인 LIFO 자료구조
- 중간 데이터에 직접 접근하거나 탐색할 때는 `O(n)`
- 괄호 검사는 가장 최근에 열린 괄호부터 닫혀야 하므로 스택에 적합

## Queue

### 개념

- 먼저 들어온 데이터가 먼저 나가는 FIFO 구조
- 삽입은 뒤쪽, 삭제는 앞쪽에서 발생

```text
front                     rear
  ↓                         ↓
[10] → [20] → [30]
```

### 주요 연산

| 연산 | 역할 | 시간 복잡도 |
| --- | --- | ---: |
| `enqueue` | 뒤에 데이터 추가 | `O(1)` |
| `dequeue` | 앞의 데이터 제거 | `O(1)` |
| `front` | 앞의 데이터 확인 | `O(1)` |
| `isEmpty` | 비어 있는지 확인 | `O(1)` |

### JavaScript 구현 시 주의점

```javascript
const queue = [];

queue.push(10); // enqueue
queue.shift(); // dequeue
```

- `push()`: 분할 상환 `O(1)`
- `shift()`: 남은 원소를 이동하므로 `O(n)`
- 효율적인 구현: `head`, `tail` 인덱스를 별도로 관리
- 연결 리스트의 `head`, `tail`을 이용한 구현도 가능

### 활용 사례

- 요청과 작업을 들어온 순서대로 처리
- 프린터 작업 대기열
- 너비 우선 탐색
- 메시지 큐와 작업 스케줄링
- JavaScript 이벤트 루프의 태스크 대기열

### 핵심 정리

- Queue: 가장 오래 기다린 데이터부터 처리
- Stack: 가장 최근에 들어온 데이터부터 처리
- 자료구조의 연산뿐 아니라 실제 구현 방식의 시간 복잡도도 확인

## Hash Table

### 개념

- 키와 값의 쌍으로 데이터 저장
- 해시 함수로 키를 저장 위치로 변환
- 저장 위치를 바로 계산해 평균 `O(1)`로 접근

### 주요 연산

| 연산 | 평균 | 최악 |
| --- | ---: | ---: |
| 삽입 | `O(1)` | `O(n)` |
| 탐색 | `O(1)` | `O(n)` |
| 삭제 | `O(1)` | `O(n)` |

### 해시 충돌

- 서로 다른 키가 같은 저장 위치를 얻는 현상
- 저장 공간은 한정되어 있으므로 충돌을 완전히 피할 수 없음
- 체이닝: 같은 위치의 데이터를 연결 리스트 등으로 연결
- 개방 주소법: 비어 있는 다른 위치를 탐색
- 충돌이 많아지면 한 위치의 데이터를 순차 탐색해 최악 `O(n)`

### 리해싱

- 데이터가 많아지면 더 큰 저장 공간 확보
- 기존 데이터를 새로운 위치에 다시 저장
- 리해싱 순간의 비용: `O(n)`
- 매번 발생하지 않으므로 삽입은 평균 `O(1)`

### JavaScript Object, Map, Set

| 자료구조 | 특징 | 주요 용도 |
| --- | --- | --- |
| `Object` | 문자열·Symbol 키 | 구조화된 데이터 표현 |
| `Map` | 모든 자료형을 키로 사용 | 키와 값의 빈번한 추가·삭제 |
| `Set` | 중복 없는 값 저장 | 중복 제거와 존재 여부 확인 |

- `Map.get()`, `Map.has()`, `Set.has()`: 평균 `O(1)`
- ECMAScript 명세는 구체적인 내부 구현과 시간 복잡도를 보장하지 않음

```javascript
const uniqueNumbers = [...new Set(numbers)];
```

- Set 생성과 새 배열 생성: 시간 `O(n)`
- 최대 `n`개의 값을 추가로 저장: 공간 `O(n)`

### 핵심 정리

- 장점: 평균 `O(1)`의 빠른 삽입·탐색·삭제
- 단점: 충돌 가능 해소와 추가 저장 공간 필요
- 최악의 경우 충돌로 인해 `O(n)`까지 저하 가능

## Tree

### 개념

- 부모와 자식 관계로 연결된 계층형 자료구조
- 루트: 가장 위에 있는 노드
- 리프: 자식이 없는 노드
- 깊이: 루트에서 특정 노드까지의 거리
- 높이: 가장 먼 리프까지의 거리
- 노드가 `n`개인 트리의 간선 수: `n - 1`

```text
        A
       / \
      B   C
     / \
    D   E
```

### 이진 트리

- 각 노드가 최대 두 개의 자식을 갖는 트리
- 왼쪽과 오른쪽 자식으로 구분
- 값의 정렬 조건은 없음
- 완전 이진 트리: 마지막 레벨을 제외하고 모두 채워지며 왼쪽부터 배치
- 균형 이진 트리: 왼쪽과 오른쪽 서브트리의 높이 차이가 크지 않음

### 이진 탐색 트리

- 왼쪽 서브트리의 모든 값은 현재 노드보다 작음
- 오른쪽 서브트리의 모든 값은 현재 노드보다 큼
- 균형 잡힌 경우 탐색·삽입·삭제: 평균 `O(log n)`
- 한쪽으로 편향된 경우: 최악 `O(n)`
- 균형을 유지하는 구조: AVL 트리, 레드-블랙 트리

### 트리 순회

| 방식 | 순서 | 특징 |
| --- | --- | --- |
| 전위 순회 | 루트 → 왼쪽 → 오른쪽 | 트리 복사, 구조 확인 |
| 중위 순회 | 왼쪽 → 루트 → 오른쪽 | 이진 탐색 트리에서 오름차순 |
| 후위 순회 | 왼쪽 → 오른쪽 → 루트 | 하위 노드부터 처리 |
| 레벨 순회 | 깊이가 낮은 노드부터 | 큐를 이용한 너비 우선 탐색 |

- 깊이 우선 순회: 재귀 호출 또는 스택 사용
- 레벨 순회: 큐 사용

### 핵심 정리

- 계층 구조 표현에 적합: 파일 시스템, DOM, 조직도
- 이진 트리와 이진 탐색 트리는 서로 다른 개념
- 이진 탐색 트리의 성능은 트리의 균형에 영향받음
- 정렬 조건은 직계 자식뿐 아니라 서브트리 전체에 적용

## Heap

### 개념

- 완전 이진 트리 형태의 자료구조
- 최대 힙: 루트에 최댓값 위치
- 최소 힙: 루트에 최솟값 위치
- 부모와 자식 사이의 우선순위만 보장
- 전체 데이터의 정렬 상태는 보장하지 않음

### 주요 연산

| 연산 | 시간 복잡도 |
| --- | ---: |
| 최댓값·최솟값 확인 | `O(1)` |
| 삽입 | `O(log n)` |
| 루트 삭제 | `O(log n)` |
| 특정 값 탐색 | `O(n)` |
| 힙 생성 | `O(n)` |

### 삽입과 삭제

- 삽입: 마지막 위치에 추가한 뒤 부모와 비교하며 위로 이동
- 위로 이동하는 과정: `heapify-up`
- 루트 삭제: 마지막 노드를 루트로 옮긴 뒤 자식과 비교하며 아래로 이동
- 아래로 이동하는 과정: `heapify-down`
- 이동 범위가 트리 높이에 비례하므로 `O(log n)`

### 이진 탐색 트리와 비교

| 이진 탐색 트리 | Heap |
| --- | --- |
| 왼쪽과 오른쪽 서브트리에 정렬 조건 적용 | 부모와 자식 사이에만 우선순위 적용 |
| 특정 값 탐색 평균 `O(log n)` | 특정 값 탐색 `O(n)` |
| 정렬된 순회 가능 | 최댓값·최솟값 조회에 적합 |

### 활용 사례

- 우선순위 큐
- 작업 스케줄링
- 힙 정렬
- 상위 `K`개 원소 탐색
- 다익스트라 최단 경로 알고리즘

### 핵심 정리

- 루트의 최댓값 또는 최솟값 확인: `O(1)`
- 삽입과 루트 삭제: `O(log n)`
- 임의의 값 탐색: `O(n)`
- JavaScript에는 기본 Heap 자료형이 없어 직접 구현하거나 라이브러리 사용
- 메모리 영역의 Heap과는 다른 개념

## Immutability

### 개념

- 기존 데이터를 직접 변경하지 않는 원칙
- 변경된 값을 가진 새로운 객체나 배열 생성
- 이전 상태를 보존해 데이터 변경 추적이 쉬움
- 참조 비교를 이용한 변경 감지에 유리

```javascript
const user = { name: "태경", age: 25 };
const nextUser = { ...user, age: 26 };

user === nextUser; // false
```

### 얕은 복사

```javascript
const original = { profile: { name: "태경" } };
const copied = { ...original };

original.profile === copied.profile; // true
```

- 스프레드 문법은 가장 바깥 단계만 복사
- 중첩된 `profile` 객체는 같은 참조를 공유
- 중첩 값을 직접 변경하면 원본에도 영향
- 변경되는 경로의 객체만 새로 만드는 구조적 공유 활용

```javascript
const copied = {
  ...original,
  profile: { ...original.profile, name: "민수" },
};
```

### 배열과 불변성

- 원본 변경: `push`, `pop`, `shift`, `unshift`, `splice`, `sort`, `reverse`
- 새 배열 반환: `map`, `filter`, `slice`, `concat`, 스프레드 문법

```javascript
const numbers = [3, 1, 2];
const sorted = [...numbers].sort();
```

### React 상태 관리

```javascript
setItems((previousItems) => [...previousItems, newItem]);
```

- 상태를 직접 수정하지 않고 새로운 참조 생성
- 참조 비교를 이용한 변경 감지
- 이전 상태 보존으로 예측과 디버깅이 쉬움
- 복사 과정에서 시간과 메모리가 추가로 필요

### 핵심 정리

- 불변성: 원본을 유지하고 새로운 값 생성
- 스프레드 문법: 깊은 복사가 아닌 얕은 복사
- 모든 데이터를 복사하지 않고 변경 경로만 새로 생성
- 예측 가능한 상태 관리와 성능 비용 사이의 균형 필요

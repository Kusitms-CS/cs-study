## 공통 개념 정리

### Big-O Notation

**빅오(Big-O)란?**

일상 사례로 먼저 보면, 전화번호부에서 이름을 찾는 상황을 생각하면 쉬워. 정렬 안 된 명단이면 처음부터 끝까지 한 명씩 확인해야 하니 명단이 길어질수록 걸리는 시간이 그대로 늘어나(O(n)). 반대로 가나다순으로 정렬돼 있으면 절반씩 건너뛰며 찾을 수 있어서(이분탐색), 명단이 2배로 늘어나도 걸리는 시간은 한 단계만 늘어나(O(log n)). 여기서 "알고리즘(찾는 방법) - 시간복잡도(명단 길이에 따라 걸리는 시간의 증가 패턴) - 빅오(그 증가 패턴을 수학적으로 표현하는 표기법)"의 관계가 나와.

- 빅오의 뜻: 입력 크기 n이 커질 때, 알고리즘의 실행 시간(또는 메모리 사용량)이 증가하는 정도의 "상한선(upper bound)"을 표현하는 점근적 표기법. 보통 최악의 경우(worst case)를 기준으로 표현함.
- 빅오 종류:
  - O(1): 입력 크기와 무관하게 항상 일정 (예: 배열 인덱스 접근)
  - O(log n): 매번 절반씩 줄어드는 경우 (예: 이분탐색)
  - O(n): 입력 크기에 비례 (예: 선형 탐색)
  - O(n log n): 정렬 알고리즘 다수 (예: 병합 정렬, 퀵 정렬 평균)
  - O(n²): 이중 반복문 (예: 버블 정렬)
  - O(2ⁿ), O(n!): 완전 탐색, 순열 등 (예: 피보나치 재귀, 외판원 문제)
- 규칙:
  1. 상수는 무시한다 (O(2n) → O(n))
  2. 가장 영향력 큰 항만 남긴다 (O(n²+n) → O(n²))
  3. 입력이 여러 개면 따로 표기한다 (O(a+b), 하나로 합치지 않음)

**어떨 때 쓰고, 어떨 때 안 쓸까?**

- 쓸 때: 서로 다른 알고리즘/자료구조의 효율성을 비교할 때, 입력 크기가 커질수록 성능 차이가 중요해지는 상황(대용량 데이터 처리)을 미리 예측할 때, 면접이나 코드 리뷰에서 효율성의 근거를 제시할 때
- 안 쓸 때(또는 큰 의미가 없을 때): 입력 크기가 애초에 아주 작아서 상수 배수 차이가 체감되지 않을 때, 가독성/유지보수성이 성능보다 더 중요한 상황일 때, 실제 병목은 캐시 적중률·I/O 등 하드웨어적 요인인데 빅오는 이런 요인을 반영하지 못한다는 점에 유의해야 할 때 (즉, 빅오가 같아도 실제 실행 속도는 다를 수 있음)

**왜 빅오(Big-O)일까?**

실제 실행 시간은 CPU 성능, 언어, 컴파일러 최적화 등 환경에 따라 달라져서 절대적인 비교 기준이 될 수 없어. 빅오는 이런 환경 요인을 배제하고 "입력 크기가 늘어날 때 연산량이 어떤 추세로 증가하는가"만 보기 때문에, 알고리즘 자체의 효율성을 환경과 무관하게 비교할 수 있는 공통 언어 역할을 해줘.

**빅오를 처음 정의한 사람과 그 배경**

O 표기법은 원래 컴퓨터 과학이 아니라 수학(정수론)에서 나왔어. 1894년 독일 수학자 파울 바흐만(Paul Bachmann)이 저서 「Die analytische Zahlentheorie」에서 처음 도입했고, 이후 에드문트 란다우(Edmund Landau)가 이 표기법을 정리하고 널리 알려서 "란다우 표기법(Landau notation)"이라고도 불려. 컴퓨터 과학 분야에는 1976년 도널드 커누스(Donald Knuth)가 알고리즘 분석 목적으로 O, Ω(오메가), Θ(세타) 표기법을 체계적으로 정리해 도입하면서 지금 우리가 쓰는 형태로 자리잡았어.

**빅오에서 등장하는 수학적 개념과 지식**

- 점근적 분석(Asymptotic Analysis): 입력 크기가 무한히 커질 때 함수(연산량)가 어떻게 행동하는지를 다루는 분석법
- 극한(limit) 개념: 두 함수 f(n), g(n)에 대해 n → ∞일 때 f(n)/g(n)이 유한한 값으로 수렴하는지를 따져서 두 알고리즘의 증가율을 비교
- 상한/하한 개념: Big-O(상한, 최악의 경우), Big-Ω(하한, 최선의 경우), Big-Θ(상한과 하한이 같을 때, 즉 평균적으로도 딱 맞아떨어지는 경우)
- 로그의 밑 변환: log의 밑(base)이 몇이든 상수 배수 차이일 뿐이라 빅오에서는 밑을 표기하지 않고 그냥 O(log n)으로 쓰는 이유

### Array

- 정의: 같은 타입의 데이터를 메모리상에 연속된 공간에 순서대로 저장하는 자료구조. 인덱스로 각 원소의 메모리 주소를 바로 계산할 수 있어서 접근이 빠름.
- 정적 배열 vs 동적 배열:
  - 정적 배열: 선언 시 크기가 고정됨 (예: Java의 배열, C의 배열)
  - 동적 배열: 크기가 가변적이며, 공간이 부족하면 내부적으로 더 큰 메모리를 새로 할당하고 기존 원소를 복사함 (예: JS Array, Python list, Java ArrayList). 이 재할당 때문에 "끝에 추가"는 대부분 O(1)이지만, 가끔 재할당이 발생할 땐 O(n)이 걸림 (평균적으로는 O(1) - 상각 시간복잡도, amortized O(1))
- 메모리 구조: 연속된 메모리 공간을 사용하기 때문에 CPU 캐시 활용도가 높아 실제 순차 접근 속도가 빠름 (캐시 지역성, cache locality)
- 단점: 중간에 원소를 삽입/삭제하려면 뒤(또는 앞) 원소들을 한 칸씩 밀어야 해서 O(n)이 걸림

### Array vs LinkedList

- 구조적 차이:
  - Array: 데이터가 메모리상에 연속으로 저장되고, 인덱스로 주소를 바로 계산해서 접근
  - LinkedList: 각 노드가 데이터 + 다음(또는 이전) 노드를 가리키는 포인터/참조를 가지고 있고, 메모리상에 흩어져 저장됨. 노드를 하나씩 따라가야만 접근 가능
- 삽입/삭제/탐색 시간복잡도 비교:

| 연산 | Array | LinkedList |
|---|---|---|
| 인덱스로 접근 | O(1) | O(n) |
| 값으로 탐색 | O(n) | O(n) |
| 맨 끝 삽입/삭제 | O(1) (동적 배열은 상각 O(1)) | O(1) (tail 포인터 있을 때) |
| 중간 삽입/삭제 | O(n) (뒤 원소들 이동 필요) | O(1) (단, 삽입할 위치까지 찾아가는 데 O(n) 소요) |

- 한 줄 정리: Array는 "접근"이 빠르고, LinkedList는 (위치를 이미 알고 있다는 전제하에) "삽입/삭제"가 빠름. 실무에서는 탐색이 잦은지, 삽입/삭제가 잦은지에 따라 선택.

### Stack / Queue

- Stack (LIFO, 후입선출):
  - push(추가)/pop(제거) 모두 O(1) — 맨 위(top)에서만 작업하기 때문
  - 예시: 함수 호출 스택(재귀), 브라우저 뒤로가기, 실행 취소(undo), 괄호 짝 검사
- Queue (FIFO, 선입선출):
  - enqueue(추가)/dequeue(제거) 모두 O(1) — 단, 배열로 구현할 때 앞에서 빼는 방식이면 O(n)이 될 수 있어 원형 큐(circular queue)나 LinkedList 기반으로 구현하는 게 일반적
  - 예시: 프린터 인쇄 대기열, BFS(너비 우선 탐색), 메시지 큐(작업 순서 보장이 필요한 시스템)
- Stack vs Queue 한 줄 비교: 둘 다 "한쪽 끝에서만 작업"하는 제한된 자료구조지만, Stack은 같은 쪽(top)에서 넣고 빼고, Queue는 반대쪽(rear에서 넣고 front에서 뺌)에서 작업한다는 점이 핵심 차이.

### Hash Table

- 내부 동작: 해시 함수(hash function)가 key를 특정 정수값(해시값)으로 변환하고, 이 값을 배열의 인덱스로 매핑해서 저장. 그래서 평균적으로 삽입/삭제/탐색이 모두 O(1).
- 해시 충돌(collision): 서로 다른 key가 같은 해시값(같은 인덱스)로 매핑될 때 발생. 해시 함수가 아무리 좋아도 완전히 피할 순 없음.
- 충돌 처리 방식:
  - 체이닝(Chaining): 같은 인덱스에 여러 값이 몰리면 그 자리에 연결리스트(또는 트리)로 이어붙여서 저장
  - 개방 주소법(Open Addressing): 충돌이 나면 다른 빈 슬롯을 찾아 나가는 방식 (선형 탐사, 이차 탐사, 이중 해싱 등)
- 최악의 경우: 충돌이 심하면 사실상 하나의 인덱스에 다 몰려서 O(n)까지 나빠질 수 있음. 이를 막기 위해 load factor(저장된 데이터 수 / 전체 슬롯 수)가 일정 기준을 넘으면 테이블 크기를 늘리고 다시 해싱(rehashing)함.

### Tree / Heap

- Tree: root(최상위 노드) - parent - child - leaf(자식 없는 노드) 구조를 가진 계층적 자료구조. 그 중 이진 탐색 트리(BST)는 왼쪽 자식은 부모보다 작고 오른쪽 자식은 크다는 규칙으로 정렬 상태를 유지.
  - 탐색/삽입/삭제: 평균 O(log n) (트리가 균형 잡혀 있을 때). 하지만 한쪽으로 계속 치우쳐 삽입되면 사실상 LinkedList와 같아져서 최악의 경우 O(n)까지 나빠짐 → 이를 막기 위해 AVL Tree, Red-Black Tree 같은 균형 트리(self-balancing tree) 사용
- Heap: 완전 이진 트리(complete binary tree) 기반의 자료구조로, "부모가 항상 자식보다 크거나(최대 힙) 작다(최소 힙)"는 규칙만 지킴 (좌우 정렬 규칙은 없음)
  - 최댓값/최솟값 조회: O(1) (항상 루트에 있음)
  - 삽입/삭제: O(log n)
  - 주로 우선순위 큐(Priority Queue) 구현에 사용됨

## 직군 심화 정리 (프론트)

### JS Array / Object / Map / Set

| | 특징 | 탐색 | 언제 쓰나 |
|---|---|---|---|
| Array | 순서 있는 리스트, 인덱스 접근 | 인덱스 O(1) / 값 탐색 O(n) | 순서가 중요한 목록 데이터 |
| Object | key-value, key는 문자열/심볼만 가능 | 평균 O(1) (해시 기반) | 구조화된 데이터(JSON 스러운 형태) |
| Map | key-value, key로 어떤 타입이든 가능(객체도 key로 사용 가능) | 평균 O(1) | 삽입 순서 보장·사이즈 관리(size)가 중요할 때, key가 문자열이 아닐 때 |
| Set | 중복 없는 값의 모음 | 평균 O(1) | 중복 제거, 존재 여부(has) 확인이 잦을 때 |

- 한 줄 정리: 순서 있는 리스트는 Array, 단순 구조체는 Object, key 타입이 자유롭거나 순서·사이즈 관리가 필요하면 Map, 중복 제거/존재 확인은 Set.

### 불변성 (Immutability)

- 정의: state나 props를 직접 변경(mutate)하지 않고, 변경이 필요할 때마다 새로운 객체/배열을 만들어서 교체하는 원칙.
- React에서 왜 중요한가: React는 리렌더링 여부를 판단할 때 이전 값과 새 값을 얕은 비교(shallow comparison, 참조값 비교)로 확인함. 객체를 직접 mutate하면 참조값(주소)이 그대로라서 React가 "값이 안 바뀌었다"고 오판해 리렌더링이 안 일어날 수 있음.
- 추가로 중요한 이유: useMemo, React.memo 같은 최적화 훅도 얕은 비교에 의존하기 때문에, 불변성을 안 지키면 이런 최적화가 아예 무력화될 수 있음. 또한 이전 상태를 그대로 보존할 수 있어 디버깅(예: 상태 변화 추적)에도 유리함.

## 예상 면접 질문

- Q. Array와 LinkedList는 언제 각각 쓰는 게 유리한가요?
  - A. 인덱스로 값에 자주 접근해야 하면 Array(O(1) 접근), 삽입/삭제가 잦고 그 위치를 이미 알고 있는 경우가 많으면 LinkedList가 유리해요. 다만 실무에서는 캐시 지역성 때문에 Array가 더 자주 쓰이는 편이에요.
- Q. 해시 충돌은 왜 발생하고, 어떻게 해결하나요?
  - A. 서로 다른 key가 같은 해시값으로 매핑될 때 발생해요. 같은 자리에 연결리스트로 이어붙이는 체이닝, 또는 다른 빈 슬롯을 찾아가는 개방 주소법으로 해결해요.
- Q. 이진 탐색 트리가 최악의 경우 왜 O(n)이 되나요?
  - A. 삽입 순서에 따라 한쪽으로만 계속 치우쳐 쌓이면 트리가 사실상 LinkedList 형태가 되기 때문이에요. 이를 방지하려고 AVL Tree, Red-Black Tree 같은 균형 트리를 씁니다.
- Q. Stack이나 Queue를 배열로 구현할 때 주의할 점은?
  - A. Stack은 배열 끝에서 push/pop하면 O(1)로 문제없지만, Queue를 배열 맨 앞에서 빼면(dequeue) 나머지 원소를 전부 한 칸씩 당겨야 해서 O(n)이 돼요. 그래서 원형 큐나 front/rear 포인터, 혹은 LinkedList 기반 구현을 씁니다.
- Q. Map과 Object 중 어떤 걸 써야 하나요?
  - A. key가 문자열/심볼이면 되고 JSON 직렬화가 중요하면 Object, key로 다양한 타입을 쓰거나 삽입 순서·사이즈 관리가 중요하면 Map이 더 적합해요.
- Q. React에서 불변성을 지키지 않으면 실제로 어떤 문제가 생기나요?
  - A. state를 직접 mutate하면 참조값이 그대로라 React가 변경을 감지 못해 화면이 리렌더링되지 않을 수 있고, useMemo나 React.memo 같은 얕은 비교 기반 최적화도 제대로 동작하지 않게됩니다.

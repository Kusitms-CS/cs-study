# 2주차 - OS - Process / Thread / 동시성

## 1. Process (프로세스)

- 운영체제로부터 **독립된 메모리 공간(주소 공간)을 할당받아 실행 중인 프로그램**
- 각 프로세스는 **Code, Data, Heap, Stack** 영역을 독립적으로 가짐
- 운영체제는 **PCB(Process Control Block)를 통해 프로세스 상태(PID, 레지스터 값, 스케줄링 정보, 메모리 정보 등)를 관리**

### 📍 프로세스의 메모리 구조

| 영역  | 설명                                                                                    |
| ----- | --------------------------------------------------------------------------------------- |
| Code  | 실행할 프로그램의 명령어(기계어) 저장, 읽기 전용                                        |
| Data  | 전역 변수, static 변수 저장                                                             |
| Heap  | 동적으로 할당되는 메모리 (런타임에 크기 증가), 낮은 주소 → 높은 주소로 증가             |
| Stack | 함수 호출 시 생성되는 지역 변수, 매개변수, 리턴 주소 저장, 높은 주소 → 낮은 주소로 증가 |

### 💡 멀티 프로세스의 장단점

**⇒ 장점:** 한 프로세스가 죽어도(crash) 메모리 공간이 독립적이라 다른 프로세스에 영향을 주지 않아 안정성이 높음. </br>
**⇒ 단점:** Context Switching 비용이 크고, 프로세스 간 데이터를 주고받으려면 IPC(Inter-Process Communication, 파이프·소켓·공유 메모리 등)라는 별도의 통신 방법이 필요해 스레드보다 통신 비용이 큼

---

## 2. Thread (스레드)

- 하나의 프로세스 내에서 실행되는 **작업의 흐름 단위**로, 프로세스의 자원을 공유하며 동작
- 같은 프로세스에 속한 스레드끼리는 **Code, Data, Heap 영역을 공유**하지만, **Stack과 Register, Program Counter(PC)는 각자 독립적으로 소유**
  ⇒ 독립된 Stack이 있어야 각 스레드가 서로 다른 함수 호출 흐름(지역 변수, 실행 위치)을 유지할 수 있기 때문

### 📍 Process vs Thread

| 구분           | Process                               | Thread                                               |
| -------------- | ------------------------------------- | ---------------------------------------------------- |
| 메모리         | 독립된 주소 공간                      | 프로세스 내 Code/Data/Heap 공유, Stack만 독립        |
| 생성/전환 비용 | 무거움 (주소 공간 전체 교체)          | 가벼움 (레지스터, Stack Pointer 정도만 교체)         |
| 통신 방법      | IPC 필요 (파이프, 소켓, 공유 메모리)  | 메모리 공유로 직접 접근 가능                         |
| 안정성         | 하나가 죽어도 다른 프로세스 영향 없음 | 하나가 죽으면 프로세스 전체(다른 스레드 포함)에 영향 |
| 대표 문제      | -                                     | Race Condition, 동기화 필요                          |

### 💡 멀티 스레드의 장단점

**⇒ 장점:** 메모리를 공유해 Context Switching 비용이 적고 통신이 빠름(IPC 불필요). </br>
**⇒ 단점:** 자원을 공유하기 때문에 동시에 같은 데이터에 접근할 때 Race Condition이 발생할 수 있어 동기화(Mutex, Semaphore 등) 처리가 필요함

---

## 3. Context Switching (문맥 교환)

- CPU가 하나의 프로세스/스레드에서 다른 프로세스/스레드로 실행을 전환할 때, 현재 실행 상태(레지스터 값, PC 등)를 **PCB/TCB에 저장**하고 다음 실행할 대상의 상태를 **복원**하는 작업
- 여러 프로세스를 동시에 처리하는 것처럼 보이게 하는 멀티태스킹의 핵심 메커니즘

### 📍 비용이 발생하는 이유

- 레지스터 저장/복원 자체의 오버헤드
- **캐시 미스(Cache Miss):** 이전 프로세스가 채워둔 CPU 캐시(L1/L2)가 새 프로세스에는 무의미해져 다시 채워야 함
- **TLB Flush:** 프로세스마다 가상 주소 공간이 다르므로 주소 변환 캐시인 TLB(Translation Lookaside Buffer)를 비우고 다시 채워야 함

### 💡 프로세스 전환이 스레드 전환보다 비용이 큰 이유

**⇒ 프로세스 전환은 페이지 테이블(주소 공간) 자체를 교체해야 해서 TLB/캐시 무효화 비용이 크지만, 같은 프로세스 내 스레드 전환은 주소 공간을 공유하므로 레지스터와 Stack Pointer 정도만 바꾸면 되어 상대적으로 가벼움**

---

## 4. 동시성 vs 병렬성 (Concurrency vs Parallelism)

- **동시성(Concurrency):** 싱글 코어에서 여러 작업을 아주 짧은 시간 단위로 번갈아 실행해, 실제로는 순차 실행이지만 **동시에 실행되는 것처럼 보이는 것** (인터리빙)
- **병렬성(Parallelism):** 멀티 코어를 이용해 여러 작업을 **물리적으로 동시에** 실행하는 것

| 구분      | 동시성 (Concurrency)                   | 병렬성 (Parallelism)                   |
| --------- | -------------------------------------- | -------------------------------------- |
| 코어 수   | 싱글 코어에서도 가능                   | 멀티 코어 필요                         |
| 실행 방식 | 빠르게 번갈아 실행(interleaving)       | 실제 동시 실행                         |
| 목적      | 자원 활용도 증가, 응답성 향상          | 처리 속도 향상                         |
| 예시      | 하나의 CPU로 여러 탭 처리하는 브라우저 | 멀티 코어로 이미지 여러 장 동시 렌더링 |

### 💡 동시성과 병렬성은 함께 쓰일 수 있을까?

**⇒ 가능함. 멀티 코어 환경에서 각 코어가 여러 작업을 동시성 방식으로 처리하면서, 코어 간에는 병렬로 실행되는 형태가 일반적인 현대 멀티태스킹 OS의 모습**

---

## 5. Race Condition (경쟁 상태)

- 여러 프로세스/스레드가 **공유 자원(critical section)에 동시에 접근할 때, 실행 순서에 따라 결과가 달라지는 문제**
- 원인: 공유 자원에 대한 읽기-수정-쓰기 같은 연산이 **원자적(atomic)이지 않아서** 중간에 다른 스레드가 끼어들 수 있기 때문

### 📍 예시

```js
// count가 여러 스레드에서 공유된다고 가정
// count++ 는 실제로 3단계 연산으로 쪼개짐
// 1. count 값을 읽음 (read)
// 2. 1을 더함 (modify)
// 3. count에 다시 씀 (write)
// 두 스레드가 동시에 read를 하면 하나의 증가 연산이 유실될 수 있음
count++;
```

### 💡 Race Condition을 막는 방법

**⇒ 공유 자원에 접근하는 코드 영역(Critical Section)에 한 번에 하나의 스레드만 진입하도록 Mutex, Semaphore 같은 동기화 도구로 상호 배제(Mutual Exclusion)를 보장해야 함**

---

## 6. Mutex / Semaphore

- 둘 다 **Critical Section에 대한 동시 접근을 제어**하기 위한 동기화 도구

### 📍 Mutex (Mutual Exclusion)

- **하나의 스레드만** 자원에 접근하도록 lock/unlock으로 제어
- **소유권(ownership) 개념 있음:** lock을 건 스레드만 unlock 가능

### 📍 Semaphore

- 내부적으로 **카운터(count)를 가지고, 지정된 수만큼의 스레드가 동시에 접근 가능하도록 허용**
- **소유권 개념 없음:** lock을 건 스레드가 아니어도 signal(release) 가능 → 스레드 간 순서 제어(신호)에도 사용

### 📍 Mutex vs Semaphore

| 구분                | Mutex                        | Semaphore                             |
| ------------------- | ---------------------------- | ------------------------------------- |
| 동시 접근 허용 개수 | 1개                          | N개 (카운터 값만큼)                   |
| 소유권              | 있음 (lock 건 주체만 unlock) | 없음 (누구나 signal 가능)             |
| 용도                | 상호 배제(mutual exclusion)  | 자원 개수 제한, 스레드 간 신호/동기화 |

### 💡 Deadlock과의 관계

**⇒ Mutex/Semaphore를 잘못 사용하면(예: 두 스레드가 서로 다른 순서로 여러 락을 잡음) 서로가 상대방이 가진 자원을 기다리며 무한 대기하는 Deadlock이 발생할 수 있음. 이를 막으려면 락 획득 순서를 일관되게 정하는 등의 규칙이 필요함**

# Frontend 심화

## 1. JS Single Thread

- JavaScript(브라우저의 메인 스레드 기준)는 **하나의 Call Stack만 가지는 싱글 스레드** 언어 → 한 번에 하나의 작업만 실행 가능
- 싱글 스레드로 설계된 이유는 **DOM 조작의 안전성** 때문 → 여러 스레드가 동시에 DOM을 변경하면 Race Condition이나 복잡한 동기화 문제가 생기므로, 이를 원천적으로 방지하기 위함

### 📍 이벤트 루프(Event Loop) 구조

- **Call Stack:** 현재 실행 중인 함수들이 쌓이는 공간 (동기 코드 실행)
- **Web APIs:** setTimeout, fetch, DOM 이벤트 등 브라우저가 제공하는 비동기 기능을 처리하는 영역 (JS 엔진 밖)
- **Task Queue (Macrotask Queue):** setTimeout, setInterval, 이벤트 콜백 등이 대기하는 큐
- **Microtask Queue:** Promise.then, async/await, MutationObserver 콜백이 대기하는 큐
- **Event Loop:** Call Stack이 비어있을 때마다 큐에서 꺼내 Call Stack으로 옮기는 역할

### 📍 동작 순서

1. 동기 코드(Call Stack) 먼저 모두 실행
2. Call Stack이 비면 **Microtask Queue를 모두 비울 때까지** 처리
3. 그 다음 **Macrotask Queue에서 하나**를 꺼내 실행
4. 다시 2번으로 반복

### 💡 setTimeout(fn, 0)이 즉시 실행되지 않는 이유

**⇒ setTimeout은 Web API로 넘어가 타이머가 끝나면 Task(Macrotask) Queue에 들어가고, Call Stack이 완전히 비워진 뒤(그리고 Microtask Queue까지 다 처리된 뒤)에야 Event Loop에 의해 Call Stack으로 옮겨져 실행되기 때문에 0ms를 줘도 동기 코드보다 항상 늦게 실행됨**

---

## 2. Web Worker

- **브라우저가 제공하는, JS를 메인 스레드와 별개의 백그라운드 스레드에서 실행할 수 있게 해주는 기능**
- 무거운 연산(대량 데이터 처리, 이미지/영상 처리, 복잡한 계산 등)을 Worker에서 처리해 **메인 스레드(UI 렌더링 담당)가 멈추지 않도록(non-blocking)** 함
- **DOM에 직접 접근 불가** → 메인 스레드와는 `postMessage`를 통한 메시지 전달(직렬화된 데이터 복사)로만 통신

### 📍 Worker 종류

| 종류             | 설명                                                                                                      |
| ---------------- | --------------------------------------------------------------------------------------------------------- |
| Dedicated Worker | 생성한 하나의 페이지(스크립트)에서만 사용 가능한 전용 워커                                                |
| Shared Worker    | 같은 origin의 여러 탭/페이지에서 하나의 Worker 인스턴스를 공유해 사용                                     |
| Service Worker   | 페이지와 독립적으로 백그라운드에서 동작, 네트워크 요청 가로채기(캐싱), 푸시 알림, 오프라인 지원 등에 사용 |

### 💡 Web Worker가 있어도 JS를 멀티 스레드 언어라고 하지 않는 이유

**⇒ Worker는 완전히 독립된 전역 스코프와 자체 Call Stack을 가진 별도의 스레드일 뿐, 메인 스레드와 메모리(변수, 객체)를 직접 공유하지 않고 메시지(복사된 데이터)만 주고받음. 즉 JS 엔진 자체의 실행 모델이 멀티 스레드로 바뀐 것이 아니라, 브라우저가 별도의 JS 실행 환경을 하나 더 제공해주는 것에 가까움**

---

## 3. 브라우저 Multi-Process 구조

- 현대 브라우저(Chrome 등)는 하나의 거대한 프로세스가 아니라 **역할별로 나뉜 여러 프로세스**로 구성됨 (Chrome의 Multi-Process Architecture)

### 📍 주요 프로세스 종류

| 프로세스                 | 역할                                                                                          |
| ------------------------ | --------------------------------------------------------------------------------------------- |
| Browser Process          | 주소창, 북마크, 탭 관리 등 브라우저 UI 전체와 각 프로세스 조율(메인 컨트롤타워)               |
| Renderer Process         | 실제 웹페이지(HTML/CSS/JS)를 파싱하고 렌더링, 원칙적으로 **탭/사이트별로 별도 프로세스** 생성 |
| GPU Process              | 화면 합성(compositing), 그래픽 렌더링 가속 처리                                               |
| Network Process          | 네트워크 요청(HTTP 등) 처리                                                                   |
| Plugin/Extension Process | 확장 프로그램 등 플러그인 실행                                                                |

### 📍 Renderer Process 내부 스레드

- **Main Thread:** HTML/CSS 파싱, DOM/CSSOM 생성, JS 실행, 레이아웃/페인트 계산 (JS Single Thread가 바로 여기)
- **Compositor Thread:** 레이어를 합성해 화면에 그리는 역할, 스크롤 등 일부 처리는 메인 스레드 없이도 처리 가능
- **Raster Thread:** 레이어를 실제 픽셀(비트맵)로 변환

### 💡 Multi-Process 구조를 사용하는 이유

**⇒ 안정성:** 한 탭(Renderer Process)이 크래시(예: 무한루프, 메모리 누수)나도 다른 탭이나 브라우저 자체는 영향을 받지 않음. </br>
**⇒ 보안:** 각 프로세스가 독립된 메모리 공간과 권한을 가지는 샌드박스(Sandbox)로 격리되어, 특정 웹페이지가 악성 코드를 실행해도 다른 사이트의 데이터나 시스템 자원에 접근하기 어려움 (Site Isolation)

# 2주차 - Process / Thread / 동시성

## Process

### 프로그램과 프로세스

- 프로그램: 저장 장치에 존재하는 실행 가능한 파일
- 프로세스: 운영체제로부터 자원을 할당받아 실행 중인 프로그램
- 같은 프로그램을 여러 번 실행하면 서로 다른 프로세스 생성 가능

### 프로세스의 자원

- 고유한 프로세스 ID
- 독립된 가상 주소 공간
- 실행 중인 코드와 데이터
- CPU 레지스터 상태
- 열린 파일 등의 운영체제 자원
- 최소 하나 이상의 스레드

### PCB

운영체제가 프로세스를 관리하기 위해 유지하는 정보:

- 프로세스 ID
- 현재 실행 상태
- 다음에 실행할 명령의 위치
- CPU 레지스터 값
- 스케줄링 정보
- 메모리 관리 정보

프로세스의 실행이 중단됐다가 재개될 때 PCB의 정보를 이용해 이전 실행 상태를 복원한다.

### 프로세스 상태

| 상태 | 의미 |
| --- | --- |
| 생성 | 프로세스를 만드는 중 |
| 준비 | 실행할 준비를 마치고 CPU 할당을 기다림 |
| 실행 | CPU를 할당받아 명령을 수행 중 |
| 대기 | 입출력 등의 작업 완료를 기다림 |
| 종료 | 실행이 끝남 |

```text
실행 → 대기 → 준비 → 실행
```

- 입출력 요청: 실행 → 대기
- 입출력 완료: 대기 → 준비
- 스케줄러의 CPU 할당: 준비 → 실행

### 핵심 정리

- 프로그램은 정적인 파일, 프로세스는 실행 중인 동적인 상태
- 프로세스는 운영체제의 자원 할당 단위
- 프로세스별 메모리 분리로 오류 영향 감소
- 프로세스 간 데이터 교환에는 IPC 등의 별도 통신 방식 필요

### 자주 묻는 질문

#### 준비 상태와 대기 상태의 차이는?

- 준비: CPU를 받으면 바로 실행 가능
- 대기: 입출력이 끝나지 않아 CPU를 받아도 실행 불가

## Thread

### 개념

- 프로세스 내부에서 실제 명령을 실행하는 단위
- 하나의 프로세스는 최소 하나 이상의 스레드 보유
- 프로세스는 자원 할당 단위, 스레드는 CPU 실행 단위

### 공유 자원과 독립 자원

같은 프로세스의 스레드가 공유하는 자원:

- 코드
- 데이터
- 힙
- 열린 파일 등 프로세스 자원

각 스레드가 독립적으로 가지는 정보:

- 스택
- CPU 레지스터
- 프로그램 카운터

### 프로세스와 스레드 비교

| 프로세스 | 스레드 |
| --- | --- |
| 독립된 메모리 공간 | 같은 프로세스의 메모리 공유 |
| 생성과 전환 비용이 비교적 큼 | 생성과 전환 비용이 비교적 작음 |
| 통신할 때 IPC 필요 | 공유 메모리로 데이터 교환 가능 |
| 다른 프로세스의 오류에 비교적 안전 | 하나의 문제가 전체 프로세스에 영향 가능 |

### 멀티스레드

장점:

- 여러 작업을 함께 처리
- 입출력 대기 중 다른 작업 수행
- 프로세스 자원을 효율적으로 공유
- 프로그램의 응답성 향상

주의점:

- 공유 데이터의 동기화 필요
- Race Condition 발생 가능
- 실행 순서를 예측하기 어려움
- 디버깅 난이도 증가

### 핵심 정리

- 자원 공유로 빠르게 협력할 수 있지만 동기화 문제 발생 가능
- 스레드마다 독립된 스택이 있어 함수 호출과 지역 변수 분리
- 멀티스레드는 성능뿐 아니라 안정성과 복잡성도 함께 고려

## Context Switching

### 개념

- CPU가 현재 작업을 중단하고 다른 프로세스나 스레드로 전환하는 과정
- 기존 작업의 실행 상태를 저장하고 다음 작업의 상태를 복원
- 여러 작업이 동시에 진행되는 것처럼 보이게 하는 기반

저장하고 복원하는 정보:

- 프로그램 카운터
- CPU 레지스터
- 스택 포인터
- 프로세스 또는 스레드의 실행 상태

### 발생 시점

- 할당된 CPU 시간 종료
- 입출력 대기
- 우선순위가 높은 작업의 실행 준비
- 인터럽트 발생
- 실행 중인 작업의 CPU 양보

### 오버헤드

- 실행 상태 저장과 복원
- 다음 작업을 선택하는 스케줄링
- CPU 캐시 효율 저하
- 프로세스 전환 시 주소 공간 변경 가능
- 전환 중에는 사용자 작업을 직접 처리하지 않음

### 프로세스 전환과 스레드 전환

- 프로세스 전환: 주소 공간이 달라질 수 있어 비용이 비교적 큼
- 같은 프로세스의 스레드 전환: 공유 자원이 많아 비교적 저렴
- 스레드 전환도 레지스터와 스택 상태 변경이 필요해 비용 발생

### 핵심 정리

- 실행 가능한 스레드가 지나치게 많으면 전환 횟수 증가
- 잦은 전환은 상태 저장·복원과 캐시 손실로 성능 저하 가능
- Race Condition은 공유 데이터 문제, 전환 오버헤드는 작업 교체 비용

## 동시성과 병렬성

### 동시성

- 여러 작업이 일정 시간 동안 함께 진행되는 구조
- 하나의 CPU 코어에서도 가능
- 작업을 번갈아 실행해 여러 작업이 진행 중인 상태 유지
- 작업 관리와 응답성에 초점

### 병렬성

- 여러 작업이 같은 순간에 실제로 실행되는 방식
- 일반적으로 여러 CPU 코어 필요
- 여러 작업을 나누어 처리해 실행 시간 단축 가능
- 처리 속도 향상에 초점

### 비교

| 동시성 | 병렬성 |
| --- | --- |
| 여러 작업을 번갈아 진행 | 여러 작업을 실제로 동시에 실행 |
| 하나의 코어에서도 가능 | 일반적으로 여러 코어 필요 |
| 동시에 실행되는 것처럼 보일 수 있음 | 물리적으로 같은 시점에 실행 |

### Context Switching과의 차이

- 동시성: 여러 작업을 함께 진행하는 개념
- Context Switching: CPU가 실행할 프로세스나 스레드를 교체하는 과정
- 하나의 코어에서는 Context Switching으로 동시성 구현 가능
- 동시성이 항상 운영체제 수준의 Context Switching을 의미하지는 않음
- JavaScript 이벤트 루프도 하나의 스레드에서 동시성 있는 작업 처리 가능

### 핵심 정리

- 동시성은 작업을 다루는 구조, 병렬성은 실제 동시 실행
- Context Switching은 동시성을 구현할 수 있는 방법 중 하나
- JavaScript 메인 스레드는 동시성 처리가 가능하지만 코드의 병렬 실행은 아님

## Race Condition

### 개념

- 여러 실행 흐름이 공유 자원에 접근할 때 실행 순서에 따라 결과가 달라지는 문제
- 하나 이상의 실행 흐름이 공유 자원을 변경할 때 발생 가능
- 모든 실행 흐름이 읽기만 한다면 일반적으로 발생하지 않음

```text
초기값: counter = 0

스레드 A: 읽기 0 → 계산 1 → 저장 1
스레드 B: 읽기 0 → 계산 1 → 저장 1

기대 결과: 2
실제 결과: 1
```

### 발생 조건

- 여러 프로세스나 스레드가 같은 자원에 접근
- 하나 이상이 공유 자원을 변경
- 접근 순서가 제어되지 않음
- 실행 순서에 따라 결과가 달라짐

### 임계 영역

- 공유 자원에 접근하는 코드 영역
- 한 번에 하나의 실행 흐름만 접근하도록 보호할 필요가 있는 부분
- Mutex와 Semaphore 등의 동기화 도구로 접근 제어

### Frontend 사례

- 사용자가 `a` 검색 후 바로 `ab` 검색
- `ab` 응답이 먼저 도착해 최신 결과 표시
- 이전 요청인 `a` 응답이 나중에 도착해 화면을 덮어씀
- 비동기 작업의 완료 순서에 따라 화면 결과가 달라짐

해결 방법:

- 이전 요청 취소
- 요청마다 식별자 부여
- 가장 최근 요청의 결과만 반영

### 핵심 정리

- 동시 접근 자체보다 제어되지 않은 공유 데이터 변경이 문제
- 한 번의 코드처럼 보여도 읽기·계산·저장으로 나뉠 수 있음
- 실행 순서가 달라도 결과가 같도록 동기화 필요

## Mutex와 Semaphore

### Mutex

- 임계 영역에 한 번에 하나의 실행 흐름만 접근
- 잠김 또는 열림 상태
- 잠금을 획득한 실행 흐름이 해제하는 것이 원칙
- 하나의 공유 자원을 보호할 때 적합

### Semaphore

- 내부 카운터로 동시에 접근 가능한 실행 흐름의 수를 제한
- 접근 시 카운터 감소, 반환 시 카운터 증가
- 여러 개의 동일한 자원을 관리할 때 적합
- 예시: 연결이 3개인 데이터베이스 연결 풀

### 비교

| Mutex | Semaphore |
| --- | --- |
| 한 번에 하나만 접근 | 정해진 개수만큼 접근 |
| 잠금의 소유권이 있음 | 일반적으로 소유권 개념이 없음 |
| 임계 영역 보호에 적합 | 자원 개수 관리에 적합 |
| 잠금과 해제 | 카운터 감소와 증가 |

- 이진 Semaphore는 값이 0과 1
- 한 번에 하나만 접근하게 할 수 있지만 소유권 차이로 Mutex와 동일하지 않음

### 동기화 시 주의점

- 교착 상태: 서로가 가진 잠금을 기다려 진행하지 못함
- 기아 상태: 특정 실행 흐름이 계속 자원을 얻지 못함
- 성능 저하: 잠금 범위가 크면 동시 처리량 감소

교착 상태 예방 방법:

- 잠금을 항상 같은 순서로 획득
- 잠금 범위를 작게 유지
- 일정 시간이 지나면 잠금 획득 포기
- 불필요한 중첩 잠금 제거

### 핵심 정리

- Mutex: 하나의 공유 자원에 대한 상호 배제
- Semaphore: 제한된 여러 자원의 접근 개수 관리
- 동기화는 Race Condition을 막지만 잘못 사용하면 교착 상태와 성능 문제 발생

## 브라우저 Multi-Process 구조

Chrome과 Chromium을 기준으로 한 구조이며, 브라우저마다 구현 방식이 다를 수 있다.

### 주요 프로세스

| 프로세스 | 역할 |
| --- | --- |
| Browser Process | 주소창과 브라우저 UI 관리, 다른 프로세스 조정 |
| Renderer Process | HTML·CSS 처리, JavaScript 실행, DOM과 화면 구성 |
| GPU Process | 그래픽 관련 작업 처리 |
| Utility Process | 네트워크와 오디오 등의 기능을 서비스로 처리 |

- 프로세스는 독립된 메모리 공간 사용
- 서로 다른 프로세스는 IPC로 통신
- Renderer Process는 제한된 Sandbox 환경에서 실행

### 탭과 Renderer Process

- 탭마다 항상 정확히 하나의 Renderer Process가 존재하는 것은 아님
- 교차 출처 iframe이 별도 Renderer Process를 사용할 수 있음
- 여러 탭이 같은 Renderer Process를 공유하는 경우도 있음
- Site Isolation으로 서로 다른 사이트를 가능한 한 프로세스 단위로 격리

### 장점

- 안정성: 한 Renderer의 문제가 다른 탭과 브라우저 전체로 퍼지는 것을 제한
- 보안: Renderer를 Sandbox에 격리
- 병렬성: 여러 프로세스가 여러 CPU 코어 활용 가능

### 단점

- 독립된 프로세스마다 메모리 사용
- 프로세스 사이의 IPC 비용
- 프로세스 생성과 Context Switching 비용

### 핵심 정리

- 브라우저 UI와 웹 콘텐츠를 별도 프로세스로 분리
- 특정 Renderer가 중단돼도 Browser Process와 다른 Renderer는 계속 실행 가능
- 탭 하나와 프로세스 하나가 항상 일대일로 대응하는 것은 아님

### 참고 자료

- [Chromium Multi-process Architecture](https://www.chromium.org/developers/design-documents/multi-process-architecture/)
- [Inside look at modern web browser](https://developer.chrome.com/blog/inside-browser-part1)

## JavaScript Single Thread

### 개념

- 메인 실행 환경에서 한 번에 하나의 JavaScript 작업 실행
- 하나의 호출 스택 사용
- 현재 함수가 끝나야 다음 JavaScript 작업 실행
- 브라우저 전체가 Single Thread라는 의미는 아님

Renderer Process에는 JavaScript 메인 스레드 외에도 렌더링과 통신 등을 위한 다른 스레드가 존재할 수 있다.

### 비동기 작업 처리

```javascript
console.log(1);

setTimeout(() => console.log(2), 0);

console.log(3);
```

출력 순서: `1 → 3 → 2`

```text
JavaScript 실행
→ 브라우저에 타이머 작업 요청
→ 현재 코드 계속 실행
→ 완료된 콜백이 대기열로 이동
→ 호출 스택이 비면 콜백 실행
```

- 타이머와 네트워크 작업 등은 브라우저 환경에 위임 가능
- 완료 후 콜백의 JavaScript 코드는 메인 스레드에서 실행
- `setTimeout(..., 0)`은 즉시 실행이 아닌 실행 가능한 시점 이후의 예약

### 비동기와 병렬

- 비동기: 작업 완료를 기다리는 동안 다음 작업 진행
- 병렬: 여러 작업이 같은 시점에 실제로 실행
- 비동기 API를 사용해도 콜백이 메인 스레드에서 병렬로 실행되는 것은 아님
- `setTimeout()` 안의 무거운 계산도 실행되는 동안 메인 스레드를 막음

### 긴 작업의 영향

- 사용자 입력 처리 지연
- 다른 JavaScript 작업 지연
- 화면 갱신 지연
- 페이지가 멈춘 것처럼 보일 수 있음

### 핵심 정리

- JavaScript Single Thread는 메인 실행 흐름을 기준으로 한 설명
- 브라우저는 여러 프로세스와 스레드를 사용
- 작업의 위임과 콜백의 실행 위치를 구분
- Single Thread 환경에서도 비동기 완료 순서에 따른 Race Condition 발생 가능

## Web Worker

### 개념

- JavaScript를 메인 스레드가 아닌 별도 작업 스레드에서 실행
- 무거운 계산 중에도 메인 스레드가 UI와 사용자 입력 처리 가능
- 환경에 따라 메인 스레드와 병렬 실행 가능
- 작업량을 줄이는 기능이 아니라 실행 위치를 옮기는 방법

### 통신

```javascript
const worker = new Worker("./worker.js");

worker.postMessage(data);
worker.addEventListener("message", (event) => {
  console.log(event.data);
});
```

- `postMessage()`: 메인 스레드와 Worker 사이의 데이터 전달
- `message` 이벤트: 전달된 데이터 수신
- 일반적으로 JavaScript 객체를 직접 공유하지 않고 복제하여 전달
- 큰 데이터는 복제와 통신 비용 발생 가능
- 일부 데이터는 Transferable 방식으로 소유권 이전 가능

### 제한사항

- `window` 접근 불가
- `document`와 DOM 요소 접근 불가
- Worker의 계산 결과를 메인 스레드에 전달한 뒤 DOM 변경
- `SharedArrayBuffer`로 메모리를 공유하면 `Atomics` 등의 동기화 필요

### 활용 사례

- 대량 데이터 계산
- 이미지와 영상 데이터 처리
- 암호화와 압축
- 복잡한 검색과 정렬
- 파일 데이터 분석

### React와 Next.js

- React Client Component는 기본적으로 메인 스레드에서 실행
- React Concurrent Rendering은 Web Worker의 병렬 실행과 다른 개념
- Next.js Server Component는 서버에서 실행되며 Web Worker가 아님
- React와 Next.js에서도 Web Worker는 개발자가 명시적으로 생성

### 핵심 정리

- CPU 사용량이 큰 작업을 메인 스레드 밖으로 이동
- DOM 변경은 메인 스레드에서 처리
- 작은 작업은 Worker 생성과 통신 비용이 더 클 수 있음
- UI 응답성 향상과 통신 비용 사이의 균형 필요

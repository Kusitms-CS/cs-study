온라인 쇼핑몰에서 VM 기반 WEB/WAS 서버 4대를 쿠버네티스로 이전하면서 기존 설정을 거의 그대로 옮겼다고 가정하자. 

WAS 1대당 50개였던 DB Connection Pool은 이미지 내부 설정에 그대로 넣었고, Pod는 최대 20개까지 자동으로 늘어나게 했다. DB는 최대 연결 수가 1,000개인 MySQL 한 대다. 로그인 세션은 DB에, 상품 정보는 각 Pod 메모리에 저장한다. 쿠폰 만료는 앱 내부 스케줄러가 처리하고, 리뷰 이미지는 트랜잭션 안에서 S3에 업로드한다.

블랙프라이데이 타임세일에 접속자가 평소의 5배로 몰리자 Pod가 20개까지 늘어났지만, ‘Too many connections’ 오류와 커넥션 대기 타임아웃이 쏟아졌다.

사용자들은 결제 중 로그아웃되거나, 리뷰 사진 업로드에 실패하거나, 쿠폰이 두 번 차감되는 문제를 겪었다. 운영팀은 Pool 크기를 바로 줄이지 못했고, 재시작된 Pod의 로그는 사라져 원인 파악도 늦어졌다.

트래픽이 몰려서 Pod를 늘렸더니 오히려 장애가 났다. 왜일까?

**답: Pod는 늘어나도 DB 는 한 대 그대로이기 때문임**

즉, 캐시(각 Pod 메모리), 로그(Pod 내부 파일), 설정(이미지 내부)이 Pod 안에 남아 있었고, 스케줄러는 모든 Pod에서 실행되는 구조였다. -> Stateful 구조를 그대로 옮김
**모든 부담이 DB로 몰려서 장애가 난 것이다.**

결론적으로는 
  1) DB 커넥션 수(Pod 수 × Pool)가 한계를 넘었고,
  2) 캐시 미스, 세션 조회, 트랜잭션 안의 S3 업로드가 커넥션을 더 소모했으며,
  3) 스케줄러 중복 실행으로 쿠폰이 이중 차감되고,
  4) 로그 유실과 설정 고정 때문에 대응도 늦어졌다.



정리 흐름(무엇인지 → 어떻게 동작하는지 → 이번 장애에서 어떤 의미였는지)


## 1. 아키텍처


**Stateful/Stateless**

개념:서버가 요청 사이에 기억을 들고 있다? Stateful
    아무것도 기억을 하지 못함? Stateless

과정: 
  [Stateful]  사용자 → 서버A (로그인 기억) → 다음 요청이 서버B로 가면? → "???"
  [Stateless] 사용자 → 아무 서버 → 외부 저장소(Redis, DB, S3)에서 정보 조회 → 정상 처리

Stateless의 이점: 서버를 아무 때나 늘리고, 줄이고, 교체할 수 있음

이번 문제> 서버 안에 남아 있는 Stateful 구조를 그대로 둔 채 컨테이너로 옮긴 것이 근본 원인

> 위의 제시문으로 Stateful 구조임을 어떻게 추론할 수 있을까?

1. 상품 정보는 각 Pod 메모리에 저장 -> 캐시가 Pod 안에& Pod마다 따로 있고, 새 Pod는 빈 상태로 시작
2. 쿠폰 만료는 앱 내부 스케줄러가 처리 -> 앱이 떠 있는 모든 Pod에서 스케줄러가 실행 &"한 대에서만 실행"이라는 서버 의존적 구조
3. 재시작된 Pod의 로그는 사라져 -> 로그가 Pod 내부 디스크에 저장





**VM vs 컨테이너**

| 구분 | VM | 컨테이너 |
|---|---|---|
| 수명 | 몇 달, 몇 년씩 운영 | 수시로 생성되고 삭제됨 |
| 개수 | 고정 (예: 4대) | 유동적 (예: 4~20개) |
| IP | 고정 | 뜰 때마다 바뀜 |
| 디스크 | 계속 유지 | 컨테이너가 삭제되면 함께 사라짐 |

> !!**이번 사례**의 핵심!!: "서버는 4대"라는 레거시의 전제가 깨졌는데, 설정은 그 전제를 그대로 따르고 있었다.


**오토 스케일링(HPA)**

개념: CPU 나 메모리 사용량을 보고 Pod 개수를 자동으로 조절하는 쿠버네티스 기능

과정
1. 약 15초 마다 Pod의 CPU 사용률을 확인
2. 목표치를 넘는다? 필요한 Pod 수를 계산
  => 필요 pod 수 = 현재 pod 수 X  (현재 사용률 ÷ 목표 사용률)
3. 계산 결과만큼 pod를 늘림. 최대치를 넘지 않도록

HPA는 앱(pod)만 늘림!! DB, 외부 API 같은 공용 자원은 그대로 둠!!


## 2. DB 커넥션

**DB Connection Pool**

개념: DB 연결을 미리 만들어두고 빌려 쓰고 반납하는 방식
왜 필요한가? DB 연결 하나를 만들려면 TCP 연결, 인증, 세션 생성을 거쳐야 해서 요청마다 새로 만들면 느리고 DB에도 부담이 됨.

과정

  ① 앱 시작 → Pool에 연결 N개 미리 생성
  ② 요청 도착 → Pool에서 연결 1개 빌림 (borrow)
  ③ 쿼리 실행
  ④ 연결 반납 (return) → 다음 요청이 재사용
  ⑤ 남은 연결이 없으면 → 대기 → 시간 초과 시 에러


**HikariCP**

개념: Spring Boot의 기본 Connection Pool

주요 설정
| 설정 | 의미 | 기본값 |
|---|---|---|
| `maximumPoolSize` | 최대 연결 수 | 10 |
| `minimumIdle` | 쉬고 있어도 유지할 연결 수 | `maximumPoolSize`와 같음 |
| `connectionTimeout` | 연결을 빌릴 때 최대 대기 시간 | 30초 |
| `idleTimeout` | 쉬는 연결을 정리하기까지의 시간 | 10분 |
| `maxLifetime` | 연결 하나의 최대 수명 | 30분 |

=> maximumPoolSize = minimumIdle = 50이라서, Pod는 뜨자마자 50개를 한꺼번에 요청

** HikariCP는 minimumIdle을 따로 설정하지 않으면 maximumPoolSize와 같은 값을 씀



**max_connections**
개념: DB가 동시에 허용하는 최대 연결 수.  MySQL 기본값은 151이고, 이 사례에서는 1,000으로 설정

```console

  필요한 연결 = Pod 수 × Pool 크기 (+ 관리 도구, 배치 등)

  레거시:  4 × 50 = 200   → 여유 있음

  확장 후: 20 × 50 = 1,000 → 한도 도달 → 새 연결 거부 → "Too many connections"
```

그냥 무작정 늘리면 안되나? 연결 하나하나가 DB의 메모리와 CPU를 쓴다.연결이 너무 많으면 DB 자체가 느려짐...



**커넥션 타임아웃**

개념: Pool에 남은 연결이 없어서 설정한 connectionTimeout 만큼 기다리다가 실패 처리

**과정**

```console
요청 도착 → Pool 확인 → 50개 모두 사용 중 → 대기열에서 기다림
  → 30초 안에 반납된 연결이 없음
  → "Connection is not available, request timed out after 30000ms"
```
**원인** : 연결 수가 부족하거나, 연결을 오래 쥐고 있는 작업(느린 쿼리, 트랜잭션 안의 외부 호출) 때문


**DB 프록시**
개념: 앱과 DB 사이에서 연결을 모아서 관리하는 중간 계층

과정:
```markdown
  [프록시 없음]  Pod 20개 × 50 = 1,000개 연결 → DB
  [프록시 있음]  Pod 20개 × 50 = 1,000개 연결 → 프록시 → 실제 DB 연결 100개만 유지
```
> 앱 쪽 연결이 많아져도 DB가 실제로 받는 연결 수는 일정하게 유지




## 3. 상태관리

**스티키 세션(Sticky Session)**

개념: 로드밸런서가 같은 사용자를 항상 같은 서버로 보내는 방식
보통 쿠키나 IP 기준으로 

과정: 
```markdown
  첫 요청 → 서버A 배정 → 쿠키에 "서버A" 표시 → 이후 요청은 계속 서버A로
```
한계: 서버 A가 죽거나 교체되면 세션이 사라짐 + 부하가 특정 서버에 몰릴 수도 있음  - Pod가 자주 바뀌는 컨테이너 환경과는 맞지 않음


**Redis 세션 / JWT**

**Redis 세션(외부 세션 저장소)**

세션을 서버 메모리 대신 Redis에 저장
메모리 기반이라 매우 빠른 저장소

과정
  ```markdown
  로그인 → 세션ID 발급(쿠키) + Redis에 저장
  다음 요청 → 아무 Pod → 쿠키의 세션ID로 Redis 조회 → 로그인 확인

  ```


**JWT (JSON Web Token)**
서버가 아무것도 저장하지 않고, 로그인 정보를 담은 서명된 토큰을 사용자에게 제공
구조: Header.Payload.Signature


 ```markdown
  로그인 → 서버가 토큰 발급 (사용자 ID, 만료 시간 + 서명)
  다음 요청 → 토큰 첨부 → 서버는 서명만 검증 → DB나 Redis 조회 없음
 ```

장점: 완전한 Stateless
단점: 발급한 토큰을 강제로 만료시키기 어려움 + 보통 짧은 만료 시간과 Refresh Token을 함께 사용

이번 문제> 세션을 DB에 저장해서 모든 요청이 DB 연결을 하나씩 씀+  연결을 못 얻으면 세션 조회가 실패하고, 사용자는 로그아웃 처리








**로컬 캐시/공유 캐시**

캐시란? **자주 조회하는 데이터를 빠른 곳에 임시로 보관**해서 DB 조회를 줄이는 기법




| 구분 | 로컬 캐시 | 공유 캐시 |
|---|---|---|
| 위치 | 각 Pod 메모리 (Caffeine, Ehcache) | 외부 서버 (Redis) |
| 속도 | 가장 빠름 | 빠름 (네트워크 경유) |
| Pod 간 공유 | ❌ Pod마다 따로 | ⭕ 모두 같은 데이터 |
| Pod 재시작 시 | 사라짐 | 유지 |

과정 (Cache-Aside 패턴)

 ```markdown
  요청 → 캐시 확인 → 있으면(Hit) 바로 응답
                   → 없으면(Miss) DB 조회 → 캐시에 저장 → 응답
 ```

**Cold Cache**

개념: 캐시가 비어있는 상태 새로 뜬 Pod는 로컬 캐시가 비어있음
과정

```markdown
  새 Pod 16개 생성 → 각자 캐시 비어 있음 → 모든 상품 조회가 Miss
  → 16개 Pod가 동시에 DB 조회 → DB 쿼리 폭증 **(이번 사례에서 20배)**
```

같은 키에 요청이 한꺼번에 몰려 DB를 두드리는 현상을 Cache Stampede
해결: 공유 캐시를 쓰거나, 기동할 때 캐시를 미리 채워두는 Cache Warm-up



**트랜잭션과 커넥션 점유**

개념: Spring의 @Transactional은 메서드가 시작될 때 연결을 빌리고, 커밋이나 롤백이 끝나야 반납


```java

  @Transactional
  public void writeReview(...) {
      // ① 여기서 DB 연결 빌림
      s3.upload(image);        // ② 업로드 3초... 연결은 계속 점유
      reviewRepo.save(review); // ③ 실제 DB 작업은 수 ms
  }   // ④ 이제야 반납


  -->
  public void writeReview(...) {
      String url = s3.upload(image);  // 트랜잭션 밖 (연결 안 씀)
      reviewService.save(review, url); // 짧은 트랜잭션만 연결 사용
  }


```


**원칙: 트랜잭션 안에는 DB 작업만 짧게 둠. 외부 API 호출이나 파일 업로드는 밖으로 뺌.**





**S3(오브젝트 스토리지)**


개념: AWS의 파일 저장 서비스 / 서버 디스크와 상관없이 파일을 영구 보관
WHY? 컨테이너 디스크는 Pod가 사라지면 함께 사라지고, Pod끼리 공유되지도 않기 때문에 외부 저장소를 둬야 함

과정
 ```markdown
  이미지 업로드 → S3 저장 → 파일 URL만 DB에 저장 → 조회 시 URL로 접근
 ```

 이번 사례> S3을 썼지만, 트랜잭션 안에서 호출해서 문제가 됨



## 4. 운영

**스케줄러 중복 실행**

개념: Spring의 @Scheduled는 앱이 떠 있는 모든 인스턴스에서 각각 실행
과정
```markdown
  레거시:  "1번 서버에서만 스케줄러 켜기" 같은 설정으로 1회 실행
  컨테이너: 이미지가 모두 같으므로 Pod 20개 → 20번 동시 실행
           → 같은 쿠폰 데이터 동시 UPDATE → 락 대기, 이중 차감
```

락 대기 ? 
락(Lock): 같은 데이터를 여러 곳에서 동시에 수정하지 못하게 DB가 거는 잠금

다른 트랜잭션이 같은 행을 수정하려면 잠금이 풀릴 때까지 **기다려야** 한다. → **락 대기**


**왜 문제인가**

1. **커넥션을 쥔 채로 기다린다**
   - 대기 중인 트랜잭션은 DB 커넥션을 반납하지 않는다.
   - 대기가 길어질수록 Pool의 커넥션이 묶여서 주문 같은 다른 요청이 커넥션을 못 얻는다. → **커넥션 대기 타임아웃**
2. **기다리다 실패한다**
   - MySQL은 일정 시간(`innodb_lock_wait_timeout`, 기본 50초)이 지나면 대기 중인 쿼리를 에러로 끝낸다.
3. **데드락(Deadlock)이 생길 수 있다**
   - Pod A는 쿠폰1 → 쿠폰2 순서로, Pod B는 쿠폰2 → 쿠폰1 순서로 잠그면 서로 상대가 풀기를 영원히 기다린다.
   - MySQL이 감지해서 한쪽을 강제로 실패시킨다.

**락이 있는데도 왜 이중 차감이 되나?**

- 락은 **"동시에"** 수정하는 것만 막고, **"차례대로 여러 번"** 실행하는 것은 막지 않는다.


- 그래서 **분산 락/CronJob으로 한 번만 실행**되게 하고, **멱등성**(조건부 UPDATE 등)으로 중복 실행돼도 결과가 같게 만들어야 한다.




**CronJob / 분산 락**

**1. CronJob(쿠버네티스)**
정해진 시간에 별도의 Pod를 하나 띄워 작업을 실행하고 종료하는 기능

과정
```markdown
  매 5분 → CronJob이 배치 Pod 1개 생성 → 쿠폰 만료 처리 → 종료
```

웹 서비스와 분리되기 때문에 커넥션 풀도 따로 쓴다!~~~~

**2. 분산 락**
여러 서버 중 락을 먼저 잡은 한 곳만 작업을 실행하게 하는 방법

```markdown
  20개 Pod가 동시에 실행 시도 → 공용 저장소(DB, Redis)에 락 요청
  → Pod 7번만 성공 → 작업 실행 → 락 해제
  → 나머지 19개는 건너뜀
```


**멱등성**
개념: 같은 작업을 여러 번 실행해도 결과가 한 번 실행한 것과 같은 성질

사례와 연결

```markdown
  ❌ 멱등하지 않음: "쿠폰 잔여 수량 -1"        → 2번 실행하면 2 차감
  ⭕ 멱등함:"쿠폰 상태를 '만료'로 변경" → 몇 번 실행해도 '만료'
  ⭕ 멱등함: "상태가 '사용 가능'인 쿠폰만 '만료'로 변경" (조건부 UPDATE)
```

분산 환경에서는 재시도와 중복 실행이 언제든 생길 수 있어서, 락과 함께 최후의 안전장치로 쓰임



**ConfigMap / Secret**

개념: 설정값을 컨테이너 이미지 밖에서 주입하는 쿠버네티스 기능

ConfigMap: 일반 설정 (Pool 크기, DB 주소, 로그 레벨)
Secret: 민감 정보 (DB 비밀번호, API 키). 기본은 base64 인코딩일 뿐이라 별도 암호화 설정이 권장됩니다.

과정
 ```markdown
  [이전] application.yml(이미지 안) 수정 → 재빌드 → 재배포 (이번 사례: 35분)
  [개선] ConfigMap 수정 → Pod 롤링 재시작 → 수 분 내 반영
 ```

원칙: 이미지는 하나로 두고, 환경별 설정만 바꿈



**stdout 로그 / 중앙 로그 수집**

개념: 컨테이너 로그는 파일에 쓰지 않고 **표준 출력(stdout)**으로 내보낸 뒤 한곳에 모음

과정

```markdown
  앱 → stdout 출력
     → 컨테이너 런타임이 노드에 임시 저장 (/var/log/containers)
     → 수집기(Fluent Bit, DaemonSet)가 읽어감
     → 저장소(Elasticsearch, Loki)에 보관
     → 조회 화면(Kibana, Grafana)에서 검색하고 알람 설정
```

효과: Pod가 죽어도 로그가 남고, 20개 Pod의 로그를 한 화면에서


이번 사례: 로그가 /app/logs/app.log에 있었기 때문에 Pod 재시작과 함께 사라짐


## 결론

```markdown
블랙프라이데이 트래픽 5배
  → HPA가 Pod를 4개에서 20개로 확장
  → [Pool] 20 × 50 = 1,000 → max_connections 초과 → Too many connections
  → [캐시] 새 Pod의 Cold Cache → DB 조회 폭증 → 커넥션 점유 증가
  → [세션] 세션 조회도 커넥션 필요 → 실패 → 로그아웃
  → [트랜잭션] S3 업로드 중 커넥션 점유 → 업로드 실패
  → [스케줄러] 20번 중복 실행 → 락 대기, 쿠폰 이중 차감
  → [설정] 이미지 안에 있음 → 재빌드 필요 → 대응 지연
  → [로그] 컨테이너 안에 있음 → 재시작 시 유실 → 원인 파악 지연
```

## 키워드 연관관계

```
데이터 보호
├─ 인코딩 (Base64) : 형식 변환, 보안 아님
├─ 단방향 (해시) : 복호화 불가 ──> 무결성 검증, 비밀번호 저장
│     └─ BCrypt / Argon2 : 비밀번호용 느린 해시
└─ 양방향 (암호화) : 키로 복호화 가능 ──> 기밀성
      ├─ 대칭키 (AES) : 암·복호화 키 동일, 빠름, 키 배포 문제
      └─ 비대칭키 (RSA) : 공개키/개인키 쌍, 느림, 키 배포 문제 해결
            ├─ 전자서명 : 개인키로 서명, 공개키로 검증 (해시 + 비대칭키)
            │     └─ 인증서(CA) : 공개키의 소유자를 보증
            └─ HTTPS(TLS) : 비대칭키로 대칭키 교환 → 대칭키로 통신
```

## 암호화 기본 개념

- **평문 / 암호문**: 암호화 전 원본 / 암호화된 데이터
- **암호화 / 복호화**: 키로 평문 → 암호문 / 암호문 → 평문
- **키(Key)**: 암·복호화에 쓰는 비밀 값
- **CIA**: 기밀성(암호화), 무결성(해시), 가용성

| | 인코딩 | 해시 | 암호화 |
|---|---|---|---|
| 목적 | 형식 변환 | 무결성 검증 | 기밀성 |
| 키 | 없음 | 없음 | 필요 |
| 복원 | 누구나 가능 | **불가능** | 키가 있으면 가능 |
| 예 | Base64 | SHA-256, BCrypt | AES, RSA |

- JWT Payload는 Base64URL **인코딩**이라 누구나 읽을 수 있음 (7주차 참고)

## 단방향 암호화 (해시)

- **해시(Digest)**: 입력을 고정 길이 값으로 변환, **원문 복원 불가**
- 용도: 비밀번호 저장, 무결성 검증, 전자서명(원문 요약)
- 특징: **결정적**(같은 입력 → 같은 출력), **고정 길이**, **눈사태 효과**, **충돌 저항성**(Collision)
- 알고리즘
  - **MD5, SHA-1**: 충돌 발견 → 보안 용도로 사용 금지
  - **SHA-256**: 현재 널리 사용 (SHA-2 계열)
- 비밀번호 저장에는 **BCrypt / Argon2**를 사용
  - SHA-256은 빨라서 Brute Force 대입에 취약, BCrypt/Argon2는 **의도적으로 느리고** Cost(작업 계수) 조절 가능
  - BCrypt: Spring Security `BCryptPasswordEncoder` / Argon2: 메모리 사용량까지 조절 (최신 권장)
  - 검증: 복호화하지 않고 입력값을 해시해 저장된 값과 **비교**

## 양방향 암호화

- 키로 **암호화와 복호화가 모두 가능** (기밀성이 목적)
- 키 구조에 따라 **대칭키**와 **비대칭키**로 구분

### 대칭키 (AES)

- **같은 키**로 암호화·복호화
- 장점: **빠름** (대용량 데이터) / 단점: **키 배포 문제**
- **AES**: 표준 대칭키 알고리즘 (키 128/192/256비트). DES는 키가 짧아 사용 금지
- **운영 모드**: ECB(패턴 노출, 사용 금지), CBC, **GCM**(무결성까지 제공, 권장)
- **IV**: 같은 평문도 다른 암호문이 되게 하는 초기값 (재사용 금지)

### 비대칭키 (RSA)

- **공개키 / 개인키 쌍**, 한쪽으로 암호화하면 짝인 다른 키로만 복호화
- 공개키는 공개해도 안전 → **키 배포 문제 해결**

| 목적 | 암호화 | 복호화 |
|---|---|---|
| **기밀성** | 수신자의 공개키 | 수신자의 개인키 |
| **전자서명** | 송신자의 개인키 | 송신자의 공개키 |

- **RSA**: **소인수분해의 어려움**에 기반, 권장 키 길이 2048비트 이상
- 단점: **느림**, 암호화 가능한 데이터 크기 제한 → 대량 데이터 부적합
- **ECC**(타원곡선): 더 짧은 키로 같은 보안 수준 (ECDSA, ECDH)

### 대칭키 vs 비대칭키

| | 대칭키 (AES) | 비대칭키 (RSA) |
|---|---|---|
| 키 | 동일 키 1개 | 공개키/개인키 쌍 |
| 속도 | 빠름 | 느림 |
| 키 배포 | 어려움 | 쉬움 |
| 주 용도 | 대용량 데이터 암호화 | 키 교환, 전자서명 |

## 전자서명 / 인증서

**전자서명**: **무결성, 송신자 인증, 부인 방지** 보장

1. 원문을 **해시**해 Digest 생성
2. Digest를 **송신자의 개인키로 암호화** → 서명
3. 원문 + 서명 전송
4. 수신자가 서명을 **송신자의 공개키로 복호화**한 값과 원문의 해시값을 비교 → 같으면 위변조 없음
- 해시값에 서명하는 이유: 비대칭키 연산이 느려서 짧은 요약만 서명
- JWT **RS256**: 개인키로 서명 / 공개키로 검증 (HS256은 대칭키 기반 HMAC)

**인증서**
- 문제: 받은 공개키가 정말 그 사이트의 것인가? (중간자 공격)
- **CA**(인증기관)가 "이 공개키는 이 도메인의 것"임을 **CA의 개인키로 서명**한 것 (X.509)
- 포함: 도메인, 공개키, 유효기간, 발급자, CA 서명
- **인증서 체인**: 서버 인증서 → 중간 CA → **루트 CA** (루트는 OS/브라우저에 내장)

## HTTPS와 암호화

- HTTPS = HTTP + **TLS** → 기밀성, 무결성, 서버 인증
- **하이브리드 방식**: 비대칭키로 **키 교환**, 대칭키로 **데이터 암호화** (속도)

**TLS Handshake (간략)**
1. Client Hello: TLS 버전, 암호 스위트, 랜덤 값
2. Server Hello: 선택한 암호 스위트, 랜덤 값, **서버 인증서**
3. 클라이언트가 **인증서 검증** (CA 서명, 도메인, 유효기간)
4. **키 교환**(ECDHE 등)으로 **세션 키(대칭키)** 합의
5. 이후 통신은 **세션 키(AES 등)로 암호화**

- **Forward Secrecy**: 세션마다 키가 새로 생성되어 한 세션이 노출돼도 다른 세션은 안전
- 자세한 내용은 5주차 HTTP/HTTPS 참고

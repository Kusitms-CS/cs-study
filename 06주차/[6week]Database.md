# 6주차 — Database

> **키워드** RDB/NoSQL · PK/FK · 정규화 · JOIN · Index · B+Tree
> **FE 심화** Server State · API 데이터 관리 · Client Cache와 서버 데이터 정합성

---

## 0. 개요

| 묶음 | 키워드 | 한 줄 요약 |
|---|---|---|
| 어떻게 담나 | RDB/NoSQL, PK/FK, 정규화 | 데이터를 주제별로 **쪼개고**, 키로 **연결**해 둠 |
| 어떻게 꺼내나 | JOIN, Index, B+Tree | 쪼갠 걸 다시 **붙이고**, **빨리 찾음** |
| (BE) 더 빨리 꺼내기 | 복합·커버링 인덱스, 실행 계획 | DB가 실제로 **어떻게 읽는지** 보고 고침 |
| (FE) 받은 데이터 관리 | Server State, 정합성 | 화면의 데이터는 DB의 **사본** → 언제 낡는지 관리 필요 |

연결 고리
- 정규화로 테이블을 쪼갬 → PK/FK로 관계를 표시 → 읽을 땐 JOIN으로 다시 합침 → 쪼갤수록 JOIN이 늘어 **인덱스**가 중요해짐
- 인덱스의 정체는 **정렬된 B+Tree**. "정렬돼 있다"는 성질 하나로 범위 검색, ORDER BY 최적화, 복합 인덱스의 컬럼 순서 규칙이 모두 설명됨
- 프론트 캐시가 낡는 문제와 DB에서 두 사람이 동시에 수정하는 문제(Lost Update)는 뿌리가 같음 → 둘 다 **"내가 본 값이 지금도 맞나?"**의 문제

## 1. RDB / NoSQL

**정의**
- **RDB**: 데이터를 행과 열로 된 **테이블**에 저장하고, 테이블끼리 **관계**(키)로 연결하는 DB. SQL로 다룸 (MySQL, PostgreSQL, Oracle)
- **NoSQL**: 테이블·관계 모델이 아닌 방식(Key-Value, Document, Wide-Column, Graph)으로 저장하는 DB의 총칭. "Not Only SQL"의 줄임

**같은 데이터(회원 1명 + 주문 2건)를 저장하는 방식 비교**

RDB: 주제별 테이블로 쪼개서 저장 → 읽을 때 JOIN으로 합침
```text
users --< orders --< order_items >-- products
      1:N        1:N             N:1

SELECT ... FROM users JOIN orders JOIN order_items JOIN products ...
```

Document DB (MongoDB): 같이 읽는 모양 그대로 한 문서에 묶어 저장 → JOIN 없이 한 번에 읽음
```json
{
  "_id": 1,
  "name": "지민",
  "orders": [
    { "id": 101, "items": [{ "product": "노트북", "qty": 1 }] },
    { "id": 102, "items": [{ "product": "마우스", "qty": 2 }] }
  ]
}
```

| | RDB | NoSQL (Document 기준) |
|---|---|---|
| 데이터 모양 | 테이블 (정해진 컬럼) | 문서·키-값 등 (형태 자유) |
| 스키마 | 미리 정함 | 유연함 |
| 관계 표현 | FK + JOIN | 문서 안에 넣거나(내장) 참조 |
| 중복 | 정규화로 최소화 | 읽기 편하게 중복 허용 ("노트북"이 여러 문서에) |
| 확장 | 주로 Scale-up, 읽기 복제 | Scale-out(샤딩)을 전제로 한 설계가 많음 |
| 강점 | 정합성, 복잡한 조회 | 유연성, 대량 처리, 특정 조회 패턴 |

**NoSQL 4가지 유형**

| 유형 | 저장 모양 | 예시 | 주 용도 |
|---|---|---|---|
| Key-Value | `session:7 → {...}` | Redis, DynamoDB | 캐시, 세션, 랭킹 |
| Document | `{ "name": "지민", ... }` | MongoDB | 구조가 자주 바뀌는 데이터 |
| Wide-Column | 행마다 컬럼 수천 개 가능 | Cassandra, HBase | 대량 쓰기, 로그, 시계열 |
| Graph | `(지민)-[:팔로우]->(서준)` | Neo4j | 관계 탐색, 추천, SNS |

**헷갈리는 포인트**
- **"NoSQL은 트랜잭션이 없다"는 옛말임**. MongoDB는 4.0부터 여러 문서를 묶는 트랜잭션을 지원함. 차이는 "되냐 안 되냐"보다 기본 설계가 무엇을 우선하냐에 있음
- **"RDB는 수평 확장이 안 된다"도 틀림**. 어렵지만 읽기 복제본, 샤딩으로 가능함. NoSQL은 처음부터 그걸 쉽게 만든 쪽일 뿐임
- **선택 기준**: 관계와 정합성이 중요하면(주문·결제·재고) RDB, 구조가 자주 바뀌거나 단순 키 조회·대량 쓰기면 NoSQL. 실무는 섞어 씀 (MySQL + Redis 캐시)

## 2. PK / FK

**정의**
- **PK (Primary Key, 기본키)**: 각 행을 **유일하게 구분**하는 컬럼(들). NULL 불가, 중복 불가, 테이블당 1개. 여러 컬럼을 묶은 **복합키** 가능
- **FK (Foreign Key, 외래키)**: 다른 테이블의 PK(또는 UNIQUE 컬럼)를 가리키는 컬럼. **존재하지 않는 대상을 못 가리키게** 막음 → 참조 무결성

**예시 스키마** (3장 정규화 결과)
```text
+-------------+       +------------------+       +---------------------+       +-------------+
| users       |       | orders           |       | order_items         |       | products    |
+-------------+       +------------------+       +---------------------+       +-------------+
| PK id       |1     N| PK id            |1     N| PK,FK order_id      |N     1| PK id       |
| UQ email    |-------| FK user_id       |-------| PK,FK product_id    |-------|    name     |
|    name     |       |    ordered_at    |       |       qty           |       |    price    |
+-------------+       +------------------+       +---------------------+       +-------------+
```
- `orders.user_id` → `users.id` (1:N, 회원 한 명이 주문 여러 개)
- `order_items.order_id` → `orders.id` (1:N)
- `order_items.product_id` → `products.id` (N:1)
- 주문 ↔ 상품은 N:M (한 주문에 상품 여러 개, 한 상품이 여러 주문에) → 연결 테이블 `order_items`로 1:N 두 개로 풀어냄. PK는 (order_id, product_id) 복합키

**키의 종류** (users 기준)
```text
슈퍼키   {id}, {email}, {id, name}, {email, name} ...   유일성만 만족
  └ 후보키   {id}, {email}                           유일성 + 최소성
      └ 기본키   {id}                                 후보키 중 대표 1개
  대체키   {email}                                    PK로 안 뽑힌 후보키 → 보통 UNIQUE
```

**PK 선택: 자연키 vs 대리키**

| | 자연키 | 대리키 |
|---|---|---|
| 예 | 이메일, 주민번호 | AUTO_INCREMENT id, UUID |
| 장점 | 의미가 있음 | 절대 안 바뀜, 짧음 |
| 단점 | **바뀔 수 있음**(이메일 변경), 개인정보 | 의미 없음 → 자연키엔 UNIQUE를 따로 걺 |

- 실무 기본은 **대리키**
- PK 타입도 성능에 영향이 있음. 랜덤 UUID(v4)는 새 행이 B+Tree 곳곳에 끼어들어 느려짐 → AUTO_INCREMENT나 시간순 정렬되는 ID(UUID v7 등)를 많이 씀

**참조 무결성 동작**

| 상황 | 동작 |
|---|---|
| `INSERT INTO orders (user_id) VALUES (99)` (없는 회원) | ✗ 거부 → 고아 데이터 방지 |
| 부모 삭제, 지정 안 함 (= RESTRICT, MySQL 기본) | ✗ 자식이 있으면 삭제 거부 |
| `ON DELETE CASCADE` | 자식도 같이 삭제 |
| `ON DELETE SET NULL` | 자식의 FK만 NULL로 변경 (컬럼이 NULL 허용이어야 함) |

**헷갈리는 포인트**
- **FK 제약은 공짜가 아님**. 자식 행을 넣을 때마다 부모 존재 여부를 확인함. MySQL InnoDB는 FK 컬럼에 인덱스가 없으면 자동 생성함
- **실무에선 FK 제약을 안 거는 경우도 있음**. 대량 쓰기, 샤딩(DB가 여러 대면 DB 간 FK 불가), 배포 순서 문제 때문임. 이때도 관계(논리적 FK)는 있고 제약(물리적 FK)만 없는 것 → 정합성 책임이 애플리케이션으로 넘어감
- **CASCADE 주의**. 회원 하나를 지웠는데 주문·결제 기록까지 연쇄 삭제될 수 있음 → 기록이 중요한 데이터는 실제 삭제 대신 `deleted_at`을 채우는 **소프트 삭제**를 많이 씀

## 3. 정규화

**정의**: 중복을 줄이고 **이상 현상**(Anomaly)을 없애기 위해 "한 사실은 한 곳에만" 있도록 테이블을 나누는 과정

**함수 종속**: `X → Y`는 X 값이 정해지면 Y 값이 하나로 정해진다는 뜻 (회원ID → 회원명). 정규화는 이 종속 관계를 보고 테이블을 나누는 작업임

| 단계 | 규칙 | 한 줄 |
|---|---|---|
| 1NF | 모든 칸이 **원자값** | 한 칸에 값 여러 개 X |
| 2NF | **부분 함수 종속** 제거 | 복합 PK의 일부에만 종속된 컬럼을 분리 |
| 3NF | **이행 함수 종속** 제거 | PK → A → B처럼 PK가 아닌 컬럼을 거쳐 정해지는 컬럼을 분리 |
| BCNF | 모든 결정자가 **후보키** | 3NF보다 엄격 (실무에선 보통 3NF까지) |

**예시: 주문 데이터 정규화**

① 비정규형: 한 칸에 값이 여러 개

| 주문번호 | 회원ID | 회원명 | 상품 |
|---|---|---|---|
| 1001 | u1 | 지민 | **노트북, 마우스** ← ✗ |
| 1002 | u2 | 서준 | 노트북 |

② 1NF: 상품별로 행을 나눔. PK = (주문번호, 상품ID). 대신 중복이 생김

| 주문번호 (PK) | 상품ID (PK) | 회원ID | 회원명 | 상품명 | 수량 |
|---|---|---|---|---|---|
| 1001 | P1 | u1 | **지민** | **노트북** | 1 |
| 1001 | P2 | u1 | **지민** | 마우스 | 2 |
| 1002 | P1 | u2 | 서준 | **노트북** | 1 |

- **수정 이상**: 지민의 이름을 바꾸면 행 2개를 모두 고쳐야 함 → 하나라도 빠지면 불일치
- **삽입 이상**: 아직 주문이 없는 새 상품(P3 키보드)은 PK인 주문번호가 없어 못 넣음
- **삭제 이상**: 주문 1002를 지우면 서준이라는 회원 정보까지 사라짐

③ 2NF: PK의 **일부**에만 종속된 컬럼을 분리 (`상품ID → 상품명`, `주문번호 → 회원ID, 회원명`)

| 테이블 | 컬럼 | 비고 |
|---|---|---|
| 주문 | **주문번호**, 회원ID, 회원명 | 회원명이 여전히 주문마다 중복 |
| 주문상품 | **주문번호, 상품ID**, 수량 | 수량은 둘 다 있어야 정해지므로 남김 |
| 상품 | **상품ID**, 상품명 | |

④ 3NF: `주문번호 → 회원ID → 회원명`의 다리를 끊음 (PK가 아닌 컬럼끼리의 종속 분리)

| 테이블 | 컬럼 |
|---|---|
| 주문 | **주문번호**, 회원ID |
| 회원 | **회원ID**, 회원명 |
| 주문상품 | **주문번호, 상품ID**, 수량 |
| 상품 | **상품ID**, 상품명 |

(굵은 글씨 = PK)

**결과와 대가**
- 회원명·상품명이 각각 한 곳에만 존재 → 수정 1번으로 끝, 주문 없이도 회원·상품 등록 가능, 주문을 지워도 회원은 남음
- 대신 "주문 + 회원명 + 상품명"을 보려면 JOIN이 여러 번 필요해짐

**반정규화**: 정규화 후 성능을 위해 **일부러** 다시 합치거나 중복을 두는 것
- 예: 게시글 테이블에 `comment_count` 컬럼을 둬서 매번 `COUNT(*)`를 안 하게 함
- 대신 댓글 추가·삭제 때마다 같이 갱신해야 하는 정합성 책임이 생김

**헷갈리는 포인트**: 정규화는 "무조건 끝까지"가 아니고, 반정규화는 "정규화를 안 한 것"이 아님 → **정규화를 먼저 하고, 측정해서 느린 곳만 의도적으로 반정규화**하는 순서

## 4. JOIN

**정의**: 두 테이블을 **조건**(보통 PK = FK)으로 이어 붙여 하나의 결과로 만드는 연산

**예시 데이터** (`users.id = orders.user_id`로 붙임)

users

| id | name |
|---|---|
| 1 | 지민 |
| 2 | 서준 |
| 3 | 하은 ← 주문 없는 회원 |

orders

| id | user_id | amount |
|---|---|---|
| 101 | 1 | 30,000 |
| 102 | 1 | 12,000 |
| 103 | 2 | 8,000 |
| 104 | NULL | 5,000 ← 비회원 주문 |

**JOIN 종류별 결과** (✓ = 그 JOIN 결과에 포함되는 행)

| u.id | u.name | o.id | o.amount | INNER | LEFT | RIGHT | FULL |
|---|---|---|---|---|---|---|---|
| 1 | 지민 | 101 | 30,000 | ✓ | ✓ | ✓ | ✓ |
| 1 | 지민 | 102 | 12,000 | ✓ | ✓ | ✓ | ✓ |
| 2 | 서준 | 103 | 8,000 | ✓ | ✓ | ✓ | ✓ |
| 3 | 하은 | NULL | NULL | | ✓ | | ✓ |
| NULL | NULL | 104 | 5,000 | | | ✓ | ✓ |
| **행 수** | | | | **3** | **4** | **4** | **5** |

| 종류 | 결과 |
|---|---|
| INNER | 양쪽 다 짝이 있는 행만 |
| LEFT (OUTER) | 왼쪽 전부 + 짝이 없으면 오른쪽을 NULL로 채움 |
| RIGHT (OUTER) | 오른쪽 전부 (보통 순서를 바꿔 LEFT로 씀) |
| FULL (OUTER) | 양쪽 전부. MySQL은 미지원 → LEFT `UNION` RIGHT |
| CROSS | 모든 조합 (행 수 = A × B) |
| SELF | 같은 테이블끼리 (예: 직원 ↔ 직원의 매니저) |

**헷갈리는 포인트**
- **LEFT JOIN + WHERE**: 오른쪽 테이블 조건을 WHERE에 쓰면 NULL 행(하은)이 걸러져 결과가 INNER JOIN과 같아짐
  ```sql
  -- ✗ 하은이 사라짐
  SELECT * FROM users u LEFT JOIN orders o ON u.id = o.user_id WHERE o.amount > 10000;
  -- ✓ 하은 유지, 1만 원 넘는 주문만 붙음
  SELECT * FROM users u LEFT JOIN orders o ON u.id = o.user_id AND o.amount > 10000;
  ```
- **1:N JOIN은 행을 늘림**. 지민은 주문이 2건이라 결과에 2번 나옴 → 회원 수는 `COUNT(DISTINCT u.id)`로 세야 함. 1:N 두 개를 한 번에 JOIN하면 행이 곱으로 불어나 `SUM`이 부풀려짐
- **"JOIN은 느리다"는 반만 맞음**. JOIN 자체보다 **JOIN 컬럼에 인덱스가 없을 때** 느림 (7-3 참고)

## 5. Index

**정의**: 원하는 행을 빨리 찾기 위해 **특정 컬럼 값을 정렬해 둔 별도 자료구조**. 책 뒤의 "찾아보기"와 같음. MySQL·PostgreSQL의 기본 인덱스는 B+Tree

**트레이드오프**

| 좋아지는 것 | 나빠지는 것 |
|---|---|
| WHERE·JOIN·ORDER BY가 빨라짐 | INSERT·UPDATE·DELETE마다 인덱스도 갱신 → **쓰기가 느려짐** |
| | 저장 공간이 늘어남 |

- "모든 컬럼에 인덱스"는 답이 아님
- **자주 조회 조건이 되는 컬럼**, **카디널리티(고유 값 개수)가 높은 컬럼**에 검
- 성별처럼 값이 2개뿐인 컬럼은 효과가 적음

### 클러스터드 vs 세컨더리 (MySQL InnoDB)

```text
SELECT * FROM users WHERE email = 'b@x.com';

(1) secondary index: idx_email          (2) clustered index: PK id  (= table)
+-----------+--------+                  +----+-----------+-------+-------+
| email     | PK(id) |                  | id | email     | name  | city  |
+-----------+--------+                  +----+-----------+-------+-------+
| a@x.com   | 3      |                  | 1  | c@x.com   | ...   | ...   |
| b@x.com   | 7      | -----+           | 3  | a@x.com   | ...   | ...   |
| c@x.com   | 1      |      |           | 5  | d@x.com   | ...   | ...   |
| d@x.com   | 5      |      +---------> | 7  | b@x.com   | ...   | ...   |
+-----------+--------+                  +----+-----------+-------+-------+
  leaf = email + PK                       leaf = whole row
```
1. 세컨더리 인덱스(email 순 정렬)에서 `b@x.com` 탐색 → PK `7` 획득
2. 클러스터드 인덱스(PK 순 정렬, 리프 = 행 전체)에서 PK `7` 탐색 → 행 전체 획득

| | 클러스터드 인덱스 | 세컨더리 인덱스 |
|---|---|---|
| 개수 | 테이블당 **1개** (데이터를 정렬하는 방법은 하나뿐) | 여러 개 |
| 기준 | PK (없으면 첫 NOT NULL UNIQUE, 그것도 없으면 숨은 row ID) | 지정한 컬럼 |
| 리프에 있는 것 | **행 전체** = 테이블 그 자체 | 인덱스 컬럼 + **PK 값** |
| 조회 | 한 번에 행 도착 | PK로 클러스터드 인덱스를 **한 번 더** 탐색 |

**주의**
- 세컨더리 인덱스로 찾은 행이 많으면 2번이 행마다 반복됨 (랜덤 I/O) → 옵티마이저가 차라리 풀 스캔을 고르기도 함
- PK 값은 모든 세컨더리 인덱스에 복사됨 → PK가 길면(문자열 UUID 등) 인덱스 전부가 같이 커짐

## 6. B+Tree

**정의**: 키를 정렬된 상태로 저장하는 **균형 트리**. 내부 노드엔 "길 안내용" 키만 있고, **리프에만 실제 데이터**가 있으며, 리프끼리 연결돼 있음

```text
                                      [40|80]                                    <- root
           +-----------------------------+-----------------------------+
           |                             |                             |
        [15|28]                       [52|66]                      [91|105]      <- internal
  +--------+---------+         +---------+---------+         +---------+----------+
  |        |         |         |         |         |         |         |          |
[3,9]<->[15,21]<->[28,33]<->[40,47]<->[52,58]<->[66,72]<->[80,85]<->[91,98]<->[105,112]   <- leaf
```
- 각 노드의 키가 "어느 쪽으로 내려갈지" 기준이 됨. 루트 `[40|80]`이면 40 미만은 왼쪽, 40~79는 가운데, 80 이상은 오른쪽
- 리프의 `<->`는 옆 리프와의 연결 (범위 검색에 사용)

**탐색 예시**
- **한 건 찾기** (`id = 58`): 루트에서 40 ≤ 58 < 80 → 가운데 `[52|66]` → 52 ≤ 58 < 66 → 가운데 리프 `[52,58]`에서 발견 → 노드 3개만 읽음
- **범위 찾기** (`id BETWEEN 15 AND 33`): 시작점 15만 트리로 찾아 리프 `[15,21]` 도착 → `<->`를 따라 `[28,33]` → 다음 리프 `[40,47]`에서 40 > 33이므로 종료. 이미 정렬돼 있어 ORDER BY도 추가 비용 없음

**B+Tree를 쓰는 이유**: DB의 병목은 계산이 아니라 **디스크에서 페이지를 읽는 횟수**임. 트리 높이 = 읽는 횟수이므로 높이를 낮추는 게 핵심

| 후보 | 문제 |
|---|---|
| 해시 테이블 | `=`는 빠르지만 정렬이 없음 → 범위 검색·ORDER BY·`LIKE 'abc%'` 불가 |
| 이진 탐색 트리 | 노드당 키 1개 → 100만 건이면 높이 약 20 → 디스크 읽기 20번 |
| B-Tree | 모든 노드에 데이터가 있어 노드당 키를 덜 담음 → 높이 증가, 범위 검색 시 트리를 오르내림 |
| **B+Tree** | 내부 노드엔 키만 → 노드당 키 수백 개 → **높이 3~4**. 리프가 연결돼 있어 **범위 스캔이 옆으로 이어짐** |

- 내부 노드엔 데이터 없이 키 + 포인터만 있음 → 한 페이지(InnoDB 16KB)에 키 수백 개 → 높이 3~4 정도로도 수천만 건 처리

**헷갈리는 포인트**
- **B는 Binary가 아님**. 자식이 2개가 아니라 수백 개이고, 흔히 Balanced로 설명함
- **Balanced의 의미**: 모든 리프의 깊이가 같음 → 어떤 키를 찾든 읽는 횟수가 같음. 삽입·삭제 때 노드를 쪼개거나(split) 합쳐서 균형을 유지함 → 인덱스가 쓰기를 느리게 하는 이유 중 하나

## 8. FE 심화

### 8-1. Server State

| | Client State | Server State |
|---|---|---|
| 주인 | 내 브라우저 | **서버(DB)**. 나는 사본만 가짐 |
| 예 | 모달 열림, 입력 중인 값, 다크 모드 | 게시글 목록, 유저 정보, 장바구니 |
| 바뀌는 시점 | 내가 바꿀 때만 | **다른 사람·다른 기기에서도** 바뀜 |
| 다룰 것 | 값 저장·변경 | 가져오기, **캐싱, 낡음 판단, 재요청, 중복 요청 제거**, 에러·재시도 |
| 도구 | useState, Zustand, Redux | TanStack Query, SWR, RTK Query |

**TanStack Query 캐싱·동기화 흐름**
```js
useQuery({ queryKey: ['posts'], queryFn: fetchPosts, staleTime: 30_000 })
```
```text
 Component                         Query Cache                        API Server
     |                                  |                                  |
     |----- (1) mount A: useQuery ----->|                                  |
     |                                  | miss -> isPending                |
     |                                  |--------- (2) GET /posts -------->|
     |                                  |<....... (3) 200 [posts] .........|
     |                                  | save, fresh 30s                  |
     |<----------- (4) data ------------|                                  |
     |----- (5) mount B: same key ----->|                                  |
     |<-- (6) cache hit, no request ----|                                  |
===================== 30s later: stale + window focus ======================
     |<------ (7) keep old data --------|                                  |
     |                                  |----- (8) background refetch ---->|
     |                                  |<......... (9) new list ..........|
================================= mutation =================================
     |------------------------- (10) POST /posts ------------------------->|
     |<........................ (11) 201 Created ..........................|
     |----- (12) invalidateQueries ---->|                                  |
     |                                  |--- (13) GET /posts (refetch) --->|
============================== all unmounted ===============================
     |                                  | inactive -> gcTime 5min -> removed
```
1. (1)~(4) A 컴포넌트 마운트 → 캐시 없음 → 로딩(`isPending`) 표시 후 GET 요청 → 응답 저장, 30초간 fresh
2. (5)~(6) 같은 키로 B 마운트 → fresh이므로 요청 없이 캐시로 바로 응답. 같은 키 = 같은 데이터라 props로 안 넘겨도 공유됨
3. (7)~(9) 30초 후(stale) 창에 다시 포커스 → 화면은 옛 데이터 그대로 유지(로딩 스피너 없음) + 뒤에서 refetch(`isFetching`) → 바뀌었으면 교체 리렌더. 이것이 **stale-while-revalidate**
4. (10)~(13) 글 작성(mutation) 성공 → `invalidateQueries({ queryKey: ['posts'] })` → stale로 표시되고 화면에 떠 있는 쿼리는 즉시 refetch
5. 모든 컴포넌트 언마운트 → 캐시는 inactive 상태 → gcTime(기본 5분) 경과 후 삭제

**Server State를 따로 다루는 이유**
- 서버 데이터를 `useEffect + useState`나 전역 store에 넣으면 로딩·에러·캐시·재요청·중복 요청 처리를 전부 직접 구현해야 함
- 여러 컴포넌트가 각자 복사본을 가져 **사본의 사본**이 생김
- Server State 라이브러리는 "queryKey 하나 = 캐시 하나"로 모아서 관리함

**staleTime vs gcTime** (헷갈리는 포인트)

| | 뜻 | 기본값 (v5) |
|---|---|---|
| `staleTime` | 받은 데이터를 **얼마 동안 믿을지**. 지나면 stale → 다음 기회(마운트·포커스·재연결)에 재요청 | 0 (받자마자 stale) |
| `gcTime` | 아무 컴포넌트도 안 쓰는 캐시를 **얼마 뒤 메모리에서 지울지** | 5분 |

- 그 밖의 기본값: 실패 시 3번 재시도, stale인 쿼리는 마운트·창 포커스·네트워크 재연결 때 다시 가져옴

### 8-2. API 데이터 관리

- **queryKey에 요청 파라미터를 전부 포함**: `['posts', { page, sort }]`. 키가 다르면 캐시도 따로 → 정렬을 바꿔도 이전 결과와 안 섞임
- **키는 계층 구조로**: `['posts']`, `['posts', { page: 2 }]`, `['posts', 7]` → `invalidateQueries({ queryKey: ['posts'] })` 한 번으로 앞부분이 같은 키를 전부 무효화
- **서버 데이터를 useState로 복사하지 않기**: 수정 폼 초기값처럼 꼭 필요할 때만 복사. 복사하는 순간 캐시와 따로 놀기 시작함
- **isPending vs isFetching**: 데이터가 아직 없음(첫 로딩 → 스켈레톤) vs 데이터는 있고 뒤에서 갱신 중(작은 인디케이터)
- **경쟁 상태(race condition)**: 검색어를 빠르게 바꾸면 늦게 온 옛 응답이 화면을 덮을 수 있음. TanStack Query는 키별로 캐시가 나뉘어 있어 거의 발생 안 함. 직접 fetch한다면 `AbortController`로 이전 요청 취소 (5주차)
- **무한 스크롤**: `useInfiniteQuery` + 서버의 **커서**(`getNextPageParam`이 마지막 id 반환) → 7-3의 OFFSET 문제와 같은 맥락

### 8-3. Client Cache와 서버 데이터 정합성

캐시가 서버와 달라지는 상황은 세 가지

| 상황 | 대응 |
|---|---|
| **내가** 바꿈 (mutation) | `invalidateQueries`로 재요청 / 응답 값으로 `setQueryData` 직접 갱신(요청 1번 절약) / **낙관적 업데이트** |
| **남이** 바꿈 | 데이터 성격에 맞게 `staleTime` 조절 + 포커스·재연결 시 재요청 / `refetchInterval` 폴링 / WebSocket·SSE로 변경 알림을 받으면 invalidate |
| **동시에** 바꿈 | 서버에서 **낙관적 락**(version, ETag + If-Match) → 409·412를 받으면 최신본 다시 받기 |

- **staleTime 정하는 기준**: 거의 안 바뀌는 것(카테고리 목록)은 길게, 자주 바뀌고 틀리면 안 되는 것(재고·잔액)은 짧게 또는 0

**낙관적 업데이트 흐름** (좋아요 버튼, 현재 12개)
```text
Like Button                        Query Cache                        API Server
     |                                  |                                  |
     |------ (1) click: mutate() ------>|                                  |
     |                                  | (2) onMutate                     |
     |                                  |     cancelQueries                |
     |                                  |     prev = 12 (snapshot)         |
     |                                  |     setQueryData -> 13           |
     |<------- (3) show 13 now ---------|                                  |
     |---------------------- (4) POST /posts/7/like ---------------------->|
================================= success ==================================
     |<........................... (5a) 200 OK ............................|
     |--- (6a) onSettled: invalidate -->|                                  |
     |                                  |------- (7a) GET /posts/7 ------->|
     |                                  |<...... 14 (server value) ........|
================================= failure ==================================
     |<......................... (5b) 500 Error ...........................|
     |--- (6b) onError: rollback 12 --->|                                  |
     | toast                            |                                  |
     |--- (7b) onSettled: invalidate -->|                                  |
```
1. 클릭 → `mutate()` 호출
2. `onMutate`
   - `cancelQueries`로 진행 중인 refetch 취소 (늦게 온 옛 값이 덮어쓰지 않게)
   - 스냅샷 저장 (`prev = 12`)
   - `setQueryData`로 13으로 변경
3. 서버 응답 전에 화면에 바로 13 표시
4. `POST /posts/7/like` 전송
5. 성공 시: `onSettled`에서 invalidate → 서버 실제 값(14, 그 사이 다른 사람도 누름)으로 맞춤
6. 실패 시: `onError`에서 스냅샷으로 롤백(12) + 에러 토스트 → `onSettled`에서 서버 값 재확인

- **쓸 곳**: 실패가 드물고 즉각 반응이 중요한 것 (좋아요, 체크박스, 순서 변경)
- **안 쓸 곳**: 결제·재고처럼 틀린 값을 잠깐이라도 보여주면 안 되는 것 → 서버 응답을 받은 뒤 반영

**Lost Update와 낙관적 락**
```text
 User A                      API Server + DB                                 User B
    |                               |                                           |
    |------ (1) GET /posts/7 ------>|                                           |
    |<........ version: 3 ..........|                                           |
    |                               |<----------- (2) GET /posts/7 -------------|
    |                               |............... version: 3 ...............>|
    |---- (3) PUT {title, v:3} ---->|                                           |
    |                               | UPDATE ... SET version = version + 1      |
    |                               | WHERE id = 7 AND version = 3              |
    |                               | -> 1 row changed (now v4)                 |
    |<..... (4) 200 OK {v:4} .......|                                           |
    |                               |<------- (5) PUT {old title, v:3} ---------|
    |                               | WHERE id = 7 AND version = 3              |
    |                               | -> 0 rows changed                         |
    |                               |............ (6) 409 Conflict ............>|
    |                               |                                           | refetch & retry
```
1. A와 B가 같은 글을 조회 (`version: 3`)
2. A가 제목을 수정해서 저장 → `WHERE id = 7 AND version = 3` 조건으로 UPDATE → 1행 변경 성공 (이제 version 4)
3. B가 옛 제목이 담긴 채로 본문을 수정해서 저장 → `version = 3`인 행이 없음 → 0행 변경 → **409 Conflict**
4. B에게 "다른 사람이 먼저 수정했어요" 안내 → 최신본을 다시 받아 비교 후 재시도

- version 체크가 없으면 3번에서 B가 A의 제목 수정을 조용히 되돌림 → 이것이 **Lost Update** (에러도 안 남)
- **HTTP 표준 방식**: 응답의 ETag를 기억 → 수정 요청에 `If-Match` 첨부 → 다르면 412 Precondition Failed
- **Spring JPA**: `@Version` 필드로 같은 방식으로 동작, 충돌 시 OptimisticLockException

**헷갈리는 포인트: 낙관적 업데이트 ≠ 낙관적 락**
- **낙관적 업데이트**: FE의 **UI 패턴**. 응답 전에 화면부터 바꾸고, 실패하면 롤백
- **낙관적 락**: DB·서버의 **동시성 제어**. 잠그지 않고 진행하다가 저장 순간 version을 비교해 충돌을 잡음
- 공통점: 이름 그대로 "충돌은 드물 거라 보고 일단 진행, 문제는 나중에 확인"
- 반대 개념인 **비관적 락**: `SELECT … FOR UPDATE`로 읽는 순간부터 잠가서 다른 사람을 기다리게 함

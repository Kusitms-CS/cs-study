# 6주차 - Database

## 1. RDB / NoSQL

### 구조

```text
RDB (관계형)                      NoSQL
┌────┬───────┬─────┐              { "id": 1,
│ id │ name  │ age │                "name": "Kim",
├────┼───────┼─────┤                "tags": ["a", "b"] }
│ 1  │ Kim   │ 20  │              (문서 / Key-Value / 그래프 등 다양한 형태)
│ 2  │ Lee   │ 21  │
└────┴───────┴─────┘
```

### 특징

- RDB: 정해진 스키마의 표(테이블) 형태로 데이터를 저장하고, 테이블끼리 관계를 맺어 SQL로 조회. 트랜잭션과 데이터 정합성에 강함
- NoSQL: 정해진 표 형태 없이 유연한 구조로 저장(Document, Key-Value 등). 스키마 변경이 쉽고 수평 확장(서버를 늘려 분산)에 유리한 경우가 많음
- 어느 쪽이 더 좋다기보다 데이터의 성격과 요구사항에 따라 선택

### 정리

- 데이터 사이의 관계가 중요하고 정확성이 중요하면 RDB, 구조가 자주 바뀌거나 대량 데이터를 빠르게 분산 처리해야 하면 NoSQL이 어울림
- 정해진 틀이 있는 표 vs 틀이 자유로운 저장소라는 차이로 이해

## 2. PK / FK

### 구조

```text
users                      orders
┌────┬──────┐              ┌────┬─────────┬─────────┐
│ id │ name │              │ id │ user_id │ product │
│(PK)│      │              │(PK)│  (FK)   │         │
├────┼──────┤              ├────┼─────────┼─────────┤
│ 1  │ Kim  │ ←──────────  │ 10 │    1    │ 책      │
└────┴──────┘              └────┴─────────┴─────────┘
```

### 특징

- PK(Primary Key): 테이블에서 각 행을 유일하게 구분하는 값, 중복과 NULL 불가
- FK(Foreign Key): 다른 테이블의 PK를 참조하는 값으로 테이블 간 관계를 표현
- FK로 존재하지 않는 값을 넣거나 참조 중인 행을 지우는 걸 막아 데이터 정합성을 지킴(참조 무결성)

### 정리

- PK는 "이 행의 주민번호", FK는 "다른 테이블의 어느 행을 가리키는지 적어둔 번호"
- FK 덕분에 없는 사용자의 주문 같은 말이 안 되는 데이터가 생기는 걸 막아줌

## 3. 정규화

### 구조

```text
정규화 전: orders(id, user_name, user_phone, product)
           → 같은 사용자의 이름/번호가 주문마다 반복 저장

정규화 후: users(id, name, phone) + orders(id, user_id, product)
           → 사용자 정보는 한 곳에만 저장
```

### 특징

- 중복 데이터를 줄이도록 테이블을 쪼개는 과정
- 중복이 있으면 수정할 때 한 곳만 바꿔서 데이터가 서로 어긋나는 문제(이상 현상)가 생길 수 있음
- 쪼갤수록 조회할 때 JOIN이 늘어나서 느려질 수 있어, 성능이 중요하면 일부러 중복을 허용하는 반정규화를 하기도 함

### 정리

- 같은 정보를 여러 곳에 중복 저장하지 않도록 테이블을 나누는 작업
- 데이터 정확성은 올라가지만 조회 때 JOIN이 늘어난다는 trade-off가 있어서, 상황에 따라 반정규화도 선택

## 4. JOIN

### 구조

```text
users  ⋈  orders   ON users.id = orders.user_id

INNER JOIN : 양쪽 모두에 매칭되는 행만
LEFT  JOIN : 왼쪽은 전부, 오른쪽은 매칭되는 것만 (없으면 NULL)
```

```sql
SELECT u.name, o.product
FROM users u
JOIN orders o ON u.id = o.user_id;
```

### 특징

- 두 개 이상의 테이블을 관계(키)를 기준으로 합쳐서 조회
- INNER JOIN은 매칭되는 행만, LEFT JOIN은 왼쪽 테이블은 전부 가져오고 없는 쪽은 NULL
- JOIN 대상이 크고 조건 컬럼에 인덱스가 없으면 느려질 수 있음

### 정리

- 쪼개놓은 테이블을 필요할 때 다시 붙여서 보는 방법
- 사용자는 있는데 주문이 없는 경우까지 보고 싶으면 LEFT JOIN, 둘 다 있는 것만 보면 INNER JOIN

## 5. Index

### 구조

```text
책의 목차와 같은 개념

Index 없음: 전체 행을 처음부터 끝까지 확인 (Full Scan, O(n))
Index 있음: 정렬된 별도 구조에서 빠르게 위치를 찾고 해당 행으로 이동 (O(log n))
```

### 특징

- 특정 컬럼 값으로 데이터를 빠르게 찾기 위해 별도로 만들어두는 정렬된 자료구조
- 조회(SELECT)는 빨라지지만, 데이터를 추가·수정·삭제할 때 인덱스도 같이 갱신해야 해서 쓰기는 느려지고 저장 공간도 더 사용
- WHERE, JOIN, ORDER BY에 자주 쓰이는 컬럼에 만드는 게 효과적
- 값의 종류가 적은 컬럼(예: 성별)은 걸러내는 효과가 작아 인덱스 효과가 적음

### 정리

- 책 뒤의 색인처럼, 처음부터 다 훑지 않고 원하는 값의 위치를 바로 찾게 해주는 구조
- 읽기는 빨라지는 대신 쓰기가 느려지고 공간을 더 쓰기 때문에, 자주 조회하는 컬럼에만 거는 게 좋음

## 6. B+Tree

### 구조

```text
                 [ 30 | 60 ]                  ← 루트/내부 노드: 길 안내용 키만 저장
               /     |      \
        [10|20]   [40|50]   [70|80]           ← 내부 노드
         /  |  \    ...
  [10→20→] ↔ [30→40→] ↔ [50→60→] ↔ [70→80→]   ← 리프 노드: 실제 데이터(포인터) 저장,
                                                   서로 연결 리스트로 이어짐
```

### 특징

- 인덱스에서 가장 많이 쓰이는 균형 트리로, 항상 균형을 유지해서 검색이 O(log n)으로 보장됨
- 한 노드에 키를 여러 개 담는 구조라 트리의 높이가 낮아서, 디스크를 읽는 횟수가 적음
- 데이터는 리프 노드에만 있고, 리프끼리 연결되어 있어서 범위 검색(BETWEEN, 정렬 순회)이 빠름
- 일반 BST와 달리 한쪽으로 치우치지 않도록 스스로 균형을 맞춤

### B-Tree와의 차이

| | B-Tree | B+Tree |
| --- | --- | --- |
| 데이터 저장 위치 | 모든 노드 | 리프 노드만 |
| 리프 노드 연결 | 없음 | 서로 연결 |
| 범위 검색 | 트리를 다시 오르내려야 함 | 리프만 따라가면 됨 |
| 내부 노드 | 키 + 데이터 | 키만(더 많은 키를 담을 수 있어 높이가 낮음) |

### 정리

- DB 인덱스는 디스크에서 읽는 횟수를 줄이는 게 핵심이라, 한 노드에 키를 많이 담아 트리 높이를 낮게 유지하는 B+Tree를 사용
- 데이터가 리프에만 있고 리프끼리 이어져 있어서, 하나 찾는 것도 빠르고 범위로 쭉 훑는 것도 빠름
- 이진 탐색 트리(BST)는 치우치면 O(n)까지 느려질 수 있지만, B+Tree는 항상 균형이 유지됨

# Frontend 심화

## 7. Server State

### 구조

```text
Client State : 화면 안에서만 의미 있는 값 (모달 열림 여부, 입력 중인 텍스트)
Server State : 서버가 원본을 가지고 있고, 클라이언트는 복사본을 들고 있는 값 (유저 목록, 게시글)
```

### 특징

- 서버가 진짜 원본을 가지고 있어서 클라이언트에 있는 값은 언제든 낡을(stale) 수 있음
- 로딩/에러/성공 상태, 캐싱, 재요청, 중복 요청 방지 등을 함께 다뤄야 함
- React Query, SWR 같은 라이브러리가 이런 서버 데이터 관리를 대신 해줌

### 정리

- 서버에 원본이 있고 나는 복사본만 들고 있는 데이터라서, "지금 이 값이 최신인가?"를 계속 신경 써야 함
- 화면 내부에서만 쓰는 값(Client State)과 구분해서 다루는 게 핵심

## 8. API 데이터 관리

### 구조

```js
// 컴포넌트마다 직접 fetch
useEffect(() => { fetch("/api/users").then(...) }, []);

// 서버 상태 라이브러리 사용
const { data, isLoading, error } = useQuery({ queryKey: ["users"], queryFn: fetchUsers });
```

### 특징

- 같은 데이터를 여러 컴포넌트에서 쓰면 중복 요청이 나가거나 값이 서로 달라질 수 있음
- Query Key로 데이터를 구분해서 캐싱하고, 같은 키의 요청은 하나로 합쳐서 처리
- staleTime(얼마 동안 최신이라고 볼지), 재시도, 백그라운드 재요청 같은 정책을 설정으로 제어

### 정리

- 컴포넌트마다 따로 fetch하면 중복 요청과 값 불일치가 생기기 쉬워서, 서버 데이터를 한곳에서 관리하는 방식이 필요
- 로딩·에러 처리와 캐싱을 직접 만드는 대신 라이브러리의 규칙(Query Key, staleTime)에 맡김

## 9. Client Cache와 서버 데이터 정합성

### 구조

```text
서버: 게시글 제목 = "B"  (다른 사용자가 수정)
클라이언트 캐시: 게시글 제목 = "A"  (낡은 값)  ← 불일치

→ 해결: 일정 시점에 다시 가져오기(refetch) / 수정 후 캐시 무효화(invalidate)
```

### 특징

- 캐시 덕분에 빠르지만, 서버 값이 바뀌면 클라이언트 캐시는 낡은 값이 되어 정합성이 깨질 수 있음
- 데이터를 수정(POST/PUT/DELETE)한 뒤에는 관련 캐시를 무효화해서 다시 가져오게 함
- Optimistic Update: 서버 응답을 기다리지 않고 화면에 먼저 반영하고, 실패하면 되돌리는 방식(체감 속도 향상)

### 캐시가 낡았는지 판단하는 기준 (stale)

```text
fresh : 최신이라고 믿는 기간 (staleTime 이내) → 서버에 안 물어보고 캐시 그대로 사용
stale : 낡았을 수 있다고 보는 상태          → 캐시를 먼저 보여주고, 뒤에서 다시 가져와서 교체
        (stale-while-revalidate)
```

- React Query 기준 staleTime 기본값은 0이라, 가져오자마자 stale로 취급되어 화면에 다시 들어오거나 창에 포커스가 돌아올 때 재요청이 발생
- staleTime: "이 기간은 최신으로 믿겠다"는 시간, gcTime: 아무도 쓰지 않는 캐시를 메모리에 얼마나 남겨둘지
- 자주 안 바뀌는 데이터(약관, 카테고리)는 staleTime을 길게, 자주 바뀌는 데이터(알림, 재고)는 짧게

### 수정 후 정합성 맞추기 (Invalidate)

```js
const mutation = useMutation({
  mutationFn: updatePost,
  onSuccess: () => {
    queryClient.invalidateQueries({ queryKey: ["posts"] }); // 관련 캐시를 stale로 만들고 다시 가져오게 함
  },
});
```

- 서버 데이터를 바꾸는 요청이 성공하면, 그 데이터와 관련된 캐시를 무효화해서 최신 값으로 다시 가져옴
- 어떤 캐시를 무효화할지는 Query Key로 지정하기 때문에, 키를 어떻게 설계하느냐가 중요

### Optimistic Update

```js
const mutation = useMutation({
  mutationFn: toggleLike,
  onMutate: async () => {
    await queryClient.cancelQueries({ queryKey: ["post", id] }); // 진행 중인 요청이 덮어쓰지 않게 중단
    const prev = queryClient.getQueryData(["post", id]);          // 실패 대비 이전 값 백업
    queryClient.setQueryData(["post", id], (old) => ({ ...old, liked: !old.liked })); // 먼저 화면에 반영
    return { prev };
  },
  onError: (_err, _vars, ctx) => {
    queryClient.setQueryData(["post", id], ctx.prev); // 실패하면 되돌림
  },
  onSettled: () => {
    queryClient.invalidateQueries({ queryKey: ["post", id] }); // 끝나면 서버 값으로 최종 동기화
  },
});
```

- 서버 응답을 기다리지 않고 화면에 먼저 반영해서 체감 속도를 높이는 방식(좋아요, 체크박스 등)
- 실패하면 백업해둔 값으로 되돌려야 하고, 끝나면 서버 값으로 한 번 더 맞춰서 어긋남을 방지
- 불변성을 지켜서 새 객체로 교체해야 화면이 갱신됨 (1주차 불변성과 연결)

### 정리

- 캐시는 빠르지만 낡은 값을 보여줄 위험이 함께 있어서, "언제까지 최신으로 믿을지(staleTime)"와 "언제 다시 가져올지"를 정하는 게 핵심
- 낡은 캐시를 먼저 보여주고 뒤에서 새 값으로 바꿔주는 stale-while-revalidate 덕분에 빠르면서도 결국 최신 값에 맞춰짐
- 수정이 성공하면 관련 캐시를 무효화(invalidate)해서 최신 값으로 갱신하고, 빠른 반응이 중요하면 먼저 반영하고 실패 시 되돌리는 Optimistic Update를 사용
- Optimistic Update는 "백업 → 먼저 반영 → 실패 시 롤백 → 끝나면 서버 값으로 재동기화" 순서로 기억

# Index / B+Tree

## Index

### 인덱스란

- 책 뒤의 색인. 특정 컬럼의 값과 그 값을 가진 행의 위치를 미리 정렬해서 따로 저장해둔 자료구조
  - 인덱스가 없으면 WHERE 조건에 맞는 행을 찾기 위해 테이블 전체를 처음부터 끝까지 읽어야 함 (Full Table Scan)
  - 인덱스가 있으면 정렬된 구조에서 탐색하므로 O(log N)에 위치를 찾고, 그 위치의 행만 읽음
  - 1,000만 건 테이블에서 풀스캔은 1,000만 번, B+Tree 인덱스는 높이 3~4 → 서너 번의 페이지 읽기로 끝남

```sql
CREATE INDEX idx_orders_member_id ON orders (member_id);
CREATE INDEX idx_orders_status_created ON orders (status, created_at);
```

- 트레이드오프
  - 읽기(SELECT)는 빨라짐
  - 쓰기(INSERT / UPDATE / DELETE)는 느려짐. 테이블뿐 아니라 인덱스도 같이 갱신해야 하므로. 인덱스가 5개면 쓰기 한 번에 6번 갱신
  - UPDATE는 인덱스 컬럼을 바꿀 때만 인덱스를 건드림. 인덱스에 없는 컬럼만 바꾸면 테이블만 갱신
  - 저장 공간을 추가로 씀. 인덱스가 많은 테이블은 인덱스 크기가 테이블보다 큰 경우도 흔함
- 종류
  - PK 인덱스 : PK를 만들면 자동 생성
  - UNIQUE 인덱스 : 중복 불가 제약 + 인덱스. 등치 조회 시 1건 찾으면 바로 멈출 수 있어 일반 인덱스보다 약간 빠름
  - 일반 (세컨더리) 인덱스 : 조회용으로 직접 만드는 것
  - 복합 인덱스 : 컬럼 여러 개를 묶은 것 ([쿼리 최적화](./query-optimization.md)에서 자세히)
  - 전문 인덱스 (FULLTEXT) : 텍스트 안의 단어 검색용. `LIKE '%단어%'` 대신 쓰는 것
  - 함수 기반 인덱스 (8.0.13+) : `INDEX ((YEAR(created_at)))` 처럼 표현식 결과에 인덱스

### 인덱스를 거는 기준

- 효과가 있는 컬럼
  - WHERE, JOIN ON, ORDER BY, GROUP BY에 자주 쓰이는 컬럼
  - 카디널리티(서로 다른 값의 개수)가 높은 컬럼. 주민번호, 이메일처럼 값이 다양할수록 인덱스로 걸러지는 행이 적어져 효과가 큼
  - 성별처럼 값이 2~3개뿐인 컬럼은 인덱스를 타도 절반을 읽어야 해서 거의 효과가 없음. 다만 "탈퇴 회원"처럼 값 분포가 극단적으로 치우쳐 있고 소수 쪽만 조회한다면 효과가 있을 수 있음
- 인덱스가 있어도 못 타는 경우
  - 컬럼을 가공하면 안 됨 : `WHERE YEAR(created_at) = 2026` → 인덱스는 created_at 원본 값으로 정렬되어 있어서 못 씀. `WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01'` 로 바꿔야 함
  - 앞에 와일드카드 : `LIKE '%keyword'` → 정렬의 시작점을 모르니 못 씀. `LIKE 'keyword%'` 는 가능
  - 묵시적 형변환 : 문자열 컬럼에 `WHERE phone = 01012345678` 처럼 숫자를 비교하면 컬럼 쪽이 숫자로 변환되면서 인덱스를 못 씀. 반대로 숫자 컬럼에 문자열을 비교하면 상수 쪽이 변환되므로 인덱스를 탐
  - 부정 조건 (`!=`, `NOT IN`), `IS NOT NULL` : 대부분의 행이 해당되므로 풀스캔이 선택되기 쉬움
  - `OR` 로 서로 다른 컬럼 조건을 묶은 경우 : 둘 다 인덱스가 있어야 index merge가 가능하고, 하나라도 없으면 풀스캔
- 옵티마이저가 인덱스를 안 쓰기로 결정하는 경우도 있음
  - 테이블의 상당 부분(대략 20~25% 이상)을 읽어야 한다면 인덱스로 하나씩 찾아가는 것보다 그냥 순서대로 전부 읽는 게 빠르다고 판단해서 풀스캔을 고름
  - 테이블이 아주 작으면(수백 건) 인덱스를 거치는 것 자체가 손해라 풀스캔
  - 왜 그런지는 아래 클러스터링 인덱스 구조를 보면 이해됨

### 인덱스 스캔 방식

- Index Range Scan : 시작점을 찾고 조건이 끝나는 곳까지 리프를 따라 읽음. `=`, `BETWEEN`, `>`, `LIKE 'x%'`. 가장 일반적인 형태
- Index Full Scan : 인덱스 전체를 처음부터 끝까지 읽음. 조건은 인덱스를 못 쓰지만 필요한 컬럼이 인덱스에 다 있을 때. 테이블보다 인덱스가 작으니 풀스캔보다는 낫다는 정도
- Index Skip Scan (8.0+) : 복합 인덱스의 첫 컬럼 조건이 없어도 첫 컬럼 값이 몇 개 안 되면 값마다 건너뛰며 탐색
- Loose Index Scan : GROUP BY나 MIN/MAX를 그룹별로 첫 값만 읽고 건너뜀. EXPLAIN에 `Using index for group-by`

## B+Tree

### 왜 해시나 이진 트리가 아닌가

- 인덱스 자료구조 후보들을 생각해보면..
- 해시 테이블
  - 등치 조회(`=`)는 O(1)로 가장 빠름
  - 그런데 정렬이 없어서 범위 조회(`BETWEEN`, `>`, `LIKE 'a%'`)와 ORDER BY에 전혀 못 씀. DB 쿼리의 상당수가 범위/정렬이라 주 인덱스로는 부적합
  - MEMORY 엔진의 기본 인덱스이고, InnoDB도 내부적으로 자주 쓰는 값에 대해 Adaptive Hash Index를 자동으로 만들긴 함
- 이진 탐색 트리 (BST, Red-Black Tree)
  - 정렬은 되는데 노드 하나에 키가 하나라 트리 높이가 깊음. 100만 건이면 높이가 20
  - 인덱스는 디스크에 있고, 디스크는 페이지(InnoDB 기준 16KB) 단위로 읽음. 노드 하나 읽으려고 페이지 하나를 읽는 거면 높이만큼 디스크 I/O가 발생함
  - 디스크 I/O는 메모리 접근보다 수천~수만 배 느리므로, 높이를 줄이는 게 핵심
- B-Tree
  - 노드 하나(= 페이지 하나)에 키를 수백 개씩 넣는 다진 트리. 자식이 수백 개라 높이가 매우 낮음
  - 대략 계산하면.. 16KB 페이지에 BIGINT 키(8바이트) + 자식 포인터(6바이트)가 들어가면 페이지당 약 1,000개. 높이 3이면 1,000 × 1,000 × 1,000 = 10억 건을 커버함. 즉 어떤 행이든 디스크 I/O 3번이면 찾음
  - 루트와 그 아래 한 단계 정도는 거의 항상 메모리(버퍼 풀)에 올라와 있어서 실제 디스크 I/O는 더 적음
  - 균형 트리라 삽입/삭제 후에도 모든 리프의 깊이가 같게 유지됨 (B는 Balanced의 B라는 설이 있지만 공식적으로 정해진 건 아님)

### B-Tree와 B+Tree

- B+Tree는 B-Tree의 변형이고, 대부분의 RDBMS 인덱스는 B+Tree를 씀
- 차이점
  - B-Tree : 모든 노드에 키와 데이터(또는 데이터 포인터)가 같이 있음
  - B+Tree : 데이터는 리프 노드에만 있고, 내부 노드는 길 찾기용 키만 있음. 리프 노드끼리는 양방향 연결 리스트
- 이게 왜 좋은가
  - 내부 노드에 데이터가 없으니 같은 페이지 크기에 키를 더 많이 넣을 수 있음 → 자식 수(fan-out)가 커짐 → 높이가 더 낮아짐
  - 리프 노드끼리 연결되어 있음 → 범위 조회 시 시작점만 트리로 찾고 그 뒤로는 리프를 옆으로 쭉 읽으면 됨. B-Tree는 범위 조회에 트리를 오르내려야 함
  - 모든 데이터가 리프에 있으니 풀스캔도 리프만 순서대로 읽으면 됨. 접근 경로가 균일해서 성능 예측이 쉬움
- 정리하면..

1. 루트 노드에서 키 비교로 어느 자식으로 갈지 결정
2. 내부 노드를 따라 내려감 (높이 3이면 2번)
3. 리프 노드에 도착. 여기에 실제 데이터(또는 데이터 위치)가 있음
4. 범위 조회면 리프의 다음 포인터를 따라 옆으로 이동

### InnoDB의 클러스터링 인덱스와 세컨더리 인덱스

[https://dev.mysql.com/doc/refman/8.0/en/innodb-index-types.html](https://dev.mysql.com/doc/refman/8.0/en/innodb-index-types.html)

- 클러스터링 인덱스 (Clustered Index)
  - InnoDB에서는 테이블 자체가 PK 기준 B+Tree임. 리프 노드에 행 데이터 전체가 들어있음
  - 즉 "PK 인덱스 따로, 테이블 데이터 따로"가 아니라 PK 인덱스의 리프가 곧 테이블임. 그래서 테이블당 하나만 존재
  - PK가 없으면 첫 번째 UNIQUE NOT NULL 컬럼을, 그것도 없으면 내부적으로 6바이트 row id를 만들어서 씀. 어차피 만들어지니 PK는 명시하는 게 낫다
  - 데이터가 PK 순서로 물리적으로 정렬되어 있어서 PK 범위 조회가 매우 빠름
- 세컨더리 인덱스 (Secondary Index)
  - PK 외의 컬럼에 만드는 인덱스. 리프 노드에 행의 물리적 위치가 아니라 **PK 값**이 들어있음
  - 그래서 세컨더리 인덱스로 조회하면 탐색이 두 번 일어남

1. 세컨더리 인덱스 B+Tree를 탐색해서 조건에 맞는 PK 값들을 얻음
2. 그 PK 값으로 클러스터링 인덱스 B+Tree를 다시 탐색해서 실제 행을 읽음

- 이 구조에서 따라 나오는 것들
  - 2번 과정이 PK 값마다 반복되는데, PK 값들이 흩어져 있으면 디스크의 여기저기를 찍는 랜덤 I/O가 됨. 조건에 맞는 행이 많아질수록 이 비용이 커져서, 어느 선을 넘으면 옵티마이저가 "그냥 처음부터 순서대로 읽자(풀스캔)"를 택함. 위에서 말한 20~25% 기준이 여기서 나옴
  - 2번을 생략하는 방법이 커버링 인덱스 ([쿼리 최적화](./query-optimization.md))
  - 세컨더리 인덱스 리프에 PK가 들어가므로, PK가 길면(UUID 문자열 36바이트 등) 모든 세컨더리 인덱스가 같이 커짐. PK는 작을수록 좋음
  - 리프에 물리 주소 대신 PK를 넣는 이유는, 페이지 분할 등으로 행의 위치가 바뀌어도 세컨더리 인덱스를 고칠 필요가 없게 하려는 것. 대신 PK 값 자체를 UPDATE하면 모든 세컨더리 인덱스를 고쳐야 하므로 PK는 바뀌지 않는 값이어야 함
- MyISAM, PostgreSQL과 비교
  - MyISAM은 PK도 세컨더리도 리프에 행의 물리 주소(ROWID)를 담는 비클러스터링 구조. 모든 인덱스가 1단계 탐색이지만 PK 순서 저장의 이점이 없음
  - PostgreSQL도 기본적으로 힙 테이블 + 모든 인덱스가 물리 주소(TID)를 가리키는 구조. CLUSTER 명령으로 한 번 정렬할 수는 있지만 유지되진 않음
  - 그래서 "PK가 세컨더리 인덱스 크기에 영향을 준다", "PK 순서로 저장된다"는 이야기는 InnoDB에 해당하는 말임

### PK 선택과 페이지 분할

[https://planetscale.com/blog/btrees-and-database-indexes](https://planetscale.com/blog/btrees-and-database-indexes)

- 클러스터링 인덱스는 PK 순서로 정렬되어 저장되므로 INSERT 시 새 행이 들어갈 자리가 PK 값으로 결정됨
- AUTO_INCREMENT 정수 PK
  - 항상 마지막 페이지 뒤에 붙음. 페이지가 차면 새 페이지를 뒤에 하나 추가하면 끝
  - 마지막 페이지만 계속 건드리니 버퍼 풀에 항상 올라와 있고, 디스크 쓰기도 순차적임
- 랜덤 값 PK (UUID v4 등)
  - 중간 아무 데나 들어감. 들어갈 페이지가 꽉 차 있으면 그 페이지를 반으로 쪼개야 함 (Page Split)
  - 쪼개진 페이지는 절반이 비어있어서 공간 효율이 떨어지고, 분할 자체도 비용임. 분할이 상위 노드까지 전파되면 트리 높이가 늘 수도 있음
  - 캐시(버퍼 풀)에 올라와 있지 않은 페이지를 건드릴 확률도 높아져서 디스크 I/O가 늘어남. 데이터가 버퍼 풀보다 커지는 순간 삽입 성능이 급격히 떨어지는 패턴
- 선택 기준
  - InnoDB에서는 단조 증가하는 PK가 권장됨
  - 분산 환경에서 UUID가 필요하면 시간 순으로 정렬되는 UUID v7이나 ULID, Snowflake ID를 쓰고, 저장은 CHAR(36)이 아니라 BINARY(16)으로 하는 게 요즘 추세
  - 삭제가 많아도 페이지에 빈 공간이 생기는데, 이건 OPTIMIZE TABLE로 정리 가능. 다만 테이블을 다시 쓰는 작업이라 큰 테이블에서는 시간이 오래 걸림

### 면접 질문으로 정리하면..

- Q. 인덱스는 왜 B+Tree를 쓰나요? → 디스크 페이지 단위 I/O에 맞춰 높이를 낮추기 위해. 해시는 범위 불가, BST는 높이가 깊음. B+Tree는 리프 연결로 범위 조회까지
- Q. 인덱스를 많이 걸면 왜 안 되나요? → 쓰기마다 인덱스 갱신, 저장 공간, 버퍼 풀 낭비. 옵티마이저가 잘못된 인덱스를 고를 가능성도
- Q. 클러스터링 인덱스가 뭔가요? → InnoDB에서 PK 순서로 행 자체가 저장된 B+Tree. 세컨더리 인덱스는 PK를 담고 있어 2단계 탐색이 일어난다는 것까지
- Q. 인덱스가 있는데 왜 안 타죠? → 컬럼 가공, 형변환, 앞 와일드카드, 선택도가 낮아 풀스캔이 더 싸다고 판단. EXPLAIN으로 확인

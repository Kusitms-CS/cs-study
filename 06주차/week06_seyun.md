# 6주차 - Database

## 1. RDB / NoSQL

- **데이터베이스(DB):** 여러 사용자가 공유하며 사용할 수 있도록 **체계적으로 저장·관리되는 데이터의 집합**
- 데이터를 어떤 모델로 저장하느냐에 따라 크게 **RDB(관계형)** 와 **NoSQL(비관계형)** 로 나뉨

### 📍 RDB (Relational Database)

- 데이터를 **행(Row)과 열(Column)로 구성된 테이블**에 저장하고, 테이블 간의 **관계(Relation)** 로 데이터를 연결하는 DB
- **스키마를 미리 정의**해야 하고, 이를 따르는 데이터만 저장 가능
- **SQL**로 데이터를 조회/조작하며, **트랜잭션(ACID)** 을 통해 데이터 정합성을 보장
- 예시: MySQL, PostgreSQL, Oracle, MariaDB

### 📍 NoSQL (Not Only SQL)

- 테이블 형태에 얽매이지 않고 **유연한 구조로 데이터를 저장**하는 비관계형 DB
- 스키마가 유연하고, 대부분 **수평 확장(Scale-out)** 을 염두에 두고 설계됨

| 유형            | 설명                                      | 예시          |
| --------------- | ----------------------------------------- | ------------- |
| Key-Value       | Key로 Value를 바로 조회, 매우 빠름        | Redis, DynamoDB |
| Document        | JSON 유사 문서 단위로 저장                | MongoDB       |
| Column-Family   | 컬럼 단위로 묶어 저장, 대용량 쓰기에 유리 | Cassandra, HBase |
| Graph           | 노드와 간선으로 관계를 표현               | Neo4j         |

### 📍 ACID

| 속성                | 설명                                                                   |
| ------------------- | ---------------------------------------------------------------------- |
| Atomicity (원자성)  | 트랜잭션은 **전부 성공하거나 전부 실패**해야 함 (All or Nothing)       |
| Consistency (일관성) | 트랜잭션 전후로 DB가 **정의된 규칙(제약조건)을 만족하는 상태**를 유지  |
| Isolation (격리성)  | 동시에 실행되는 트랜잭션이 **서로 간섭하지 않음**                      |
| Durability (지속성) | 커밋된 트랜잭션의 결과는 **장애가 나도 영구적으로 보존**됨             |

### 📍 RDB vs NoSQL

| 구분        | RDB                                      | NoSQL                                            |
| ----------- | ---------------------------------------- | ------------------------------------------------ |
| 데이터 구조 | 테이블 (정형 데이터)                     | Key-Value, Document, Graph 등 (비정형 가능)      |
| 스키마      | 엄격 (미리 정의)                         | 유연 (Schema-less)                               |
| 관계 표현   | FK와 JOIN으로 표현                       | 주로 중첩/비정규화로 한 문서에 포함              |
| 확장 방식   | 주로 수직 확장 (Scale-up)                | 주로 수평 확장 (Scale-out)                       |
| 트랜잭션    | ACID를 강하게 보장                       | 제품마다 다름 (BASE, 최종적 일관성을 택하는 경우 많음) |
| 적합한 사례 | 금융, 주문/결제 등 정합성이 중요한 서비스 | 로그, 캐시, 실시간 피드 등 대용량·유연한 구조    |

### 💡 RDB와 NoSQL 중 무엇을 선택해야 하나요?

**⇒ 데이터 간 관계가 명확하고 결제·재고처럼 정합성(트랜잭션)이 중요하다면 RDB, 스키마가 자주 바뀌거나 대용량 데이터를 빠르게 읽고 써야 하고 수평 확장이 필요하다면 NoSQL이 적합함. 어느 한쪽이 항상 우월한 것은 아니며, 실무에서는 핵심 데이터는 RDB에 저장하고 캐시·세션·로그 등은 Redis나 MongoDB 같은 NoSQL을 함께 사용하는 방식이 일반적임**

### 💡 NoSQL은 정합성을 포기한 건가요? (CAP 이론)

**⇒ 분산 시스템은 일관성(Consistency), 가용성(Availability), 분할 내성(Partition Tolerance) 세 가지를 동시에 모두 만족할 수 없다는 것이 CAP 이론임. 네트워크 분할은 분산 환경에서 피할 수 없으므로 사실상 일관성과 가용성 중 하나를 택해야 하고, 많은 NoSQL은 가용성을 우선해 일시적인 불일치를 허용하는 최종적 일관성(Eventual Consistency)을 택함. 다만 제품에 따라 강한 일관성 옵션을 제공하기도 하므로 "NoSQL은 정합성이 없다"는 것은 과한 일반화임**

## 2. PK / FK

- 테이블의 행을 식별하고, 테이블 간의 관계를 맺기 위한 **키(Key)** 개념

### 📍 키의 종류

| 키                  | 설명                                                                             |
| ------------------- | -------------------------------------------------------------------------------- |
| Super Key (슈퍼키)  | 행을 유일하게 식별할 수 있는 속성의 집합 (유일성)                                |
| Candidate Key (후보키) | 슈퍼키 중 **최소성**까지 만족하는 키 (불필요한 속성이 없음)                   |
| Primary Key (PK)    | 후보키 중 **대표로 선택한 키**                                                   |
| Alternate Key (대체키) | 후보키 중 PK로 선택되지 않은 나머지                                           |
| Foreign Key (FK)    | **다른 테이블의 PK를 참조**하는 키                                               |

### 📍 Primary Key (기본키)

- 테이블에서 **각 행을 유일하게 식별**하는 키
- **중복 불가(UNIQUE) + NULL 불가(NOT NULL)**, 테이블당 **하나만** 지정 가능 (복합키는 여러 컬럼을 묶어 하나의 PK로 사용)
- 대부분의 DB가 PK에 **자동으로 인덱스(클러스터드 인덱스)** 를 생성

### 📍 Foreign Key (외래키)

- 한 테이블의 컬럼이 **다른 테이블의 PK(또는 UNIQUE 컬럼)를 참조**하도록 하는 제약조건
- **참조 무결성(Referential Integrity):** 존재하지 않는 값을 참조하는 데이터가 생기지 않도록 보장
- FK 컬럼은 **NULL 허용 및 중복 가능**

```sql
CREATE TABLE member (
  id   BIGINT PRIMARY KEY AUTO_INCREMENT,
  name VARCHAR(50) NOT NULL
);

CREATE TABLE orders (
  id        BIGINT PRIMARY KEY AUTO_INCREMENT,
  member_id BIGINT NOT NULL,
  FOREIGN KEY (member_id) REFERENCES member(id)
    ON DELETE CASCADE -- 회원 삭제 시 주문도 함께 삭제
);
```

### 📍 참조 동작 옵션

| 옵션        | 설명                                               |
| ----------- | -------------------------------------------------- |
| CASCADE     | 부모 행 삭제/수정 시 **자식 행도 함께 삭제/수정**  |
| SET NULL    | 부모 행 삭제/수정 시 자식의 FK를 **NULL로 변경**   |
| RESTRICT / NO ACTION | 자식이 참조 중이면 부모 행의 삭제/수정을 **거부** |

### 📍 대리키(Surrogate Key) vs 자연키(Natural Key)

| 구분   | 자연키                                  | 대리키                                       |
| ------ | --------------------------------------- | -------------------------------------------- |
| 설명   | 비즈니스 의미가 있는 값 (주민번호, 이메일) | 의미 없이 **인위적으로 만든 값** (AUTO_INCREMENT, UUID) |
| 장점   | 별도 컬럼이 필요 없음                   | 비즈니스 규칙이 바뀌어도 PK가 변하지 않음    |
| 단점   | 값이 변경될 수 있고, 변경 시 FK 전파 비용 | 추가 컬럼이 필요하고 의미가 없음             |

### 💡 PK로 비즈니스 값(이메일, 주민번호 등) 대신 대리키를 주로 쓰는 이유

**⇒ 이메일이나 전화번호 같은 자연키는 정책이 바뀌거나 사용자가 값을 변경할 수 있는데, PK가 바뀌면 이를 참조하는 모든 FK도 함께 바꿔야 해서 비용이 크고 위험함. 또한 문자열 PK는 길이가 길어 인덱스와 JOIN 성능에도 불리함. 반면 대리키는 비즈니스와 무관하게 불변이고 크기가 작아 안정적이므로 실무에서는 대리키를 PK로, 자연키는 UNIQUE 제약조건으로 두는 방식을 많이 사용함**

### 💡 FK를 실무에서 안 쓰기도 하는 이유

**⇒ FK는 참조 무결성을 DB 레벨에서 보장해주지만, INSERT/UPDATE/DELETE마다 참조 테이블을 확인해야 하는 오버헤드와 락 경합이 생기고, 대규모 서비스에서 샤딩·데이터 마이그레이션·테이블 분리를 할 때 제약이 되기 때문. 그래서 일부 서비스에서는 FK 제약조건을 걸지 않고 애플리케이션 레벨에서 무결성을 관리하기도 하지만, 이 경우 정합성 보장의 책임이 개발자에게 넘어오므로 데이터 규모와 운영 환경을 고려해 선택해야 함**

## 3. 정규화 (Normalization)

- 데이터의 **중복을 최소화하고 이상(Anomaly) 현상을 방지**하기 위해 테이블을 **논리적으로 분리하는 과정**
- 하나의 테이블에 하나의 주제(관심사)만 담도록 설계하는 것이 목표

### 📍 이상 현상 (Anomaly)

| 이상 현상             | 설명                                                                           |
| --------------------- | ------------------------------------------------------------------------------ |
| 삽입 이상 (Insertion) | 불필요한 데이터가 함께 있어야만 새로운 데이터를 삽입할 수 있음                 |
| 갱신 이상 (Update)    | 중복된 데이터 중 **일부만 수정**되어 데이터 불일치가 발생                      |
| 삭제 이상 (Deletion)  | 어떤 데이터를 삭제하면 **의도치 않게 다른 정보까지 함께 삭제**됨               |

### 📍 정규형 (Normal Form)

| 정규형   | 조건                                                                  | 해결하는 문제                    |
| -------- | --------------------------------------------------------------------- | -------------------------------- |
| 1NF      | 모든 컬럼 값이 **원자값(Atomic)** — 한 칸에 여러 값이 들어가면 안 됨  | 다중 값 컬럼, 반복 그룹          |
| 2NF      | 1NF + **부분 함수 종속 제거** (복합키의 일부에만 종속되는 컬럼 분리)  | 복합키 일부에 종속된 컬럼        |
| 3NF      | 2NF + **이행적 함수 종속 제거** (A→B, B→C 일 때 A→C 분리)             | 일반 컬럼 간 종속                |
| BCNF     | 3NF + **모든 결정자가 후보키**                                        | 후보키가 아닌 결정자에 의한 종속 |

- 실무에서는 보통 **3NF(또는 BCNF)까지** 정규화함

```
[비정규형]  주문(주문ID, 고객명, 고객주소, 상품명1, 상품명2, ...)
   ↓ 1NF  : 상품을 한 칸에 하나씩 (행으로 분리)
   ↓ 2NF  : 고객 정보 / 상품 정보를 주문 키 일부에 종속되는 것끼리 분리
   ↓ 3NF  : 고객ID → 고객명, 고객주소 같은 이행 종속을 고객 테이블로 분리
```

### 📍 반정규화 (Denormalization)

- 조회 성능 향상을 위해 **정규화된 테이블에 의도적으로 중복을 허용**하는 것
- 예시: JOIN을 줄이기 위한 컬럼 중복 (주문 테이블에 `member_name` 저장), 집계 컬럼 미리 저장 (`like_count`), 테이블 병합

| 구분        | 정규화                         | 반정규화                          |
| ----------- | ------------------------------ | --------------------------------- |
| 목적        | 데이터 무결성, 중복 제거       | 조회 성능 향상                    |
| 데이터 중복 | 최소화                         | 허용                              |
| 쓰기 성능   | 유리 (한 곳만 수정)            | 불리 (중복 데이터를 모두 갱신)    |
| 읽기 성능   | JOIN이 많아져 불리할 수 있음   | JOIN이 줄어 유리                  |
| 정합성 관리 | DB가 구조적으로 보장           | 애플리케이션이 직접 관리해야 함   |

### 💡 정규화를 하면 항상 좋은가요?

**⇒ 정규화는 중복을 줄이고 이상 현상을 막아 데이터 정합성을 높여주지만, 테이블이 쪼개지면 조회 시 JOIN이 늘어나 읽기 성능이 떨어질 수 있음. 읽기 비중이 매우 높고 JOIN 비용이 병목이 되는 경우에는 반정규화로 일부 중복을 허용해 성능을 얻기도 함. 다만 반정규화는 중복 데이터의 일관성을 애플리케이션이 책임져야 하므로, 먼저 정규화로 설계한 뒤 성능 문제가 실제로 측정되었을 때 필요한 부분만 반정규화하는 것이 좋음**

## 4. JOIN

- **둘 이상의 테이블을 연결 조건(주로 PK = FK)에 따라 결합**해서 하나의 결과로 조회하는 연산
- 정규화로 분리된 테이블의 데이터를 다시 합쳐서 볼 때 사용

### 📍 JOIN의 종류

| JOIN            | 설명                                                                           |
| --------------- | ------------------------------------------------------------------------------ |
| INNER JOIN      | 양쪽 테이블에 **조건이 일치하는 행만** 반환 (교집합)                           |
| LEFT (OUTER) JOIN  | **왼쪽 테이블은 전부** 반환, 오른쪽에 일치하는 행이 없으면 NULL              |
| RIGHT (OUTER) JOIN | **오른쪽 테이블은 전부** 반환, 왼쪽에 일치하는 행이 없으면 NULL              |
| FULL OUTER JOIN | 양쪽 테이블의 **모든 행** 반환, 일치하지 않는 쪽은 NULL (MySQL은 미지원)       |
| CROSS JOIN      | 두 테이블의 **모든 행 조합(카테시안 곱)** 반환                                 |
| SELF JOIN       | **같은 테이블끼리** JOIN (계층 구조, 상사-부하 관계 등)                        |

```sql
-- INNER JOIN: 주문이 있는 회원만
SELECT m.name, o.id
FROM member m
INNER JOIN orders o ON m.id = o.member_id;

-- LEFT JOIN: 주문이 없는 회원도 포함 (주문 정보는 NULL)
SELECT m.name, o.id
FROM member m
LEFT JOIN orders o ON m.id = o.member_id;

-- 주문이 한 번도 없는 회원 찾기
SELECT m.name
FROM member m
LEFT JOIN orders o ON m.id = o.member_id
WHERE o.id IS NULL;
```

### 📍 JOIN 알고리즘 (DB 내부 동작)

| 알고리즘         | 동작 방식                                                                         | 적합한 경우                      |
| ---------------- | --------------------------------------------------------------------------------- | -------------------------------- |
| Nested Loop Join | 바깥 테이블의 각 행마다 안쪽 테이블을 탐색 (안쪽 테이블에 **인덱스**가 있으면 효율적) | 소량 데이터, 인덱스가 있는 JOIN  |
| Hash Join        | 작은 테이블로 **해시 테이블**을 만들고 큰 테이블을 훑으며 매칭                     | 대량 데이터, 등가(=) 조건 JOIN   |
| Sort Merge Join  | 양쪽을 JOIN 키로 **정렬한 뒤 병합**                                                | 이미 정렬되어 있거나 범위 조건   |

### 💡 INNER JOIN과 LEFT JOIN의 차이

**⇒ INNER JOIN은 양쪽 테이블에 조건이 모두 일치하는 행만 결과에 포함하므로 한쪽에 짝이 없는 행은 사라지고, LEFT JOIN은 왼쪽 테이블의 모든 행을 유지하면서 오른쪽에 짝이 없으면 NULL로 채움. 따라서 "주문이 없는 회원도 함께 보여줘야 한다"처럼 기준 테이블의 데이터가 누락되면 안 될 때 LEFT JOIN을 사용함. 주의할 점은 LEFT JOIN 후 오른쪽 테이블 컬럼을 WHERE 조건으로 필터링하면 NULL 행이 제거되어 INNER JOIN처럼 동작하므로, 이때는 ON 절에 조건을 넣어야 함**

### 💡 JOIN이 많아지면 왜 느려지나요?

**⇒ JOIN은 테이블마다 행을 찾아 매칭하는 연산이라 JOIN 대상 테이블이 늘고 데이터가 많아질수록 비교 횟수와 중간 결과 크기가 커지기 때문. 특히 JOIN 컬럼에 인덱스가 없으면 Nested Loop에서 안쪽 테이블을 매번 풀 스캔해 성능이 급격히 나빠짐. 그래서 JOIN 컬럼(주로 FK)에 인덱스를 걸고, 필요한 컬럼만 조회하며, 조건으로 먼저 데이터를 줄이는 방식으로 최적화하고, 그래도 부족하면 반정규화나 캐시를 검토함**

## 5. Index

- 테이블의 **특정 컬럼 값을 기준으로 데이터의 위치를 빠르게 찾을 수 있도록 만든 별도의 자료구조** (책의 색인/목차와 유사)
- 인덱스가 없으면 조건에 맞는 행을 찾기 위해 **Full Table Scan**(전체 행 탐색, O(N))을 해야 하지만, 인덱스를 사용하면 **O(log N)** 에 탐색 가능
- 인덱스는 **정렬된 상태로 유지**되므로 `ORDER BY`, 범위 조회에도 유리

### 📍 인덱스의 장단점

| 구분 | 설명                                                                                                       |
| ---- | ---------------------------------------------------------------------------------------------------------- |
| 장점 | `WHERE`, `JOIN`, `ORDER BY`, `GROUP BY`의 **조회 성능 향상**                                               |
| 단점 | INSERT/UPDATE/DELETE 시 **인덱스도 함께 갱신**해야 해서 쓰기 성능 저하, 별도의 **저장 공간** 필요          |

### 📍 클러스터드 vs 논클러스터드 인덱스

| 구분          | 클러스터드 인덱스 (Clustered)                      | 논클러스터드 인덱스 (Non-Clustered / Secondary) |
| ------------- | -------------------------------------------------- | ----------------------------------------------- |
| 데이터 저장   | **인덱스 자체가 실제 데이터(행)의 물리적 순서**를 결정 | 데이터와 **별도의 인덱스 구조**를 가짐          |
| 리프 노드     | **실제 데이터 행**                                 | **인덱스 키 + PK(또는 행 위치)**                |
| 개수          | 테이블당 **1개** (보통 PK)                         | 테이블당 **여러 개** 가능                       |
| 조회          | 인덱스 탐색만으로 데이터 접근 (빠름)               | 인덱스 탐색 후 **PK로 한 번 더 조회** (Lookup)  |

- MySQL(InnoDB)은 **PK가 클러스터드 인덱스**이며, 세컨더리 인덱스의 리프 노드에는 **PK 값**이 저장되어 PK로 다시 데이터를 찾아감

### 📍 복합 인덱스 (Composite Index)

- **여러 컬럼을 묶어 하나의 인덱스**로 만든 것으로, **컬럼 순서가 매우 중요**
- `(A, B, C)` 인덱스는 **A → B → C 순으로 정렬**되어 있어서 **왼쪽부터(Leftmost Prefix)** 사용 가능

| 조건                  | 인덱스 `(A, B, C)` 사용 여부              |
| --------------------- | ----------------------------------------- |
| `WHERE A = 1`         | O                                         |
| `WHERE A = 1 AND B = 2` | O                                       |
| `WHERE B = 2`         | **X** (첫 컬럼 A가 없음)                  |
| `WHERE A = 1 AND C = 3` | A만 사용 (B를 건너뛰어 C는 인덱스로 탐색 불가) |

- 보통 **카디널리티(고유값 수)가 높은 컬럼**과 **등호(=) 조건 컬럼**을 앞에 배치

### 📍 인덱스를 타지 못하는 경우

- 인덱스 컬럼에 **함수/연산을 적용**: `WHERE YEAR(created_at) = 2026`, `WHERE price * 2 > 100`
- **암묵적 형변환**: 문자열 컬럼을 숫자와 비교
- **LIKE '%keyword'** 처럼 앞부분에 와일드카드 (`LIKE 'keyword%'`는 가능)
- **부정 조건** (`!=`, `NOT IN`)이나 **OR** 조건의 일부
- 카디널리티가 낮은 컬럼 (성별 등) — 옵티마이저가 Full Scan이 더 빠르다고 판단

### 📍 인덱스 설계 시 고려사항

- **카디널리티가 높은** 컬럼(중복이 적은 컬럼)에 생성
- `WHERE`, `JOIN`(FK), `ORDER BY`에 자주 쓰이는 컬럼에 생성
- 쓰기가 잦은 테이블에 인덱스를 과도하게 만들지 않기
- **커버링 인덱스(Covering Index):** 쿼리에 필요한 모든 컬럼이 인덱스에 포함되어 있으면 **테이블 접근 없이 인덱스만으로 결과 반환** 가능
- `EXPLAIN`으로 실행 계획을 확인해 인덱스 사용 여부 검증

### 💡 인덱스를 모든 컬럼에 만들면 안 되는 이유

**⇒ 인덱스는 조회를 빠르게 하는 대신 별도의 저장 공간을 차지하고, INSERT/UPDATE/DELETE 때마다 인덱스 구조도 함께 갱신(정렬 유지, 노드 분할 등)해야 해서 쓰기 성능을 떨어뜨림. 또한 옵티마이저가 어떤 인덱스를 쓸지 고르는 비용도 늘어남. 따라서 조회 패턴을 분석해서 실제로 자주 쓰이고 선택도가 높은 컬럼에만 최소한으로 생성해야 함**

### 💡 복합 인덱스에서 컬럼 순서가 중요한 이유

**⇒ 복합 인덱스는 첫 번째 컬럼 기준으로 정렬되고, 그 안에서 두 번째 컬럼 순으로 정렬된 구조이기 때문에 첫 번째 컬럼 조건 없이 두 번째 컬럼만으로는 정렬된 범위를 좁힐 수 없어 인덱스를 효율적으로 사용할 수 없음. 그래서 `(A, B)`와 `(B, A)`는 완전히 다른 인덱스이며, 쿼리의 조건 패턴(등호 조건, 카디널리티)을 고려해 순서를 정해야 함**

## 6. B+Tree

- DB 인덱스에서 가장 널리 사용되는 **self-balancing 트리 자료구조**로, B-Tree를 개선한 형태
- **모든 리프 노드가 같은 깊이**를 유지해 탐색/삽입/삭제가 항상 **O(log N)** 을 보장

### 📍 왜 DB는 이진 탐색 트리가 아니라 B-Tree 계열을 쓸까?

- DB 데이터는 **디스크**에 저장되고, 디스크 I/O는 메모리 접근보다 **훨씬 느림** → **디스크 접근 횟수를 최소화**하는 것이 핵심
- 이진 트리는 노드당 자식이 최대 2개라 **트리 높이가 높아져** 디스크 접근이 많아짐
- B-Tree 계열은 **한 노드에 여러 키와 여러 자식(수백 개)** 을 담아 **트리 높이를 매우 낮게** 유지하고, 노드 크기를 디스크 페이지 크기(예: InnoDB 16KB)에 맞춰 **한 번의 I/O로 많은 키를 읽음**

### 📍 B-Tree vs B+Tree

| 구분                | B-Tree                                   | B+Tree                                                 |
| ------------------- | ---------------------------------------- | ------------------------------------------------------ |
| 데이터 저장 위치    | **모든 노드**(내부 + 리프)에 키와 데이터 저장 | **리프 노드에만** 데이터 저장, 내부 노드는 **키(길잡이)만** 저장 |
| 내부 노드 크기      | 데이터까지 있어 상대적으로 큼            | 키만 있어 작아 **한 노드에 더 많은 키 수용** → 트리 높이 감소 |
| 리프 노드 연결      | 연결되어 있지 않음                       | **리프 노드끼리 Linked List로 연결**                   |
| 범위 조회           | 트리를 계속 오르내리며 탐색 (비효율)     | 시작점을 찾은 뒤 **리프를 순차적으로 따라가며 조회** (효율적) |
| 탐색 성능           | 운 좋으면 내부 노드에서 바로 찾음 (편차 있음) | 항상 리프까지 내려가므로 **탐색 시간이 일정**          |

```
              [   30   |   60   ]                ← 내부 노드: 키만 저장 (길잡이 역할)
             /          |         \
   [10|20] → [30|40|50] → [60|70|80]              ← 리프 노드: 실제 데이터(또는 PK) 저장
     (리프 노드끼리 Linked List로 연결 → 범위 조회에 유리)
```

### 📍 B+Tree 동작 방식

- **탐색:** 루트에서 시작해 키 비교로 알맞은 자식으로 내려가며 리프에서 값을 찾음
- **삽입:** 리프에 키를 삽입하고, 노드가 가득 차면 **노드를 분할(Split)** 하고 중간 키를 부모로 올림
- **삭제:** 리프에서 키 삭제, 노드가 최소 키 수보다 적어지면 **형제 노드와 병합(Merge) 또는 재분배**
- 삽입/삭제 시 **분할/병합이 일어나므로** 인덱스가 많을수록 쓰기 비용이 커짐

### 📍 Hash Index와 비교

| 구분        | B+Tree Index                               | Hash Index                                  |
| ----------- | ------------------------------------------ | ------------------------------------------- |
| 탐색 복잡도 | O(log N)                                   | **O(1)** (평균)                             |
| 등호(=) 조회 | 가능                                      | **매우 빠름**                               |
| 범위 조회   | **가능** (정렬되어 있음)                   | **불가능** (해시값은 순서와 무관)           |
| 정렬(ORDER BY) | 가능                                    | 불가능                                      |
| 사용처      | 대부분의 RDB 기본 인덱스                   | 메모리 DB, 단순 Key 조회 (Redis 등)         |

### 💡 DB 인덱스에 B+Tree를 사용하는 이유

**⇒ DB는 디스크 I/O가 병목이므로 디스크 접근 횟수를 줄이는 것이 중요한데, B+Tree는 한 노드에 많은 키를 담아 트리 높이를 낮게 유지(수백만 건도 3~4단계)해 적은 I/O로 탐색할 수 있음. 또한 내부 노드에는 키만 저장해 한 페이지에 더 많은 키를 담을 수 있고, 모든 데이터가 리프에 있어 탐색 시간이 일정하며, 리프 노드가 Linked List로 연결되어 있어 범위 조회와 정렬된 순회가 효율적임. 이 때문에 등호뿐 아니라 `BETWEEN`, `ORDER BY` 같은 쿼리도 인덱스로 빠르게 처리할 수 있음**

### 💡 B-Tree와 B+Tree의 차이가 왜 중요한가요?

**⇒ B+Tree는 데이터를 리프 노드에만 두기 때문에 내부 노드가 가벼워져 같은 페이지 크기에서 더 많은 키를 저장할 수 있고, 그만큼 트리 높이가 낮아져 디스크 I/O가 줄어듦. 그리고 리프 노드가 연결 리스트로 이어져 있어 범위 검색 시 트리를 다시 오르내릴 필요 없이 순차 탐색이 가능함. DB는 `WHERE age BETWEEN 20 AND 30` 같은 범위 조회가 매우 빈번하므로 B+Tree가 B-Tree보다 유리함**

# Frontend 심화

## 1. Server State

- **서버에 저장되어 있고 클라이언트가 API로 가져와 사용하는 데이터**
- 클라이언트가 소유한 데이터가 아니라 **서버 데이터의 일시적인 복사본(스냅샷)** 이므로, 가져오는 순간부터 이미 **오래된(stale) 데이터가 될 수 있음**

### 📍 Client State vs Server State

| 구분            | Client State                                | Server State                                             |
| --------------- | ------------------------------------------- | -------------------------------------------------------- |
| 소유            | 클라이언트가 **직접 소유**                  | **서버가 소유**, 클라이언트는 복사본만 보유              |
| 예시            | 모달 열림 여부, 입력 폼 값, 테마, 선택된 탭 | 유저 목록, 게시글, 상품 정보                             |
| 동기 여부       | 항상 최신 (본인이 변경)                     | 다른 사용자/서버에 의해 **언제든 변경**될 수 있음 (비동기) |
| 관리 시 고려    | 상태 변경 로직                              | 로딩/에러 상태, 캐싱, 재요청, 중복 요청 제거, 동기화     |
| 도구            | `useState`, Zustand, Redux, Context         | **TanStack Query(React Query)**, SWR, Apollo Client      |

### 📍 Server State를 직접 관리할 때의 문제 (`useEffect` + `useState`)

```jsx
function UserList() {
  const [users, setUsers] = useState([]);
  const [isLoading, setIsLoading] = useState(true);
  const [error, setError] = useState(null);

  useEffect(() => {
    fetch("/api/users")
      .then((res) => res.json())
      .then(setUsers)
      .catch(setError)
      .finally(() => setIsLoading(false));
  }, []);
  // 캐싱 X, 중복 요청 제거 X, 재시도 X, 갱신 시점 관리 X, race condition 위험 ...
}
```

- **로딩/에러 상태를 매번 직접 관리**해야 하는 보일러플레이트 발생
- **캐싱이 없어** 같은 데이터를 여러 컴포넌트/페이지 이동마다 재요청
- 같은 API를 여러 컴포넌트에서 호출하면 **중복 요청** 발생
- 요청 순서가 뒤바뀌면 오래된 응답이 최신 응답을 덮어쓰는 **Race Condition**
- 탭 복귀, 네트워크 재연결 시 **데이터 갱신**, 실패 시 **재시도** 등을 직접 구현해야 함
- 서버 데이터를 전역 상태(Redux 등)에 넣으면 **캐시 만료·갱신 로직을 직접** 짜야 하는 부담

### 📍 Server State 관리 라이브러리가 해결해주는 것 (TanStack Query 기준)

| 기능                    | 설명                                                                         |
| ----------------------- | ---------------------------------------------------------------------------- |
| 캐싱                    | **Query Key** 기준으로 응답을 캐싱하고 재사용                                |
| 중복 요청 제거 (Dedup)  | 같은 Query Key로 동시에 여러 번 호출해도 **한 번만 요청**                    |
| Stale-While-Revalidate  | 캐시된(stale) 데이터를 **먼저 보여주고 백그라운드에서 재검증**               |
| 자동 갱신 (Refetch)     | 윈도우 포커스, 네트워크 재연결, 마운트 시 자동 재요청                        |
| 재시도 (Retry)          | 실패 시 지수 백오프로 자동 재시도                                            |
| 로딩/에러 상태 제공     | `isLoading`, `isError`, `isFetching` 등 상태 제공                            |
| 페이지네이션/무한 스크롤 | `useInfiniteQuery` 등 전용 API 제공                                          |
| Mutation                | 데이터 변경(POST/PUT/DELETE)과 이후 캐시 무효화/낙관적 업데이트 지원         |

```jsx
function UserList() {
  const { data, isLoading, error } = useQuery({
    queryKey: ["users"], // 캐시의 식별자
    queryFn: () => fetch("/api/users").then((res) => res.json()),
  });

  if (isLoading) return <Spinner />;
  if (error) return <ErrorView />;
  return data.map((u) => <UserItem key={u.id} user={u} />);
}
```

### 💡 Server State와 Client State를 분리해서 관리하는 이유

**⇒ Server State는 서버가 원본을 가지고 있고 클라이언트는 복사본만 들고 있어, 다른 사용자나 서버에 의해 언제든 변할 수 있고 비동기로 가져오기 때문에 캐싱, 만료(stale), 재요청, 중복 제거, 로딩/에러 처리 같은 별도의 관리가 필요함. 반면 Client State는 UI 상태처럼 클라이언트가 직접 소유하고 동기적으로 변경됨. 둘을 섞어 Redux 같은 전역 상태에 모두 넣으면 서버 데이터의 동기화 로직을 직접 구현해야 해서 복잡해지므로, Server State는 TanStack Query 같은 전용 도구에 맡기고 Client State만 `useState`/Zustand로 관리해 각자 목적에 맞게 단순하게 유지함**

## 2. API 데이터 관리

- 서버에서 받은 **API 응답 데이터를 어떻게 요청하고, 캐싱하고, 변경하고, 구조화할지**를 다루는 영역

### 📍 Query Key 설계

- Query Key는 **캐시의 식별자**이자, 값이 바뀌면 **자동으로 새 데이터를 요청**하는 의존성 배열 역할
- **서버 요청에 영향을 주는 모든 변수**를 Key에 포함해야 함

```js
["users"]                       // 유저 목록
["users", userId]               // 특정 유저 상세
["users", { page: 2, size: 10 }] // 페이지네이션 파라미터 포함
```

- 계층적으로 설계하면 `invalidateQueries({ queryKey: ["users"] })` 한 번으로 **하위 Key를 모두 무효화**할 수 있음
- Query Key 팩토리 함수로 Key를 한 곳에서 관리하면 오타와 불일치를 방지

### 📍 staleTime vs gcTime (cacheTime)

| 옵션        | 설명                                                                                          | 기본값 (TanStack Query v5) |
| ----------- | --------------------------------------------------------------------------------------------- | -------------------------- |
| `staleTime` | 데이터가 **fresh로 유지되는 시간**. 이 시간 동안은 재요청하지 않고 캐시 사용                  | 0 (받자마자 stale)         |
| `gcTime`    | 사용하는 컴포넌트가 없어진(inactive) 캐시를 **메모리에 보관하는 시간**. 지나면 가비지 컬렉션  | 5분                        |

- **fresh:** 서버 재요청 없이 캐시 사용 / **stale:** 캐시를 먼저 보여주되 조건(마운트, 포커스 등) 충족 시 백그라운드 재요청
- `staleTime`은 **"얼마나 오래 최신으로 믿을지"**, `gcTime`은 **"안 쓰는 캐시를 얼마나 들고 있을지"** 를 의미

### 📍 Mutation (데이터 변경)

- **GET(Query)과 달리 서버 데이터를 변경하는 작업**(POST/PUT/PATCH/DELETE)
- 성공/실패 시 콜백으로 **캐시 무효화, 화면 이동, 토스트** 등을 처리

```jsx
const queryClient = useQueryClient();

const { mutate } = useMutation({
  mutationFn: (newUser) => axios.post("/api/users", newUser),
  onSuccess: () => {
    queryClient.invalidateQueries({ queryKey: ["users"] }); // 목록 캐시를 stale로 만들고 재요청
  },
});
```

### 📍 API 데이터 관리 패턴

- **API 계층 분리:** 컴포넌트 안에서 `fetch`를 직접 호출하지 않고 **API 함수 / 커스텀 훅(`useUsers`)** 으로 분리해 재사용성과 테스트 용이성 확보
- **응답 변환(select/Adapter):** 서버 응답 형태를 UI에서 쓰기 좋은 형태로 변환하는 계층을 둬서, **서버 스펙 변경이 UI에 직접 영향을 주지 않도록** 격리
- **정규화된 캐시:** Apollo Client처럼 엔티티를 ID 기준으로 평탄화해 저장하면 같은 엔티티가 여러 쿼리에 있어도 한 곳만 갱신
- **Prefetch:** 사용자가 이동할 가능성이 높은 페이지의 데이터를 미리 가져와 체감 속도 향상
- **의존적 쿼리(Dependent Query):** `enabled` 옵션으로 이전 쿼리 결과가 있을 때만 다음 쿼리 실행
- **Suspense / Error Boundary:** 로딩·에러 처리를 컴포넌트 밖으로 선언적으로 분리

### 💡 Query Key에 파라미터를 반드시 포함해야 하는 이유

**⇒ 캐시는 Query Key를 기준으로 저장·조회되므로, 페이지 번호나 검색어 같은 요청 조건이 Key에 빠지면 서로 다른 데이터가 같은 Key로 캐싱되어 잘못된 데이터가 화면에 보이게 됨. 반대로 조건을 Key에 포함하면 조건이 바뀔 때 자동으로 새 요청이 일어나고, 이전 조건의 캐시도 따로 보존되어 돌아갔을 때 즉시 보여줄 수 있음**

### 💡 `staleTime`을 늘리면 어떤 장단점이 있나요?

**⇒ staleTime을 늘리면 그 시간 동안 캐시를 fresh로 간주해 불필요한 재요청이 줄어 서버 부하가 감소하고 화면 전환이 빨라짐. 하지만 그만큼 서버의 실제 데이터와 화면이 달라질 가능성(stale한 데이터 노출)이 커짐. 그래서 거의 변하지 않는 데이터(코드 테이블, 설정값)는 길게, 자주 바뀌고 정확성이 중요한 데이터(재고, 알림)는 짧게 두는 식으로 데이터 특성에 맞춰 설정함**

## 3. Client Cache와 서버 데이터 정합성

- 클라이언트 캐시는 **성능을 높여주지만 서버의 원본과 달라질 수 있는** 위험이 있어, 이 **불일치를 최소화하고 일관성을 유지**하는 것이 핵심 과제
- 캐시의 정합성은 **"언제 캐시를 믿고, 언제 서버에서 다시 가져올 것인가"** 의 문제

### 📍 정합성이 깨지는 상황

- 다른 사용자/기기가 데이터를 **변경**했지만 내 화면은 **옛날 캐시**를 보고 있는 경우
- 내가 데이터를 **수정(Mutation)** 했는데 **목록 등 다른 캐시에는 반영되지 않은** 경우
- 여러 컴포넌트가 **같은 엔티티를 서로 다른 캐시 Key**로 들고 있어 한쪽만 갱신된 경우
- 느린 요청의 응답이 나중에 도착해 **최신 데이터를 덮어쓰는** Race Condition

### 📍 정합성을 유지하는 전략

| 전략                          | 설명                                                                                          | 적합한 경우                      |
| ----------------------------- | --------------------------------------------------------------------------------------------- | -------------------------------- |
| 캐시 무효화 (Invalidation)    | Mutation 성공 후 관련 Query를 **stale로 표시하고 재요청**                                     | 가장 기본적이고 안전한 방법      |
| 직접 캐시 갱신 (`setQueryData`) | Mutation 응답 값으로 **캐시를 직접 수정**해 추가 요청 없이 반영                              | 응답에 최신 데이터가 포함된 경우 |
| 낙관적 업데이트 (Optimistic)  | 서버 응답 **전에 UI부터 먼저 갱신**하고, 실패하면 롤백                                       | 좋아요, 체크 토글 등 성공 확률 높은 동작 |
| Refetch 트리거                | 윈도우 포커스, 네트워크 재연결, 주기적 Polling(`refetchInterval`)으로 재조회                  | 변경이 잦은 데이터               |
| 실시간 푸시                   | **WebSocket / SSE** 이벤트를 받아 캐시를 무효화하거나 갱신                                    | 채팅, 알림 등 실시간 데이터      |
| HTTP 캐시 재검증              | `ETag` / `If-None-Match`로 변경 없으면 304로 응답                                             | 변경이 드문 정적 데이터          |

### 📍 낙관적 업데이트 (Optimistic Update)

- 서버 응답을 기다리지 않고 **성공할 것이라 가정하고 UI를 먼저 변경**해 **즉각적인 반응성**을 제공
- 실패하면 **이전 상태로 롤백**하고, 최종적으로는 **서버 데이터로 재동기화**

```jsx
useMutation({
  mutationFn: toggleLike,
  onMutate: async (postId) => {
    await queryClient.cancelQueries({ queryKey: ["post", postId] }); // 진행 중인 요청이 덮어쓰지 않도록 취소
    const previous = queryClient.getQueryData(["post", postId]); // 롤백용 스냅샷
    queryClient.setQueryData(["post", postId], (old) => ({
      ...old,
      liked: !old.liked,
    })); // UI 먼저 변경
    return { previous };
  },
  onError: (err, postId, ctx) => {
    queryClient.setQueryData(["post", postId], ctx.previous); // 실패 시 롤백
  },
  onSettled: (data, err, postId) => {
    queryClient.invalidateQueries({ queryKey: ["post", postId] }); // 성공/실패 무관하게 서버와 재동기화
  },
});
```

### 📍 Stale-While-Revalidate (SWR) 패턴

1. 캐시된 데이터가 있으면 **즉시 화면에 보여줌** (빠른 응답)
2. 동시에 **백그라운드에서 서버에 재검증 요청**
3. 최신 데이터가 도착하면 **화면을 갱신**

- **체감 속도(캐시)** 와 **최신성(재검증)** 을 모두 얻는 방식 (HTTP의 `stale-while-revalidate` 캐시 지시자에서 유래)

### 📍 Race Condition 방지

- 검색 자동완성처럼 요청이 연속될 때, **이전 요청을 취소(`AbortController`)** 하거나 최신 요청의 응답만 반영
- TanStack Query는 **Query Key별로 최신 요청 결과만 캐시에 반영**하고, `queryFn`에 `signal`을 전달해 취소를 지원
- Mutation 직전에 `cancelQueries`로 진행 중인 요청이 낙관적 업데이트를 덮어쓰지 않도록 방지

### 💡 Mutation 후 `invalidateQueries`와 `setQueryData` 중 무엇을 써야 하나요?

**⇒ `invalidateQueries`는 관련 캐시를 stale로 만들고 서버에서 다시 가져오므로 구현이 단순하고 항상 서버와 정합성이 보장되지만 추가 네트워크 요청이 발생함. `setQueryData`는 Mutation 응답으로 캐시를 직접 수정해 요청 없이 즉시 반영할 수 있지만, 목록·상세 등 연관된 캐시를 모두 직접 맞춰줘야 하고 서버의 계산 결과(정렬, 집계 등)와 달라질 위험이 있음. 따라서 기본은 `invalidateQueries`로 안전하게 처리하고, 응답에 최신 엔티티가 그대로 오고 영향 범위가 작은 경우에만 `setQueryData`로 최적화하는 것이 좋음**

### 💡 낙관적 업데이트를 쓸 때 주의할 점

**⇒ 서버가 실패할 수 있으므로 반드시 이전 상태를 저장해 두었다가 실패 시 롤백해야 하고, 진행 중인 요청의 응답이 낙관적 값을 덮어쓰지 않도록 `cancelQueries`로 취소해야 함. 또한 성공/실패와 관계없이 마지막에 `invalidateQueries`로 서버 데이터와 재동기화해야 최종 정합성이 맞음. 결제나 재고처럼 실패 확률이 높거나 실패 시 사용자에게 혼란을 주는 동작에는 적합하지 않고, 좋아요·북마크 같이 성공 확률이 높고 즉각 반응이 중요한 동작에 사용함**

### 💡 클라이언트 캐시의 정합성을 100% 보장할 수 있나요?

**⇒ 클라이언트가 서버의 변경을 먼저 알 수 있는 방법이 없는 한 완벽한 실시간 정합성은 불가능하고, 항상 "얼마나 늦게 알아도 괜찮은가"를 정하는 트레이드오프의 문제임(분산 시스템의 최종적 일관성과 같은 맥락). 그래서 데이터 특성에 따라 `staleTime`, Refetch 정책, 실시간 푸시(WebSocket/SSE)를 조합해 허용 가능한 지연 범위를 정하고, 정합성이 반드시 필요한 경우(결제, 재고 차감)는 최종 검증을 서버에서 수행하도록 설계함**

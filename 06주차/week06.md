# 6주차 - Database

## RDB와 NoSQL

### RDB

- 데이터를 행과 열로 구성된 테이블에 저장
- 미리 정의된 스키마 사용
- 테이블 사이의 관계 표현
- SQL로 데이터 조회
- 트랜잭션과 데이터 일관성이 중요할 때 적합
- 예: MySQL, PostgreSQL

```text
사용자 테이블
id | name | team_id
1  | 태경 | 10
```

### NoSQL

- 문서형, 키-값형, 그래프형 등 다양한 저장 방식
- 구조가 자주 변하는 데이터에 유연
- 대규모 데이터를 여러 서버에 분산하기 쉬움
- 종류에 따라 관계나 트랜잭션도 지원
- 예: MongoDB, Redis

| 구분 | RDB | NoSQL |
| --- | --- | --- |
| 저장 구조 | 테이블 | 문서, 키-값 등 |
| 스키마 | 비교적 엄격 | 비교적 유연 |
| 관계 표현 | JOIN과 FK | 중첩·참조 등 |
| 강점 | 일관성과 복잡한 관계 | 유연성과 확장성 |

### 핵심 정리

- RDB: 데이터 관계와 일관성이 중요할 때 적합
- NoSQL: 유연한 구조와 분산 확장이 중요할 때 적합
- 요구사항에 따라 적절한 데이터베이스 선택

## PK와 FK

### PK

- 테이블의 각 행을 유일하게 식별하는 기본 키
- 값 중복 불가
- `NULL` 사용 불가
- 여러 열을 묶어 하나의 PK로 구성 가능

```text
사용자
id(PK) | name
1      | 태경
2      | 민수
```

### FK

- 다른 테이블의 행을 참조하는 외래 키
- 테이블 사이의 관계 표현
- 존재하지 않는 값을 참조하려 하면 저장 거부

```text
팀
id(PK) | name
10     | 개발팀

사용자
id(PK) | name | team_id(FK)
1      | 태경 | 10
```

### 참조 데이터 삭제

- `RESTRICT`: 참조 중이면 삭제 거부
- `SET NULL`: 참조하는 FK를 `NULL`로 변경
- `CASCADE`: 참조하는 행도 함께 삭제
- `SET NULL`을 사용하려면 FK 열이 `NULL`을 허용해야 함

### 핵심 정리

- PK: 현재 테이블의 행 식별
- FK: 다른 테이블의 행 참조
- 존재하지 않는 FK 저장과 참조 대상 삭제는 서로 다른 상황

## 정규화

- 데이터 중복을 줄이고 이상 현상을 방지하도록 테이블을 나누는 과정

### 정규화 전

```text
주문
주문ID | 회원ID | 회원이름 | 회원주소 | 상품ID
1      | 10     | 태경     | 서울     | 100
2      | 10     | 태경     | 서울     | 200
```

- 회원 정보가 주문마다 반복
- 주소 변경 시 관련된 모든 행을 수정해야 함

### 정규화 후

```text
회원
회원ID(PK) | 이름 | 주소
10         | 태경 | 서울

주문
주문ID(PK) | 회원ID(FK) | 상품ID
1          | 10         | 100
2          | 10         | 200
```

- 회원 정보는 한 번만 저장
- 주문에서는 회원 ID로 참조

### 이상 현상

- 삽입 이상: 다른 데이터가 없어 필요한 데이터를 저장하기 어려움
- 수정 이상: 일부 행만 수정해 같은 정보가 서로 달라짐
- 삭제 이상: 행을 삭제하면서 필요한 정보까지 사라짐

### 정규형

- 제1정규형: 각 열에는 하나의 값만 저장
- 제2정규형: 복합 키의 일부에만 의존하는 열 제거
- 제3정규형: 기본 키가 아닌 열에 의존하는 열 제거

### 핵심 정리

- 정규화로 중복과 이상 현상 감소
- 조회 성능을 위해 의도적으로 데이터를 합치는 반정규화를 사용하기도 함

## JOIN

- 공통된 열을 기준으로 여러 테이블의 데이터를 연결해 조회

```text
회원                           주문
id | name                     id  | member_id | product
1  | 태경                     101 | 1         | 키보드
2  | 민수
```

### INNER JOIN

- 양쪽 테이블에 연결되는 데이터가 모두 있는 행만 조회

```sql
SELECT 회원.name, 주문.product
FROM 회원
INNER JOIN 주문 ON 회원.id = 주문.member_id;
```

```text
태경 | 키보드
```

### LEFT JOIN

- 왼쪽 테이블의 모든 행 조회
- 연결되는 오른쪽 데이터가 없으면 `NULL`

```sql
SELECT 회원.name, 주문.product
FROM 회원
LEFT JOIN 주문 ON 회원.id = 주문.member_id;
```

```text
태경 | 키보드
민수 | NULL
```

### 주요 JOIN

| 종류 | 조회 결과 |
| --- | --- |
| `INNER JOIN` | 양쪽에 모두 존재하는 데이터 |
| `LEFT JOIN` | 왼쪽 전체 + 연결되는 오른쪽 데이터 |
| `RIGHT JOIN` | 오른쪽 전체 + 연결되는 왼쪽 데이터 |
| `FULL OUTER JOIN` | 양쪽의 모든 데이터 |

- `FULL OUTER JOIN`은 데이터베이스 종류에 따라 직접 지원하지 않을 수 있음

### 핵심 정리

- 주문이 있는 회원만 조회: `INNER JOIN`
- 주문하지 않은 회원까지 조회: 회원을 왼쪽에 둔 `LEFT JOIN`

## Index

- 테이블의 데이터를 빠르게 찾기 위한 별도의 탐색 구조
- 책의 색인처럼 원하는 데이터의 위치를 빠르게 탐색

```sql
SELECT *
FROM 회원
WHERE email = 'test@example.com';
```

- Index가 없으면 모든 행을 확인하는 전체 탐색이 발생할 수 있음
- Index가 있으면 원하는 데이터의 위치를 빠르게 찾을 수 있음

### 장점

- `WHERE` 조건 검색 속도 향상
- `JOIN`에 사용하는 열의 탐색 속도 향상
- 경우에 따라 `ORDER BY` 정렬 비용 감소

### 단점

- 별도의 저장 공간 필요
- 데이터 추가·수정·삭제 시 Index도 함께 갱신
- Index가 많으면 쓰기 성능 저하
- 데이터가 적거나 대부분의 행을 조회하면 효과가 작을 수 있음

### 적합한 열

- 검색 조건에 자주 사용하는 열
- JOIN에 자주 사용하는 열
- 값의 종류가 많아 데이터를 잘 구분하는 열
- 성별처럼 값의 종류가 적은 열은 단독 Index의 효과가 작을 수 있음

### 핵심 정리

- Index는 읽기 성능을 높이는 대신 저장 공간과 쓰기 비용 사용
- 모든 열이 아니라 조회에 자주 사용하는 열을 중심으로 생성

## B+Tree

- 많은 관계형 데이터베이스가 Index에 사용하는 균형 트리 자료구조

```text
           [30 | 60]
          /    |    \
   [10, 20] [30, 40] [60, 70, 80]
        ↔        ↔         ↔
```

### 구조

- 루트와 중간 노드: 탐색 방향을 결정하는 키 저장
- 리프 노드: 실제 데이터 또는 데이터 위치 저장
- 모든 리프 노드의 깊이가 같음
- 리프 노드끼리 순서대로 연결

### 장점

- 검색·삽입·삭제: 일반적으로 `O(log n)`
- 한 노드에 여러 키를 저장해 트리 높이가 낮음
- 트리 높이가 낮아 디스크 접근 횟수 감소
- 리프 노드가 연결되어 범위 검색과 정렬에 유리

```sql
SELECT *
FROM 상품
WHERE price BETWEEN 10000 AND 30000
ORDER BY price;
```

- 시작 가격을 찾은 뒤 연결된 리프 노드를 순서대로 탐색

### Hash Index와 비교

- Hash: 정확히 일치하는 값 검색에 유리
- B+Tree: 일치 검색뿐 아니라 범위 검색과 정렬에도 유리

### 핵심 정리

- B+Tree는 트리 높이가 낮아 디스크 접근 횟수가 적음
- 정렬된 리프 노드가 연결되어 범위 검색에 적합

## Server State

- 서버에 저장되고 클라이언트가 API를 통해 가져와 사용하는 데이터
- 클라이언트에 있는 값은 서버 원본의 복사본

```text
서버의 원본 데이터
      ↓ API 요청
클라이언트의 복사본
```

예:

- 사용자 정보
- 상품 목록
- 게시글
- 주문 내역

### 특징

- 비동기로 가져옴
- 네트워크 오류가 발생할 수 있음
- 여러 사용자가 데이터를 변경할 수 있음
- 클라이언트의 데이터가 오래된 상태가 될 수 있음
- 로딩·오류·캐시·재요청 관리 필요

### Client State와 비교

| Server State | Client State |
| --- | --- |
| 상품 목록 | 모달 열림 여부 |
| 사용자 정보 | 선택한 탭 |
| 게시글 | 입력 중인 폼 |
| 주문 내역 | 다크 모드 |

### 핵심 정리

- Server State: 서버가 원본을 소유하는 데이터
- Client State: 현재 브라우저나 화면에서 관리하는 상태
- 서버 상태는 저장보다 동기화 시점 관리가 중요

## API 데이터 관리

- API 데이터는 값뿐 아니라 요청의 전체 상태를 함께 관리

```text
요청 전 → 로딩 → 성공
              ↘ 실패
```

### 관리할 상태

- 로딩: 요청이 진행 중
- 성공: 데이터를 정상적으로 받음
- 빈 데이터: 요청은 성공했지만 결과가 없음
- 오류: 요청 실패
- 재요청: 실패하거나 오래된 데이터를 다시 요청

```js
{
  data,
  isLoading,
  error
}
```

### 고려할 문제

- 같은 API의 중복 요청 방지
- 이전 요청이 늦게 끝나 최신 결과를 덮는 경쟁 상태
- 화면이 사라졌을 때 불필요한 요청 취소
- 페이지네이션과 무한 스크롤
- 데이터 캐싱과 재검증

### 화면 처리

```text
로딩 중  → 스켈레톤 또는 로딩 표시
성공     → 데이터 표시
빈 결과  → 빈 상태 안내
실패     → 오류와 재시도 버튼
```

### 핵심 정리

- 빈 배열은 오류가 아니라 성공한 빈 결과
- 서버 상태 관리 도구로 캐시, 중복 요청 제거, 재시도 등을 처리 가능

## 클라이언트 캐시와 서버 데이터 정합성

- 서버에서 받은 데이터를 클라이언트에 저장해 재사용
- 화면을 빠르게 표시하고 요청 횟수 감소
- 서버 데이터가 변경되면 캐시가 오래된 상태가 될 수 있음

```text
서버 원본 데이터 → API 요청 → 클라이언트 캐시
```

### 정합성을 맞추는 방법

- 일정 시간이 지나면 다시 요청
- 화면에 다시 진입할 때 요청
- 브라우저가 다시 활성화될 때 요청
- 데이터 변경 후 관련 캐시 무효화
- 주기적으로 요청
- WebSocket이나 SSE로 변경 사항 수신

### 데이터 변경 후 처리

```text
게시글 삭제 요청 성공
        ↓
게시글 목록 캐시 무효화 또는 직접 제거
        ↓
서버의 최신 데이터와 화면 일치
```

### 낙관적 업데이트

- 서버 응답을 기다리지 않고 화면을 먼저 변경
- 성공하면 변경 상태 유지
- 실패하면 이전 상태로 복구

```text
좋아요 클릭
  ↓
화면의 숫자를 즉시 증가
  ↓
서버 요청
  ├─ 성공: 유지
  └─ 실패: 이전 상태로 복구
```

### 핵심 정리

- 캐시는 빠르지만 서버 원본과 달라질 수 있음
- 변경 후 캐시 갱신·무효화로 정합성 유지
- 데이터 중요도와 변경 빈도에 따라 재요청 시점 결정

# 6주차 - Database

## 공통 키워드

### 1. RDB / NoSQL

#### RDB (Relational Database, 관계형 데이터베이스)

데이터를 행(Row)과 열(Column)로 이루어진 테이블(Table) 형태로 저장하고, 테이블 사이의 관계(Relation)를 이용해 데이터를 관리하는 데이터베이스이다.

- 데이터를 저장하기 전에 테이블의 구조(**스키마, Schema**)를 미리 정의해야 한다.
- **SQL**을 이용해 데이터를 조회하고 조작한다.
- 트랜잭션의 **ACID** 특성을 보장하여 데이터의 정합성(일관성)이 중요한 경우에 적합하다.
  - 예: 결제, 주문, 회원 정보 등
- 대표 DB: MySQL, PostgreSQL, Oracle

#### NoSQL (Not Only SQL)

테이블 형태가 아닌 다양한 형태로 데이터를 저장하는 데이터베이스이다.

- 스키마가 고정되어 있지 않아 데이터 구조를 유연하게 바꿀 수 있다.
- 서버를 여러 대로 늘리는 수평 확장(Scale-out)에 유리해 대용량 데이터나 빠른 처리 속도가 필요한 경우에 적합하다.
- 대신 RDB만큼 강한 정합성을 보장하지 않는 경우가 많다.

| 종류 | 저장 방식 | 대표 DB |
| --- | --- | --- |
| Key-Value | Key와 Value 한 쌍으로 저장 | Redis |
| Document | JSON과 비슷한 문서(Document) 형태로 저장 | MongoDB |
| Column-Family | 행이 아닌 열(Column) 단위로 묶어서 저장 | Cassandra, HBase |
| Graph | 노드(Node)와 관계(Edge)로 저장 | Neo4j |

#### RDB vs NoSQL

| 구분 | RDB | NoSQL |
| --- | --- | --- |
| 데이터 구조 | 테이블 (정해진 스키마) | Key-Value, Document 등 (유연한 스키마) |
| 확장 방식 | 주로 수직 확장(Scale-up) | 수평 확장(Scale-out)에 유리 |
| 정합성 | 강함 (ACID) | 상대적으로 약함 (대신 가용성/성능을 우선하는 경우가 많음) |
| 적합한 경우 | 데이터 구조가 명확하고 관계가 중요한 경우 | 데이터 구조가 자주 바뀌거나 대용량 데이터를 빠르게 처리해야 하는 경우 |


### 2. PK / FK

#### PK (Primary Key, 기본키)

테이블에서 각 행(Row)을 고유하게 식별하기 위한 컬럼이다.

- 중복된 값을 가질 수 없다. (**UNIQUE**)
- NULL 값을 가질 수 없다. (**NOT NULL**)
- 테이블마다 하나만 지정할 수 있다. (단, 여러 컬럼을 묶어서 하나의 PK로 만드는 복합키는 가능)
  - 예: 회원 테이블의 `user_id`

#### FK (Foreign Key, 외래키)

다른 테이블의 PK를 참조하는 컬럼으로, 테이블 사이의 관계를 만들어준다.

- 예: 주문 테이블의 `user_id`가 회원 테이블의 `user_id`(PK)를 참조
- FK를 통해 **참조 무결성**을 보장한다.
  - 참조 무결성: 참조하는 값이 실제로 존재해야 한다는 규칙
  - 예: 존재하지 않는 회원의 `user_id`로는 주문을 생성할 수 없다.
- 참조되고 있는 데이터를 삭제/수정할 때의 동작을 지정할 수 있다.
  - `CASCADE`: 참조되는 데이터가 삭제되면 참조하는 데이터도 함께 삭제
  - `RESTRICT`: 참조하는 데이터가 있으면 삭제할 수 없음
  - `SET NULL`: 참조되는 데이터가 삭제되면 FK 값을 NULL로 변경


### 3. 정규화 (Normalization)

데이터의 중복을 줄이고 데이터를 일관성 있게 관리하기 위해 테이블을 나누는 과정이다.

- 중복된 데이터가 있으면 데이터를 추가/수정/삭제할 때 문제가 생길 수 있는데, 이를 **이상 현상(Anomaly)** 이라고 한다.

#### 이상 현상 (Anomaly)

| 종류 | 설명 |
| --- | --- |
| 삽입 이상 | 불필요한 데이터까지 함께 넣어야 데이터를 추가할 수 있는 문제 |
| 갱신 이상 | 중복된 데이터 중 일부만 수정되어 데이터가 서로 달라지는 문제 |
| 삭제 이상 | 데이터를 삭제할 때 필요한 다른 데이터까지 함께 삭제되는 문제 |

#### 정규형 단계

| 정규형 | 조건 |
| --- | --- |
| 제1정규형 (1NF) | 모든 컬럼이 하나의 값(원자값)만 가져야 한다. (예: 한 칸에 `"축구, 농구"`처럼 여러 값 X) |
| 제2정규형 (2NF) | 1NF + PK의 일부에만 종속되는 컬럼이 없어야 한다. (부분 함수 종속 제거) |
| 제3정규형 (3NF) | 2NF + PK가 아닌 다른 컬럼에 종속되는 컬럼이 없어야 한다. (이행적 함수 종속 제거) |
| BCNF | 3NF + 모든 결정자가 후보키여야 한다. |

- **함수 종속**: A 값을 알면 B 값이 하나로 정해지는 관계 (A → B)
  - 예: `학번`을 알면 `이름`이 정해진다. (학번 → 이름)

#### 반정규화 (Denormalization)

- 정규화를 많이 하면 테이블이 잘게 나뉘기 때문에, 조회할 때 JOIN이 많아져 성능이 떨어질 수 있다.
- 그래서 조회 성능을 위해 일부러 데이터 중복을 허용하거나 테이블을 합치는 것을 반정규화라고 한다.


### 4. JOIN

두 개 이상의 테이블을 공통된 컬럼(주로 PK/FK)을 기준으로 연결해서 하나의 결과로 조회하는 것이다.

```sql
SELECT u.name, o.order_id
FROM users u
INNER JOIN orders o ON u.user_id = o.user_id;
```

| 종류 | 설명 |
| --- | --- |
| INNER JOIN | 두 테이블에서 조건이 일치하는 데이터만 조회 (교집합) |
| LEFT (OUTER) JOIN | 왼쪽 테이블의 데이터는 모두 조회하고, 오른쪽 테이블은 조건이 일치하는 데이터만 붙임 (없으면 NULL) |
| RIGHT (OUTER) JOIN | 오른쪽 테이블의 데이터는 모두 조회하고, 왼쪽 테이블은 조건이 일치하는 데이터만 붙임 (없으면 NULL) |
| FULL (OUTER) JOIN | 양쪽 테이블의 데이터를 모두 조회 (합집합, MySQL은 직접 지원하지 않음) |
| CROSS JOIN | 두 테이블의 모든 행을 조합 (A 행 개수 × B 행 개수) |
| SELF JOIN | 같은 테이블끼리 JOIN (예: 직원 테이블에서 직원과 상사 연결) |

- 예를 들어 주문을 한 번도 안 한 회원까지 모두 조회하고 싶다면 `INNER JOIN`이 아니라 `LEFT JOIN`을 사용해야 한다.


### 5. Index

테이블에서 원하는 데이터를 빠르게 찾기 위해 사용하는 자료구조이다.

- 책의 맨 뒤에 있는 **색인(찾아보기)** 과 비슷하다고 생각하면 된다.
- Index가 없으면 원하는 데이터를 찾기 위해 테이블 전체를 처음부터 끝까지 확인해야 한다. (**Full Table Scan**)
- Index가 있으면 정렬된 Index를 이용해 원하는 데이터의 위치를 빠르게 찾을 수 있다.
- 대부분의 RDB는 Index를 **B+Tree** 구조로 저장한다.

#### 장점

- `WHERE`, `ORDER BY`, `JOIN` 등에서 조회 속도가 빨라진다.

#### 단점

- Index도 따로 저장해야 하므로 추가 저장 공간이 필요하다.
- 데이터를 추가/수정/삭제(INSERT, UPDATE, DELETE)할 때마다 Index도 함께 갱신해야 하므로 쓰기 성능이 떨어질 수 있다.

#### Index를 걸면 좋은 컬럼

- 조회 조건(`WHERE`)이나 `JOIN`에 자주 사용되는 컬럼
- **카디널리티(Cardinality)** 가 높은 컬럼 (중복되는 값이 적은 컬럼)
  - 예: `성별`처럼 값의 종류가 적은 컬럼보다 `이메일`처럼 값이 거의 다 다른 컬럼이 Index 효과가 크다.
- 수정이 자주 일어나지 않는 컬럼


### 6. B+Tree

DB Index에서 주로 사용하는 트리 자료구조로, B-Tree를 개선한 형태이다.

#### B-Tree

- 하나의 노드가 여러 개의 Key와 자식 노드를 가질 수 있는 균형 트리(Balanced Tree)이다.
- 모든 Leaf 노드의 깊이가 같아서 어떤 데이터를 찾더라도 비슷한 시간(`O(log N)`)이 걸린다.
- 모든 노드(Root, Branch, Leaf)에 Key와 데이터가 함께 저장된다.

#### B+Tree의 특징

- **실제 데이터는 Leaf 노드에만 저장**하고, 중간 노드(Root, Branch)에는 길을 찾기 위한 Key만 저장한다.
  - 중간 노드에 데이터가 없어 하나의 노드에 더 많은 Key를 담을 수 있고, 그만큼 트리의 높이가 낮아져 디스크 접근 횟수가 줄어든다.
- **Leaf 노드끼리 연결 리스트(Linked List)로 연결**되어 있다.
  - 그래서 `BETWEEN`, `>`, `<` 같은 범위 검색을 할 때 Leaf 노드를 따라 순서대로 읽기만 하면 되어 효율적이다.

#### B-Tree vs B+Tree

| 구분 | B-Tree | B+Tree |
| --- | --- | --- |
| 데이터 저장 위치 | 모든 노드 | Leaf 노드에만 |
| Leaf 노드 연결 | X | O (연결 리스트) |
| 범위 검색 | 트리를 여러 번 오가야 해서 비효율적 | Leaf 노드를 순서대로 읽으면 되어 효율적 |
| 단일 검색 | 중간 노드에서 바로 찾을 수도 있음 | 항상 Leaf 노드까지 내려가야 함 (대신 검색 시간이 일정) |

#### 왜 Hash Table이 아니라 B+Tree를 쓸까?

- Hash Table은 `=` 검색은 `O(1)`로 매우 빠르지만, 데이터가 정렬되어 있지 않아 범위 검색이나 정렬(`ORDER BY`)에는 사용할 수 없다.
- DB에서는 범위 검색과 정렬이 자주 사용되기 때문에 B+Tree를 주로 사용한다.

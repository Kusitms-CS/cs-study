# 정규화와 JOIN

## 정규화

### 이상 현상

- 정규화를 왜 하는지는 안 했을 때 생기는 문제를 보면 됨. 수강 신청 테이블을 한 장으로 만들었다고 하면..

| 학번 | 이름 | 과목코드 | 과목명 | 교수 | 교수연구실 | 성적 |
| --- | --- | --- | --- | --- | --- | --- |
| 100 | 윤지 | CS101 | 자료구조 | 김교수 | A동 301 | A |
| 100 | 윤지 | CS201 | 운영체제 | 이교수 | B동 102 | B+ |
| 200 | 세윤 | CS101 | 자료구조 | 김교수 | A동 301 | A0 |

- 삽입 이상 : 새 과목 "CS301 데이터베이스"가 개설됐는데 수강생이 아직 없으면 넣을 수가 없음. 학번이 비어있어야 하는데 학번이 키의 일부라서
- 갱신 이상 : 김교수의 연구실이 바뀌면 김교수가 나오는 모든 행을 다 고쳐야 함. 하나라도 빠뜨리면 데이터가 서로 안 맞게 됨
- 삭제 이상 : 세윤이 CS101을 수강 취소해서 행을 지웠는데, 윤지도 취소하면 "CS101이 자료구조고 김교수가 가르친다"는 정보 자체가 사라짐
- 원인은 하나의 테이블에 서로 다른 주제(학생, 과목, 교수, 수강)가 섞여 있어서 같은 사실이 여러 행에 중복되기 때문
  - 정규화는 결국 "한 가지 사실은 한 곳에만 저장한다"를 단계적으로 달성하는 절차임

### 함수 종속

- 정규화의 기준이 되는 개념. X 값이 정해지면 Y 값이 하나로 정해질 때 "Y는 X에 함수 종속" 이라 하고 X → Y 로 씀
  - 학번 → 이름 (학번을 알면 이름이 정해짐)
  - 과목코드 → 과목명, 교수
  - 교수 → 교수연구실
  - (학번, 과목코드) → 성적
- 종류
  - 완전 함수 종속 : 복합 키 전체에 종속. (학번, 과목코드) → 성적. 학번만으로도, 과목코드만으로도 성적은 안 정해짐
  - 부분 함수 종속 : 복합 키의 일부에만 종속. (학번, 과목코드) 중 학번만으로 이름이 정해짐
  - 이행 함수 종속 : X → Y, Y → Z 이면 X → Z. 과목코드 → 교수 → 교수연구실
- 함수 종속은 데이터를 보고 추측하는 게 아니라 업무 규칙에서 나옴
  - "한 과목은 교수 한 명이 가르친다"는 규칙이 있어야 과목코드 → 교수가 성립함. 팀 티칭이 가능하면 이 종속은 깨지고 설계도 달라져야 함

### 1NF ~ BCNF

- 제1정규형 (1NF)
  - 모든 컬럼 값이 원자값이어야 함. 한 칸에 "CS101, CS201" 처럼 여러 값을 넣지 않음
  - 안 지키면 "CS101 듣는 학생 찾기" 같은 쿼리를 LIKE로 해야 하고 인덱스도 못 씀. 값 하나를 수정하려면 문자열을 파싱해야 함
  - 반복 그룹(과목1, 과목2, 과목3 컬럼)도 1NF 위반으로 봄. 4번째 과목이 생기면 컬럼을 추가해야 하니까
- 제2정규형 (2NF)
  - 1NF + 부분 함수 종속 제거
  - 위 테이블의 키는 (학번, 과목코드)인데 이름은 학번에만 종속됨 → 학생 테이블로 분리. 과목명, 교수, 연구실은 과목코드에만 종속됨 → 과목 테이블로 분리
  - 키가 단일 컬럼이면 부분 종속이 생길 수 없으므로 자동으로 만족함. 대리키를 PK로 쓰는 테이블은 2NF를 신경 쓸 일이 거의 없음

```
학생(학번, 이름)
과목(과목코드, 과목명, 교수, 교수연구실)
수강(학번, 과목코드, 성적)
```

- 제3정규형 (3NF)
  - 2NF + 이행 함수 종속 제거
  - 과목 테이블에서 과목코드 → 교수 → 교수연구실 이므로 교수연구실은 키가 아닌 교수에 종속됨 → 교수 테이블로 분리

```
학생(학번, 이름)
과목(과목코드, 과목명, 교수ID)
교수(교수ID, 교수명, 연구실)
수강(학번, 과목코드, 성적)
```

- BCNF (Boyce-Codd 정규형)
  - 3NF를 조금 더 엄격하게. 모든 결정자(화살표 왼쪽)가 후보키여야 함
  - 3NF인데 BCNF가 아닌 경우 : 수강(학번, 과목명, 교수) 테이블에서 (학번, 과목명) → 교수 이고 동시에 교수 → 과목명 일 때. 교수가 결정자인데 후보키가 아님
  - 후보키가 여러 개이고 서로 겹칠 때 생기는 드문 케이스라, 실무에서는 3NF까지 가면 거의 BCNF도 만족함
- 외우는 법
  - 키가 아닌 컬럼은 "키에, 전체 키에, 오직 키에만" 종속되어야 한다 (the key, the whole key, and nothing but the key)
  - 키에 → 1NF/2NF 전제, 전체 키에 → 2NF, 오직 키에만 → 3NF
- 4NF, 5NF도 있지만 다치 종속, 조인 종속 같은 특수한 상황이라 보통 3NF/BCNF까지만 다룸

### 반정규화

- 정규화를 하면 테이블이 여러 개로 쪼개지고, 읽을 때마다 조인이 필요해짐
  - 조인은 공짜가 아님. 테이블 수가 늘수록 쿼리가 복잡해지고 옵티마이저도 계획을 잘못 세울 확률이 올라감
- 그래서 읽기 성능을 위해 일부러 중복을 허용하는 것이 반정규화 (Denormalization)
  - 집계 컬럼 : 게시글 테이블에 댓글 수, 좋아요 수 컬럼을 두기. 목록 조회마다 COUNT 하지 않으려고
  - 조회용 중복 컬럼 : 주문 테이블에 회원 이름을 같이 저장. 주문 목록에서 회원 테이블 조인을 피하려고
  - 집계/통계 테이블 : 일별 매출, 월별 가입자 수를 미리 계산해두는 테이블
  - 테이블 병합 : 1:1 관계인 회원 - 회원상세를 하나로 합치기
- 요구사항 때문에 중복처럼 보이는 경우는 반정규화가 아님
  - 주문 테이블에 주문 당시의 상품명/가격을 복사해 두는 것 → 상품 정보가 나중에 바뀌어도 주문 내역은 당시 값으로 남아야 하므로, 이건 "같은 사실"이 아니라 "다른 시점의 사실"임
- 중복을 허용했으니 갱신 시 두 곳을 같이 바꿔야 하고, 그 책임은 애플리케이션으로 넘어옴
  - 댓글이 달릴 때 댓글 INSERT와 게시글의 댓글 수 UPDATE가 한 트랜잭션이어야 함
  - 그래도 어긋날 수 있으니 주기적으로 재계산하는 배치를 같이 두는 경우가 많음
- 순서가 중요함
  - 정규화는 쓰기 정합성, 반정규화는 읽기 성능을 위한 것. 둘 중 하나가 정답이 아니라 "일단 정규화하고, 측정해서 느린 곳만 반정규화"가 순서임
  - 처음부터 반정규화하면 어디가 중복인지 추적이 안 되고, 나중에 요구사항이 바뀌었을 때 되돌리기 어려움
  - NoSQL의 문서 모델링은 사실상 반정규화의 극단임. 읽을 모양대로 한 문서에 다 넣어두는 것

## JOIN

### 조인 종류

- 정규화로 쪼갠 테이블을 다시 합쳐서 읽는 연산. 두 테이블의 행을 조건에 따라 짝지음
- INNER JOIN : 양쪽에 모두 매칭되는 행만
- LEFT (OUTER) JOIN : 왼쪽 테이블은 전부, 오른쪽은 매칭되면 값 / 없으면 NULL
  - "주문이 없는 회원도 포함해서 회원 목록" 같은 경우
- RIGHT (OUTER) JOIN : LEFT의 반대. 테이블 순서를 바꾸면 LEFT로 쓸 수 있어서 잘 안 씀
- FULL OUTER JOIN : 양쪽 다 전부. MySQL은 지원하지 않아서 LEFT JOIN UNION RIGHT JOIN으로 흉내 냄
- CROSS JOIN : 조건 없이 모든 조합 (카티션 곱). M × N 행이 나옴. 조인 조건을 빠뜨리면 의도치 않게 이게 됨
- SELF JOIN : 같은 테이블끼리. 직원 - 상사 관계처럼 한 테이블 안에서 참조할 때

```sql
-- 주문이 없는 회원도 포함, 주문 수 집계
SELECT m.id, m.name, COUNT(o.id) AS order_count
FROM members m
LEFT JOIN orders o ON o.member_id = m.id
GROUP BY m.id, m.name;

-- 주문이 한 번도 없는 회원만 (안티 조인 패턴)
SELECT m.id, m.name
FROM members m
LEFT JOIN orders o ON o.member_id = m.id
WHERE o.id IS NULL;
```

- OUTER JOIN에서 조건을 ON에 쓰는 것과 WHERE에 쓰는 것은 결과가 다름
  - ON의 조건은 "짝지을 때" 적용되어서 매칭 안 되면 NULL로 남음
  - WHERE의 조건은 조인이 끝난 뒤 적용되어서 NULL인 행이 걸러짐. LEFT JOIN을 했는데 WHERE에서 오른쪽 테이블 컬럼으로 필터링하면 사실상 INNER JOIN이 됨

```sql
-- 모든 회원 + 2026년 주문만 붙임 (주문 없는 회원도 남음)
SELECT m.name, o.id
FROM members m
LEFT JOIN orders o ON o.member_id = m.id AND o.created_at >= '2026-01-01';

-- 2026년 주문이 있는 회원만 남음 (LEFT JOIN 의미가 사라짐)
SELECT m.name, o.id
FROM members m
LEFT JOIN orders o ON o.member_id = m.id
WHERE o.created_at >= '2026-01-01';
```

### 조인 알고리즘

[https://dev.mysql.com/doc/refman/8.0/en/nested-loop-joins.html](https://dev.mysql.com/doc/refman/8.0/en/nested-loop-joins.html)

- SQL에 조인을 적으면 DBMS가 내부적으로는 아래 방법 중 하나로 실행함
- Nested Loop Join (NLJ)
  - 이중 for문. 바깥 테이블(드라이빙 테이블)의 행을 하나씩 읽으면서, 안쪽 테이블(드리븐 테이블)에서 매칭되는 행을 찾음

```
for row_a in A:                 # 드라이빙 테이블
    for row_b in B where B.key = row_a.key:   # 드리븐 테이블, 인덱스로 탐색
        emit(row_a, row_b)
```

  - 드리븐 테이블의 조인 컬럼에 인덱스가 있어야 함. 없으면 드라이빙 테이블 행 수만큼 드리븐 테이블을 풀스캔하게 됨 (1,000 × 1,000,000 번 읽기)
  - 그래서 옵티마이저는 보통 WHERE로 거른 뒤 행 수가 적은 쪽을 드라이빙 테이블로 잡음. 바깥 루프 횟수를 줄여야 하니까
  - MySQL이 전통적으로 쓰던 유일한 방식. 결과 행이 적고 인덱스가 있는 OLTP 쿼리에 잘 맞음
- Block Nested Loop (BNL)
  - 드리븐 테이블에 인덱스가 없을 때, 드라이빙 테이블 행을 조인 버퍼에 여러 개 모아두고 드리븐 테이블을 한 번 훑으면서 버퍼의 행들과 한꺼번에 비교. 드리븐 테이블 스캔 횟수를 줄이는 방식
  - MySQL 8.0.20부터는 이 자리를 Hash Join이 대신함
- Hash Join

[https://dev.mysql.com/doc/refman/8.0/en/hash-joins.html](https://dev.mysql.com/doc/refman/8.0/en/hash-joins.html)

  - 작은 쪽 테이블로 메모리에 해시 테이블을 만들고(build), 큰 쪽 테이블을 한 번 훑으면서 해시 테이블에서 짝을 찾음(probe)
  - 인덱스가 없어도 되고, 두 테이블을 각각 한 번씩만 읽으면 됨. 등가 조건(=)에서만 가능
  - 해시 테이블이 메모리(join_buffer_size)를 넘으면 디스크에 나눠 쓰면서 처리하므로 느려짐
  - MySQL 8.0.18부터 지원. 대량 데이터를 인덱스 없이 조인하는 집계/배치 쿼리에서 효과가 큼
- Sort Merge Join
  - 양쪽을 조인 컬럼으로 정렬한 뒤 나란히 읽으면서 합침. 이미 정렬된 인덱스가 있으면 정렬 비용이 없어 유리함
  - PostgreSQL, Oracle은 지원하고 MySQL은 안 씀
- 정리하면..
  - 드리븐 테이블에 인덱스 있음 + 결과 행이 적음 → NLJ
  - 인덱스 없음 + 대량 데이터 등가 조인 → Hash Join
  - 어떤 걸 골랐는지는 EXPLAIN의 Extra에서 확인 (`Using join buffer (hash join)`). [쿼리 최적화](./query-optimization.md)에서 자세히

### SQL 실행 순서

[https://blog.jooq.org/a-beginners-guide-to-the-true-order-of-sql-operations/](https://blog.jooq.org/a-beginners-guide-to-the-true-order-of-sql-operations/)

- SQL은 SELECT부터 쓰지만 논리적으로는 아래 순서로 처리됨

1. FROM / JOIN : 대상 테이블을 정하고 합침
2. WHERE : 행 단위 필터링
3. GROUP BY : 그룹핑
4. HAVING : 그룹 단위 필터링
5. SELECT : 컬럼 선택, 별칭 부여, 윈도우 함수 계산
6. DISTINCT
7. ORDER BY : 정렬
8. LIMIT / OFFSET

- 이 순서를 알면 설명되는 것들
  - WHERE에서는 SELECT의 별칭을 못 쓰고 ORDER BY에서는 쓸 수 있음. 별칭이 5단계에서 생기니까
  - 집계 함수 결과로 필터링하려면 WHERE가 아니라 HAVING을 써야 함. WHERE 시점에는 아직 그룹이 없음
  - WHERE로 거를 수 있는 조건을 HAVING에 쓰면 그룹핑을 다 하고 나서 버리는 거라 낭비. 행 조건은 WHERE, 그룹 조건은 HAVING
  - 조인 → 필터링 순서라서, 조인 전에 행 수를 줄일 수 있으면(서브쿼리, 인덱스) 조인 비용이 줄어듦. 실제 실행은 옵티마이저가 순서를 바꾸기도 하지만 결과는 이 논리 순서와 같아야 함
- ORM에서 연관 엔티티를 조인 없이 하나씩 조회하면 N+1 문제가 생김. 조인(fetch join)으로 한 번에 가져오는 게 해결책 중 하나 (10주차에서 자세히)

### 면접 질문으로 정리하면..

- Q. INNER JOIN과 LEFT JOIN의 차이는? → 매칭 안 되는 행을 버리느냐 NULL로 남기느냐. LEFT JOIN + WHERE 조건 함정까지 말하면 좋음
- Q. 조인은 내부적으로 어떻게 동작하나요? → NLJ 설명 + 드리븐 테이블 인덱스의 중요성 + 8.0 Hash Join
- Q. WHERE와 HAVING의 차이는? → 실행 순서로 설명. 행 필터 vs 그룹 필터

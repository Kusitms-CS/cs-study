# TCP·UDP / 3-way·4-way Handshake / Port

## TCP

- **프로토콜** : 클라이언트와 서버가 정보를 교환할 수 있도록 하는 메시지 형식에 대한 규칙. HTTP / IP / TCP / UDP 모두 프로토콜임
  - 수신 호스트가 메시지를 이해하려면 설계된 규칙에 따라 작성된 형식이어야 함 (예 : `256.256.256.256` 은 규칙을 깨므로 존재하지 않는 IP)
- **TCP (Transmission Control Protocol, 전송 제어 프로토콜)**
  - IP 가 IP 주소와 패킷 규칙으로 복잡한 인터넷 망에서 통신하게 해 준다면, TCP 는 IP 만으로는 부족하거나 불안정한 부분(패킷 순서 뒤바뀜, 유실)을 커버해 **패킷 전송을 제어하고 신뢰성을 보증**하는 프로토콜
  - IP 와 TCP 는 별개의 규칙임. IP 규칙대로 목적지까지 도달했으면, TCP 규칙대로 올바르게 도착했는지·정확히 누구에게 전달돼야 하는지 하나하나 따짐
  - 은행 업무, 메일처럼 반드시 수신자가 정보를 받아야 하는 신뢰성 있는 통신에 사용
- 택배 비유 : IP 는 배달 주소지, TCP 는 목적지까지 문제없이 가도록 순서·검증·전송 제어 정보를 담은 **택배 스티커**
  - 포장 과정 : 전송 데이터 → TCP 포장 → IP 포장 → 이더넷 포장 → 상대 서버에서 하나씩 풀며 수신 (캡슐화)
- TCP 는 통신을 시작할 때와 종료할 때 서로 준비가 되어 있는지 반드시 먼저 물어보고, 패킷 순서를 정한 뒤에야 본격적인 통신을 시작함 → **3-way / 4-way Handshake**
  - 한 번 통신하는 데 Handshake 를 두 번 하므로 신뢰성이 과할 정도로 보장됨

### TCP Flag 종류

패킷 안의 인증 플래그 값을 보고 클라이언트와 서버가 서로 보낸 패킷의 순서와 제대로 받았는지를 검증함. "내가 너한테 전송했다는 인증 도장" 정도로 생각하면 됨

| Flag | tcpdump 표기 | 설명 |
| --- | --- | --- |
| SYN | `S` | 접속 요청을 할 때 보내는 패킷. TCP 접속 시 가장 먼저 보냄 |
| ACK | `.` | 상대방의 패킷을 잘 받았다고 알려주는 패킷. 다른 플래그와 같이 출력되기도 함 (SYN-ACK 는 `S.`) |
| PSH | `P` | 데이터를 즉시 목적지로 보내라는 의미 |
| FIN | `F` | 접속 종료를 위한 플래그. 현재 접속을 끊고자 할 때 사용 |

### TCP 전송 제어 기법

- TCP 는 원활한 통신을 위해 전송 흐름을 제어하는 기능을 프로토콜 자체에 포함함
  - TCP 가 없었다면 개발자가 데이터를 어떤 단위로 보낼지, 패킷이 유실되면 어떻게 예외 처리할지 일일이 신경 써야 했음 → 덕분에 상위 동작에만 집중 가능
- **흐름 제어 (Flow Control)**
  - 수신자가 처리할 수 있는 데이터 속도가 다르므로, 송신 측이 수신 측의 처리 속도를 파악해 얼마나 빠르게·어느 정도의 데이터를 보낼지 제어
  - **슬라이딩 윈도우(Sliding Window)** 방식 : Window 라는 데이터를 담는 공간을 동적으로 조절해 데이터량을 조절
- **오류 제어 (Error Control)**
  - 통신 도중 데이터가 유실되거나 잘못된 데이터가 수신되었을 때 대처
  - **Go-Back-N** : 오류가 발생한 지점을 파악해 그 부분부터 다시 순서대로 보냄
  - **Selective Repeat** : 에러 난 데이터만 재전송하고, 그 전에 받아 둔 순서가 잘못된 데이터 버퍼를 재정렬함
- **혼잡 제어 (Congestion Control)**
  - 네트워크가 불안정해 재전송이 반복되면 네트워크가 붕괴될 수 있음
  - 네트워크 혼잡 상태가 감지되면 송신 측의 전송 데이터 크기를 조절해 전송량을 줄임
  - Tahoe, Reno, New Reno, Cubic, Elastic-TCP 등 다양한 기법이 존재

### TCP 헤더 구성

오래 전에 설계되었고 기능이 많아 헤더가 거의 꽉 차 있음

- **Source Port** : 데이터를 생성한 애플리케이션이 사용하는 포트 번호
- **Destination Port** : 목적지 애플리케이션이 사용하는 포트 번호
- **Sequence Number** : 세그먼트 순서를 맞추기 위한 필드
- **Acknowledgement Number** : 다음 세그먼트 수신 준비 및 모든 데이터 수신 확인
- **Data Offset** : TCP 헤더의 크기 (5~15, 32bit 단위 → 160~480bit)
- **Reserved** : 차후 사용을 위한 예약 필드
- **Control Flags** (SYN, ACK, FIN …) : 긴급, 혼잡, 확인, 수신 거부 등의 기능
- **Window size** : 수신자가 한 번에 받을 수 있는 데이터의 양. 송신자는 Window size 만큼은 ACK 를 기다리지 않고 연속 전송 가능
- **Checksum** : 세그먼트 내용의 유효성과 손상 여부 검사

## UDP

- **UDP (User Datagram Protocol, 사용자 데이터그램 프로토콜)**
  - **데이터그램 방식** : 각 패킷 간 순서가 존재하지 않는 독립적인 패킷을 사용
  - 패킷의 목적지만 정해져 있으면 중간 경로는 신경 쓰지 않으므로 Handshake 같은 **연결 설정이 필요 없음**
  - TCP 가 신뢰성을 위해 거치는 과정을 생략하므로 속도가 빠를 수밖에 없음 → 실시간 영상 스트리밍처럼 고용량 데이터를 다루는 곳에 사용
  - 방송·동영상은 중간에 끊길지언정 바로바로 빠르게 송출하는 것이 더 중요하기 때문
- 배경 : 인터넷이 발전하며 동영상·음악 같은 멀티미디어를 전송하게 되어 데이터가 커지고 빠른 통신이 필요해짐
  - HTTP 2.0 은 한 번 연결한 TCP 회선을 길게 유지하고 스트림 형태로 보내는 식으로 극복했지만, TCP 자체의 근본적 특징 때문에 속도 한계가 있었음
- `nc -u` 로 UDP 전송을 캡처해 보면 잘 받았다는 응답 패킷 없이 **보내기만 하고 끝**임 (로그 한 줄)

### UDP 헤더 구성

데이터 전송 자체에만 초점을 맞춰 설계되어 헤더에 들어 있는 게 거의 없음 ("하얀 도화지" 비유)

- **Source Port** : 데이터를 생성한 애플리케이션이 사용하는 포트 번호
- **Destination Port** : 목적지 애플리케이션이 사용하는 포트 번호
- **Length** : 패킷의 길이
- **Checksum** : 송신된 자료의 무결성을 보호하는 단순한 중복 검사. TCP 와 달리 **사용해도 되고 안 해도 되는 옵션**

### UDP 는 신뢰성이 없는 게 아니라 탑재를 안 했을 뿐

- "UDP 는 빠르지만 신뢰성이 없어 사용성이 적다"는 이해는 명확하지 않음
- UDP 자체는 헤더에 든 게 없어 신뢰성이 낮고 제어 기능도 없지만, 개발자가 애플리케이션에서 어떻게 구현하느냐에 따라 TCP 와 비슷한 수준의 기능을 가질 수 있음 → **커스터마이징이 가능**한 것이 진짜 장점

### HTTP/3 가 TCP 를 버리고 UDP(QUIC) 를 택한 이유

- TCP 의 구조적 한계
  - 여러 파일의 패킷을 동시다발적으로 교환하거나, 모바일처럼 네트워크 환경을 바꿔 가며 통신할 것을 상상하지 못한 시기에 설계됨 → 와이파이를 바꾸면 새 커넥션을 맺어야 해서 끊김
  - 패킷은 신뢰성을 위해 무조건 순서대로 처리되어야 하고, 이전 패킷을 파싱하기 전까지 다음 패킷을 처리할 수 없음. 중간에 유실되면 다시 받아야 함
  - 이로 인한 병목이 **HOLB (Head of Line Blocking)**. TCP 설계상 어쩔 수 없는 문제라 HTTP/1.1 뿐 아니라 HTTP/2 도 갖고 있던 고질적 문제
- **QUIC (Quick UDP Internet Connections)** : UDP 기반으로 TCP + TLS + HTTP 의 기능을 모두 구현한 프로토콜. HTTP/3 가 UDP 를 쓴다는 말은 정확히는 QUIC 을 채택했다는 뜻
  - 3-way Handshake 를 거치지 않음
  - **RTT (Round Trip Time)** : 클라이언트 요청 → 서버 처리 → 클라이언트 응답의 한 사이클
    - TCP 는 연결 생성에 1 RTT, TLS 암호화까지 하면 TLS 자체 핸드쉐이크가 더해져 총 3 RTT
    - QUIC 은 TLS 를 내포하고 있어 연결 설정 정보와 함께 데이터까지 보내므로 첫 연결에 **1 RTT**, 한 번 연결에 성공하면 서버가 설정을 캐싱해 두어 다음 연결은 **0 RTT** 로 바로 통신 가능
  - 패킷 손실 감지 시간 단축, 클라이언트 IP 가 바뀌어도 연결 유지 (모바일에서 와이파이를 바꿔도 끊김 없음)
- 2022년 11월 네이버가 한국 최초로 HTTP/3 도입

## TCP vs UDP 비교

| 구분 | TCP | UDP |
| --- | --- | --- |
| 연결 방식 | 연결형 서비스 | 비연결형 서비스 |
| 패킷 교환 | 가상 회선 방식 | 데이터그램 방식 |
| 전송 순서 보장 | 보장함 | 보장하지 않음 |
| 신뢰성 | 높음 | 낮음 |
| 전송 속도 | 느림 | 빠름 |
| 연결 설정 | 3-way / 4-way Handshake | 없음 |
| 헤더 | Port, Seq/Ack, Flags, Window, Checksum 등 (풀방) | Port, Length, Checksum(옵션) |
| 사용 예 | 은행 업무, 메일, 파일 전송 | 실시간 스트리밍, 방송, HTTP/3 (QUIC) |

## 3-way Handshake

통신을 **시작**할 때 거치는 과정

1. 클라이언트가 접속을 요청하는 `SYN` 패킷을 보냄 → 응답을 기다리며 **SYN_SENT** 상태
2. **LISTEN** 상태였던 서버가 SYN 을 받으면 요청을 수락하는 `ACK` 와 함께 `SYN` 을 보냄 (서버도 클라이언트에 접속해야 양방향 통신이 되기 때문) → 클라이언트의 ACK 를 기다리며 **SYN_RCVD** 상태
3. 클라이언트가 다시 서버에 `ACK` 를 보냄 → 이후 **ESTABLISHED** 상태가 되어 데이터 통신 가능

- **seq 번호** : 패킷의 전달 순서를 식별하는 순서 번호. 운영체제가 랜덤하게 생성해 SYN 패킷에 담아 보내고, 서버는 동기화 답신으로 seq 를 +1 해서 ack 에 담아 응답함
- 데이터 통신 과정 (ESTABLISHED 이후)
  - 클라이언트 → 서버 : 데이터 전송 (`PSH ACK`)
  - 서버 → 클라이언트 : 잘 받았다는 `ACK`
  - 클라이언트가 ACK 를 못 받으면 제대로 송신되지 않은 것으로 판단하고 **재전송**

## 4-way Handshake

통신을 **종료**할 때 거치는 과정

1. 연결된 상태에서 클라이언트가 접속을 끊기 위해 `CLOSE()` 호출 → `FIN` 플래그 전송, 클라이언트는 **FIN_WAIT1** 상태
2. 서버는 클라이언트가 CLOSE 한다는 것을 알고 **CLOSE_WAIT** 상태로 바꾼 뒤 `ACK` 전송
   - 서버에서 클라이언트로 보낼 남은 데이터가 있으면 이때 나머지를 모두 전송
3. ACK 를 받은 클라이언트는 **FIN_WAIT2** 상태. 서버는 `CLOSE()` 를 호출하고 `FIN` 을 클라이언트에 보냄
4. 서버도 연결을 닫았다는 신호를 받은 클라이언트가 `ACK` 를 보낸 뒤 **TIME_WAIT** 상태로 전환 → 모든 것이 끝나면 **CLOSED**

- 실제 리눅스에서 `tcpdump` 로 캡처해 보면 서버가 먼저 종료 신호를 보내기도 하고, 이때 ACK 와 FIN 이 하나(`FIN ACK`)로 합쳐져 3번의 패킷으로 끝나기도 함

### 직접 확인해 보기 (Linux)

```bash
# 설치
$ apt install tcpdump        # Ubuntu
$ yum install tcpdump        # CentOS

# 터미널 1 : 80 포트 패킷 캡처
$ tcpdump -i any -nn port 80

# 터미널 2 : TCP 로 전송
$ echo "Hello World" | nc naver.com 80

# 터미널 2 : UDP 로 전송 (-u)
$ echo "Hello World" | nc -u naver.com 80
```

- 로그의 각 줄은 `보낸 쪽 > 받은 쪽` 형식이고, `Flags [S]` 처럼 대괄호 안 대문자가 플래그를 뜻함 (`S`, `S.`, `.`, `P`, `F`)
- TCP 는 3-way handshake → 데이터 → 4-way handshake 전체가 찍히고, UDP 는 응답 없이 한 줄로 끝남

## Port

- TCP 는 IP 정보뿐 아니라 **Port** 를 이용해 연결함. 도착한 데이터가 단말의 어느 입구(Port)로 들어가야 하는지 알아야 연결할 수 있기 때문
- 예 : HTTP 문서를 주고받으려면 3306 이나 21 이 아닌 **80 Port** 로 연결해야 함
- 항구 비유 : 부산항에 도착한 화물선은 어선항이 아니라 상항에 들어가야 함
- TCP / UDP 헤더 모두 **Source Port**(데이터를 생성한 애플리케이션의 포트)와 **Destination Port**(목적지 애플리케이션의 포트)를 가짐

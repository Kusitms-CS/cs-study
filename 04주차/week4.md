# Network: 주소를 찾고, 연결하고, 요청을 주고받기까지

지난주에는 실행 중인 프로그램이 메모리를 어떻게 사용하는지 살펴봤다. 이번에는 그 프로그램이 **다른 컴퓨터의 프로그램과 어떻게 통신하는지**를 따라가 봤다. 브라우저에서 주소를 입력한 뒤 서버에 연결하기까지의 흐름을 기준으로 OSI 계층, IP, TCP/UDP, DNS, Port를 연결해 정리했다. 마지막에는 백엔드 서버가 연결을 받아들이고 유지하는 방법까지 살펴봤다.

---

## 1. OSI 7 Layer와 TCP/IP

### 네트워크를 왜 계층으로 나눌까?

한 컴퓨터의 데이터를 다른 컴퓨터에 전달하려면 여러 문제가 해결되어야 한다.

```text
어떤 응용 프로그램의 데이터인가?       → 응용 계층
상대 프로그램과 어떻게 주고받을까?     → 전송 계층
어느 컴퓨터로 보내야 할까?            → 인터넷/네트워크 계층
현재 연결된 구간에서 어떻게 전달할까?  → 링크 계층
```

각 계층이 맡은 문제를 분리하면, 예를 들어 HTTP를 사용하는 애플리케이션이 네트워크 카드의 세부 동작을 직접 구현하지 않아도 된다.

OSI 7계층은 통신 과정을 설명하는 **참조 모델**이고, 실제 인터넷 프로토콜을 이해할 때는 보통 TCP/IP 계층 모델을 함께 사용한다. 두 모델이 정확히 일대일로 대응하는 것은 아니다.

| OSI 계층 | 주요 역할 | TCP/IP에서의 대략적인 위치 | 예시 |
| --- | --- | --- | --- |
| 7. 응용 | 애플리케이션 간 통신 규칙 | 응용 | HTTP, DNS |
| 6. 표현 | 데이터 표현과 변환 | 응용 | 문자 인코딩, TLS와 연관된 기능 |
| 5. 세션 | 대화 상태 관리 | 응용 | 세션 관리 기능 |
| 4. 전송 | 프로세스 간 전달 | 전송 | TCP, UDP |
| 3. 네트워크 | 호스트 주소와 경로 | 인터넷 | IP |
| 2. 데이터 링크 | 같은 링크에서 프레임 전달 | 링크 | Ethernet, Wi-Fi |
| 1. 물리 | 신호 전송 | 링크의 물리 매체 | 케이블, 무선 신호 |

표현·세션 계층의 기능을 특정 프로토콜 하나에 기계적으로 대응시키기보다는, 실제 TCP/IP에서는 응용 계층과 관련 라이브러리에 걸쳐 구현될 수 있다고 이해하는 편이 정확하다.

데이터를 보낼 때는 위 계층에서 아래 계층으로 내려가며 각 계층의 제어 정보가 붙는다. 받는 쪽에서는 반대로 이를 해석한다.

```text
HTTP 요청 데이터
    ↓ TCP 헤더: 출발지/목적지 Port, 순서 번호 등
TCP 세그먼트
    ↓ IP 헤더: 출발지/목적지 IP 주소 등
IP 패킷
    ↓ 링크 헤더/트레일러
프레임 → 물리 매체 → 상대 호스트
```

이 과정을 **캡슐화**라고 한다. 실제 전송 중에는 MTU, 분할, 터널링 등에 따라 패킷의 모습이 더 복잡해질 수 있지만, 기본적인 역할 구분에는 이 흐름이 유용하다.

## 2. IP: 어느 컴퓨터로 보낼까?

IP(Internet Protocol)는 패킷에 출발지와 목적지 **IP 주소**를 담아 네트워크 사이로 전달한다. 라우터는 목적지 주소를 보고 다음 경로를 고른다.

```text
내 컴퓨터 → 공유기/라우터 → 여러 네트워크 → 서버
               목적지 IP를 기준으로 다음 경로 선택
```

IPv4 주소는 32비트이고, IPv6 주소는 128비트다. `192.0.2.10`과 `2001:db8::10`은 각각 문서에서 예시로 쓰는 IPv4, IPv6 주소다. 서버가 여러 IP 주소를 가질 수도 있고, 하나의 공인 IP 뒤에 여러 장치가 있을 수도 있으므로 **IP 주소 = 물리적인 컴퓨터 한 대**라고 단정하면 안 된다.

IP 자체는 전달을 *시도*하는 서비스다. 패킷이 중간에 사라지거나, 순서가 바뀌거나, 중복될 수 있다. 따라서 IP만으로는 애플리케이션이 원하는 순서와 전달 보장을 얻지 못한다. 필요하다면 그 위 계층에서 처리해야 한다.

### 같은 IP에 여러 프로그램이 있다면?

IP가 목적지 호스트를 찾는 데 쓰인다면, **Port는 그 호스트에서 통신할 서비스를 구분**하는 데 쓰인다. 그래서 웹 서버에 요청할 때는 보통 `IP 주소 + Port`가 필요하다. Port는 뒤에서 더 자세히 살펴본다.

## 3. TCP와 UDP: 어떤 방식으로 전달할까?

TCP와 UDP는 모두 전송 계층 프로토콜이지만 제공하는 기능이 다르다.

| 구분 | TCP | UDP |
| --- | --- | --- |
| 통신 방식 | 연결을 설정하고 바이트 스트림 전송 | 연결 설정 없이 데이터그램 전송 |
| 데이터 경계 | 바이트 스트림이라 메시지 경계가 보존되지 않음 | 데이터그램 경계가 보존됨 |
| 손실·순서 | 확인 응답, 재전송, 순서 제어 제공 | 프로토콜 자체에서는 보장하지 않음 |
| 전송량 조절 | 흐름 제어와 혼잡 제어 제공 | 프로토콜 자체에서는 제공하지 않음 |
| 사용 예 | 전통적인 HTTP/1.1, HTTP/2, 데이터베이스 연결 | DNS 질의, 실시간 통신, QUIC의 기반 |

### TCP에서 '신뢰성'은 무엇일까?

TCP는 데이터를 보낸 뒤 상대가 받은 범위를 ACK로 확인하고, 손실이 의심되면 재전송한다. 순서 번호로 순서를 복원하고, 수신 측의 처리 가능량과 네트워크 혼잡도도 고려한다.

```text
애플리케이션이 쓴 바이트들
       ↓
TCP가 나누어 보내고 순서·재전송 관리
       ↓
받는 애플리케이션에는 순서대로 이어진 바이트 스트림 제공
```

단, `write()` 한 번이 상대의 `read()` 한 번과 정확히 대응하지는 않는다. TCP는 **메시지가 아니라 바이트 스트림**을 제공한다. 따라서 애플리케이션 프로토콜은 메시지 길이, 구분자 같은 방법으로 데이터의 끝을 정의해야 한다. 또한 TCP가 데이터를 전달했다고 해서 상대 애플리케이션의 비즈니스 처리가 성공했다는 뜻은 아니다.

### UDP는 언제 유용할까?

UDP는 데이터그램을 보내는 단순한 전송 방식이다. TCP처럼 연결 설정, 순서 복원, 재전송을 프로토콜 자체에서 수행하지 않는다. 이런 기능이 필요하면 애플리케이션이나 상위 프로토콜이 구현해야 한다.

```text
실시간 음성:
오래된 소리를 늦게 재전송받는 것보다 최신 소리를 제때 받는 편이 유리할 수 있음

QUIC:
UDP 위에서 필요한 신뢰성·혼잡 제어 등을 직접 구현
```

따라서 **TCP는 무조건 느리고 UDP는 무조건 빠르다**는 식으로 외우기보다, 애플리케이션이 어떤 전달 특성을 필요로 하는지 봐야 한다.

## 4. TCP 3-way Handshake: 연결은 어떻게 시작할까?

TCP 통신을 시작할 때 양쪽은 순서 번호를 교환하고 연결 상태를 맞춘다. 이를 흔히 3-way Handshake라고 부른다.

```text
클라이언트                           서버
    | -------- SYN, seq=x --------> |
    | <--- SYN+ACK, seq=y, ack=x+1 - |
    | -------- ACK, ack=y+1 -------> |
    |          데이터 전송 가능        |
```

1. 클라이언트가 `SYN`으로 연결을 요청하고 자신의 초기 순서 번호를 알린다.
2. 서버가 `SYN+ACK`로 요청을 확인하면서 자신의 초기 순서 번호를 알린다.
3. 클라이언트가 `ACK`를 보내 서버의 순서 번호를 확인한다.

여기서 순서 번호는 TCP 바이트 스트림의 위치를 추적하는 데 쓰인다. `SYN` 자체도 순서 번호 공간을 하나 사용하므로 예시의 ACK가 `x+1`, `y+1`이 된다.

핸드셰이크가 끝나면 **TCP 연결**이 성립한다. 이는 HTTP 요청/응답의 시작과는 별개의 단계다. 이미 열려 있는 TCP 연결을 재사용한다면 HTTP 요청마다 3-way Handshake를 다시 하지 않을 수도 있다.

## 5. TCP 연결 종료: 왜 4-way라고 부를까?

TCP는 양방향 통신이다. 한쪽이 더 이상 보낼 데이터가 없다고 알려도 반대쪽은 아직 데이터를 보내고 있을 수 있다. 일반적인 종료 흐름을 그리면 다음과 같다.

```text
먼저 닫는 쪽                          나중에 닫는 쪽
    | -------- FIN ----------------> |
    | <------- ACK ----------------- |
    |     반대 방향 전송은 가능        |
    | <------- FIN ----------------- |
    | -------- ACK ----------------> |
    |       TIME-WAIT 후 종료          |
```

`FIN`은 **내가 보내는 방향을 종료**한다는 뜻이다. 상대는 이를 ACK로 확인하고, 자신도 보낼 데이터를 마치면 FIN을 보낸다. 마지막 ACK를 보낸 쪽은 일반적으로 `TIME-WAIT` 상태에 머문다. 지연된 이전 연결의 세그먼트가 새 연결에 영향을 주지 않도록 하고, 마지막 ACK가 유실되었을 때 상대의 FIN 재전송에 응답할 시간을 확보하기 위해서다.

다만 **항상 네 개의 패킷으로 끝나는 것은 아니다.** 상대의 ACK와 FIN이 합쳐질 수 있고, 양쪽이 동시에 종료를 시작할 수도 있으며, 오류로 `RST`를 보내 종료하는 경우도 있다. '4-way'는 종료의 대표적인 예시라고 이해했다.

## 6. DNS: 도메인 이름을 IP 주소로 바꾸기

사람은 `example.com` 같은 이름을 기억하기 쉽지만, IP로 패킷을 보내려면 목적지 주소가 필요하다. DNS(Domain Name System)는 이름과 관련된 정보를 조회하는 분산 시스템이다.

대표적인 레코드는 다음과 같다.

| 레코드 | 의미 |
| --- | --- |
| `A` | 이름에 연결된 IPv4 주소 |
| `AAAA` | 이름에 연결된 IPv6 주소 |
| `CNAME` | 다른 정식 이름을 가리킴 |
| `MX` | 메일을 받을 서버에 관한 정보 |

DNS 조회를 단순화하면 다음과 같다.

```text
애플리케이션
    ↓ 운영체제의 이름 해석 기능·로컬 캐시 등 확인
재귀 DNS 리졸버
    ↓ 캐시에 답이 없으면 필요한 권한 서버를 찾아 질의
Root → TLD(.com 등) → 도메인의 권한 DNS 서버
    ↓
레코드 응답 → IP 주소를 이용해 연결 시도
```

클라이언트는 보통 설정된 재귀 리졸버에 답을 요청하고, 리졸버가 필요한 조회를 대신 수행한다. Root 서버가 곧바로 모든 도메인의 최종 IP를 알려주는 것은 아니다. 실제 조회에서는 캐시, 위임 정보, CNAME 등이 개입하므로 매번 Root부터 순서대로 방문하지 않는다.

응답은 TTL에 따라 캐시될 수 있다. 따라서 DNS 레코드를 바꿔도 모든 사용자에게 즉시 같은 결과가 보이지 않을 수 있다. DNS는 UDP와 TCP를 모두 사용할 수 있고, DNS over TLS/HTTPS 같은 전송 방식도 있다. **DNS는 언제나 UDP 53번 포트만 쓴다**는 설명은 정확하지 않다.

## 7. Port: 같은 서버의 어느 서비스인가?

Port는 TCP나 UDP에서 사용하는 16비트 번호로, 범위는 `0~65535`다. `0`은 일반적인 원격 서비스의 목적지 포트로 쓰기보다 운영체제에 임시 포트 할당을 요청할 때 흔히 사용한다.

```text
서버 IP: 203.0.113.10
TCP 443 → HTTPS 서비스
TCP 5432 → PostgreSQL 서비스의 흔한 기본 설정
```

위 숫자는 **관례나 설정값**이다. 서비스가 반드시 그 포트를 사용해야 하는 것은 아니다. 또한 같은 번호라도 TCP 53과 UDP 53은 서로 다른 전송 프로토콜의 포트다.

클라이언트가 서버의 `443`으로 연결할 때는 클라이언트에도 운영체제가 고른 출발지 포트가 생긴다. TCP 연결은 보통 아래 조합으로 구분한다.

```text
(출발지 IP, 출발지 Port, 목적지 IP, 목적지 Port)
```

그래서 한 서버의 `443` 포트로 여러 클라이언트가 동시에 연결할 수 있다. 각 연결의 출발지 주소나 포트가 다르기 때문이다. 단, 이 조합은 **같은 전송 프로토콜 안에서**의 구분이며 TCP와 UDP까지 함께 논할 때는 프로토콜도 구분해야 한다.

## 8. Socket: 프로그램이 네트워크를 사용하는 창구

Socket은 애플리케이션이 운영체제의 네트워크 기능을 사용할 때 다루는 통신 끝점이다. TCP 서버의 전형적인 흐름은 다음과 같다.

```text
서버: socket() → bind(IP, Port) → listen() → accept()
클라이언트: socket() → connect(서버 IP, Port)

accept() 성공
    ↓
서버는 해당 클라이언트와 통신할 연결 Socket을 얻음
    ↓
read()/write() → close()
```

서버가 `listen()` 중인 Socket과 `accept()`가 돌려준 **개별 연결 Socket**은 역할이 다르다. 하나의 리스닝 Socket이 여러 연결을 받아들이고, 각 연결은 별도의 Socket으로 다룬다.

Java로 감을 잡으면 다음과 같다. 실제 서비스에서는 예외 처리, 종료, 동시 연결 처리가 더 필요하다.

```java
try (ServerSocket server = new ServerSocket(8080)) {
    try (Socket client = server.accept()) {
        // client.getInputStream()과 getOutputStream()으로 통신
    }
}
```

이 코드는 연결 하나를 처리하고 서버를 닫는 **개념 예시**다. 지속적으로 요청을 받는 서버는 반복해서 연결을 받고 여러 연결을 함께 관리한다.

## 9. 서버는 많은 Connection을 어떻게 관리할까?

새 연결이 오면 서버는 이를 받아들여 요청을 읽고 응답한 뒤, 정책에 따라 연결을 유지하거나 닫는다.

```text
Listening Socket
    ↓ accept
Connected Socket
    ↓ 요청 읽기 / 처리 / 응답 쓰기
재사용을 위해 유지 또는 종료
```

연결 하나마다 전용 스레드를 두는 방식은 이해하기 쉽지만, 연결이 많아지면 스레드의 메모리와 스케줄링 비용이 커진다. 다른 방식으로는 제한된 스레드 풀이나 비동기 I/O, 이벤트 루프를 사용한다. **연결 수와 스레드 수가 반드시 일대일인 것은 아니다.** 어떤 방식을 쓰든 느린 요청이 처리 자원을 오래 점유하지 않도록 상한을 둬야 한다.

동시 연결이 늘어나면 Socket뿐 아니라 파일 디스크립터, 버퍼 메모리, 애플리케이션 작업 자원도 사용한다. 서버는 수용 가능한 연결 수와 작업량을 정하고, 초과 시 대기·거절·종료 등의 정책을 세워야 한다. `listen()`의 backlog도 연결을 기다리는 큐와 관련 있지만, 그 값 하나가 서버의 **전체 동시 연결 한도**를 의미하지는 않는다.

HTTP의 연결 재사용은 여러 요청에서 TCP 연결을 다시 여는 비용을 줄인다. 하지만 유휴 연결을 무한히 유지하면 자원을 차지하므로 유휴 시간과 최대 연결 수를 함께 관리해야 한다. 연결 풀은 클라이언트가 서버나 DB에 대한 연결을 재사용할 때에도 같은 맥락에서 등장한다.

## 10. Connection Timeout: 어디서 얼마나 기다릴까?

네트워크 작업이 끝나지 않을 때 무한히 기다리면 요청과 서버 자원이 묶인다. **어느 단계의 기다림인지**에 따라 타임아웃을 따로 설정한다.

| 종류 | 기다리는 상황 | 예시 |
| --- | --- | --- |
| Connect timeout | TCP 연결 수립을 기다림 | 연결할 수 없는 서버에 접속 시도 |
| Read/response timeout | 연결 후 데이터나 응답을 기다림 | 외부 API가 응답을 늦게 보냄 |
| Write timeout | 데이터를 보내는 작업의 진행을 기다림 | 상대가 데이터를 읽지 않음 |
| Idle timeout | 연결이 열린 채 활동이 없음 | 재사용 연결이 오랫동안 유휴 상태 |
| 전체 요청 기한 | 여러 단계를 합친 작업의 총 시간 | DNS, 연결, 응답을 모두 포함한 외부 호출 |

타임아웃 이름과 정확한 적용 범위는 사용하는 HTTP 클라이언트, 서버, 프록시, DB 드라이버마다 다르다. 예를 들어 **연결 타임아웃을 설정했다고 응답 대기 시간까지 제한되는 것은 아니다.** 또한 DNS 조회, 연결 풀 대기 등이 전체 기한에 포함되는지 라이브러리 설정을 확인해야 한다.

```text
외부 API 호출
  ├─ DNS 조회
  ├─ 연결 풀 대기 또는 새 TCP 연결
  ├─ 요청 전송
  └─ 응답 대기
          ↑
각 단계의 제한 + 전체 요청 기한을 함께 고려
```

TCP Keepalive는 장시간 유휴 상태인 연결의 생존 여부를 확인하는 기능이고, HTTP 연결 재사용(Keep-Alive)이나 애플리케이션의 응답 타임아웃과는 목적이 다르다. 연결이 살아 있다고 해도 원하는 응답이 제때 온다는 보장은 없다.

타임아웃 값은 무조건 짧게 잡는 것이 아니라 정상 요청의 지연 시간, 호출 대상의 특성, 사용자가 기다릴 수 있는 시간에 맞춰 정해야 한다. 타임아웃 이후 재시도할 경우에는 중복 요청이 발생할 수 있으므로 작업의 멱등성과 재시도 횟수도 함께 생각해야 한다.

# 전체 흐름 정리

브라우저에서 `https://example.com`에 접속하는 상황을 단순화하면 다음과 같다.

```text
도메인 입력
    ↓
DNS로 접속할 IP 주소 조회
    ↓
서버 IP의 목적지 Port(HTTPS라면 보통 TCP 443) 선택
    ↓
TCP 3-way Handshake로 연결 수립
    ↓
HTTPS라면 TLS Handshake
    ↓
HTTP 요청/응답
    ↓
연결 재사용 또는 TCP 연결 종료
```

이 흐름은 **TCP를 사용하는 HTTPS 연결의 예시**다. HTTP/3은 UDP 기반 QUIC을 사용하므로 동일한 TCP 핸드셰이크 경로를 따르지 않는다. 중간에 프록시나 CDN이 있다면 실제 연결 대상 역시 원본 서버와 다를 수 있다.

이번 주제를 공부하면서 `IP가 컴퓨터를 찾고 Port가 프로그램을 찾는다`는 한 줄 설명이 출발점으로는 유용하지만, 실제 문제를 풀기에는 부족하다는 것을 알게 됐다. DNS가 어떤 IP를 돌려줬는지, TCP 연결이 수립됐는지, TLS와 HTTP 중 어디에서 지연되는지, 서버의 연결과 타임아웃 정책이 무엇인지 구분해야 장애 원인을 좁힐 수 있다.

# 4주차 - Network

## 1. OSI 7 Layer / TCP-IP

- 네트워크 통신 과정을 **계층별로 나눠 각 계층이 맡은 역할만 수행**하도록 정의한 참조 모델
- 계층을 분리하면 **한 계층의 구현이 바뀌어도 다른 계층에 영향을 주지 않고**, 문제가 생겼을 때 원인 계층을 좁혀서 디버깅하기 쉬움
- 데이터는 송신 측에서 **위 계층 → 아래 계층으로 내려가며 각 계층의 헤더가 붙고(캡슐화)**, 수신 측에서는 **아래 → 위로 올라가며 헤더가 제거(역캡슐화)됨**

### 📍 OSI 7 Layer

| 계층 | 이름                    | 역할                                                | 대표 프로토콜/장비    | 전송 단위 |
| ---- | ----------------------- | --------------------------------------------------- | --------------------- | --------- |
| 7    | 응용 (Application)      | 사용자와 가장 가까운 서비스 제공                    | HTTP, FTP, SMTP, DNS  | Data      |
| 6    | 표현 (Presentation)     | 데이터 형식 변환, 인코딩, 암호화, 압축              | TLS/SSL(경계), JPEG   | Data      |
| 5    | 세션 (Session)          | 연결(세션) 수립/유지/종료 관리                      | NetBIOS, RPC          | Data      |
| 4    | 전송 (Transport)        | 프로세스 간(End-to-End) 신뢰성/흐름/오류 제어       | TCP, UDP              | Segment   |
| 3    | 네트워크 (Network)      | 목적지까지의 경로 결정(라우팅), 논리 주소           | IP, ICMP, 라우터      | Packet    |
| 2    | 데이터 링크 (Data Link) | 같은 네트워크 내 노드 간 전달, 물리 주소, 오류 검출 | Ethernet, MAC, 스위치 | Frame     |
| 1    | 물리 (Physical)         | 비트를 전기/광 신호로 전송                          | 케이블, 허브, 리피터  | Bit       |

### 📍 TCP/IP 4 Layer

- 실제 인터넷에서 사용되는 프로토콜 모음을 4개 계층으로 단순화한 모델

| TCP/IP 계층              | 대응하는 OSI 계층              | 주요 프로토콜              |
| ------------------------ | ------------------------------ | -------------------------- |
| Application              | 7 (응용) + 6 (표현) + 5 (세션) | HTTP, HTTPS, FTP, DNS, SSH |
| Transport                | 4 (전송)                       | TCP, UDP                   |
| Internet                 | 3 (네트워크)                   | IP, ICMP, ARP              |
| Network Interface (Link) | 2 (데이터 링크) + 1 (물리)     | Ethernet, Wi-Fi            |

### 💡 OSI 7 Layer와 TCP/IP의 차이

**⇒ OSI 7 Layer는 통신 과정을 이해하기 위한 이론적인 참조 모델이고, TCP/IP는 실제 인터넷에서 사용되는 프로토콜 구현체를 기반으로 만든 실용적인 모델임. 이 때문에 TCP/IP는 OSI의 상위 3계층(응용/표현/세션)을 Application 하나로 합치고, 하위 2계층(데이터 링크/물리)을 Network Interface 하나로 합쳐 4계층으로 단순화함**

## 2. IP (Internet Protocol)

- 네트워크 계층(3계층)에서 **출발지에서 목적지까지 패킷이 전달되도록 주소를 지정하고 경로를 찾는 프로토콜**
- **비연결성(Connectionless), 비신뢰성(Unreliable):** 패킷이 잘 도착했는지, 순서대로 도착했는지 보장하지 않음 → 이런 신뢰성 보장은 상위 계층인 TCP가 담당

### 📍 IP 주소

- **IPv4:** 32비트 주소 (예: `192.168.0.1`), 약 43억 개 → 주소 고갈 문제 발생
- **IPv6:** 128비트 주소 (예: `2001:db8::1`), 사실상 무한에 가까운 주소 공간 제공
- **Public IP(공인 IP):** 인터넷에서 유일한 공인 주소 / **Private IP(사설 IP):** 내부 네트워크에서만 사용하는 사설 주소 (`10.x.x.x`, `172.16~31.x.x`, `192.168.x.x`)
- **NAT (Network Address Translation):** 공유기가 여러 사설 IP를 하나의 공인 IP로 변환해주는 기술 → IPv4 주소 고갈을 완화

### 📍 IP vs MAC 주소

| 구분 | IP 주소                               | MAC 주소                          |
| ---- | ------------------------------------- | --------------------------------- |
| 계층 | 3계층 (네트워크)                      | 2계층 (데이터 링크)               |
| 성격 | 논리 주소 (네트워크 환경에 따라 변경) | 물리 주소 (NIC에 부여된 고유 값)  |
| 역할 | 최종 목적지까지의 경로 결정           | 같은 네트워크 내 다음 장치로 전달 |

### 💡 IP 주소가 있는데 MAC 주소도 필요한 이유

**⇒ IP는 최종 목적지를 가리키는 논리 주소이고, 실제로 패킷이 한 구간(hop)씩 전달될 때는 바로 다음 장치의 물리 주소(MAC)가 필요하기 때문. 패킷이 라우터를 거칠 때마다 IP 주소(출발지/목적지)는 그대로 유지되지만 MAC 주소는 구간마다 다음 hop의 것으로 바뀜. 같은 네트워크에서 IP에 해당하는 MAC 주소를 알아내는 데 ARP를 사용함**

## 3. TCP / UDP

- 전송 계층(4계층)에서 **프로세스(Port) 간 통신**을 담당하는 프로토콜

### 📍 TCP (Transmission Control Protocol)

- **연결 지향(Connection-oriented):** 데이터를 주고받기 전에 연결을 먼저 수립(3-way Handshake)
- **신뢰성 보장:** 순서 보장(Sequence Number), 손실 시 재전송(ACK), 오류 검출(Checksum)
- **흐름 제어(Flow Control):** 수신 측 버퍼가 넘치지 않도록 윈도우 크기로 전송량 조절
- **혼잡 제어(Congestion Control):** 네트워크가 혼잡해지지 않도록 전송 속도 조절 (Slow Start, AIMD 등)

### 📍 UDP (User Datagram Protocol)

- **비연결형(Connectionless):** 연결 수립 없이 데이터를 바로 전송
- 순서 보장, 재전송, 흐름/혼잡 제어가 **없음** → 헤더가 단순(8byte)하고 빠름

### 📍 TCP vs UDP

| 구분        | TCP                               | UDP                                     |
| ----------- | --------------------------------- | --------------------------------------- |
| 연결        | 연결 지향 (3-way Handshake)       | 비연결형                                |
| 신뢰성      | 보장 (재전송, 순서 보장)          | 보장하지 않음                           |
| 속도        | 상대적으로 느림                   | 상대적으로 빠름                         |
| 헤더 크기   | 20byte 이상                       | 8byte                                   |
| 제어        | 흐름 제어, 혼잡 제어 있음         | 없음                                    |
| 전송 단위   | Segment (바이트 스트림)           | Datagram (메시지 경계 유지)             |
| 대표 사용처 | 웹(HTTP/HTTPS), 이메일, 파일 전송 | 실시간 스트리밍, 온라인 게임, DNS, VoIP |

### 💡 UDP는 신뢰성이 없는데도 왜 사용하나요?

**⇒ 신뢰성 보장(연결 수립, 재전송, 순서 정렬)에는 그만큼의 지연과 오버헤드가 따르기 때문. 실시간 영상/음성/게임처럼 일부 패킷이 유실되더라도 최신 데이터를 빠르게 받는 것이 더 중요한 경우에는 재전송을 기다리는 TCP보다 UDP가 적합함. 또한 HTTP/3(QUIC)처럼 UDP 위에서 애플리케이션 계층이 직접 신뢰성을 구현해 TCP의 단점(Head-of-Line Blocking, 긴 연결 수립 시간 등)을 피하는 방식도 등장함**

## 4. 3-way / 4-way Handshake

### 📍 3-way Handshake (연결 수립)

1. **SYN:** 클라이언트가 서버에 연결 요청 (`SYN`, seq=x)
2. **SYN + ACK:** 서버가 요청을 수락하며 자신의 연결 요청도 함께 전송 (`SYN`, seq=y, `ACK`, ack=x+1)
3. **ACK:** 클라이언트가 서버의 응답을 확인 (`ACK`, ack=y+1) → 연결 수립(ESTABLISHED)

### 💡 왜 2-way가 아니라 3-way인가요?

**⇒ 양쪽 모두 "내가 보낼 수 있고, 상대가 받을 수 있다"는 것을 확인하고 초기 시퀀스 번호(ISN)를 서로 동기화해야 하기 때문. 2-way만 하면 서버는 자신의 SYN+ACK가 클라이언트에게 도착했는지 확인할 수 없고, 지연되어 뒤늦게 도착한 오래된 SYN 요청에도 연결을 열어버려 자원을 낭비할 수 있음**

### 📍 4-way Handshake (연결 종료)

1. **FIN:** 종료를 원하는 쪽(클라이언트)이 `FIN` 전송 → `FIN_WAIT_1`
2. **ACK:** 서버가 `ACK`로 응답 → 클라이언트 `FIN_WAIT_2`, 서버는 `CLOSE_WAIT`
   - 서버는 아직 보낼 데이터가 남아 있을 수 있어 이 시점에 바로 종료하지 않음
3. **FIN:** 서버가 남은 데이터를 모두 전송한 뒤 `FIN` 전송 → `LAST_ACK`
4. **ACK:** 클라이언트가 `ACK`로 응답 → `TIME_WAIT` 후 연결 종료(`CLOSED`)

### 📍 TIME_WAIT

- 마지막 ACK를 보낸 클라이언트가 **일정 시간(보통 2MSL, 약 60초) 동안 바로 종료하지 않고 대기**하는 상태

### 💡 4-way Handshake에서 TIME_WAIT가 필요한 이유

**⇒ (1) 마지막 ACK가 유실되어 서버가 FIN을 재전송하더라도 다시 ACK를 보내줄 수 있어야 하고, (2) 같은 IP/Port 조합으로 새 연결이 만들어졌을 때 이전 연결의 지연된 패킷이 새 연결에 섞여 들어오는 것을 방지하기 위함**

## 5. DNS (Domain Name System)

- 사람이 읽기 쉬운 **도메인 이름(예: `www.google.com`)을 IP 주소로 변환**해주는 분산 계층형 네임 시스템
- 응용 계층 프로토콜이며, 주로 **UDP 53번 포트**를 사용 (응답 크기가 크거나 Zone Transfer 등에는 TCP 사용)

### 📍 DNS 서버 계층 구조

| 구분                     | 설명                                                                                   |
| ------------------------ | -------------------------------------------------------------------------------------- |
| Root DNS Server          | 최상위 서버, TLD DNS 서버의 주소를 알려줌                                              |
| TLD DNS Server           | `.com`, `.kr`, `.org` 등 최상위 도메인을 관리, Authoritative 서버 주소를 알려줌        |
| Authoritative DNS Server | 해당 도메인의 실제 IP 주소 정보를 가지고 있는 최종 서버                                |
| Recursive Resolver       | 클라이언트를 대신해 위 서버들을 차례로 질의하고 결과를 캐싱하는 서버 (ISP, 8.8.8.8 등) |

### 📍 DNS 조회 과정 (www.example.com)

1. 브라우저 캐시 → OS 캐시 → hosts 파일 확인 (있으면 바로 사용)
2. 없으면 **Recursive Resolver**에 질의
3. Resolver가 **Root → TLD(.com) → Authoritative** 서버 순으로 질의하며 IP 주소를 찾음
4. 찾은 IP 주소를 클라이언트에 응답하고, **TTL(Time To Live)** 동안 캐싱

### 📍 주요 DNS 레코드

| 레코드 | 설명                                            |
| ------ | ----------------------------------------------- |
| A      | 도메인 → IPv4 주소                              |
| AAAA   | 도메인 → IPv6 주소                              |
| CNAME  | 도메인의 별칭(Alias), 다른 도메인 이름으로 연결 |
| MX     | 메일 서버 지정                                  |
| NS     | 해당 도메인의 네임서버 지정                     |
| TXT    | 임의의 텍스트 정보 (도메인 소유 인증, SPF 등)   |

### 💡 DNS가 계층 구조와 캐싱을 사용하는 이유

**⇒ 전 세계 모든 도메인 정보를 한 서버에서 관리하면 트래픽이 집중되고 장애 시 전체 인터넷이 마비되므로 역할을 계층적으로 분산함. 또한 매번 Root부터 질의하면 응답이 느리고 부하가 크기 때문에 각 단계(브라우저, OS, Resolver)에서 TTL만큼 결과를 캐싱해 응답 속도를 높이고 DNS 서버의 부하를 줄임**

## 6. Port

- 하나의 IP 주소 안에서 **어떤 프로세스(애플리케이션)로 데이터를 전달할지 구분하는 논리적인 번호** (16비트, 0 ~ 65535)
- IP가 "어느 컴퓨터로 갈 것인가"라면 Port는 **"그 컴퓨터의 어떤 프로그램으로 갈 것인가"를 의미**
- 네트워크 통신은 **`IP:Port` 조합(Socket)으로 프로세스를 식별**

### 📍 Port 번호 범위

| 범위          | 이름                     | 설명                                             |
| ------------- | ------------------------ | ------------------------------------------------ |
| 0 ~ 1023      | Well-known Port          | 잘 알려진 표준 서비스용 (관리자 권한 필요)       |
| 1024 ~ 49151  | Registered Port          | 특정 애플리케이션이 등록해서 사용                |
| 49152 ~ 65535 | Dynamic / Ephemeral Port | 클라이언트가 연결할 때 OS가 임시로 할당하는 포트 |

### 📍 대표적인 Well-known Port

| Port  | 프로토콜 | Port | 프로토콜 |
| ----- | -------- | ---- | -------- |
| 20/21 | FTP      | 53   | DNS      |
| 22    | SSH      | 80   | HTTP     |
| 25    | SMTP     | 443  | HTTPS    |

### 💡 하나의 서버가 어떻게 수많은 클라이언트의 연결을 동시에 처리하나요?

**⇒ TCP 연결은 `(출발지 IP, 출발지 Port, 목적지 IP, 목적지 Port)` 4-tuple로 식별되기 때문. 서버는 80/443 같은 하나의 포트로 listen하지만, 클라이언트마다 IP와 임시 포트(Ephemeral Port)가 달라 각각 서로 다른 연결로 구분할 수 있음. 같은 포트를 여러 클라이언트가 동시에 사용해도 충돌하지 않는 이유가 이것임**

# Frontend 심화

## 1. 브라우저 Network 요청

- 브라우저 주소창에 URL을 입력하고 화면이 그려지기까지, **위에서 정리한 네트워크 개념들이 순서대로 동작**함

### 📍 URL 입력 후 페이지가 뜨기까지의 과정

1. **URL 파싱:** 프로토콜(https), 도메인, 포트, 경로 등을 분리하고, 캐시(HSTS 등) 확인
2. **DNS 조회:** 도메인 → IP 주소 변환 (브라우저/OS 캐시 → Resolver → Root/TLD/Authoritative)
3. **TCP 연결:** 서버와 3-way Handshake로 연결 수립
4. **TLS Handshake (HTTPS):** 인증서 검증 및 세션 키 교환으로 암호화 채널 수립
5. **HTTP 요청/응답:** 브라우저가 HTTP 요청을 보내고 서버가 HTML을 응답
6. **렌더링:** HTML 파싱 → DOM/CSSOM 생성 → 렌더 트리 → 레이아웃 → 페인트 (중간에 CSS/JS/이미지 등 추가 리소스 요청)

### 📍 HTTP 버전별 차이

| 버전     | 전송 프로토콜 | 특징                                                                                     |
| -------- | ------------- | ---------------------------------------------------------------------------------------- |
| HTTP/1.1 | TCP           | Keep-Alive로 연결 재사용, 하지만 한 연결에서 요청/응답이 순차 처리되어 HOL Blocking 발생 |
| HTTP/2   | TCP           | 하나의 연결에서 **멀티플렉싱**(여러 요청 동시 처리), 헤더 압축(HPACK), 서버 푸시         |
| HTTP/3   | UDP (QUIC)    | TCP 수준의 HOL Blocking 해소, 연결 수립 시간 단축(0-RTT/1-RTT), 연결 마이그레이션        |

### 📍 브라우저의 요청 최적화

- **Connection 재사용(Keep-Alive):** 한 번 맺은 TCP 연결을 재사용해 Handshake 비용 절감
- **도메인당 동시 연결 수 제한:** HTTP/1.1에서는 도메인당 보통 6개 연결로 제한 → 도메인 샤딩 등의 우회 기법이 쓰였으나 HTTP/2에서는 불필요
- **캐싱:** `Cache-Control`, `ETag` 등을 이용해 불필요한 요청을 줄이거나 조건부 요청(304)으로 대체
- **리소스 힌트:** `preconnect`, `dns-prefetch`, `preload` 등으로 미리 DNS/연결/리소스를 준비

### 💡 HTTP/2를 쓰면 왜 더 빨라지나요?

**⇒ HTTP/1.1은 한 연결에서 응답이 앞선 요청 순서대로 처리되어 앞의 요청이 느리면 뒤 요청이 막히는 HOL Blocking이 있고, 이를 피하려고 여러 TCP 연결을 열어야 해서 Handshake 비용이 늘어남. HTTP/2는 하나의 TCP 연결 안에서 여러 요청/응답을 스트림 단위로 쪼개 동시에 주고받는 멀티플렉싱과 헤더 압축을 지원해 연결 수와 전송량을 줄임. 다만 TCP 자체의 패킷 손실 시 HOL Blocking은 남아있어 이를 해결하려고 UDP 기반의 HTTP/3가 등장함**

## 2. WebSocket

- **하나의 TCP 연결 위에서 클라이언트와 서버가 양방향(Full-Duplex)으로 실시간 통신**할 수 있게 해주는 프로토콜
- HTTP는 **클라이언트가 요청해야만 서버가 응답**하는 단방향 구조라 서버가 먼저 데이터를 보낼 수 없는 한계가 있는데, WebSocket으로 이를 해결
- 채팅, 실시간 협업 도구, 온라인 게임, 주식 시세 등 **저지연 양방향 통신이 필요한 서비스**에 사용

### 📍 동작 방식

1. **Handshake (HTTP Upgrade):** 처음에는 일반 HTTP 요청으로 시작해 `Upgrade: websocket`, `Connection: Upgrade` 헤더로 프로토콜 전환을 요청
2. 서버가 `101 Switching Protocols`로 응답하면 **HTTP 연결이 WebSocket 연결로 전환**됨
3. 이후 같은 TCP 연결을 유지한 채 **가벼운 프레임(Frame) 단위로 양쪽에서 자유롭게 메시지 송수신**
4. 어느 한쪽이 Close 프레임을 보내면 연결 종료

```js
const ws = new WebSocket("wss://example.com/chat");

ws.onopen = () => ws.send("hello"); // 연결 수립 후 메시지 전송
ws.onmessage = (e) => console.log(e.data); // 서버가 먼저 보낸 메시지도 수신
ws.onclose = () => console.log("closed");
```

### 📍 HTTP vs WebSocket

| 구분          | HTTP                                | WebSocket                                   |
| ------------- | ----------------------------------- | ------------------------------------------- |
| 통신 방향     | 단방향 (Request → Response)         | 양방향 (Full-Duplex)                        |
| 연결 방식     | 요청마다 (또는 Keep-Alive로 재사용) | 최초 Handshake 이후 연결 지속               |
| 헤더 오버헤드 | 요청마다 큰 헤더 포함               | 최초 Handshake 이후 작은 프레임 헤더만 사용 |
| 서버 Push     | 불가 (Polling 등 우회 필요)         | 가능                                        |
| 상태          | Stateless                           | Stateful (연결 유지)                        |

### 💡 Polling / Long Polling 대신 WebSocket을 쓰는 이유

**⇒ Polling은 주기적으로 요청을 보내 변경 여부를 확인하므로 데이터가 없어도 요청/응답 헤더 오버헤드가 계속 발생하고 실시간성도 폴링 주기에 제한됨. Long Polling은 응답을 대기시켜 지연을 줄이지만 매번 연결을 새로 맺어야 함. WebSocket은 한 번 연결한 뒤 필요한 순간에 바로 메시지를 주고받아 지연과 오버헤드가 작음. 다만 연결을 계속 유지해야 하므로 서버 자원(연결 수) 부담이 있고, 연결 끊김 시 재연결 로직을 직접 구현해야 함**

## 3. SSE (Server-Sent Events)

- **서버에서 클라이언트로 데이터를 단방향으로 지속적으로 전송**하는 기술 (Server → Client)
- 일반 **HTTP 연결을 끊지 않고 유지**하며, 서버가 `Content-Type: text/event-stream` 형식으로 이벤트를 계속 흘려보내는 방식
- 알림, 실시간 피드, 진행률 표시, LLM 응답 스트리밍 등 **서버가 일방적으로 데이터를 push하는 경우**에 적합

### 📍 동작 방식

1. 클라이언트가 `EventSource`로 서버에 HTTP 요청을 보냄
2. 서버가 `Content-Type: text/event-stream`으로 응답하고 **연결을 닫지 않고 유지**
3. 서버가 이벤트가 생길 때마다 `data: ...\n\n` 형식으로 텍스트를 전송
4. 연결이 끊기면 브라우저가 **자동으로 재연결**을 시도하며, `Last-Event-ID` 헤더로 마지막에 받은 이벤트 이후부터 이어받기 가능

```js
const es = new EventSource("/events");

es.onmessage = (e) => console.log(e.data); // 서버가 보낸 이벤트 수신
es.addEventListener("notice", (e) => console.log(e.data)); // 이름 있는 이벤트
es.onerror = () => console.log("연결 오류, 브라우저가 자동 재연결 시도");
```

### 📍 WebSocket vs SSE

| 구분          | WebSocket                                         | SSE                                             |
| ------------- | ------------------------------------------------- | ----------------------------------------------- |
| 통신 방향     | 양방향 (Full-Duplex)                              | 단방향 (Server → Client)                        |
| 프로토콜      | `ws://`, `wss://` (HTTP Upgrade 후 별도 프로토콜) | 일반 HTTP                                       |
| 데이터 형식   | 텍스트 + 바이너리                                 | 텍스트(UTF-8)만 가능                            |
| 자동 재연결   | 직접 구현 필요                                    | 브라우저가 기본 제공 (`EventSource`)            |
| 인프라 호환성 | 프록시/방화벽 설정이 필요한 경우 있음             | 일반 HTTP라 호환성이 좋음, HTTP/2와 궁합이 좋음 |
| 적합한 사례   | 채팅, 게임, 협업 편집                             | 알림, 실시간 피드, 스트리밍 응답                |

### 💡 WebSocket과 SSE 중 무엇을 선택해야 하나요?

**⇒ 클라이언트도 서버로 자주 메시지를 보내야 하는 양방향 통신(채팅, 게임, 협업 도구)이라면 WebSocket, 서버에서 클라이언트로 일방적으로 데이터를 밀어주는 경우(알림, 시세, 진행률, LLM 스트리밍)라면 구현이 단순하고 자동 재연결과 기존 HTTP 인프라를 그대로 활용할 수 있는 SSE가 더 적합함. 단, HTTP/1.1에서는 SSE도 도메인당 동시 연결 수 제한(약 6개)에 걸릴 수 있으므로 HTTP/2 사용을 권장함**

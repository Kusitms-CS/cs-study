# 4주차 - Network

## 1. OSI 7 Layer / TCP-IP

### 구조

```text
OSI 7계층                  TCP/IP 4계층
7 Application  ┐
6 Presentation ├────────── Application
5 Session      ┘
4 Transport    ────────── Transport
3 Network      ────────── Internet
2 Data Link    ┐
1 Physical     ┘────────── Network Access
```

### 특징

- 데이터 통신 과정을 계층별로 나눠서 역할을 분리한 모델
- 각 계층은 자기 아래 계층이 어떻게 동작하는지 몰라도 되도록 설계됨
- 실제 인터넷은 이론적인 OSI 7계층보다, 이를 단순화한 TCP/IP 4계층 모델을 기준으로 동작

### 정리

- 통신 과정을 여러 층으로 쪼개서, 층마다 자기 역할만 신경 쓰면 되게 만든 구조
- 예를 들어 HTTP(Application)는 아래에서 TCP가 어떻게 전송하는지 몰라도 되고, TCP도 IP가 어떻게 길을 찾는지 몰라도 됨
- OSI는 이론적인 7계층 모델이고, 실제로 쓰이는 건 이걸 단순화한 TCP/IP 4계층

---

## 2. IP

### 구조

```text
출발지 IP → [라우터] → [라우터] → ... → 목적지 IP
```

### 특징

- 네트워크 상에서 각 장치를 구분하는 주소
- 데이터를 목적지까지 전달할 경로를 찾는 역할(라우팅)을 담당하지만, 도착 자체를 보장하지는 않음
- IPv4(32비트), IPv6(128비트) 두 가지 버전이 있음

### 정리

- 인터넷에서 컴퓨터마다 붙는 주소이고, 이 주소를 보고 데이터가 갈 길을 찾아감
- IP 혼자서는 데이터가 제대로 도착했는지, 순서가 맞는지 확인해주지 않음 → 그 역할은 위 계층인 TCP가 담당

---

## 3. TCP / UDP

### 구조

```text
TCP: 연결 설정 → 데이터 전송(순서/확인) → 연결 종료
UDP: 연결 없이 바로 전송
```

### 특징

- TCP: 연결을 맺고 데이터가 순서대로 빠짐없이 도착했는지 확인하며 전송(신뢰성 O), 그만큼 속도는 상대적으로 느림
- UDP: 연결 없이 바로 데이터를 보냄(신뢰성 X), 확인 절차가 없어서 더 빠름

### 정리

- TCP는 데이터를 확실하게 순서대로 보내는 대신 느리고, UDP는 확인 절차 없이 빠르게 보내는 대신 중간에 데이터가 빠지거나 순서가 바뀔 수 있음
- 그래서 정확성이 중요한 곳엔 TCP(파일 전송, 웹 요청), 속도가 더 중요한 실시간 서비스(스트리밍, 게임)엔 UDP를 선택해서 씀

## 4. 3-way / 4-way Handshake

### 구조

```text
[3-way Handshake - 연결]
Client → SYN      → Server
Client ← SYN+ACK  ← Server
Client → ACK      → Server

[4-way Handshake - 종료]
Client → FIN → Server
Client ← ACK ← Server
Client ← FIN ← Server
Client → ACK → Server
```

### 특징

- 3-way Handshake: TCP 연결을 시작하기 전에 서로 통신할 준비가 됐는지 확인하는 과정
- 4-way Handshake: 연결을 끊을 때 양쪽 모두 더 보낼 데이터가 없는지 확인하고 종료하는 과정
- 종료 과정이 한 단계 더 많은 이유는 양쪽이 각자 독립적으로 종료 의사를 밝혀야 하기 때문

### 정리

- 연결을 시작할 때는 "보낼게 → 좋아, 받을게 → 그럼 시작할게" 이렇게 3번 확인하고 시작함
- 끊을 때는 이쪽에서 끊자고 하면 저쪽이 일단 알겠다고만 하고, 저쪽도 준비되면 따로 끊자고 해야 해서 확인이 4번으로 늘어남

## 5. DNS

### 구조

```text
도메인 이름(example.com) 입력
        ↓
DNS 서버에 물어봄
        ↓
IP 주소(93.184.216.34) 받음
        ↓
그 IP로 실제 요청 전송
```

### 특징

- 사람이 외우기 쉬운 도메인 이름을 실제 통신에 필요한 IP 주소로 바꿔주는 시스템
- 매번 DNS 서버에 묻지 않도록 브라우저/OS 단에서 결과를 잠시 저장(캐싱)해둠
- 도메인 하나가 바로 최종 IP를 아는 게 아니라, 여러 단계를 거쳐 찾아감

### 정리

- 사람이 쓰는 도메인 이름을 컴퓨터가 실제로 통신할 수 있는 IP 주소로 바꿔주는 역할
- 매번 새로 찾으면 느리니까 한 번 찾은 결과는 어딘가에 잠시 저장해뒀다가 재사용함

## 6. Port

### 구조

```text
같은 IP 주소를 쓰는 한 컴퓨터 안에서

IP: 192.168.0.1
 ├─ Port 80   → 웹 서버
 ├─ Port 22   → SSH 서버
 └─ Port 3306 → DB 서버
```

### 특징

- IP가 컴퓨터(장치)를 구분한다면, Port는 그 안에서 어떤 프로그램(서비스)으로 데이터를 보낼지 구분해주는 번호
- 잘 알려진 서비스는 정해진 번호를 씀(HTTP 80, HTTPS 443 등)
- 같은 IP에서도 포트 번호가 다르면 서로 다른 서버/프로그램으로 취급됨

### 정리

- 같은 컴퓨터(IP) 안에서 어떤 프로그램한테 데이터를 전달할지 정해주는 번호
- IP만으로는 "어느 컴퓨터인지"만 알 수 있고, "그 안의 어떤 프로그램인지"는 Port로 구분함

# Frontend 심화

## 7. 브라우저 Network 요청

### 구조

```text
브라우저 → 요청(Request) → 서버
브라우저 ← 응답(Response) ← 서버
```

### 특징

- fetch, XHR, 리소스 태그(img, script 등)로 요청을 보내는 시점이 다양함
- 페이지 하나를 로드할 때 HTML/CSS/JS/이미지 등 여러 요청이 동시에 나가고, 브라우저마다 동시에 처리할 수 있는 요청 개수에 제한이 있음
- 개발자도구 Network 탭에서 각 요청의 순서, 상태 코드, 걸린 시간을 직접 확인할 수 있음

### 정리

- 페이지 하나를 띄우는 데도 HTML 하나만 받는 게 아니라, 그 안에 필요한 CSS/JS/이미지까지 여러 번 따로따로 요청함
- 브라우저가 이 요청들을 어느 정도는 동시에 처리해주지만 무한정은 아니라서, 요청이 너무 많으면 뒤로 밀려서 느려질 수 있음

## 8. WebSocket

### 구조

```text
Client → (HTTP로 연결 요청, Upgrade) → Server
Client ↔ (한 번 연결되면 양방향으로 계속 데이터 주고받음) ↔ Server
```

### 특징

- 처음 연결만 HTTP로 맺고, 이후에는 별도의 방식으로 연결을 유지하며 양방향 통신
- 서버도 클라이언트에게 먼저 데이터를 보낼 수 있음 (기존 HTTP는 클라이언트가 요청해야 응답이 옴)
- 채팅, 실시간 알림처럼 서버 쪽 변화를 계속 받아야 하는 경우에 사용

### 정리

- 한 번 연결을 맺어두면 그 연결을 계속 유지하면서 양쪽에서 아무 때나 데이터를 보낼 수 있는 방식
- 기존 방식처럼 클라이언트가 매번 다시 요청할 필요 없이, 서버가 먼저 소식을 보내줄 수 있다는 게 가장 큰 차이

---

## 9. SSE (Server-Sent Events)

### 구조

```text
Client → (HTTP 요청, 연결 유지) → Server
Client ← (Server가 계속 데이터를 흘려보냄) ← Server
```

### 특징

- 하나의 HTTP 연결을 계속 열어두고, 서버가 클라이언트에게 한쪽 방향으로만 계속 데이터를 보내는 방식
- 클라이언트에서 서버로는 별도 요청을 보내지 않고, 서버 → 클라이언트 방향으로만 데이터가 흐름
- 실시간 주식 시세, 알림처럼 서버 발 업데이트만 필요할 때 WebSocket보다 가볍게 쓸 수 있음

### 비교 대상 늘리기: Polling / Long Polling도 함께 보기

```text
[Polling]
Client → 요청 → Server   (일정 시간마다 반복)
Client ← 응답(변화 없어도 바로 응답) ← Server

[Long Polling]
Client → 요청 → Server
              (서버가 변화 생길 때까지 응답을 들고 있음)
Client ← 응답(변화 생기면 응답) ← Server
Client → 다시 요청 → Server   (반복)
```

| | Polling | Long Polling | SSE | WebSocket |
| --- | --- | --- | --- | --- |
| 연결 방식 | 매번 새 요청 | 요청 하나를 길게 들고 있음 | 연결 하나를 계속 열어둠 | 연결 하나를 계속 열어둠 |
| 데이터 방향 | 클라이언트가 계속 물어봄 | 클라이언트가 계속 물어봄 | 서버 → 클라이언트만 | 양방향 |
| 끊겼을 때 재연결 | 다음 요청 때 자연스럽게 | 응답 오면 바로 재요청 | 브라우저가 알아서 재연결 시도 | 직접 재연결 로직을 만들어야 함 |
| 쓰기 좋은 상황 | 실시간성이 크게 중요하지 않을 때 | SSE/WebSocket 못 쓸 때의 대안 | 알림·시세처럼 서버 발 업데이트만 필요할 때 | 채팅처럼 양쪽 다 계속 보내야 할 때 |

### 정리

- WebSocket과 다르게 서버에서 클라이언트로만 계속 데이터를 흘려보내는 방식(양방향이 필요 없을 때 사용)
- 연결 하나를 계속 열어두고 서버가 새 소식이 있을 때마다 그 연결로 흘려보내주는 구조라, 실시간 알림 같은 데 적합함
- Polling은 구현이 제일 간단하지만 변화가 없어도 계속 요청을 날리는 거라 자원 낭비가 심하고, Long Polling은 응답을 들고 있다가 변화가 생기면 내려주는 방식이라 Polling보다는 낫지만 매번 새 요청을 다시 맺어야 함
- SSE는 브라우저(EventSource)가 연결이 끊기면 알아서 재연결을 시도해준다는 게 WebSocket과 다른 점이고, WebSocket은 양방향이 다 필요할 때 쓰는 대신 재연결 로직을 직접 만들어줘야 함
- 정리하면, 서버가 알림만 주면 되는 경우엔 SSE, 클라이언트도 계속 메시지를 보내야 하는 경우엔 WebSocket, 실시간성이 크게 중요하지 않으면 Polling만으로도 충분함

# 3주차 - OS - Memory / Virtual Memory

## 1. Memory 구조

### 구조

프로그램이 실행되면 메모리가 역할별 영역으로 나뉘어 사용된다.

```text
높은 주소
┌──────────┐
│  Stack   │  ↓ 아래로 증가
├──────────┤
│          │
├──────────┤
│  Heap    │  ↑ 위로 증가
├──────────┤
│  Data    │
├──────────┤
│  Code    │
└──────────┘
낮은 주소
```

### 특징

- Code: 실행할 명령어가 저장되는 영역
- Data: 전역 변수, static 변수가 저장되는 영역
- Heap: 동적으로 할당되는 메모리 영역
- Stack: 함수 호출 정보(지역 변수, 매개변수, 리턴 주소)가 저장되는 영역

### 정리

- 프로그램이 실행되면 메모리가 역할별로 나뉘어서 쓰이는 구조
- Stack은 함수를 호출할 때마다 쌓이고 끝나면 자동으로 정리되는 공간, Heap은 필요할 때 직접 늘렸다 줄였다 하는 공간
- 코드와 전역 변수는 프로그램이 시작할 때부터 끝날 때까지 고정된 자리를 차지함

---

## 2. Stack / Heap

### 구조

```text
Stack                       Heap
┌─────┐                     ┌──────────────┐
│ C() │ ← 최근 호출된 함수    │ 임의 순서로    │
├─────┤                     │ 할당·해제됨    │
│ B() │                     │              │
├─────┤                     └──────────────┘
│ A() │
└─────┘
```

### 특징

- Stack: 함수 호출 순서대로 쌓였다가 반대 순서로 제거됨(LIFO), 크기가 정해져 있어 너무 깊이 쌓이면 Stack Overflow 발생
- Heap: 필요한 만큼 직접 요청해서 할당, 사용이 끝나면 명시적으로 해제하거나 GC가 정리, 자유롭게 할당·해제되는 만큼 빈 공간이 조각날 수 있음

### 정리

- Stack은 함수를 부른 순서대로 자동으로 쌓였다 사라지는 공간, Heap은 필요할 때마다 요청해서 쓰는 공간이라는 차이가 있음
- Stack은 크기가 정해져 있어서 재귀를 너무 깊게 돌리면 넘칠 수 있고, Heap은 자유로운 대신 여기저기 흩어져 쓰이다 보니 관리가 더 복잡함

---

## 3. Virtual Memory

### 구조

프로세스마다 실제 물리 메모리보다 크고 독립된 주소 공간을 가진 것처럼 보여준다.

```text
Process A 가상 주소            물리 메모리
┌───────────┐                ┌───────────┐
│  0x0000   │ ─────────────→ │  Frame 3  │
│  0x1000   │ ─────────────→ │  Frame 7  │
│    ...    │                │    ...    │
└───────────┘                └───────────┘
```

### 특징

- 실제 물리 메모리보다 더 큰 주소 공간을 프로세스에게 있는 것처럼 보여줌
- 프로세스마다 독립된 가상 주소 공간을 가져서 서로 다른 프로세스의 메모리를 직접 침범할 수 없음
- 가상 주소 → 물리 주소로의 변환은 페이지 테이블을 통해 이뤄짐

### 정리

- 실제로 있는 메모리보다 더 넉넉한 공간을 쓰는 것처럼 보이게 해주는 개념, 진짜 물리 메모리는 뒤에서 따로 관리됨
- 프로세스마다 자기만의 가상 주소 공간을 가지고 있어서 다른 프로세스의 메모리를 직접 건드릴 걱정이 없음

---

## 4. Paging

### 구조

메모리를 일정한 크기(Page)로 잘라서 관리하고, 물리 메모리도 같은 크기(Frame)로 나눠서 대응시킨다.

```text
가상 메모리 (Page)           물리 메모리 (Frame)
┌────────┐                  ┌────────┐
│ Page 0 │ ───────────────→ │Frame 2 │
│ Page 1 │ ───────────────→ │Frame 5 │
│ Page 2 │ ───────────────→ │ (디스크) │
└────────┘                  └────────┘
```

### 특징

- 메모리를 일정한 크기(Page)로 잘라서 관리
- 필요한 Page만 물리 메모리에 올려두고, 당장 필요 없는 Page는 디스크에 남겨둘 수 있음
- Page 단위로 관리하기 때문에 물리 메모리를 효율적으로 나눠 쓸 수 있음

### 정리

- 메모리를 일정한 크기로 잘라서 관리하는 방식이라, 프로세스 전체를 한 번에 메모리에 올리지 않아도 됨
- 지금 당장 쓰는 부분만 물리 메모리에 두고 나머지는 디스크에 둘 수 있어서, 실제 메모리보다 큰 프로그램도 돌릴 수 있게 해줌

---

## 5. Page Fault

### 구조

```text
CPU가 특정 Page 요청
      ↓
페이지 테이블 확인
      ↓
물리 메모리에 없음 → Page Fault 발생
      ↓
디스크에서 해당 Page를 물리 메모리로 불러옴
      ↓
다시 실행 재개
```

### 특징

- 필요한 Page가 물리 메모리에 없을 때 발생하는 예외 상황
- 발생 시 디스크에서 해당 Page를 읽어와야 해서 상대적으로 큰 지연이 생김
- Page Fault가 너무 잦으면 실제 작업 시간보다 Page를 갈아 끼우는 시간이 길어지는 스래싱 상태로 이어질 수 있음

### 정리

- 지금 필요한 Page가 물리 메모리에 없어서 디스크까지 가서 가져와야 하는 상황
- 디스크 접근은 메모리 접근보다 훨씬 느려서, Page Fault가 자주 나면 프로그램이 눈에 띄게 느려짐
- Page Fault가 계속 반복되면서 실제 작업은 못 하고 Page만 갈아 끼우는 상태를 스래싱이라고 부름

# Frontend 심화

## 6. JS Memory Heap

### 구조

```js
const user = { name: "Kim" }; // Heap에 객체 저장, user는 그 위치를 가리킴
```

### 특징

- 객체, 배열, 함수처럼 크기가 정해지지 않은 값은 Heap에 저장
- 숫자, 문자열 같은 원시값은 Call Stack 안에 바로 저장
- 더 이상 어디서도 참조되지 않는 Heap 객체는 GC의 정리 대상이 됨

### 정리

- 객체나 배열처럼 크기가 유동적인 값은 Heap에 저장되고, 변수는 그 값이 있는 위치를 가리키기만 함
- 크기가 작고 고정되어 있는 숫자·문자열 같은 값은 Stack 쪽에 바로 저장됨

---

## 7. Call Stack

### 구조

```js
function a() { b(); }
function b() { c(); }
function c() { console.log("end"); }

a();
```

```text
Call Stack
┌───────┐
│  c()  │
├───────┤
│  b()  │
├───────┤
│  a()  │
└───────┘
```

### 특징

- 함수를 호출하면 Stack에 쌓이고, 함수가 끝나면 Stack에서 제거됨
- 가장 나중에 호출된 함수부터 먼저 종료됨(LIFO)
- 재귀 함수가 끝없이 호출되면 Stack이 넘쳐서 오류(Stack Overflow)가 발생

### 정리

- 함수를 부를 때마다 쌓이고, 끝나면 위에서부터 사라지는 구조
- 재귀 함수에서 끝나는 조건을 빠뜨리면 이 Stack이 계속 쌓이다가 한계를 넘어서 오류로 이어짐

---

## 8. Garbage Collection

### 구조

```text
Root(전역 변수, 현재 실행 중인 함수의 변수)에서 시작
      ↓
참조를 따라가며 "닿을 수 있는" 객체 표시 (Mark)
      ↓
표시되지 않은 객체는 더 이상 쓰이지 않는 것으로 판단 → 메모리에서 제거 (Sweep)
```

### 특징

- 더 이상 어디에서도 참조하지 않는 객체를 자동으로 찾아서 메모리에서 없애줌
- 개발자가 직접 메모리를 해제하지 않아도 되지만, 정확히 언제 실행되는지는 예측하기 어려움
- 참조가 하나라도 남아있으면 해당 객체는 정리 대상이 되지 않음

### 정리

- 어디서도 더 이상 가리키지 않는 값을 찾아서 자동으로 치워주는 기능
- 직접 메모리를 해제할 필요는 없지만, 실수로 참조를 계속 남겨두면 정리 대상에서 빠지게 됨 (Memory Leak으로 이어질 수 있음)
- 참고로 Closure도 참조를 남기는 대표적인 방법 중 하나라 GC와 관련이 있는데, Closure 자체는 다음 주차에서 더 다룰 예정이라 여기서는 이 정도만 짚고 넘어감

## 9. Memory Leak (브라우저 관점)

### 구조

```js
let cache = [];

function addData(data) {
  cache.push(data); // 계속 쌓이기만 하고 지워지지 않음
}
```

### 특징

- 더 이상 필요 없는 데이터인데 어딘가에서 계속 참조하고 있어서 GC가 정리하지 못하는 상황
- 전역 변수에 계속 데이터를 쌓거나, 이벤트 리스너를 제거하지 않고 계속 등록하는 경우 자주 발생
- 시간이 지날수록 메모리 사용량이 계속 늘어나 결국 성능 저하나 크래시로 이어질 수 있음

### 대표적인 브라우저 Memory Leak 패턴

**1. 제거되지 않은 이벤트 리스너**

```js
function setup() {
  const button = document.getElementById("btn");
  button.addEventListener("click", () => {
    console.log("clicked");
  });
}
```

버튼을 화면에서 없애도 리스너 콜백이 살아있으면, 그 콜백이 참조하는 데이터까지 같이 계속 메모리에 남음. `removeEventListener`로 직접 정리하거나, React 등에서는 컴포넌트가 사라질 때(cleanup 함수 등) 정리해줘야 함.

**2. 정리되지 않은 타이머**

```js
function startPolling() {
  setInterval(() => {
    fetchData();
  }, 1000);
}
```

`setInterval`을 `clearInterval`로 멈추지 않으면, 해당 화면을 벗어나도 콜백과 그 안에서 참조하던 데이터가 계속 살아있음.

**3. 분리된(Detached) DOM 노드**

```js
let detachedNode;

function removeBox() {
  const el = document.getElementById("box");
  el.remove(); // 화면(DOM 트리)에서는 사라짐
  detachedNode = el; // 그런데 변수가 여전히 이 요소를 참조 중
}
```

화면에서 안 보이게 지워졌다고 메모리에서도 바로 사라지는 게 아님. 어딘가의 변수가 그 요소를 계속 들고 있으면 DOM 트리 밖에서 붕 뜬 채로 메모리를 계속 차지함 (Detached DOM).

**4. 전역 변수에 계속 쌓이는 데이터**

위 구조 예시의 `cache`처럼, 끝을 정해두지 않고 계속 push만 하는 배열/객체.

### 정리

- 이벤트 리스너, 타이머, 구독처럼 "시작한 쪽에서 직접 정리해야 하는" 것들을 안 지우는 게 흔한 원인
- 화면에서 안 보이게 지워졌다고 메모리에서도 사라진 건 아니고, 어딘가에서 그 요소를 변수로 들고 있으면 Detached 상태로 계속 남아있을 수 있음
- 컴포넌트나 페이지가 없어질 때 등록해뒀던 리스너·타이머·구독을 정리하는 습관이 Memory Leak을 막는 핵심
- 크롬 개발자도구의 Memory 탭에서 Heap 스냅샷을 찍어보면 Detached 노드나 계속 늘어나는 객체를 직접 확인할 수 있음

# 3주차 - OS - Memory / Virtual Memory

## 1. 메모리 구조

프로세스가 실행되면 OS는 해당 프로세스의 **가상 주소 공간**을 할당한다. 

```
높은 주소
┌─────────────────┐
│      Stack      │  ↓ 아래로 성장
├─────────────────┤
│       ...       │  (빈 공간)
├─────────────────┤
│      Heap       │  ↑ 위로 성장
├─────────────────┤
│   BSS / Data    │
├─────────────────┤
│   Code (Text)   │
└─────────────────┘
낮은 주소
```

| 영역 | 저장 대상 | 할당 시점 | 특징 |
|---|---|---|---|
| Code(Text) | 실행할 기계어 코드 | 컴파일 타임 | read-only, 여러 프로세스가 공유 가능 |
| Data | 초기화된 전역/static 변수 | 컴파일 타임 | 프로그램 종료까지 유지 |
| BSS | 초기화되지 않은 전역/static 변수 | 컴파일 타임 | 실행 시 0으로 초기화, 바이너리에 값 미포함 |
| Heap | 동적 할당 객체 (`malloc`, `new`) | 런타임 | 개발자/런타임이 수명 관리, 낮은 주소 → 높은 주소로 성장 |
| Stack | 지역 변수, 매개변수, 리턴 주소 | 런타임 | 함수 호출 단위(스택 프레임), 높은 주소 → 낮은 주소로 성장 |

> Heap과 Stack이 서로를 향해 성장하다 충돌하면 각각 `OOM(Out Of Memory)` / `Stack Overflow`가 발생한다.

## 2. Stack vs Heap

| 비교 항목 | Stack | Heap |
|---|---|---|
| 할당 방식 | 컴파일 타임에 크기 결정, SP 이동만으로 할당 | 런타임에 크기 결정, 할당자(allocator)가 빈 공간 탐색 |
| 해제 방식 | 함수 리턴 시 자동 | 명시적 해제(`free`) 또는 GC |
| 속도 | 빠름 (포인터 증감 1회) | 느림 (메타데이터 탐색, 단편화 관리) |
| 크기 | 작고 제한적 (보통 1~8MB) | 큼 (가상 주소 공간 한도) |
| 스레드 | **스레드마다 독립적** | **프로세스 내 모든 스레드가 공유** |
| 단편화 | 없음 (LIFO 구조) | 외부 단편화 발생 |
| 대표 에러 | StackOverflow (깊은 재귀) | Memory Leak, OOM |

**스택 프레임(Stack Frame)**: 함수 호출 1회당 생성되는 단위. 매개변수 · 지역변수 · 이전 프레임 포인터 · 복귀 주소를 담는다. 재귀가 깊어지면 프레임이 쌓여 스택 영역을 초과한다.

## 3. Virtual Memory

### 왜 필요한가
물리 메모리를 프로세스가 직접 쓰면 세 가지 문제가 생긴다.
1. **용량 한계** — 물리 메모리보다 큰 프로그램을 실행할 수 없다.
2. **보호 부재** — 프로세스 A가 B의 메모리를 덮어쓸 수 있다.
3. **배치 문제** — 프로그램마다 시작 주소가 달라져 컴파일이 복잡해진다.

가상 메모리는 **모든 프로세스에게 0번지부터 시작하는 연속된 주소 공간이 있는 것처럼** 보여주고, 실제 물리 주소로의 매핑은 OS와 **MMU(Memory Management Unit)** 가 담당한다.

### 주소 변환
```
CPU → 가상 주소(VA) → [MMU + Page Table] → 물리 주소(PA) → RAM
                          ↑
                      TLB 캐시 조회
```

### 핵심 이점
- **격리(Isolation)**: 프로세스마다 별도 페이지 테이블 → 남의 메모리 접근 자체가 불가능
- **오버커밋**: 실제 물리 메모리보다 많은 양을 약속하고, 실제 접근 시점에만 할당(Demand Paging)
- **공유**: 동일한 라이브러리 코드 페이지를 여러 프로세스가 같은 프레임에 매핑
- **Copy-on-Write**: `fork()` 시 페이지를 복사하지 않고 공유하다가, 쓰기 시도 시점에 복사

## 4. Paging

가상 주소 공간을 고정 크기 **Page**(보통 4KB)로, 물리 메모리를 같은 크기의 **Frame**으로 나눠 매핑한다.

### 주소 구성
```
가상 주소 = [ Page Number | Offset ]
              ↓ 페이지 테이블 조회
물리 주소 = [ Frame Number | Offset ]
```
Offset은 변환 없이 그대로 사용되므로, 페이지 테이블은 페이지 번호 → 프레임 번호 매핑만 담당한다.

### 다단계 페이지 테이블 (Multi-level Page Table)
32비트 + 4KB 페이지 기준 엔트리 수는 2^20개 = 약 4MB. 프로세스마다 이걸 상주시키면 낭비가 크다.
→ 페이지 테이블을 계층화해 **실제 사용하는 구간의 하위 테이블만** 메모리에 올린다. (x86-64는 4단계)

### TLB (Translation Lookaside Buffer)
페이지 테이블 조회 자체가 메모리 접근이므로, 변환 없이 접근하면 매 접근마다 메모리를 2번 읽게 된다.
TLB는 최근 주소 변환 결과를 담는 **MMU 내부 캐시**다.
- TLB Hit → 즉시 물리 주소 획득
- TLB Miss → 페이지 테이블 조회 후 TLB에 적재
- 컨텍스트 스위칭 시 TLB flush 발생 (ASID로 완화)

### Paging vs Segmentation

| | Paging | Segmentation |
|---|---|---|
| 분할 단위 | 고정 크기 | 논리 단위(code, data, stack) 가변 크기 |
| 단편화 | 내부 단편화 | 외부 단편화 |
| 관리 | 단순 | 복잡 |

> 현대 OS는 대부분 페이징 기반이며, 세그먼테이션은 보호 속성 표현 정도로만 남아있다.

## 5. Page Fault

CPU가 접근한 페이지가 물리 메모리에 없을 때 MMU가 발생시키는 **트랩(예외)**.

### 처리 과정
1. MMU가 페이지 테이블의 valid bit = 0 확인 → Page Fault 트랩 발생
2. OS가 커널 모드로 전환, 해당 접근이 유효한지 검증 (아니면 `SIGSEGV`)
3. 빈 프레임 확보 (없으면 **페이지 교체 알고리즘**으로 희생자 선정)
4. 희생 페이지가 dirty면 디스크(swap)에 기록
5. 디스크에서 요청 페이지를 프레임에 적재
6. 페이지 테이블 갱신(valid bit = 1), TLB 갱신
7. 실패했던 명령어를 **재실행**

### 종류
- **Minor Fault**: 페이지가 이미 메모리에 있으나 매핑만 없는 경우 (page cache 재사용, CoW) — 빠름
- **Major Fault**: 디스크 I/O가 필요한 경우 — 느림. 성능 문제의 주범
- **Invalid Fault**: 잘못된 접근 → Segmentation Fault

### 페이지 교체 알고리즘

| 알고리즘 | 동작 | 특징 |
|---|---|---|
| FIFO | 가장 먼저 들어온 페이지 교체 | 구현 단순, **Belady's Anomaly** 발생 |
| Optimal | 가장 나중에 사용될 페이지 교체 | 이론상 최적, 미래를 알아야 해 구현 불가 |
| LRU | 가장 오래 참조되지 않은 페이지 교체 | 성능 우수, 타임스탬프/연결리스트 관리 비용 |
| Clock (2nd Chance) | reference bit 순회, 1이면 0으로 바꾸고 통과 | LRU 근사, 실제 OS에서 채택 |

> **Belady's Anomaly**: 프레임 수를 늘렸는데 오히려 page fault가 증가하는 현상. FIFO에서 발생하며, LRU 같은 스택 알고리즘에서는 발생하지 않는다.

### Thrashing
프로세스가 필요로 하는 페이지 집합(**Working Set**)보다 할당된 프레임이 적을 때, 페이지 교체가 끝없이 반복되며 CPU 이용률이 급락하는 현상.
- 해결: Working Set 모델, PFF(Page Fault Frequency) 기반 프레임 조절, 멀티프로그래밍 정도 낮추기

## Backend 심화 — JVM

### 1. Runtime Data Area

```
┌──────────────────────── JVM ────────────────────────┐
│                                                     │
│   [ 모든 스레드 공유 ]                                  │
│   ┌─────────────┐  ┌────────────────────────────┐   │
│   │    Heap     │  │ Method Area (Metaspace)    │   │
│   │   객체/배열   │  │ 클래스 메타데이터, static,      │   │
│   │             │  │ Runtime Constant Pool      │   │
│   └─────────────┘  └────────────────────────────┘   │
│                                                     │
│   [ 스레드별 생성 ]                                     │
│   ┌──────────┐ ┌──────────────┐ ┌────────────────┐  │
│   │ JVM Stack│ │ PC Register  │ │ Native Method  │  │
│   │   프레임   │ │ 현재 명령 주소  │ │ Stack          │  │
│   └──────────┘ └──────────────┘ └────────────────┘  │
└─────────────────────────────────────────────────────┘
```

- **Heap**: `new`로 생성된 모든 객체와 배열. GC의 대상이 되는 유일한 영역
- **Method Area**: 클래스 구조, 메서드 정보, static 변수, 상수 풀. Java 8부터 **PermGen → Metaspace**로 이동해 네이티브 메모리를 사용한다(→ `OutOfMemoryError: PermGen` 이 `Metaspace`로 대체)
- **JVM Stack**: 메서드 호출마다 **프레임** push. 지역 변수, 피연산자 스택, 참조값 보관. 초과 시 `StackOverflowError`
- **PC Register**: 스레드가 실행 중인 JVM 명령어 주소
- **Native Method Stack**: JNI를 통한 네이티브 코드 실행용 스택

> 핵심: **객체는 Heap에, 그 객체를 가리키는 참조 변수는 Stack에** 있다.

### 2. Heap 구조

```
┌──────────────── Young Generation ────────────────┐ ┌─ Old Gen ─┐
│  Eden        │  Survivor 0   │  Survivor 1       │ │           │
└──────────────┴───────────────┴───────────────────┘ └───────────┘
```

- **Eden**: 새로 생성된 객체가 먼저 놓이는 곳
- **Survivor 0 / 1**: Minor GC에서 살아남은 객체가 번갈아 이동. 항상 하나는 비어 있다
- **Old Generation**: Survivor를 일정 횟수(age threshold) 이상 넘긴 장수 객체가 승격(Promotion)
- **TLAB(Thread Local Allocation Buffer)**: Eden을 스레드별 영역으로 쪼개 락 없이 할당 → 할당 비용을 포인터 증가 수준으로 낮춤

**약한 세대 가설(Weak Generational Hypothesis)**: 대부분의 객체는 금방 죽고, 오래된 객체가 젊은 객체를 참조하는 경우는 드물다. 세대별 GC는 이 가정에 기반한다.

### 3. Garbage Collection

#### 어떤 객체를 수거하는가 — Reachability
**GC Root**에서 참조 그래프를 타고 도달 가능한지 판단한다. 도달 불가능(unreachable)하면 수거 대상.

GC Root에 해당하는 것:
- 스택 프레임의 지역 변수 · 매개변수
- static 변수
- JNI 네이티브 참조
- 모니터 락을 가진 객체

> 참조 카운팅과 달리 **순환 참조도 정상적으로 수거**된다.

#### 기본 동작
1. **Mark**: GC Root부터 순회하며 살아있는 객체 표시
2. **Sweep**: 표시되지 않은 객체 회수
3. **Compact**: 남은 객체를 앞으로 몰아 외부 단편화 제거

#### Minor GC vs Major(Full) GC

| | Minor GC | Major GC |
|---|---|---|
| 대상 | Young Generation | Old Generation (+ 전체) |
| 빈도 | 잦음 | 드묾 |
| 소요 시간 | 짧음 | 김 |
| STW | 매우 짧음 | 길다 — 성능 이슈 주범 |

**Stop-The-World**: GC 수행을 위해 애플리케이션 스레드를 전부 멈추는 구간. GC 튜닝의 목표는 대부분 STW 시간 단축이다.

#### GC 알고리즘 비교

| GC | 특징 | 적합한 환경 |
|---|---|---|
| Serial | 단일 스레드로 수집 | 싱글 코어, 소규모 |
| Parallel | 멀티 스레드로 수집, 처리량 중심 | Java 8 기본, 배치 성 작업 |
| CMS | 동시 마킹으로 STW 최소화 | Java 14에서 제거됨 |
| **G1** | Heap을 Region으로 분할, 쓰레기 많은 Region 우선 수집 | Java 9+ 기본, 대용량 Heap |
| ZGC / Shenandoah | 대부분 작업을 동시 수행, STW를 1ms 이하로 | 초저지연 요구 서비스 |

### 4. OS 가상 메모리와의 연결
- JVM Heap은 결국 **프로세스 가상 주소 공간의 일부**다. `-Xmx`는 가상 주소 예약량이지 물리 메모리 점유량이 아니다.
- Heap 일부가 **swap out** 되면 GC의 전체 Heap 스캔에서 major page fault가 대량 발생 → STW가 수 초 단위로 폭증한다. 그래서 운영 환경에서는 **swap을 끄거나** Heap을 물리 메모리 안에 확실히 들어가게 잡는다.
- 컨테이너 환경에서 `-Xmx`를 물리 메모리보다 크게 잡으면 JVM OOM이 아니라 **cgroup OOM Killer에 의한 프로세스 강제 종료(exit 137)** 로 이어진다.

### 5. Memory Leak in Java
GC가 있어도 누수는 발생한다. **참조가 끊기지 않은 채 방치된 객체**가 원인.
- static 컬렉션에 계속 add만 하는 경우
- 캐시에 만료 정책이 없는 경우 (→ `WeakHashMap`, Caffeine 등 활용)
- 리스너/콜백 등록 후 해제 누락
- `ThreadLocal` 사용 후 `remove()` 미호출 (스레드 풀에서 특히 치명적)
- 스트림, 커넥션 등 close 누락

## 면접 대비 정리

**Q. 가상 메모리가 왜 필요한가요?**
물리 메모리 크기의 제약을 없애고, 프로세스 간 메모리를 격리해 보호하며, 프로그램이 항상 동일한 주소 레이아웃을 가정할 수 있게 하기 위해서입니다.

**Q. Page Fault가 발생하면 어떤 일이 일어나나요?**
MMU가 트랩을 발생시키고, OS가 접근 유효성을 검증한 뒤 빈 프레임을 확보합니다. 필요하면 교체 알고리즘으로 희생 페이지를 골라 swap에 내리고, 디스크에서 요청 페이지를 올린 다음 페이지 테이블을 갱신하고 실패한 명령을 재실행합니다.

**Q. Stack과 Heap의 차이는?**
Stack은 스레드별로 독립적이고 함수 호출 단위로 자동 해제되며 할당이 빠릅니다. Heap은 프로세스 내 스레드가 공유하고 런타임에 동적으로 할당되며, 해제를 개발자나 GC가 책임집니다.

**Q. TLB는 무엇인가요?**
주소 변환 결과를 캐싱하는 MMU 내부 캐시입니다. 없으면 모든 메모리 접근이 페이지 테이블 조회 + 실제 접근으로 두 번의 메모리 접근을 유발합니다.

**Q. GC 대상이 되는 객체는 어떻게 판단하나요?**
참조 카운팅이 아니라 Reachability로 판단합니다. GC Root(스택 지역변수, static 변수, JNI 참조 등)에서 시작해 참조 그래프를 탐색하고, 도달할 수 없는 객체를 수거합니다. 그래서 순환 참조도 수거됩니다.

**Q. Java에 GC가 있는데 왜 메모리 누수가 생기나요?**
GC는 도달 불가능한 객체만 수거합니다. static 컬렉션, 만료 없는 캐시, 해제되지 않은 ThreadLocal처럼 논리적으로는 필요 없지만 참조는 살아있는 객체는 영원히 수거되지 않습니다.

**Q. Minor GC와 Full GC의 차이는?**
Minor GC는 Young Generation만 대상으로 하며 자주 발생하지만 STW가 매우 짧습니다. Full GC는 Old Generation을 포함한 전체를 대상으로 해 빈도는 낮지만 STW가 길어 지연 시간 문제를 일으킵니다.

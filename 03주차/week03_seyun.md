# 3주차 - OS - Memory / Virtual Memory

## 1. Memory 구조

- 프로세스가 실행되면 OS는 **독립된 가상 주소 공간**을 할당하고, 그 안을 역할에 따라 여러 영역으로 나눠서 사용
- 주소 공간은 보통 **낮은 주소 → 높은 주소** 순서로 `Code(Text) → Data → BSS → Heap → (빈 공간) → Stack`으로 배치됨

### 📍 영역별 설명

| 영역        | 설명                                                                             |
| ----------- | -------------------------------------------------------------------------------- |
| Code (Text) | 실행할 명령어(기계어) 저장, 읽기 전용                                            |
| Data        | 초기화된 전역/static 변수 저장                                                   |
| BSS         | 초기화되지 않은 전역/static 변수 저장 (실행 시 0으로 초기화)                     |
| Heap        | 동적으로 할당되는 메모리, 낮은 주소 → 높은 주소로 증가                           |
| Stack       | 함수 호출 시 생성되는 지역 변수/매개변수/리턴 주소, 높은 주소 → 낮은 주소로 증가 |

### 💡 Heap과 Stack이 서로 반대 방향으로 자라도록 설계한 이유

**⇒ 두 영역이 마주 보며 자라게 하면 가운데의 빈 공간을 Heap과 Stack이 유연하게 나눠 쓸 수 있음. 크기가 고정된 두 영역을 양 끝에 각각 배치했다면 한쪽이 다 차도 다른 쪽 여유 공간을 쓰지 못했겠지만, 이 구조 덕분에 둘 중 하나가 상대적으로 더 커져도 남은 공간을 활용할 수 있어 메모리 활용도가 높아짐**

---

## 2. Stack / Heap

- **Stack:** 컴파일 타임에 크기가 결정되는 **정적 메모리 영역**, 함수 호출마다 스택 프레임이 push되고 함수가 끝나면 pop됨
- **Heap:** 런타임에 개발자(또는 런타임)가 필요한 만큼 요청해서 사용하는 **동적 메모리 영역**

### 📍 Stack vs Heap

| 구분        | Stack                                | Heap                                                        |
| ----------- | ------------------------------------ | ----------------------------------------------------------- |
| 할당 방식   | 정적 할당, 컴파일 타임에 크기 결정   | 동적 할당, 런타임에 크기 결정                               |
| 관리 주체   | OS/컴파일러가 자동으로 push/pop      | 개발자가 직접 해제(C/C++) 또는 GC가 관리(Java, JS)          |
| 속도        | 빠름 (포인터 이동만으로 할당/해제)   | 느림 (빈 공간 탐색, 단편화 관리 필요)                       |
| 크기        | 상대적으로 작고 고정적               | 상대적으로 크고 가변적                                      |
| 생명 주기   | 함수 호출 시 생성, 반환 시 자동 소멸 | 명시적으로 해제하기 전까지(또는 GC 대상이 되기 전까지) 유지 |
| 저장 데이터 | 지역 변수, 매개변수, 리턴 주소       | 객체, 동적으로 크기가 변하는 데이터                         |

### 💡 Stack Overflow는 왜 발생하나요?

**⇒ Stack은 프로세스마다 한정된 고정 크기로 할당되는데, 재귀 호출의 종료 조건이 없거나 호출 깊이가 너무 깊어지면 스택 프레임이 계속 쌓여 할당된 Stack 영역을 초과하게 되고, 이때 Stack Overflow가 발생함. 반대로 Heap은 상대적으로 크고 가변적이라 잘못된 동적 할당·해제 누락이 누적되면 Stack Overflow가 아니라 메모리 누수(Memory Leak)나 OOM(Out Of Memory)으로 이어짐**

---

## 3. Virtual Memory (가상 메모리)

- 프로세스가 **실제 물리 메모리(RAM) 주소를 직접 알지 못하도록**, OS가 프로세스마다 독립된 **가상 주소 공간**을 제공하고 이를 물리 주소로 매핑해주는 기법
- **MMU(Memory Management Unit)가** CPU와 RAM 사이에서 가상 주소 → 물리 주소 변환을 담당

### 📍 가상 메모리를 쓰는 이유

- **프로세스 간 메모리 격리:** 각 프로세스는 자신만의 가상 주소 공간을 가지므로, 다른 프로세스의 메모리 영역을 침범하거나 들여다볼 수 없음 (보안/안정성)
- **물리 메모리보다 큰 프로그램 실행 가능:** 전체 프로그램을 한 번에 RAM에 올리지 않고, 필요한 부분만 올려서(Demand Paging) 실행 가능
- **메모리 효율적 사용:** 여러 프로세스가 물리 메모리를 유연하게 나눠 쓸 수 있고, 비어있는 물리 메모리 공간을 효율적으로 재배치 가능

### 💡 모든 프로세스가 비슷한 가상 주소(예: 0x0000)부터 시작하는 것처럼 보이는 이유

**⇒ 가상 주소 공간은 프로세스마다 독립적으로 존재하는 논리적인 개념이라, 실제 물리 메모리상의 위치와 무관하게 항상 동일한 형태(0번지부터 시작 등)로 보이도록 추상화되어 있기 때문. MMU가 이 가상 주소를 실제 물리 주소로 변환해주므로 프로세스 입장에서는 마치 자신이 메모리 전체를 독점하는 것처럼 동작할 수 있음**

---

## 4. Paging

- 가상 주소 공간을 **Page**라는 고정 크기 단위로, 물리 메모리를 **Frame**이라는 동일한 크기 단위로 나눠서 Page ↔ Frame을 매핑하는 가상 메모리 구현 방식
- 각 프로세스는 **Page Table**을 가지며, 여기에 어떤 Page가 어떤 Frame에 매핑되어 있는지 정보를 저장

### 📍 주소 변환 과정

1. CPU가 가상 주소(Page Number + Offset)를 생성
2. Page Table에서 해당 Page Number에 대응하는 Frame Number를 조회
3. Frame Number + Offset으로 실제 물리 주소를 계산해 메모리 접근

### 📍 TLB (Translation Lookaside Buffer)

- Page Table은 메모리(RAM)에 저장되어 있어 매번 조회하면 접근 속도가 느려짐
- **TLB**는 최근에 사용한 Page-Frame 매핑 정보를 캐싱해두는 고속 캐시로, TLB Hit 시 Page Table 조회 없이 바로 물리 주소를 구할 수 있음

### 📍 다단계 페이지 테이블 (Multi-level Page Table)

- 프로세스의 가상 주소 공간이 커질수록 단일 Page Table 크기도 함께 커져 메모리 낭비가 발생
- Page Table 자체를 계층적으로 나눠(예: 2단계, 3단계), 실제 사용되는 주소 영역에 대해서만 하위 테이블을 생성함으로써 메모리 낭비를 줄임

### 💡 Paging과 Segmentation의 차이

**⇒ Paging은 물리적으로 고정된 크기(Page)로 메모리를 나누기 때문에 외부 단편화(External Fragmentation)가 없지만, 내부적으로 남는 공간인 내부 단편화(Internal Fragmentation)는 발생할 수 있음. 반대로 Segmentation은 코드/데이터처럼 논리적 의미 단위(가변 크기)로 나누기 때문에 내부 단편화는 없지만, 가변 크기 조각들이 메모리에 배치되면서 외부 단편화가 발생하기 쉬움. 현대 OS는 대부분 Paging을 기반으로 하되, 논리적 구분을 위해 Segmentation 개념을 혼합해서 사용**

---

## 5. Page Fault

- CPU가 접근하려는 Page가 **물리 메모리(RAM)에 올라와 있지 않을 때** 발생하는 예외(Trap)
- 가상 메모리는 프로그램 전체를 한 번에 메모리에 올리지 않고, 필요한 시점에만 Page를 올리는 **Demand Paging** 방식을 사용하기 때문에 필연적으로 발생함

### 📍 Page Fault 처리 과정

1. CPU가 특정 가상 주소에 접근 → Page Table에서 해당 Page의 **Valid/Invalid bit**를 확인
2. Invalid(메모리에 없음)라면 CPU가 Page Fault Trap을 발생시키고 OS(커널)로 제어권이 넘어감
3. OS가 해당 Page를 디스크(스왑 영역 등)에서 찾아 **빈 Frame에 적재**
   - 빈 Frame이 없다면 **Page Replacement 알고리즘**으로 기존 Page 중 하나를 골라 내보냄(필요 시 디스크에 write-back)
4. Page Table의 매핑 정보를 갱신
5. Fault를 일으켰던 명령어를 재실행

### 📍 Page Replacement 알고리즘

| 알고리즘 | 설명                                                                                      |
| -------- | ----------------------------------------------------------------------------------------- |
| FIFO     | 가장 먼저 들어온 Page부터 교체                                                            |
| LRU      | 가장 오랫동안 사용되지 않은(Least Recently Used) Page를 교체                              |
| Optimal  | 앞으로 가장 오래 사용되지 않을 Page를 교체 (이론상 최적, 미래 예측 필요해 실제 구현 불가) |

### 💡 Thrashing이란?

**⇒ 물리 메모리가 부족한 상태에서 여러 프로세스가 실행되면, Page Fault가 너무 자주 발생해 CPU가 실제 연산보다 Page를 디스크와 주고받는 데(Swapping) 대부분의 시간을 쓰게 되는 현상. 이렇게 되면 CPU 사용률은 오히려 급격히 떨어지고 시스템 전체 성능이 저하됨. 이를 막기 위해 OS는 프로세스별로 적절한 Frame 수를 배분하는 Working Set 모델이나 동시 실행 프로세스 수를 제한하는 방법 등을 사용**

# Frontend 심화

## 1. JS Memory Heap / Call Stack

- JS 엔진은 데이터 종류에 따라 메모리를 저장하는 위치가 다름

### 📍 Call Stack vs Memory Heap

| 구분      | Call Stack                                  | Memory Heap                                      |
| --------- | ------------------------------------------- | ------------------------------------------------ |
| 저장 대상 | 함수 실행 컨텍스트, 원시 타입(primitive) 값 | 객체, 배열, 함수 등 참조 타입(reference) 값      |
| 구조      | LIFO (정적, 순서가 정해짐)                  | 구조화되지 않은 넓은 메모리 영역 (동적)          |
| 크기      | 상대적으로 작고 제한적                      | 상대적으로 크고 가변적                           |
| 관리 방식 | 함수 호출/반환에 따라 자동 push/pop         | Garbage Collector가 참조 여부를 추적해 관리      |
| 접근 방식 | 값 자체를 저장 (Call by Value)              | Call Stack에는 Heap 객체의 **참조(주소)**만 저장 |

### 💡 원시 타입과 참조 타입을 저장 위치가 다르게 설계한 이유

**⇒ 원시 타입은 크기가 고정적이고 변경 불가능(immutable)해서 Stack에 값 자체를 두면 빠르게 push/pop할 수 있지만, 객체는 크기가 동적으로 변할 수 있고 여러 변수가 같은 객체를 참조(공유)할 수 있어야 하므로 Heap에 실제 데이터를 두고 Stack에는 그 주소(참조)만 저장하는 방식이 메모리 효율과 동작 방식 양쪽에서 더 적합함**

---

## 2. Garbage Collection

- JS는 C/C++처럼 개발자가 직접 메모리를 해제하지 않고, **더 이상 참조되지 않는 객체를 엔진(GC)이 자동으로 탐지해 회수**함

### 📍 Reference Counting (참조 카운팅) 방식과 한계

- 객체를 참조하는 변수 수를 카운트해서, 카운트가 0이 되면 회수하는 방식
- **한계 — 순환 참조(Circular Reference):** 두 객체가 서로를 참조하고 있으면 외부에서 더 이상 접근할 수 없는 상태여도 참조 카운트가 0이 되지 않아 회수되지 않음 → 메모리 누수 발생

### 📍 Mark-and-Sweep (표시-후-청소) 알고리즘

- 현대 JS 엔진(V8 등)이 사용하는 방식으로, 순환 참조 문제를 해결
- **Mark:** GC Root(전역 객체 등)에서 시작해 도달 가능한(reachable) 모든 객체를 표시
- **Sweep:** 표시되지 않은(도달 불가능한) 객체를 메모리에서 제거
- ⇒ 참조 카운트가 아니라 **"루트에서 도달 가능한가"**를 기준으로 판단하므로, 서로를 참조하더라도 외부에서 도달할 수 없으면 정상적으로 회수됨

### 📍 V8의 Generational GC

- 대부분의 객체는 생성된 직후 금방 사라진다는 **Generational Hypothesis(세대 가설)**에 기반해 힙을 세대별로 나눠 관리
- **Young Generation (New Space):** 새로 생성된 객체가 위치, 크기가 작고 GC(Scavenger, 주로 Minor GC)가 빈번하게 짧게 일어남
- **Old Generation (Old Space):** Young Generation에서 일정 기간 살아남은 객체가 승격(promotion)되는 영역, GC(Major GC, Mark-Sweep-Compact)가 상대적으로 덜 자주 일어나지만 비용이 큼

### 💡 GC가 있어도 Memory Leak이 발생할 수 있는 이유

**⇒ GC는 "도달 불가능한" 객체만 회수하기 때문에, 실제로는 더 이상 필요 없는 객체라도 어딘가에서 여전히 참조하고 있다면(=도달 가능하다면) 회수 대상이 되지 않음. 즉 JS의 메모리 누수는 대부분 개발자가 의도치 않게 불필요한 참조를 계속 유지하는 코드 패턴에서 발생함**

---

## 3. Memory Leak

- 더 이상 사용하지 않는 객체가 **어딘가에서 계속 참조되고 있어 GC의 회수 대상이 되지 못하고 메모리에 남아있는 현상**

### 📍 대표적인 발생 원인

| 원인                           | 설명                                                                                         |
| ------------------------------ | -------------------------------------------------------------------------------------------- |
| 의도치 않은 전역 변수          | `var`/선언 없이 값을 할당하면 전역 객체(window 등)에 프로퍼티로 남아 앱이 끝날 때까지 유지됨 |
| 해제되지 않은 이벤트 리스너    | `addEventListener`로 등록한 콜백을 `removeEventListener`하지 않으면 관련 참조가 계속 유지됨  |
| 클로저의 과도한 참조 유지      | 클로저가 필요 이상으로 큰 외부 스코프 변수를 캡처해 계속 붙들고 있는 경우                    |
| 분리된 DOM 참조 (Detached DOM) | DOM에서 이미 제거된 노드를 JS 변수가 여전히 참조하고 있어 GC되지 못하는 경우                 |
| 정리되지 않은 타이머           | `setInterval`/`setTimeout`을 `clearInterval`/`clearTimeout` 없이 계속 실행되도록 두는 경우   |

### 💡 Memory Leak은 어떻게 탐지하고 방지하나요?

**⇒ Chrome DevTools의 Memory 탭에서 Heap Snapshot을 여러 시점에 찍어 비교하면, 시간이 지나도 계속 늘어나는(회수되지 않는) 객체 그룹을 찾아낼 수 있음. 특히 Detached DOM 트리가 남아있는지 확인하는 것이 대표적인 진단 방법. 예방을 위해서는 컴포넌트/페이지가 언마운트될 때 등록했던 이벤트 리스너와 타이머를 명시적으로 해제하고, 전역 스코프에 불필요한 참조를 남기지 않도록 주의해야 함**

# 5주차 - HTTP / HTTPS

## 1. HTTP

### 구조

```text
Client → 요청(Request: 메서드, URL, 헤더, 바디) → Server
Client ← 응답(Response: 상태 코드, 헤더, 바디) ← Server
```

### 특징

- 클라이언트가 요청하면 서버가 응답하는 구조의 통신 규칙(프로토콜)
- 요청/응답 모두 시작 줄, 헤더, 바디로 구성됨
- TCP 위에서 동작하고, 기본 포트는 80(HTTPS는 443)

### 정리

- 브라우저와 서버가 서로 말을 주고받을 때 지켜야 하는 약속
- 항상 클라이언트가 먼저 요청하고, 서버는 그 요청에 대한 응답만 돌려주는 방식

---

## 2. Stateless

### 구조

```text
요청 1: "로그인했어요"   → Server (응답 후 기억 안 함)
요청 2: "내 정보 줘"     → Server (누구인지 모름)
```

### 특징

- 서버가 이전 요청의 상태를 기억하지 않고, 요청마다 독립적으로 처리
- 요청에 필요한 정보는 매번 요청 안에 담아 보내야 함
- 서버를 늘려도 어느 서버가 처리하든 결과가 같아서 확장하기 쉬움
- 로그인 상태 유지는 Cookie/Session, Token 같은 별도 방식으로 해결

### 정리

- 서버가 "아까 그 사람"을 기억하지 않기 때문에 요청할 때마다 필요한 정보를 같이 보내야 함
- 대신 서버 입장에선 상태를 들고 있을 필요가 없어서 서버를 여러 대로 늘리기 쉬움

## 3. Method

### 구조

```text
GET    /users      → 목록 조회
GET    /users/1    → 단건 조회
POST   /users      → 생성
PUT    /users/1    → 전체 수정(교체)
PATCH  /users/1    → 일부 수정
DELETE /users/1    → 삭제
```

### 특징

- 요청이 서버에서 어떤 동작을 원하는지 나타내는 값
- GET: 조회, 바디 없이 요청, 같은 요청을 여러 번 보내도 결과가 같음(멱등)
- POST: 생성 등 서버 상태를 바꾸는 요청, 여러 번 보내면 결과가 달라질 수 있음
- PUT: 전체를 교체, PATCH: 일부만 수정

### 정리

- 요청이 "무엇을 하고 싶은지"를 알려주는 값
- 조회는 GET, 생성은 POST처럼 의미에 맞게 쓰는 게 약속
- PUT은 통째로 바꾸고 PATCH는 필요한 부분만 바꾼다는 차이

## 4. Status Code

### 구조

```text
1xx : 처리 중
2xx : 성공        (200 OK, 201 Created, 204 No Content)
3xx : 리다이렉션   (301 영구 이동, 302 임시 이동, 304 Not Modified)
4xx : 클라이언트 오류 (400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found)
5xx : 서버 오류    (500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable)
```

### 특징

- 요청 결과를 숫자로 알려주는 값, 앞자리로 대략적인 종류를 구분
- 4xx는 요청을 잘못 보낸 쪽(클라이언트)의 문제, 5xx는 서버 쪽 문제
- 401은 로그인(인증)이 안 된 상태, 403은 로그인은 했지만 권한이 없는 상태

### 정리

- 앞자리만 봐도 성공/이동/클라이언트 잘못/서버 잘못을 구분할 수 있음
- 401은 "누구신지 모르겠어요", 403은 "누군지는 아는데 권한이 없어요"라는 차이

## 5. HTTP/1.1 · 2 · 3

### 구조

```text
HTTP/1.1 : 요청을 하나씩 순서대로 처리 (앞이 느리면 뒤가 밀림)
HTTP/2   : 하나의 연결로 여러 요청을 동시에 주고받음 (Multiplexing)
HTTP/3   : TCP 대신 UDP 기반(QUIC) 위에서 동작
```

### 특징

- HTTP/1.1: 연결을 재사용(Keep-Alive)하지만 한 연결에서 요청은 순서대로 처리돼서, 앞 요청이 느리면 뒤 요청이 대기(Head-of-Line Blocking). 그래서 브라우저가 도메인당 연결을 여러 개 맺어서 우회
- HTTP/2: 연결 하나에서 여러 요청을 동시에 처리하고, 헤더를 압축해서 전송량을 줄임. 다만 TCP 자체의 대기 문제는 남아있음
- HTTP/3: UDP 기반의 QUIC을 사용해서 패킷 하나가 유실돼도 다른 요청에 영향을 덜 주고, 연결 맺는 시간도 짧음

### 버전별 흐름: 왜 계속 바뀌었나

```text
[HTTP/1.1] 한 연결에서 요청을 줄 세워 처리
  요청 A ━━━━━━(느림)━━━━━━ 응답 A
  요청 B                    대기... → 응답 B   ← 앞이 막히면 뒤도 막힘 (HOL Blocking)
  → 우회: 도메인당 연결을 6개 정도 맺어서 나눠 처리

[HTTP/2] 한 연결 안에서 요청을 쪼개서 섞어 보냄 (Multiplexing)
  A1 B1 A2 C1 B2 A3 ...  → 응답이 오는 대로 조립
  → HTTP 레벨 대기는 해결, 하지만 밑에 있는 TCP는 패킷 하나가 유실되면
    그 연결 전체가 재전송을 기다림 (TCP 레벨 HOL Blocking)

[HTTP/3] TCP 대신 UDP 위의 QUIC 사용
  요청마다 독립된 스트림 → 한 스트림의 패킷이 유실돼도 다른 스트림은 계속 진행
```

| | HTTP/1.1 | HTTP/2 | HTTP/3 |
| --- | --- | --- | --- |
| 하위 프로토콜 | TCP | TCP | QUIC (UDP 기반) |
| 요청 처리 | 연결당 순서대로 | 연결 하나에서 동시에(Multiplexing) | 스트림별로 독립 |
| 헤더 | 매번 텍스트 그대로 전송 | 압축해서 전송 | 압축해서 전송 |
| 대기(HOL) 문제 | HTTP 레벨에서 발생 | HTTP 레벨은 해결, TCP 레벨은 남음 | 둘 다 완화 |
| 연결 시작 | TCP 핸드셰이크 + TLS 핸드셰이크 | 동일 | 핸드셰이크를 합쳐서 더 빠름 |

### 정리

- 버전이 올라갈수록 "한 번에 더 많은 요청을 더 빠르게" 처리하는 방향으로 발전
- 1.1은 한 줄로 서 있는 구조라 앞 요청이 느리면 뒤가 밀리고, 그래서 연결을 여러 개 맺어 우회했음
- 2는 한 연결 안에서 요청을 쪼개 섞어 보내서 연결을 여러 개 맺을 필요가 없어졌지만, 그 밑의 TCP가 패킷 유실에 약하다는 한계가 남음
- 3은 아예 연결 방식을 TCP에서 UDP 기반(QUIC)으로 바꿔서, 한 요청에서 문제가 생겨도 다른 요청에 영향이 가지 않게 함
- 한 문장으로 말하면 "1.1의 줄 서기 → 2에서 섞어 보내기 → 3에서 밑바닥(TCP)까지 교체"

## 6. HTTPS

### 구조

```text
HTTP  : Client ←─── 평문 ───→ Server   (중간에서 훔쳐볼 수 있음)
HTTPS : Client ←─ 암호화 ─→ Server     (중간에서 봐도 알 수 없음)
```

### 특징

- HTTP에 암호화(TLS)를 더한 방식
- 도청 방지(암호화), 위조/변조 방지(무결성), 접속한 서버가 진짜인지 확인(인증)
- 서버 인증서를 통해 접속한 사이트가 신뢰할 수 있는 곳인지 확인

### 정리

- 주고받는 내용을 암호화해서 중간에서 가로채도 내용을 알 수 없게 만든 HTTP
- 암호화뿐 아니라 "이 서버가 진짜 맞는지"까지 인증서로 확인해줌

---

## 7. TLS

### 구조

```text
Client                                  Server
  │ ── Client Hello (지원 암호 목록) ──→   │
  │ ←─ Server Hello + 인증서 ───────────   │
  │ ── 인증서 확인, 키 교환 ───────────→   │
  │ ←─────── 같은 비밀 키 확보 ────────→   │
  │ ←══ 이후 데이터는 비밀 키로 암호화 ══→  │
```

### 특징

- 연결 초기에 핸드셰이크로 서로 쓸 암호 방식과 키를 정함
- 비대칭 키(공개키/개인키)로 안전하게 비밀 키를 교환하고, 실제 데이터는 비밀 키 하나로 암·복호화하는 대칭 키 방식으로 처리
- 비대칭 키는 안전하지만 느리고, 대칭 키는 빠르지만 키를 전달하는 게 위험하다는 점을 서로 보완

### 정리

- 처음에는 느리지만 안전한 방식으로 비밀 키를 안전하게 주고받고, 이후 실제 데이터는 빠른 방식(같은 키)으로 암호화해서 주고받음
- 두 방식의 장점만 섞어 쓰는 구조

# Frontend 심화

## 8. HTTP Cache

### 구조

```text
첫 요청 : Client → Server → 200 + 데이터 + (Cache-Control, ETag)
재요청  : 캐시가 유효하면 서버에 안 가고 바로 사용
          유효기간이 지났으면 → 서버에 "바뀌었어?" 확인 (If-None-Match)
              ├─ 안 바뀜 → 304 Not Modified (본문 없이 응답, 캐시 계속 사용)
              └─ 바뀜   → 200 + 새 데이터
```

### 특징

- 한 번 받은 리소스를 저장해두고 재사용해서 요청과 전송량을 줄임
- Cache-Control: max-age로 유효 기간 지정, no-cache는 "사용 전에 서버에 확인", no-store는 "저장 자체를 금지"
- ETag: 리소스의 버전을 나타내는 값으로, 서버가 바뀌었는지 비교하는 데 사용

### 정리

- 이미 받은 파일을 다시 받지 않도록 브라우저가 저장해두는 방식
- 유효 기간 안에는 서버에 아예 요청을 안 보내고, 기간이 지나면 "바뀌었는지"만 물어봐서 안 바뀌었으면 304로 가볍게 끝남
- no-cache는 캐시를 안 쓰는 게 아니라 "쓰기 전에 확인"하는 것이고, 저장 자체를 막는 건 no-store

## 9. Fetch / Axios

### 구조

```js
// fetch
const res = await fetch("/api/users");
if (!res.ok) throw new Error(res.status); // 4xx/5xx도 직접 확인해야 함
const data = await res.json();

// axios
const { data } = await axios.get("/api/users"); // 4xx/5xx면 자동으로 에러
```

### 특징

- Fetch: 브라우저 내장 API, 추가 설치 없이 사용
- Axios: 별도 라이브러리, 편의 기능이 많음
- Fetch는 서버가 4xx/5xx로 응답해도 에러로 처리하지 않고, 네트워크 자체가 실패했을 때만 에러가 발생해서 `res.ok`를 직접 확인해야 함
- Axios는 2xx가 아니면 자동으로 에러로 처리하고, JSON 변환·인터셉터·타임아웃 설정을 기본으로 제공

### 정리

- Fetch는 기본 기능만 가볍게, Axios는 편의 기능(자동 JSON 변환, 인터셉터, 타임아웃 등)이 포함된 방식
- Fetch에서 가장 많이 놓치는 부분이 404/500이어도 에러가 안 난다는 점이라 `res.ok` 확인이 필수

## 10. Resource Loading

### 구조

```html
<script src="a.js"></script>        <!-- HTML 파싱 멈추고 다운로드+실행 -->
<script src="b.js" async></script>  <!-- 병렬 다운로드, 끝나면 바로 실행 -->
<script src="c.js" defer></script>  <!-- 병렬 다운로드, HTML 파싱 끝난 뒤 순서대로 실행 -->
```

### 특징

- 브라우저는 HTML을 위에서부터 읽으면서 필요한 리소스를 요청
- 일반 script는 다운로드·실행하는 동안 HTML 파싱이 멈춤
- async: 다운로드는 병렬, 다운로드 끝나는 즉시 실행(실행 순서 보장 안 됨)
- defer: 다운로드는 병렬, HTML 파싱이 끝난 뒤에 순서대로 실행
- CSS는 화면 그리기를 막는 리소스라서, 로딩이 늦어지면 화면 표시도 늦어짐

### 정리

- script를 그냥 넣으면 HTML 읽는 게 멈추기 때문에, 보통 defer나 async로 파싱을 막지 않게 함
- 순서가 중요한 스크립트는 defer, 서로 독립적인 스크립트(광고, 분석 등)는 async

# 5주차 - HTTP / HTTPS

## 1. HTTP (HyperText Transfer Protocol)

- 응용 계층(7계층)에서 **클라이언트와 서버가 요청(Request)과 응답(Response)을 주고받는 방식을 정의한 프로토콜**
- 클라이언트가 요청을 보내면 서버가 응답하는 **Request-Response 구조**이며, 주로 **TCP 위에서 동작** (HTTP/3는 UDP 기반 QUIC)
- HTML뿐 아니라 JSON, 이미지, 영상 등 **거의 모든 형태의 데이터를 전송**할 수 있음

### 📍 HTTP 메시지 구조

| 구분          | Request (요청)                                  | Response (응답)                                  |
| ------------- | ----------------------------------------------- | ------------------------------------------------ |
| Start Line    | `GET /users/1 HTTP/1.1` (Method, Path, Version) | `HTTP/1.1 200 OK` (Version, Status Code, Reason) |
| Header        | `Host`, `Content-Type`, `Authorization` 등      | `Content-Type`, `Set-Cookie`, `Cache-Control` 등 |
| Empty Line    | 헤더와 바디를 구분하는 빈 줄                    | 헤더와 바디를 구분하는 빈 줄                     |
| Body (선택적) | 전송할 데이터 (POST, PUT 등)                    | 응답 데이터 (HTML, JSON 등)                      |

### 💡 HTTP는 왜 텍스트 기반(HTTP/1.x)으로 설계되었나요?

**⇒ 사람이 읽고 디버깅하기 쉽고, 특정 플랫폼/언어에 종속되지 않아 확장성이 좋기 때문. 다만 텍스트 헤더는 매 요청마다 중복 데이터가 크고 파싱 비용이 있어서, HTTP/2부터는 바이너리 프레임 방식과 헤더 압축(HPACK)을 도입해 이를 개선함**

## 2. Stateless

- 서버가 **클라이언트의 이전 요청 상태를 저장하지 않는 성질**
- 각 요청은 **독립적이므로 요청 하나만으로 처리에 필요한 모든 정보를 담고 있어야 함**

### 📍 Stateful vs Stateless

| 구분        | Stateful                                         | Stateless                                  |
| ----------- | ------------------------------------------------ | ------------------------------------------ |
| 상태 저장   | 서버가 클라이언트 상태를 기억                    | 서버가 상태를 기억하지 않음                |
| 서버 변경   | 같은 서버가 계속 응답해야 함 (서버 변경 시 유실) | 아무 서버나 응답 가능                      |
| 확장성      | 스케일 아웃이 어려움 (세션 공유 필요)            | 서버를 쉽게 증설 가능 (Scale-out 유리)     |
| 요청 데이터 | 적음 (이전 맥락을 서버가 알고 있음)              | 많음 (매 요청마다 필요한 정보를 모두 전달) |
| 예시        | 세션 기반 서버, TCP 연결                         | HTTP                                       |

### 📍 Stateless의 한계를 보완하는 방법

- **Cookie:** 서버가 `Set-Cookie`로 내려준 값을 브라우저가 저장하고, 이후 요청마다 자동으로 `Cookie` 헤더에 담아 전송
- **Session:** 상태(로그인 정보 등)는 서버에 저장하고, 클라이언트에는 세션 ID만 쿠키로 전달
- **Token (JWT):** 상태 정보를 토큰에 담아 클라이언트가 보관하고, 매 요청마다 `Authorization` 헤더로 전달

### 💡 HTTP를 Stateless하게 설계한 이유

**⇒ 서버가 클라이언트별 상태를 저장하지 않으면 어느 서버든 요청을 처리할 수 있어서, 서버 장애 시 다른 서버로 쉽게 대체되고 트래픽이 늘어도 서버를 수평 확장(Scale-out)하기 쉬움. 로그인처럼 상태가 꼭 필요한 부분만 쿠키/세션/토큰으로 최소한으로 보완하는 방식이 효율적이기 때문. 참고로 Connection은 Keep-Alive로 유지될 수 있지만, 이는 TCP 연결의 재사용일 뿐 HTTP 요청 간 상태를 공유한다는 의미는 아님**

## 3. Method

- 클라이언트가 서버에게 **어떤 동작을 수행하길 원하는지를 나타내는 요청의 종류**

### 📍 주요 HTTP Method

| Method  | 용도                                         | Body   | 멱등성 | 안전 |
| ------- | -------------------------------------------- | ------ | ------ | ---- |
| GET     | 리소스 조회                                  | X      | O      | O    |
| POST    | 리소스 생성, 프로세스 실행                   | O      | X      | X    |
| PUT     | 리소스 전체 교체 (없으면 생성)               | O      | O      | X    |
| PATCH   | 리소스 일부 수정                             | O      | X(\*)  | X    |
| DELETE  | 리소스 삭제                                  | 보통 X | O      | X    |
| HEAD    | GET과 같지만 헤더만 응답 (Body 없음)         | X      | O      | O    |
| OPTIONS | 서버가 지원하는 Method 확인 (CORS Preflight) | X      | O      | O    |

- **안전(Safe):** 호출해도 리소스 상태를 변경하지 않음
- **멱등(Idempotent):** 같은 요청을 한 번 보내든 여러 번 보내든 **결과(서버 상태)가 동일**
- (\*) PATCH는 구현에 따라 멱등할 수도 있지만, 보장되지 않으므로 비멱등으로 취급

### 📍 PUT vs PATCH

| 구분        | PUT                                       | PATCH                          |
| ----------- | ----------------------------------------- | ------------------------------ |
| 수정 범위   | 리소스 **전체**를 교체                    | 리소스의 **일부**만 수정       |
| 누락된 필드 | 보내지 않은 필드는 삭제(초기화)될 수 있음 | 보내지 않은 필드는 그대로 유지 |

### 💡 멱등성이 왜 중요한가요?

**⇒ 네트워크 환경에서는 타임아웃이나 응답 유실로 클라이언트가 요청의 성공 여부를 알 수 없는 경우가 많고, 이때 같은 요청을 재시도해야 하는데 멱등한 Method(GET, PUT, DELETE)는 여러 번 호출해도 결과가 같아 안전하게 재시도할 수 있음. 반면 POST는 멱등하지 않아서 재시도 시 중복 결제·중복 주문이 생길 수 있어, 이를 막기 위해 Idempotency Key 같은 별도의 장치가 필요함**

## 4. Status Code

- 서버가 **요청을 어떻게 처리했는지 결과를 알려주는 3자리 숫자 코드**

### 📍 Status Code 분류

| 범위 | 분류          | 설명                                               |
| ---- | ------------- | -------------------------------------------------- |
| 1xx  | Informational | 요청을 받았고 처리 중 (101 Switching Protocols 등) |
| 2xx  | Success       | 요청이 성공적으로 처리됨                           |
| 3xx  | Redirection   | 요청 완료를 위해 추가 동작(리다이렉트)이 필요      |
| 4xx  | Client Error  | **클라이언트**의 잘못된 요청                       |
| 5xx  | Server Error  | **서버** 내부 처리 중 오류                         |

### 📍 자주 쓰는 Status Code

| 코드 | 이름                  | 설명                                                    |
| ---- | --------------------- | ------------------------------------------------------- |
| 200  | OK                    | 요청 성공                                               |
| 201  | Created               | 리소스 생성 성공 (POST 응답, `Location` 헤더 포함)      |
| 204  | No Content            | 성공했지만 응답 Body 없음 (DELETE 등)                   |
| 301  | Moved Permanently     | 영구 이동 (검색엔진/브라우저가 캐싱)                    |
| 302  | Found                 | 임시 이동                                               |
| 304  | Not Modified          | 캐시된 리소스가 최신 → 캐시 사용 (조건부 요청 응답)     |
| 400  | Bad Request           | 잘못된 문법/유효하지 않은 요청                          |
| 401  | Unauthorized          | **인증**되지 않음 (로그인 필요)                         |
| 403  | Forbidden             | 인증은 됐으나 **권한** 없음                             |
| 404  | Not Found             | 리소스를 찾을 수 없음                                   |
| 409  | Conflict              | 리소스의 현재 상태와 충돌                               |
| 429  | Too Many Requests     | 요청 횟수 제한 초과 (Rate Limit)                        |
| 500  | Internal Server Error | 서버 내부 오류                                          |
| 502  | Bad Gateway           | 게이트웨이/프록시가 상위 서버로부터 잘못된 응답을 받음  |
| 503  | Service Unavailable   | 서버 과부하 또는 점검으로 일시적 사용 불가              |
| 504  | Gateway Timeout       | 게이트웨이/프록시가 상위 서버 응답을 기다리다 시간 초과 |

### 💡 401 Unauthorized와 403 Forbidden의 차이

**⇒ 401은 "누구인지 확인할 수 없음"(인증 실패 - 로그인 안 했거나 토큰이 유효하지 않음)이고, 403은 "누구인지는 알지만 이 리소스에 접근할 권한이 없음"(인가 실패)을 의미함. 따라서 401은 로그인/토큰 재발급으로 해결될 수 있고, 403은 로그인을 다시 해도 권한이 없으면 해결되지 않음**

### 💡 301 vs 302 리다이렉트

**⇒ 301은 영구적으로 주소가 바뀐 것이라 브라우저와 검색엔진이 새 주소를 캐싱하고 기억하지만, 302는 임시 이동이라 다음에도 원래 주소로 요청을 보냄. 따라서 도메인 이전처럼 영구 변경에는 301, 일시적인 점검 페이지나 로그인 후 이동에는 302를 사용함**

## 5. HTTP/1.1 · 2 · 3

- HTTP는 **"요청 하나당 더 빠르게, 연결 하나로 더 많이" 처리**하는 방향으로 발전해 옴

### 📍 HTTP/1.1

- **Persistent Connection(Keep-Alive):** 한 번 맺은 TCP 연결을 재사용해 매 요청마다 3-way Handshake를 하지 않음 (1.0에서는 요청마다 연결)
- **Pipelining:** 응답을 기다리지 않고 요청을 연속으로 전송할 수 있으나, 응답은 요청 순서대로 와야 해서 **HOL Blocking** 발생 → 실제로는 거의 사용되지 않음
- 텍스트 기반 헤더를 매번 중복 전송
- 브라우저는 도메인당 약 6개의 TCP 연결을 병렬로 열어 한계를 우회

### 📍 HTTP/2

- **바이너리 프레임:** 텍스트 대신 바이너리로 메시지를 프레임 단위로 쪼개 효율적으로 파싱
- **멀티플렉싱(Multiplexing):** **하나의 TCP 연결에서 여러 요청/응답을 스트림 단위로 동시에** 주고받음 → HTTP 레벨 HOL Blocking 해소
- **헤더 압축(HPACK):** 중복되는 헤더를 인덱싱해 전송량 감소
- **Server Push:** 클라이언트 요청 전에 서버가 필요한 리소스를 미리 전송 (실사용 효과가 낮아 최근 브라우저에서는 제거되는 추세)
- 여전히 TCP 기반이라 **TCP 레벨 HOL Blocking**(패킷 하나 손실 시 전체 스트림이 대기)은 남아있음

### 📍 HTTP/3

- **QUIC(UDP 기반)** 위에서 동작하며, 신뢰성/혼잡 제어를 QUIC가 직접 구현
- **스트림 단위의 독립적인 손실 복구:** 하나의 스트림에서 패킷이 손실되어도 다른 스트림은 영향받지 않음 → TCP 레벨 HOL Blocking 해소
- **연결 수립 시간 단축:** QUIC가 TLS 1.3을 내장해 전송 + 암호화 핸드셰이크를 합쳐 1-RTT(재연결 시 0-RTT)로 연결
- **Connection Migration:** IP/네트워크가 바뀌어도(Wi-Fi ↔ LTE) **Connection ID로 연결을 유지**

### 📍 버전별 비교

| 구분           | HTTP/1.1          | HTTP/2                | HTTP/3                |
| -------------- | ----------------- | --------------------- | --------------------- |
| 전송 프로토콜  | TCP               | TCP                   | UDP (QUIC)            |
| 메시지 형식    | 텍스트            | 바이너리 프레임       | 바이너리 프레임       |
| 동시 요청 처리 | 연결 여러 개 필요 | 멀티플렉싱 (연결 1개) | 멀티플렉싱 (연결 1개) |
| 헤더 압축      | X                 | HPACK                 | QPACK                 |
| HOL Blocking   | HTTP + TCP 레벨   | TCP 레벨에 존재       | 해소                  |
| 연결 수립      | TCP + (TLS)       | TCP + TLS             | QUIC (1-RTT / 0-RTT)  |
| TLS            | 선택              | 사실상 필수(브라우저) | 필수 (내장)           |

### 💡 HTTP/3가 UDP를 선택한 이유

**⇒ TCP는 OS 커널에 구현되어 있어 프로토콜을 수정·배포하기 어렵고, 패킷 하나가 손실되면 그 뒤의 모든 데이터가 대기하는 TCP 레벨 HOL Blocking을 근본적으로 해결할 수 없기 때문. UDP는 단순히 데이터를 전달하는 역할만 하므로 그 위에서 QUIC가 스트림별 독립적인 손실 복구, 혼잡 제어, 암호화를 사용자 공간에서 직접 구현해 빠르게 발전시킬 수 있음**

## 6. HTTPS / TLS

- **HTTPS = HTTP + TLS(SSL)**: HTTP 통신을 **TLS로 암호화**해서 전송하는 프로토콜 (기본 포트 443)
- 평문으로 전송되는 HTTP는 중간자(MITM)가 **도청, 변조, 사칭**할 수 있어 이를 막기 위해 사용

### 📍 HTTPS가 보장하는 것

| 보안 요소 | 설명                                    | 제공 기술                  |
| --------- | --------------------------------------- | -------------------------- |
| 기밀성    | 제3자가 데이터를 엿볼 수 없음           | 대칭키 암호화              |
| 무결성    | 전송 중 데이터가 변조되지 않았음을 확인 | MAC(해시 기반 메시지 인증) |
| 인증      | 접속한 서버가 진짜 해당 서버임을 확인   | 인증서 (공개키 기반)       |

### 📍 대칭키 vs 비대칭키 암호화

| 구분          | 대칭키                           | 비대칭키 (공개키)                     |
| ------------- | -------------------------------- | ------------------------------------- |
| 키            | 암호화/복호화에 **같은 키** 사용 | 공개키로 암호화, **개인키**로 복호화  |
| 속도          | 빠름                             | 느림                                  |
| 문제점        | 키를 안전하게 전달하기 어려움    | 연산 비용이 커서 대량 데이터에 부적합 |
| 대표 알고리즘 | AES                              | RSA, ECDSA, ECDH                      |

### 📍 TLS Handshake (TLS 1.2 기준)

1. **Client Hello:** 클라이언트가 지원하는 TLS 버전, 암호화 방식(Cipher Suite 목록), 랜덤 값을 전송
2. **Server Hello + 인증서:** 서버가 사용할 Cipher Suite를 선택하고, **인증서(공개키 포함)와 서버 랜덤 값을 전송**
3. **인증서 검증:** 클라이언트가 인증서가 신뢰할 수 있는 **CA(인증 기관)에서 서명**했는지, 도메인/유효기간이 맞는지 검증
4. **키 교환:** 클라이언트가 Pre-Master Secret을 서버의 공개키로 암호화해 전송 (또는 ECDHE로 키 교환) → 양쪽이 랜덤 값들을 조합해 **동일한 세션 키(대칭키)를 생성**
5. **Finished:** 양쪽이 핸드셰이크가 올바르게 끝났음을 확인한 뒤, 이후 **세션 키(대칭키)로 HTTP 데이터를 암호화해 통신**

- **TLS 1.3:** 핸드셰이크 왕복을 줄여 **1-RTT**로 완료되고(재연결 시 0-RTT), 취약한 암호화 방식을 제거함

### 📍 인증서와 CA (Certificate Authority)

- **인증서:** 서버의 공개키와 도메인 정보 등을 담고, **CA가 자신의 개인키로 서명**한 전자 문서
- **신뢰 체인(Chain of Trust):** 서버 인증서 → 중간 CA 인증서 → Root CA 인증서. 브라우저/OS에는 **신뢰할 수 있는 Root CA 목록**이 미리 설치되어 있어 서명을 검증할 수 있음

### 💡 HTTPS는 왜 비대칭키와 대칭키를 함께 사용하나요?

**⇒ 대칭키는 빠르지만 키를 안전하게 전달할 방법이 없고, 비대칭키는 키 전달 문제는 없지만 연산이 느려서 대량 데이터 통신에 부적합하기 때문. 그래서 핸드셰이크 단계에서는 비대칭키(또는 ECDHE)로 안전하게 세션 키를 교환하고, 이후 실제 데이터는 이 세션 키를 이용한 빠른 대칭키 암호화로 통신하는 하이브리드 방식을 사용함**

### 💡 인증서가 없으면 중간자 공격(MITM)을 막을 수 없는 이유

**⇒ 공개키 암호화만 사용하면 공격자가 중간에서 자신의 공개키를 서버의 것처럼 속여 전달할 수 있고, 클라이언트는 그 공개키가 진짜 서버의 것인지 확인할 방법이 없음. CA가 서명한 인증서는 "이 공개키는 이 도메인의 것이 맞다"는 것을 신뢰할 수 있는 제3자가 보증해주므로, 클라이언트가 서버의 신원을 검증하고 공격자의 위조 공개키를 걸러낼 수 있음**

# Frontend 심화

## 1. HTTP Cache

- 이전에 받은 **리소스를 저장해뒀다가 재사용**해서 네트워크 요청 자체를 줄이거나, 전송량을 줄이는 기법
- 로딩 속도 향상, 서버 부하와 네트워크 비용 감소

### 📍 캐시의 종류

| 구분                    | 설명                                              |
| ----------------------- | ------------------------------------------------- |
| Browser Cache (Private) | 개별 사용자의 브라우저에 저장, 해당 사용자만 사용 |
| Shared Cache            | CDN, 프록시 서버 등 여러 사용자가 공유하는 캐시   |

### 📍 캐시 제어 헤더 - 강력한 캐시(Strong Cache)

- 캐시가 **유효한 동안은 서버에 요청 자체를 보내지 않고** 브라우저 캐시에서 바로 사용 (DevTools에 `from disk cache` / `from memory cache`)

| 헤더                              | 설명                                                                      |
| --------------------------------- | ------------------------------------------------------------------------- |
| `Cache-Control: max-age=N`        | 응답을 받은 시점부터 N초 동안 캐시가 신선(fresh)                          |
| `Cache-Control: no-cache`         | 캐시를 저장은 하되, **사용 전에 반드시 서버에 재검증**                    |
| `Cache-Control: no-store`         | 캐시에 **아예 저장하지 않음** (민감한 정보)                               |
| `Cache-Control: public / private` | `public`: CDN 등 공유 캐시도 저장 가능 / `private`: 브라우저에만 저장     |
| `Expires`                         | 만료 시각 지정 (HTTP/1.0 방식, `Cache-Control`이 있으면 `max-age`가 우선) |

### 📍 캐시 재검증 - 협상 캐시(Conditional Request)

- 캐시가 만료되면 서버에 **"이 리소스가 변경되었는지"를 조건부로 요청**하고, 변경이 없으면 **304 Not Modified**(Body 없이 헤더만)로 응답받아 기존 캐시를 재사용

| 방식            | 응답 헤더 (서버 → 클라) | 요청 헤더 (클라 → 서버) | 설명                                       |
| --------------- | ----------------------- | ----------------------- | ------------------------------------------ |
| 수정 시간 기반  | `Last-Modified`         | `If-Modified-Since`     | 마지막 수정 시각을 비교 (초 단위)          |
| 내용(해시) 기반 | `ETag`                  | `If-None-Match`         | 리소스의 고유 식별자(해시)를 비교, 더 정확 |

### 📍 캐시 동작 흐름

1. 브라우저가 리소스 요청 → **캐시에 있고 `max-age` 이내**라면 서버 요청 없이 바로 사용 (200, from cache)
2. 캐시가 **만료**되었다면 `If-None-Match`(ETag) 등을 담아 서버에 재검증 요청
3. 서버: 변경 없음 → **304 Not Modified** (Body 없음, 기존 캐시 재사용) / 변경됨 → **200 OK** + 새 리소스

### 📍 캐시 무효화 전략 (Cache Busting)

- 정적 리소스(JS, CSS, 이미지)는 **파일명에 해시를 포함**(`main.a1b2c3.js`)하고 `Cache-Control: max-age=31536000, immutable`로 **오래 캐싱**
- 내용이 바뀌면 파일명(해시)이 바뀌어 **새 URL로 요청**하므로 자동으로 캐시가 무효화됨
- 반면 **HTML(index.html)은 `no-cache`로 설정**해 항상 최신 HTML을 확인하게 하고, 최신 HTML이 새 해시의 JS/CSS를 가리키도록 함

### 💡 `no-cache`와 `no-store`의 차이

**⇒ 이름과 달리 `no-cache`는 "캐시하지 말라"가 아니라 "캐시를 저장은 하되 매번 서버에 재검증(304 확인)한 뒤에 사용하라"는 의미이고, `no-store`는 응답 자체를 어떤 캐시에도 저장하지 말라는 의미임. 따라서 항상 최신 데이터를 보장하되 변경이 없을 땐 전송량을 아끼고 싶으면 `no-cache`, 개인정보나 결제 정보처럼 민감한 데이터는 `no-store`를 사용함**

### 💡 SPA 배포 시 JS 파일은 길게, HTML은 짧게 캐싱하는 이유

**⇒ JS/CSS는 빌드할 때마다 파일명에 해시가 붙어 내용이 바뀌면 URL도 바뀌므로 오래 캐싱해도 오래된 파일을 쓸 위험이 없음. 반면 `index.html`은 URL이 고정되어 있는데 이 파일이 최신 해시의 JS를 가리키는 진입점이므로, HTML이 캐시되면 새로 배포해도 사용자가 이전 버전의 JS를 계속 받게 됨. 따라서 HTML은 `no-cache`로 항상 재검증하도록 해 배포 즉시 반영되도록 함**

## 2. Fetch / Axios

- 브라우저에서 **HTTP 요청을 보내는 두 가지 대표 방법**: 브라우저 내장 API인 **Fetch**, 외부 라이브러리인 **Axios**

### 📍 Fetch

- 브라우저 내장 **Promise 기반** API (별도 설치 불필요, Node 18+에서도 지원)

```js
const res = await fetch("/api/users", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ name: "seyun" }), // 직접 직렬화
});

if (!res.ok) throw new Error(`HTTP ${res.status}`); // 4xx/5xx는 직접 처리
const data = await res.json(); // 직접 파싱
```

### 📍 Axios

- XMLHttpRequest/Node http 모듈을 감싼 **Promise 기반 HTTP 클라이언트 라이브러리**

```js
const instance = axios.create({ baseURL: "/api", timeout: 5000 });

// 요청/응답 Interceptor
instance.interceptors.request.use((config) => {
  config.headers.Authorization = `Bearer ${token}`;
  return config;
});

const { data } = await instance.post("/users", { name: "seyun" }); // 자동 직렬화/파싱
```

### 📍 Fetch vs Axios

| 구분           | Fetch                                              | Axios                                          |
| -------------- | -------------------------------------------------- | ---------------------------------------------- |
| 설치           | 브라우저 내장                                      | 별도 설치 필요 (번들 크기 증가)                |
| 에러 처리      | **4xx/5xx도 reject하지 않음** (`res.ok` 확인 필요) | 4xx/5xx 응답이면 **자동으로 reject**           |
| JSON 처리      | `JSON.stringify` / `res.json()` 직접 호출          | 자동 직렬화/파싱 (`response.data`)             |
| 타임아웃       | 기본 지원 X (`AbortController`로 구현)             | `timeout` 옵션 제공                            |
| Interceptor    | 없음 (직접 래퍼 함수 구현)                         | 요청/응답 Interceptor 기본 제공                |
| 요청 취소      | `AbortController`                                  | `AbortController` (`CancelToken`은 deprecated) |
| 업로드 진행률  | 지원 어려움 (스트림 직접 처리)                     | `onUploadProgress`로 간편하게 지원             |
| 쿠키 전송 옵션 | `credentials: "include"`                           | `withCredentials: true`                        |

### 📍 요청 취소 (AbortController)

```js
const controller = new AbortController();

fetch("/api/search?q=abc", { signal: controller.signal })
  .then((res) => res.json())
  .catch((e) => {
    if (e.name === "AbortError") return; // 취소된 요청은 무시
    throw e;
  });

controller.abort(); // 이전 요청 취소 (검색 자동완성, 컴포넌트 언마운트 시)
```

### 💡 Fetch는 404나 500 응답에서도 왜 에러가 발생하지 않나요?

**⇒ Fetch의 Promise는 "요청이 서버에 도달해 응답을 받았는지"를 기준으로 resolve/reject되기 때문. 서버가 404/500을 응답했더라도 네트워크 통신 자체는 성공한 것이므로 resolve되고, 네트워크 단절·CORS 실패·요청 취소처럼 응답을 받지 못한 경우에만 reject됨. 따라서 Fetch를 사용할 때는 `res.ok`나 `res.status`를 직접 확인해 에러로 처리해야 하고, Axios는 2xx 범위를 벗어나면 자동으로 reject해 이 과정을 생략할 수 있음**

### 💡 CORS와 Preflight 요청

**⇒ 브라우저는 보안(Same-Origin Policy)을 위해 다른 Origin(프로토콜/도메인/포트)으로의 요청 응답을 `Access-Control-Allow-Origin` 헤더로 서버가 허용했을 때만 JS에 노출함. `PUT/DELETE` 또는 커스텀 헤더, `application/json` 같은 "단순하지 않은 요청"은 본 요청 전에 `OPTIONS` Method로 **Preflight 요청**을 먼저 보내 서버가 해당 Method/헤더를 허용하는지 확인함. CORS는 서버가 아닌 브라우저가 막는 정책이므로, 해결은 서버에서 허용 헤더를 설정하는 것이 원칙임**

## 3. Resource Loading

- 브라우저가 HTML을 파싱하면서 **CSS, JS, 이미지, 폰트 등 외부 리소스를 요청하고 로드하는 과정**
- 어떤 리소스를 **언제, 어떤 우선순위로** 불러오는지가 **초기 렌더링 속도(FCP, LCP)** 에 큰 영향을 줌

### 📍 렌더링을 막는 리소스 (Render Blocking)

- **CSS:** 렌더 트리를 만들려면 CSSOM이 필요하므로 **CSS 로드/파싱이 끝날 때까지 렌더링이 차단**됨 (Render Blocking)
- **JS:** 기본 `<script>`는 **HTML 파싱을 중단(Parser Blocking)** 하고 JS를 다운로드·실행한 뒤 파싱을 재개함. JS가 DOM/CSSOM을 조작할 수 있기 때문

### 📍 script 로딩 방식 비교 (`defer` / `async`)

| 방식             | HTML 파싱 | 다운로드              | 실행 시점                                     | 실행 순서      |
| ---------------- | --------- | --------------------- | --------------------------------------------- | -------------- |
| `<script>`       | **중단**  | 파싱 중단 후 다운로드 | 다운로드 직후 즉시 실행                       | 문서 순서      |
| `<script async>` | 병렬 진행 | 파싱과 **병렬**       | 다운로드 완료 즉시 (파싱을 잠시 중단)         | **보장 X**     |
| `<script defer>` | 병렬 진행 | 파싱과 **병렬**       | **HTML 파싱 완료 후** (DOMContentLoaded 직전) | 문서 순서 보장 |

- `defer`: DOM이 필요하거나 실행 순서가 중요한 일반 앱 스크립트에 적합
- `async`: 다른 스크립트/DOM에 의존하지 않는 독립적인 스크립트(분석, 광고 등)에 적합
- `type="module"`은 기본적으로 `defer`처럼 동작

### 📍 리소스 힌트 (Resource Hints)

| 힌트           | 설명                                                                                           |
| -------------- | ---------------------------------------------------------------------------------------------- |
| `dns-prefetch` | 해당 도메인의 **DNS 조회만 미리** 수행                                                         |
| `preconnect`   | **DNS + TCP + TLS 연결까지 미리** 수립 (외부 API/CDN/폰트 도메인에 유용)                       |
| `preload`      | **현재 페이지에서 반드시 필요한** 리소스를 높은 우선순위로 미리 다운로드 (폰트, LCP 이미지 등) |
| `prefetch`     | **다음 페이지에서 사용할 가능성이 있는** 리소스를 유휴 시간에 낮은 우선순위로 미리 다운로드    |

```html
<link rel="preconnect" href="https://cdn.example.com" />
<link
  rel="preload"
  href="/fonts/pretendard.woff2"
  as="font"
  type="font/woff2"
  crossorigin
/>
<link rel="prefetch" href="/next-page.js" />
<script src="/app.js" defer></script>
```

### 📍 이미지 / 폰트 로딩 최적화

- **Lazy Loading:** `<img loading="lazy">`로 뷰포트에 가까워질 때까지 이미지 로드를 지연 (단, LCP 이미지에는 적용하지 말 것)
- **이미지 포맷/크기 최적화:** WebP/AVIF 사용, `srcset`/`sizes`로 해상도별 이미지 제공, `width`/`height` 명시로 **CLS(레이아웃 이동) 방지**
- **폰트:** `font-display: swap`으로 폰트 로딩 전에도 대체 폰트로 텍스트를 먼저 표시해 **FOIT(텍스트가 보이지 않는 현상)** 방지
- **코드 스플리팅 / 동적 import:** 초기에 필요하지 않은 JS는 `import()`로 분리해 필요할 때 로드 → 초기 번들 크기 감소

### 💡 CSS를 `<head>`에, JS를 `<body>` 끝(또는 `defer`)에 두는 이유

**⇒ CSS는 렌더 트리 생성에 필수적이라서 최대한 빨리 받아 스타일이 적용되지 않은 화면이 깜빡이는 FOUC를 막아야 하고, 반대로 JS는 파싱을 차단하므로 `<body>` 끝에 두거나 `defer`를 사용해 HTML 파싱·렌더링을 방해하지 않도록 하는 것이 초기 로딩 성능에 유리하기 때문. 단, JS 앞에 CSS가 완료되지 않았다면 JS 실행도 CSSOM이 준비될 때까지 대기하므로, 불필요하게 큰 CSS가 JS 실행까지 지연시킬 수 있음**

### 💡 `preload`와 `prefetch`의 차이

**⇒ `preload`는 현재 페이지 렌더링에 반드시 필요한 리소스를 발견이 늦어지지 않도록 높은 우선순위로 미리 가져오는 힌트이고(예: CSS 안에서 참조하는 폰트, LCP 이미지), `prefetch`는 사용자가 다음에 이동할 가능성이 있는 페이지의 리소스를 브라우저가 한가할 때 낮은 우선순위로 미리 받아 캐시해두는 힌트임. 현재 페이지에 필요 없는 리소스를 `preload`하면 오히려 중요한 리소스의 대역폭을 빼앗아 성능이 나빠질 수 있음**

# 5주차 - HTTP / HTTPS

## 공통 키워드

### 1. HTTP

HTTP(HyperText Transfer Protocol)는 클라이언트와 서버가 데이터를 주고받기 위한 통신 규칙(프로토콜)이다.

통신은 크게 요청(Request)과 응답(Response)으로 이루어진다.

#### Request (클라이언트 → 서버)

Request Line, Headers, Body로 구성된다.

- **Request Line**: `Method`, `경로(Path)`, `HTTP 버전`으로 구성되며, 서버에게 무엇을 할 건지 알려준다.
  - Method: GET, POST, PUT, PATCH, DELETE 등
    - GET은 URL의 Path나 Query Parameter를 통해 필요한 데이터를 전달
    - PUT은 데이터를 전체적으로 수정할 때, PATCH는 일부만 수정할 때 사용
- **Headers**: HTTP 요청/응답에 대한 추가 정보(메타데이터)를 전달
  - `Content-Type`: 보내는 데이터의 형식이 무엇인지
  - `Authorization`: 요청을 보내는 사용자가 누구인지 확인할 수 있는 인증 정보
- **Body**: 요청에서 실제로 전달할 데이터가 들어가는 부분 (주로 GET 외의 메서드에서 사용)

#### Response (서버 → 클라이언트)

Status Line, Headers, Body로 구성된다.

- **Status Line**: 응답 상태를 알려준다.
  - `2xx`: 성공
  - `3xx`: 리다이렉션 (요청을 완료하기 위해 추가적인 동작이 필요하거나 다른 위치로 이동해야 하는 경우)
  - `4xx`: 클라이언트 오류 (클라이언트가 보낸 요청에 문제가 있는 경우)
  - `5xx`: 서버 오류
- **Headers / Body**: Request와 동일하게 메타데이터와 실제 전달 데이터를 담는다.

> HTTP는 기본적으로 **Stateless(무상태)** 프로토콜이다.


### 2. Stateless (무상태)

서버가 클라이언트의 이전 요청 상태를 기억하지 않는 것으로, HTTP의 대표적인 특징 중 하나이다.

- 각각의 요청은 서로 독립적으로 처리된다.
- 그래서 클라이언트는 자신이 누구인지 확인할 수 있는 정보를 매 요청마다 함께 보내야 한다.
  - 이때 사용하는 대표적인 방법이 Cookie, Session, Token(JWT 등)

#### 장점

- 서버가 클라이언트의 상태를 따로 저장하지 않아도 된다.
- 특정 클라이언트 상태에 의존하지 않기 때문에 서버를 여러 대로 늘리기(수평 확장, Scale-out) 쉽다.

#### 단점

- 매 요청마다 인증 정보를 함께 보내야 하므로 요청 크기가 커지고, 인증을 위한 추가 조회(DB, 캐시 등)가 필요할 수 있다.


### 3. Method

클라이언트가 서버에게 어떤 동작을 요청하는지 나타내며, Request Line에 포함된다.

| Method | 설명 | 주요 특징 |
| --- | --- | --- |
| GET | 데이터를 조회할 때 사용. 필요한 데이터는 주로 URL의 Path나 Query Parameter로 전달 | 안전(Safe), 멱등(Idempotent) |
| POST | 새로운 데이터를 생성하거나 서버에 데이터를 전달할 때 사용. 데이터는 주로 Body에 담아 전달 | 멱등하지 않음 (같은 요청을 여러 번 보내면 데이터가 여러 개 생성될 수 있음) |
| PUT | 데이터를 전체적으로 수정하거나 새로운 상태로 대체할 때 사용 | 멱등 |
| PATCH | 데이터의 일부만 수정할 때 사용 | 멱등하지 않을 수 있음 |
| DELETE | 데이터를 삭제할 때 사용 | 멱등 |

#### 안전(Safe) / 멱등(Idempotent) 개념

- **안전(Safe)**: 같은 요청을 여러 번 보내도 서버의 데이터(리소스 상태)가 변경되지 않는 것 (GET이 대표적)
- **멱등(Idempotent)**: 같은 요청을 여러 번 보내도 결과가 동일한 것 (GET, PUT, DELETE는 멱등하지만, POST는 멱등하지 않음)


### 4. Status Code

서버가 클라이언트의 요청을 처리한 결과를 나타내는 3자리 숫자로, 첫 번째 숫자를 통해 결과의 종류를 알 수 있다.

| 구분 | 의미 |
| --- | --- |
| 2xx | 요청을 정상적으로 처리함 (성공) |
| 3xx | 추가적인 동작이 필요하거나 다른 위치를 확인해야 함 (리다이렉션) |
| 4xx | 클라이언트가 보낸 요청에 문제가 있음 (클라이언트 오류) |
| 5xx | 요청 자체는 문제없지만 서버에서 처리 중 문제가 발생함 (서버 오류) |

#### 2xx (성공)

- `200 OK`: 요청이 정상적으로 처리됨
- `201 Created`: 요청이 성공적으로 처리되어 새로운 리소스가 생성됨
- `204 No Content`: 요청은 성공했지만 응답으로 전달할 데이터가 없음 (예: 삭제 성공)

#### 3xx (리다이렉션)

- `301 Moved Permanently`: 리소스가 영구적으로 다른 URL로 이동함
- `302 Found`: 리소스가 일시적으로 다른 URL에 있음
- `304 Not Modified`: 이전에 캐시한 데이터와 변경 사항이 없어 캐시를 그대로 사용해도 됨

#### 4xx (클라이언트 오류)

- `400 Bad Request`: 요청의 형식이나 내용이 잘못됨
- `401 Unauthorized`: 인증이 되지 않은 경우
- `403 Forbidden`: 인증은 되었지만(누군지는 알지만) 해당 리소스에 접근할 권한이 없는 경우
- `404 Not Found`: 요청한 리소스를 찾을 수 없음

#### 5xx (서버 오류)

- `500 Internal Server Error`: 서버 내부에서 오류 발생
- `502 Bad Gateway`: 서버가 다른 서버(상위 서버)로부터 정상적인 응답을 받지 못한 경우
- `503 Service Unavailable`: 서버가 과부하나 점검 등으로 현재 요청을 처리할 수 없는 상태


### 5. HTTP/1.1 · 2 · 3

HTTP는 처음부터 지금까지 계속 성능과 통신 효율을 개선하며 발전해왔다.

| 버전 | 전송 프로토콜 | 핵심 특징 |
| --- | --- | --- |
| HTTP/1.1 | TCP | 하나의 TCP 연결 재사용(Keep-Alive) 가능, 요청/응답이 순차 처리됨 |
| HTTP/2 | TCP | Multiplexing, Header Compression, Binary Framing |
| HTTP/3 | QUIC(UDP 기반) | TCP의 HOL Blocking 문제 해결, 빠른 연결 수립 |

#### HTTP/1.1

- 하나의 TCP 연결에서 여러 요청을 처리할 수 있다 (Keep-Alive).
- 하지만 요청과 응답이 순차적으로 처리되는 특성 때문에 성능 문제가 발생할 수 있다.
  - 앞의 요청이 지연되면 뒤의 요청도 영향을 받는다.
  - 이러한 문제를 **Head-of-Line Blocking(HOL Blocking)** 이라고 한다.

#### HTTP/2

- HTTP/1.1의 성능 문제를 개선하기 위해 등장했다.
- **Multiplexing(다중화)**: 하나의 TCP 연결에서 여러 요청과 응답을 동시에 처리할 수 있어 통신 효율을 높인다.
- **Header Compression(HPACK)**: 요청마다 반복해서 전송되는 헤더 정보를 압축하여 데이터 크기를 줄인다.
- **Binary Framing**: 데이터를 텍스트가 아닌 Frame이라는 작은 단위로 나눠 바이너리 형태로 전송한다.
- 다만 TCP를 사용하기 때문에 TCP 수준의 HOL Blocking 문제는 여전히 존재한다.
  - TCP는 패킷이 하나라도 유실되면, 순서를 맞추기 위해 뒤에 도착한 데이터까지 기다려야 한다.

#### HTTP/3

- TCP 기반 문제(TCP의 HOL Blocking)를 해결하기 위해 등장했다.
- TCP 대신 **QUIC**를 사용한다.
  - QUIC는 UDP를 기반으로 만들어진 새로운 전송 프로토콜로, 스트림 단위로 독립적으로 데이터를 전달해 하나의 스트림에서 패킷 유실이 생겨도 다른 스트림에는 영향을 주지 않는다.
  - TLS 기능이 기본적으로 포함되어 있어 연결 수립과 암호화 협상을 더 빠르게(0-RTT) 처리할 수 있다.


### 6. HTTPS

HTTP 통신에 암호화와 인증 기능을 추가한 프로토콜이다.

- HTTP가 데이터를 그대로 전달한다면, HTTPS는 데이터를 암호화해서 전달한다.
- HTTP 자체를 바꾼 것이 아니라, HTTP 통신을 **TLS**로 보호하는 구조이다. (HTTP + TLS = HTTPS)

#### TLS가 제공하는 보안 요소

- **암호화**: 통신 내용을 다른 사람이 보더라도 내용을 알아보기 어렵게 만든다.
- **무결성**: 통신 중에 누군가 데이터를 몰래 변경하지 않았는지 확인할 수 있다.
- **인증**: 내가 접속한 서버가 진짜 그 서버인지 인증서를 이용해 확인할 수 있다.


### 7. TLS

네트워크에서 데이터를 안전하게 주고받기 위한 보안 프로토콜이다.

- 특징은 위 HTTPS 항목과 동일(암호화, 무결성, 인증).
- 데이터를 바로 암호화해서 보내는 것이 아니라, 안전하게 통신할 준비를 하는 과정(**TLS Handshake**)이 먼저 필요하다.

#### TLS Handshake

클라이언트와 서버가 안전하게 통신하기 위해 암호화 방식과 키 등을 설정하는 과정이다.

1. 클라이언트가 지원 가능한 암호화 방식 목록 등을 서버에 전달
2. 서버가 인증서(Certificate)를 클라이언트에 전달하여 서버의 신원을 증명
3. 클라이언트가 인증서를 검증(CA를 통해 신뢰할 수 있는지 확인)
4. 이후 데이터를 암호화할 때 사용할 키를 안전하게 교환
5. 이후 실제 데이터는 암호화하여 주고받음

#### 인증서(Certificate)

- 서버가 실제 해당 도메인의 서버가 맞는지 증명하는 전자 문서이다.
- **CA(인증 기관, Certificate Authority)** 가 인증서를 발급하고, 전자 서명을 통해 위변조 여부를 검증할 수 있게 한다.

#### 암호화 키

- Handshake 과정에서는 **비대칭키(공개키/개인키)** 방식을 이용해 안전하게 키를 교환한다.
- 실제 데이터 통신에서는 속도가 빠른 **대칭키**를 사용하여 데이터를 암호화한다.
  - **대칭키**: 하나의 같은 키로 암호화와 복호화를 하는 방식. 속도는 빠르지만 키를 안전하게 전달하는 것이 중요하다.
  - **비대칭키**: 공개키로 암호화한 데이터는 짝이 되는 개인키로만 복호화할 수 있는 방식. 키 교환은 안전하지만 대칭키보다 속도가 느려서, 최초 키 교환에만 사용하고 실제 데이터 전송은 대칭키로 처리한다.

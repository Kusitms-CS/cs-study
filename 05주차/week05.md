# 5주차 - HTTP / HTTPS

## HTTP 기본 구조

- 클라이언트와 서버가 데이터를 주고받기 위한 응용 계층 프로토콜
- 클라이언트가 요청하면 서버가 응답하는 구조

```text
클라이언트 ── 요청 ──→ 서버
클라이언트 ←─ 응답 ─── 서버
```

### HTTP 요청

```http
GET /users/1 HTTP/1.1
Host: example.com
Accept: application/json
```

- 시작 줄: 메서드, 경로, HTTP 버전
- 헤더: 요청에 대한 추가 정보
- 본문: 서버에 전달할 실제 데이터
- 로그인 정보처럼 민감한 데이터는 URL이 아닌 본문에 담고 HTTPS 사용

### HTTP 응답

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"id":1,"name":"태경"}
```

- 시작 줄: HTTP 버전, 상태 코드
- 헤더: 응답에 대한 추가 정보
- 본문: 서버가 반환한 실제 데이터

### 핵심 정리

- 요청: 시작 줄 + 헤더 + 본문
- 응답: 시작 줄 + 헤더 + 본문
- 본문에 데이터를 넣어도 자동으로 암호화되지는 않음

## Stateless

- HTTP는 이전 요청의 상태를 기억하지 않음
- 각 요청을 서로 독립적으로 처리

```text
1번 요청: 로그인했습니다.
2번 요청: 상품 정보를 주세요.
```

- 서버는 2번 요청만으로 로그인한 사용자인지 알 수 없음

### 장점

- 서버가 클라이언트 상태를 계속 저장할 필요가 없음
- 여러 서버가 요청을 나눠 처리하기 쉬움
- 서버 확장이 쉬움

### 로그인 상태 유지

- 쿠키와 세션
- 액세스 토큰

```text
요청 + 세션 ID 또는 토큰 → 서버
```

- 브라우저가 인증 정보를 요청마다 함께 전송
- HTTP가 상태를 기억하는 것이 아니라 추가 정보로 상태가 있는 것처럼 구현

### 핵심 정리

- HTTP 자체는 Stateless
- 로그인 상태는 쿠키·세션 또는 토큰으로 유지

## HTTP Method

| Method | 역할 | 예시 |
| --- | --- | --- |
| `GET` | 데이터 조회 | 사용자 목록 조회 |
| `POST` | 데이터 생성 | 새 사용자 생성 |
| `PUT` | 데이터 전체 수정 | 사용자 정보 전체 교체 |
| `PATCH` | 데이터 일부 수정 | 닉네임만 변경 |
| `DELETE` | 데이터 삭제 | 사용자 삭제 |

```http
GET /users/1
POST /users
PATCH /users/1
DELETE /users/1
```

### PUT과 PATCH

- `PUT`: 리소스 전체를 전달해 교체
- `PATCH`: 변경할 부분만 전달해 일부 수정

### 멱등성

- 같은 요청을 여러 번 실행해도 서버의 최종 상태가 같은 성질
- 멱등: `GET`, `PUT`, `DELETE`
- 일반적으로 멱등하지 않음: `POST`, `PATCH`
- 같은 `POST` 요청이 두 번 처리되면 데이터가 중복 생성될 수 있음
- 주문·결제 API는 멱등성 키를 사용해 중복 처리를 방지하기도 함

### 핵심 정리

- Method는 서버에 원하는 작업을 표현
- `PUT`은 전체 수정, `PATCH`는 일부 수정
- 재시도할 때는 요청의 멱등성 확인 필요

## HTTP 상태 코드

| 범위 | 의미 |
| --- | --- |
| `1xx` | 요청 처리 중 |
| `2xx` | 성공 |
| `3xx` | 리다이렉션·캐시 |
| `4xx` | 클라이언트 요청 오류 |
| `5xx` | 서버 오류 |

### 주요 상태 코드

- `200 OK`: 요청 성공
- `201 Created`: 데이터 생성 성공
- `204 No Content`: 성공했지만 응답 본문 없음
- `301 Moved Permanently`: 영구적인 주소 이동
- `302 Found`: 임시 주소 이동
- `304 Not Modified`: 캐시된 데이터 재사용
- `400 Bad Request`: 잘못된 요청
- `401 Unauthorized`: 인증 필요
- `403 Forbidden`: 인증됐지만 권한 없음
- `404 Not Found`: 리소스 없음
- `409 Conflict`: 현재 상태와 요청 충돌
- `429 Too Many Requests`: 너무 많은 요청
- `500 Internal Server Error`: 서버 내부 오류
- `502 Bad Gateway`: 중간 서버가 잘못된 응답을 받음
- `503 Service Unavailable`: 서버가 일시적으로 요청 처리 불가

### 401과 403

- `401`: 로그인하지 않았거나 인증 정보가 유효하지 않음
- `403`: 로그인했지만 해당 작업을 수행할 권한이 없음

### 핵심 정리

- 상태 코드의 첫 번째 숫자로 처리 결과의 종류 구분
- 인증 실패는 `401`, 권한 부족은 `403`

## HTTP/1.1·HTTP/2·HTTP/3

### HTTP/1.1

- TCP 기반
- 연결을 재사용하는 Keep-Alive 지원
- 한 연결에서는 요청과 응답을 주로 순서대로 처리
- 병렬 처리를 위해 여러 TCP 연결 사용
- 앞 요청이 지연되면 뒤 요청도 기다릴 수 있음

### HTTP/2

- TCP 기반
- 데이터를 이진 프레임으로 전송
- 하나의 연결에서 여러 요청과 응답을 동시에 처리
- 헤더 압축 지원
- TCP 패킷이 유실되면 같은 연결의 모든 스트림이 지연될 수 있음

### HTTP/3

- UDP 기반 QUIC 사용
- 스트림을 독립적으로 처리
- 한 스트림의 패킷이 유실돼도 다른 스트림은 계속 처리 가능
- 연결 설정 시간이 짧고 네트워크가 변경되는 환경에 유리
- QUIC에 TLS 보안 기능 통합

| 구분 | HTTP/1.1 | HTTP/2 | HTTP/3 |
| --- | --- | --- | --- |
| 기반 | TCP | TCP | QUIC·UDP |
| 병렬 처리 | 여러 연결 사용 | 하나의 연결에서 처리 | 독립 스트림으로 처리 |
| 패킷 유실 영향 | 해당 연결 지연 | 모든 스트림 지연 가능 | 해당 스트림 위주로 지연 |
| 데이터 형식 | 텍스트 | 이진 프레임 | 이진 프레임 |

### 핵심 정리

- HTTP/2는 하나의 TCP 연결에서 여러 요청을 동시에 처리
- TCP는 순서를 보장하므로 패킷 유실 시 다른 스트림까지 대기 가능
- HTTP/3는 QUIC의 독립 스트림으로 이 문제를 완화

## HTTPS와 TLS

- HTTPS는 HTTP에 TLS 보안을 적용한 통신 방식

```text
HTTP + TLS = HTTPS
```

### TLS의 역할

- 기밀성: 데이터를 암호화해 제3자가 읽지 못하게 함
- 무결성: 전송 중 데이터가 변조됐는지 확인
- 인증: 인증서를 통해 접속한 서버의 신원 확인

### TLS 연결 과정

1. 클라이언트와 서버가 사용할 암호화 방식 결정
2. 서버가 인증서 전달
3. 클라이언트가 인증서의 도메인과 발급 기관 등을 검증
4. 키 교환을 통해 양쪽이 같은 세션 키 생성
5. 세션 키로 HTTP 데이터를 암호화해 통신

```text
클라이언트                         서버

지원 암호화 방식 전달 ───────────→
                  ←──────── 인증서 전달
인증서 검증과 키 교환
암호화된 HTTP 통신 ⇄
```

- 공개키 방식은 서버 인증과 안전한 키 교환에 사용
- 실제 데이터는 빠른 대칭키인 세션 키로 암호화
- 인증서 검증은 공격자가 서버인 척 통신을 가로채는 것을 방지

### 핵심 정리

- HTTPS는 암호화뿐 아니라 데이터 무결성과 서버 인증도 제공
- HTTPS를 사용해도 서버 내부의 데이터 보안까지 자동으로 보장되지는 않음

## HTTP 캐시

- 브라우저가 서버 응답을 저장하고 재사용하는 기능
- 페이지 로딩 속도 향상
- 네트워크 사용량과 서버 요청 감소

```text
첫 요청: 브라우저 → 서버 → 응답 저장
다음 요청: 브라우저 캐시 재사용
```

### Cache-Control

```http
Cache-Control: max-age=3600
```

- `max-age=3600`: 3600초 동안 서버 확인 없이 캐시 사용
- `no-cache`: 저장 가능, 재사용할 때마다 서버에 변경 여부 확인
- `no-store`: 응답을 캐시에 저장하지 않음

### 캐시 재검증

- 캐시 유효 기간이 끝나면 서버에 데이터 변경 여부 확인
- `ETag`: 응답의 식별값
- `Last-Modified`: 마지막 수정 시간

```http
If-None-Match: "abc123"
```

- 변경되지 않음: `304 Not Modified` → 기존 캐시 사용
- 변경됨: `200 OK` → 새로운 데이터 저장 후 사용

### 핵심 정리

- 민감한 응답을 저장하지 않으려면 `no-store`
- `no-cache`는 저장 금지가 아니라 재검증을 요구하는 설정

## Fetch와 Axios

- 모두 Promise 기반으로 HTTP 요청을 처리

| 구분 | Fetch | Axios |
| --- | --- | --- |
| 설치 | 브라우저 내장 | 별도 설치 |
| JSON 변환 | 직접 `response.json()` 호출 | 자동 변환 |
| HTTP 오류 | 직접 상태 확인 | 기본적으로 오류 처리 |
| 인터셉터 | 직접 구현 | 기본 제공 |
| 제한 시간 | 별도 설정 필요 | `timeout` 제공 |

### Fetch

```js
const response = await fetch("/users");

if (!response.ok) {
  throw new Error("요청 실패");
}

const data = await response.json();
```

- `404`, `500` 같은 HTTP 오류에서도 Promise가 자동으로 거부되지 않음
- `response.ok` 또는 `response.status`를 직접 확인
- 네트워크 오류나 요청 취소 등에서는 Promise 거부

### Axios

```js
const response = await axios.get("/users");
const data = response.data;
```

- 응답 데이터 자동 변환
- 기본 설정에서 성공 범위를 벗어난 상태 코드를 오류로 처리
- 요청·응답 인터셉터 지원
- 공통 주소, 헤더, 제한 시간 설정에 편리

### 핵심 정리

- 간단한 요청과 적은 의존성이 중요하면 Fetch
- 공통 인증·오류 처리 등 설정이 많으면 Axios
- Fetch는 HTTP 오류에 대해 `response.ok`를 직접 확인

## Resource Loading

- 브라우저는 HTML을 분석하며 CSS, JavaScript, 이미지 등을 추가로 요청
- 중요한 리소스는 먼저, 나중에 필요한 리소스는 늦게 로딩해 성능 개선

### JavaScript 로딩

```html
<script src="app.js"></script>
```

- 다운로드와 실행이 끝날 때까지 HTML 분석 중단

```html
<script async src="analytics.js"></script>
```

- HTML 분석과 동시에 다운로드
- 다운로드가 끝나면 바로 실행
- 실행 순서를 보장하지 않음
- 다른 코드와 독립적인 스크립트에 적합

```html
<script defer src="app.js"></script>
```

- HTML 분석과 동시에 다운로드
- HTML 분석이 끝난 뒤 실행
- 작성된 순서대로 실행
- DOM이나 다른 스크립트에 의존하는 코드에 적합

### Preload

```html
<link rel="preload" href="/font.woff2" as="font" crossorigin />
```

- 현재 페이지에서 곧 사용할 중요한 리소스를 미리 다운로드
- 글꼴과 주요 이미지 등에 사용
- 너무 많이 사용하면 다른 리소스와 네트워크를 경쟁할 수 있음

### Lazy Loading

```html
<img src="/photo.jpg" loading="lazy" alt="사진" />
```

- 화면 밖 리소스의 로딩을 미룸
- 초기 로딩 시간과 네트워크 사용량 감소
- 처음부터 화면에 보이는 핵심 이미지는 지연 로딩하지 않는 것이 좋음

### 핵심 정리

- 독립적이고 즉시 실행할 스크립트: `async`
- DOM과 실행 순서에 의존하는 스크립트: `defer`
- 곧 사용할 중요한 리소스: `preload`
- 화면 밖의 나중에 필요한 리소스: 지연 로딩
